# C02 — "The Verdict"

**One question. One answer. Everything else is evidence.**

Concept owner note: every claim about today's code below is either quoted from the dossier with its
`[CODE]` tag intact or was re-read from `/home/user/terpcontrol.cloud` while writing this. Where I invent a
number I say so.

---

## 1. Thesis

**The app answers one question — "Is my grow OK?" — with a plain-language verdict computed from
time-in-range against a declared goal, and demotes every chart to evidence you drill into only when the
verdict says you should.**

Terp Control today ships a 1205-line chart page with fifteen independent hidden y-axes as the closest
thing it has to an answer, and a dashboard card that calls a €289 controller a fridge. The user's actual
question is not "what was the humidity at 03:40 on Tuesday" — it is "do I need to get up." The diabetes
world solved exactly this shape of problem: a continuous sensor, a forced daily cycle, a target band, a
patient who is not a clinician, and a consensus report — the **Ambulatory Glucose Profile** — that
compresses 14 days of raw data into *% time in range*, *% above*, *% below*, split by day and night, with
the longest excursion reported **as a duration**. This concept transplants that scorecard wholesale onto a
grow room and makes it the home screen. The controller already has the raw material: it stores measured
values in InfluxDB, setpoints in `device.configuration`, alarm thresholds on `Device.alarms`, and per-stage
VPD bands in `GROW_STAGE_PRESETS` — *none* of which ever meet each other on a screen. The verdict is where
they meet. The stoner reads one sentence. The techie taps three times and reaches the raw sample count the
percentage was computed from.

Three concrete decisions:

1. **`ion-tab-bar` without `ion-tabs`.** Ionic 6 renders `<ion-tab-bar slot="bottom">` with
   `<ion-tab-button [routerLink]="…" routerLinkActive="tab-selected">` inside a plain `ion-footer`. That
   gives a tab bar with **zero** routing restructure — no `ion-tabs` outlet, no `loadChildren` rewrite, no
   NgModule surgery. The dossier records `<ion-fab>` = 0 hits and no tab bar today; this is the cheapest
   possible fix for the "six outline buttons on the overview card" navigation.
2. **The device switcher is in the header title**, as an `ion-select` interface="popover" when the account
   has >1 device. Today there is no device switcher at all — you go back to `/list`.
3. **One `<ion-fab>` bottom-right on Status and Journal only**: the journal capture button (§6). This is the
   first FAB in the codebase.

**Restricted modes** (constraint 8) are honoured because the shell resolves `resolveDeviceAccessInfo` once
and passes `locked` / `canEdit` / `webcamAllowed` / `chartsAllowed` down. A share link that grants
`page: 'charts'` gets the shell with **only the Belege tab enabled**; Status is hidden, not disabled, because
a share is a view of a chart, not a verdict about someone's grow. Demo sessions get all four tabs with
saves disabled. Public view swaps the menu button for the theme toggle, as today.

### 3.2 What each element is, precisely

**The freshness pill** (`<tc-freshness>`, new shared component, used in seven places). Three states, one
source of truth — `Device.lastseen`:

| State | Rule | Render |
| --- | --- | --- |
| `live` | `now - lastseen < 120 s` | `● live` / `● live`, `--tc-text-success` |
| `stale` | `120 s … 600 s` | `● vor 4 Min` / `● 4 min ago`, `--tc-text-warning` |
| `offline` | `> 600 s` (the existing definition — `simulate-device.sh` documents it) | `● offline · Stand 14:02` / `● offline · as of 14:02`, `--tc-text-danger` |

This is P0 gap #5 — *"the app will say a fan is running at 10 speed but the fan will not be running"* — the
single most-complained-about thing across all five consumer brands, and it costs a pipe and a component.

**The verdict card.** Six states, ranked. The first that matches wins:

| Rank | State | Condition | Glyph |
| --- | --- | --- | --- |
| 1 | `alarm` | any `Alarm.isTriggered` | `!` red |
| 2 | `offline` | freshness = offline | `?` grey |
| 3 | `unknown` | data coverage < 80 % of the window | `?` grey |
| 4 | `problem` | worst judged channel TIR < 70 % **or** longest excursion > 180 min | `!` red |
| 5 | `watch` | worst judged channel TIR < 90 % **or** longest excursion > 60 min | `~` amber |
| 6 | `ok` | everything else | `✓` green |

Plus `idle` (`workmode === 'off'` and no declared goal), which pre-empts 4–6 with its own copy.

> **The thresholds 90 % / 70 % / 60 min / 180 min are invented.** AGP's ≥70 % TIR has a clinical consensus
> behind it (*Diabetes Care* 42(8):1593, itself flagged UNVERIFIED in the dossier because the journal page
> 403s). There is **no horticultural equivalent and I will not pretend otherwise.** They ship as editable
> defaults under Ziele → Beurteilung, with a one-line disclaimer, and the shipped defaults are announced as
> defaults in the release notes.

**Metrics, and where each comes from:**

| Metric | Source | Note |
| --- | --- | --- |
| % in / above / below | raw Influx samples, dwell-time weighted | **must not** use `aggregateWindow(fn: mean)` |

| longest excursion | contiguous out-of-band run, **in seconds** | Mean-Kinetic-Temperature's lesson: duration, never alarm count |

### 3.6 The server side

New endpoint, and it is the only genuinely new backend work in v1:

```
GET /data/scorecard/:device_id?from=&to=&channels=temperature,humidity,vpd&tz=Europe/Berlin
```

```ts
interface ChannelScore {
  channel: 'temperature'|'humidity'|'vpd'|'co2'|'photoperiod';
  advisory: boolean;                       // true = measured but not controllable (§10)
  band: { low: number|null; high: number|null; unit: string;
          source: 'alarm'|'setpoint'|'stage'; stepped: boolean };
  coverage: number;                        // 0..1
  sampleCount: number;
  overall: RangeStats; day: RangeStats; night: RangeStats;
  excursions: { direction: 'above'|'below'; startedAt: number; endedAt: number;
                seconds: number; extreme: number }[];  // capped at 20, sorted by seconds desc
}
interface RangeStats { inPct: number; abovePct: number; belowPct: number;
                       mean: number; min: number; max: number; madFromSetpoint: number; }
interface DeviceVerdict {
  state: 'alarm'|'offline'|'unknown'|'problem'|'watch'|'ok'|'idle';
  headlineKey: string; params: Record<string,string|number>;
  worstChannel: string|null; coverage: number; computedAt: number; windowSeconds: number;
}
```

Three non-negotiable implementation notes:

1. **Raw samples only.** The Flux is `range() |> filter() |> sort(columns:["_time"])` with no
   `aggregateWindow`. TIR is then a dwell-time integral over consecutive sample pairs. Averaging a
   bang-bang controller's oscillation destroys the excursions the metric exists to count, and *the error is
   invisible by eye* — this is the correctness trap the dossier names explicitly.
2. **Fix `getSeries`' Flux injection first** (`data.service.ts:80-89`: `measure`, `from`, `to`, `interval`
   interpolated raw; the `limit(n:50000)` guard is piped *after* `yield()` and bounds nothing). The
   scorecard endpoint widens the measure vocabulary and must not inherit that. Allowlist `channels`,
   parse `from`/`to` to epoch integers, and clamp the window to 90 days.
3. **Cache it.** 24 h × 5 s × 4 channels = ~69 k points per request. v1 caches the result in Mongo keyed
   `{device_id, windowStart, windowEnd, bandHash}` with a 5-minute TTL and computes lazily on read.
   v1.1 adds an Influx task writing hourly `in/above/below` seconds per channel so the 7-day and per-stage
   windows are a sum, not a scan. **There are zero Influx tasks in the repo today; this is real, unbudgeted
   work and I am naming it here rather than in a footnote.**

### 3.7 Where the goal comes from — `GrowGoal`

This is the piece that makes the philosophy work for a device that controls nothing.

`device.configuration` **cannot carry new keys** (`grow-presets.ts:31-34`, verbatim: the firmware strips
unknown keys when it echoes config back). And a monitor-only controller sits at `workmode: 'off'` with
meaningless setpoints. So the goal lives cloud-side:

```ts
interface GrowGoal {                       // MongoDB, keyed by device_id, one active at a time
  goal_id: string; device_id: string; owner_id: string;
  source: 'device' | 'stage' | 'manual';   // device = derived from configuration each read
  stagePresetId?: GrowStagePresetId;       // when source = 'stage'
  temperature?: { day: [number,number]; night: [number,number] };
  humidity?:    { day: [number,number]; night: [number,number] };
  vpd?:         { day: [number,number]; night: [number,number] };
  co2?:         { day: [number,number] };
  photoperiodHours?: number;
  tolerances: { temperatureK: number; humidityPct: number; vpdKpa: number };
  activeFrom: number; activeUntil?: number;
  createdAt: number; updatedAt: number;
}
```

**Band source priority, resolved server-side and always labelled on screen** (adopted verbatim from the
dossier's §7.2.2):

1. **Alarm thresholds** — `Alarm.upperThreshold` / `lowerThreshold` for that `sensorType`. Hard edge, the
   user's own declared "unacceptable". Today these are *never* drawn on the chart.
2. **Setpoint ± tolerance** — `day.temperature` / `night.temperature` from `device.configuration`, stepped
   at `daynight.day`/`daynight.night`. Default tolerances reuse the numbers `grow-assistant-card` already
   ships (**±1.5 K, ±7 % RH**) so nothing in the app contradicts anything else.
3. **Stage recommendation** — `GROW_STAGE_PRESETS[].vpdRange` and the preset's day/night targets.
   Advisory. Labelled as such.

`GrowGoal` history (`activeFrom`/`activeUntil`) means a per-stage window can be judged against the band
that was actually in force at the time, instead of retroactively re-scoring a veg week against flowering
targets. That matters the first time a user taps "Phase" on the window switcher.

## 4. The chart overhaul

Charts are demoted, not neglected. When you *do* open Belege it must be the best chart in the category,
because it is the thing the verdict points at.

### 4.1 Library

**Migrate to Apache ECharts 6, tree-shaken, behind a hand-rolled ~50-line Angular directive.** Reasoning in
the order that decides it:

- **Licence.** Highcharts Stock is proprietary; the repo has **no LICENSE file and no Highcharts licence
  artefact**, and terpcontrol.com calls the cloud *"quelloffen"* while advertising a public no-login demo
  at `/demo` — which the Highcharts licence text calls an External Application requiring a quote-only SaaS
  licence. Whether a licence is held off-repo is unverified; **redistributing Highcharts source under an OSS
  licence is not curable by buying seats.** This alone decides it. If the owner answers Open Question 2 with
  "we hold a SaaS licence and the cloud will not be open-sourced", this decision is reversible and the rest
  of §4 stands unchanged — every technique below has a Highcharts equivalent.
- **Memory.** 166,650-point benchmark: Highcharts 10.3.3 (Terp's exact version) 416 ms / 97 MB peak; ECharts
  5.4.1 148 ms / 17 MB peak. On a mid-range Android that is the whole game.
- **Honest cost:** tree-shaken ECharts is **bigger** — 195.6 KB gz vs 132.7 KB gz for Highstock. Deleting
  the entirely-dead `chart.js` / `ng2-charts` / `chartjs-adapter-luxon` stack repays 68.8 KB gz of it. I am
  not selling this on bundle size.
- **Hand-roll the directive.** `highcharts-angular` 5.x needs Angular ≥19, `ng2-charts` 10 needs ≥21;
  `ngx-echarts` ≤19.0.0 declares no `@angular/core` peer and installs cleanly but ships a major per Angular
  major. ~50 lines decouple the chart from the framework upgrade path.
- **The replacement for a load-bearing default:** Highstock's implicit `dataGrouping` — configured nowhere —
  is currently the only thing keeping a 4,320-point render cheap. `sampling: 'minmax'` is not polish, it is
  the replacement. **`'lttb'` is rejected for the main plot** because it smooths away the exact oscillation a
  grower is looking for; LTTB is fine for the navigator.

### 4.3 Techniques adopted from the dossier §7.2, and rejected

| # | Technique | Verdict | Why |

### 4.4 Colour — the concept's signature chart move

Adopt Okabe-Ito, but apply the **High-Performance-HMI discipline**: saturated colour is reserved *exclusively*
for abnormal conditions. The philosophy demands it — a calm grow must produce a calm chart.

| Role | Light | Dark |
| --- | --- | --- |
| actual value (in band) | `#4a4f57` graphite | `#c8ccd2` |
| actual value (above band) | `#D55E00` vermillion | same |
| actual value (below band) | `#0072B2` blue | same |
| setpoint | `#009E73`, 2 px, `dashed`, `step:'left'` | same |
| target band | 8 % `#009E73` fill **+ 1 px 60 %-alpha hairline top and bottom** | same |
| night region | `--ion-color-step-100` @ 50 %, **no hue** | `--ion-color-step-150` |
| annotation user / device | `#CC79A7` / `#999999` | same |

The hairline exists specifically because `fillOpacity: 0.1` area fills almost certainly fail WCAG 2.2
SC 1.4.11's 3:1 non-text contrast requirement — the border carries the contrast, the fill carries the
grouping. Implemented as `visualMap: { type: 'piecewise' }` over a computed `deviation` dimension, which is
a first-class ECharts primitive, not a hack.

Today's palette is replaced outright: `#e05a4e` red next to `#b0743c` brown is the textbook deuteranopia
collision, `Lights` and `Day` share `#c8a23c`, and `out_fan` and `out_fan-internal` share `#2e9e8f`.
`darkMode: 'auto'` + `setDarkMode()` replaces the hand-written 30-property theme and the `MutationObserver`
on `body.class`.

### 4.5 Query-string compatibility

`applyViewParams` gains **only additive** params, all optional, all defaulting to today's behaviour:
`panels` (comma list; absent ⇒ derive from `measures` exactly as today), `band` (`auto|off`),
`outputs` (`0|1`), `rail` (`0|1`). Every existing `ChartPreset.query` and `ShareLink.query` in circulation
renders identically to today's chart in the new engine. **No existing link breaks.** That is a hard
requirement, not an aspiration — the query string is on-disk user data in two collections.

## 5. The multi-plant diary

### 5.1 The problem being fixed

There is no diary data model. Every entry is a row in the single `DeviceLog` collection whose
`categories[0] === 'diary'`; a grow's identity is a free-text `lifecycleName` defaulting to the literal
`'My Strain'`; and a "grow cycle" is **inferred in the browser at runtime** by
`convertEventsToGrowCycles()`, which starts a new cycle whenever the stage ordinal rolls back or the
trimmed name string differs. **Renaming a plant mid-grow forks the history. A re-veg fabricates a new
plant.** Cycle identity in URLs is the cycle's start timestamp, so editing an entry's time breaks share
links.

None of that is fixable by adding fields. It needs entities.

### 5.2 The entities

All cloud-side MongoDB (constraint 2), all fields optional except the ids (constraint 5 — no migration
tooling exists), with read-time normalisers and one idempotent boot-time backfill.

```ts
interface Plant {
  plant_id: string;            // nanoid; stable forever; IDENTITY, not the name
  kind: 'plant' | 'tent';      // 'tent' = the whole-room pseudo-plant, see 5.4
  device_id: string;
  owner_id: string;
  label: string;               // RENAMEABLE without forking anything
  strainName?: string;         // free text. SeedFinder's API has been dead since 2024-07-01.
  source?: 'seed' | 'clone' | 'unknown';
  motherPlantId?: string;      // clones point at their mother
  medium?: 'soil' | 'coco' | 'hydro' | 'rockwool' | 'other';
  potLiters?: number;
  position?: string;           // free text: "hinten links"
  colorIndex: number;          // 0..7 → Okabe-Ito ring; the plant's identity on every chart
  startedAt: number;           // epoch ms — day 1 of the day counter
  archivedAt?: number;
  createdAt: number; updatedAt: number;
}

interface PlantStageEvent {
  event_id: string; plant_id: string; device_id: string;
  stage: DiaryLifecycleStage | 'harvest';   // 'harvest' is NEW and cloud-only
  at: number;
  note?: string;
  actor_id?: string;
  createdAt: number;
}

interface JournalEntry {
  entry_id: string; device_id: string; owner_id: string;
  plant_ids: string[];         // [] means "the whole tent" — the tax-free default
  at: number;                  // user-editable; separate from createdAt
  kind: 'note'|'water'|'feed'|'measure'|'training'|'pest'|'photo'|'stage'|'harvest'|'co2refill'|'task';
  text?: string;
  images: string[];            // image_id
  actor_id?: string;           // WHO — §8
  data?: JournalEntryData;     // discriminated on `kind`, server-VALIDATED (today: zero validation)
  legacy_log_id?: string;      // provenance from the DeviceLog backfill
  createdAt: number; updatedAt: number; deletedAt?: number;   // a REAL soft delete
}
```

Three deliberate corrections to inherited traps:

- **`deletedAt`, not `deleted`.** Today `deleted` means "hide from the device overview log stream"; manual
  diary entries are *created* with `deleted: true`, which is why **"Clear logs" deletes nothing from the
  diary**. `JournalEntry` starts clean and `deleted` is never carried over.
- **Server-side validation of `data`.** Today it is `Schema.Types.Mixed` with zero validation and no units.
- **A discriminator field.** Today the split is a string-prefix convention on `categories[0]`, which is why
  the server's own stage-transition entry (written with `categories: ['diary-plant-lifecycle']`, *without*
  the `'diary'` prefix) is invisible in the Entries report while the identical manual entry is visible and
  editable.

### 5.3 The backfill

`convertEventsToGrowCycles()` becomes a **one-time server-side migration**, not a runtime algorithm. For
each device: run the existing algorithm over its `DeviceLog` history, create one `Plant` per detected cycle
(`label = lifecycleName`, `startedAt = cycle start`), one `PlantStageEvent` per lifecycle row, and one
`JournalEntry` per `categories[0] === 'diary'` row with `legacy_log_id` set and `plant_ids` = the cycle's
plant. Idempotent (skip if `legacy_log_id` exists), run from a service constructor as the house style
dictates. `grow-report.component.spec.ts`'s five existing tests over `convertEventsToGrowCycles` become the
migration's test suite — the *only* meaningful tests in the repo get reused rather than deleted.

### 5.4 The tax-free path, and how plants are created

**A device has zero real plants by default, and the journal works exactly as it does today.**

The trick is `kind: 'tent'`. On first journal write, if the device has no `Plant`, the server lazily creates
one with `kind:'tent'`, `label = device.name`. Every entry with `plant_ids: []` is resolved to it. So there
is exactly **one downstream code path** — stage events, day counters, timelapses, the grow report, the chart
band all read a `Plant` — and the user who does not care about plants never sees the word "Pflanze"
anywhere. The tent plant is never listed, never shown, never nameable separately from the device.

Plants appear only when the user asks:

- **In the setup wizard**, one step, one tap: `Wie viele Pflanzen?  [1] [2] [3] [4] [mehr] [ist mir egal]`
  — with **"ist mir egal" / "doesn't matter" as a full-width, visually equal option**, not a link. Picking
  it creates zero plants. Picking 3 creates `Pflanze 1..3` with colour indices 0,1,2.
- **In the Journal tab**, `[ Pflanzen verwalten ]` in the header.

If the account has never created a real plant, the plant selector does not render in the capture sheet at
all. That is the whole answer to "how is a user who does not care about plants not taxed by any of it."

### 5.5 Re-veg, clone, rename, harvest

| Case | Handling |
| --- | --- |
| **Rename** | `Plant.label` is mutable; identity is `plant_id`. Nothing forks. This is the direct fix for the string-comparison cycle detector. |
| **Re-veg** | Just another `PlantStageEvent` with `stage:'vegetative'` after a `'flowering'` one. A backwards stage ordinal is **normal**, not a new plant. The chart draws veg-band → flower-band → veg-band → flower-band. Two day counters exist: `Tag 96` (since `startedAt`) and `Tag 12 der Blüte` (since the current stage event). |
| **Clone** | `[ Klon anlegen ]` on a plant → new `Plant` with `source:'clone'`, `motherPlantId`, `startedAt = now`. The mother's history is **linked, never copied** ("Mutter: Zelt 1 · Nordlicht"). |
| **Harvest** | `PlantStageEvent { stage: 'harvest' }` — a *date*, first-class. This is gap #13: today harvest is not even a lifecycle stage (`flowering → drying`) and "how did this grow do?" is unanswerable. |
| **Weights** | A separate optional `JournalEntry{kind:'harvest', data:{wetGrams?, dryGrams?}}`, gated behind an account toggle **Erträge erfassen — default OFF** with one honest sentence: *"Erntegewichte und Pflanzenzahlen sind in vielen Ländern genau die Angaben, die einen legalen Anbau von einer Straftat trennen. Standardmäßig speichern wir sie nicht."* (§8). |

Adding `'harvest'` to the stage vocabulary is additive but not free: `DiaryLifecycleStage` is imported by
`RecipeStep.stage` and by several `switch` statements in the webapp. Every one needs a `default:` arm and
two i18n keys. It is a half-day, and I am counting it.

### 6.2 The schedule-following flow

```
┌ Düngeplan ───────────────────────────────┐
│ Coco EC-Leiter (mittel)                  │
│ Schritt 7 von 18  ·  Blüte, 2. Woche     │
│ ●●●●●●○○○○○○○○○○○○                       │
├──────────────────────────────────────────┤
│ Ziel-EC 1,8   ·   pH 5,8 – 6,2           │
│ Dein Leitungswasser 0,4 →                │
│ dein Messgerät sollte 2,2 zeigen.        │  ← the EC+ line. See below.
├──────────────────────────────────────────┤
│ Für 10 Liter — in dieser Reihenfolge:    │
│  1  Silizium          10 ml              │
│  2  Basis A           25 ml              │
│  3  Basis B           25 ml              │
│  4  Cal-Mag           10 ml              │
│  5  pH−        zuletzt, nach Messung     │
├──────────────────────────────────────────┤
│ [ Gedüngt ]     [ Schritt überspringen ] │
└──────────────────────────────────────────┘
```

Four domain facts from the research, each rendered as one line of UI:

1. **`ec_basis: absolute | delta_over_source`.** CANNA publishes **EC+**, not EC — verbatim: *"Add the EC
   of the tap water that is used to the recommended EC."* A UI that alarms against the raw chart value is
   actively wrong. The line "Dein Leitungswasser 0,4 → dein Messgerät sollte 2,2 zeigen" *is* that fact.
2. **Store EC canonical; never render a bare "ppm".** Three PPM scales are in circulation; at EC 1.8 a
   Bluelab reads 1260 and a Hanna reads 900 for the same liquid. The account setting names the scale, and
   ppm is always rendered as `1260 ppm₇₀₀`.
3. **Advance by feed event, not wall clock.** `Schritt 7 von 18`. Growers feed Tue/Fri and slip; a schedule
   that advances on Mondays is wrong by week three.
4. **Mixing order as an ordered list with pH last.** Cheapest possible fix for a real failure mode (silica
   reacting with phosphate; "adding pH− can increase EC").

Plus: **batch volume, not reservoir size** ("Für 10 Liter") — this serves the hand-waterer with a can and the
DWC grower with a reservoir identically. And an **autoflower strength multiplier (×0.25–0.5, no 12/12 flip
event)**, because essentially no manufacturer chart has an auto column and this is a real gap fillable
without borrowing anything.

### 6.3 What gets stored

```ts
interface FeedData {                       // JournalEntry.data for kind 'water' | 'feed'
  volumeMl?: number; volumeIsTotal?: boolean;   // total across plants vs per plant
  runoffMl?: number;
  ecIn?: number; ecOut?: number;           // mS/cm, ALWAYS canonical
  phIn?: number; phOut?: number;
  sourceWaterEc?: number;
  waterTempC?: number;
  scheduleId?: string; scheduleStepId?: string;
  products?: { productName: string; dose: number; unit: DoseUnit; totalMl?: number }[];
}
type DoseUnit = 'ml/L'|'ml/10L'|'ml/100L'|'g/L'|'g/10L'|'drops/10L'|'ratio'|'ml_total';

interface FeedSchedule {
  schedule_id: string;
  owner_id?: string;                       // ABSENT = ownerless seeded schedule
  name: string; medium?: string; strength?: 'light'|'medium'|'heavy';
  ecBasis: 'absolute'|'delta_over_source';
  indexBy: 'feedEvent';                    // v1 supports exactly one indexing scheme
  autoflowerMultiplier?: number;
  source?: { url?: string; retrievedAt?: number;
             kind: 'ownerless'|'user'|'official_pdf'|'official_calculator'|'manual_transcription';
             chartVersion?: string };
  steps: FeedScheduleStep[];
}
interface FeedScheduleStep {
  step_id: string; stage: DiaryLifecycleStage; indexInStage: number; label?: string;
  targetEc?: [number, number]; targetPh?: [number, number];
  products: { productName: string; dose: number | [number, number] | string; unit: DoseUnit; note?: string }[];
  mixOrder?: string[];

```

`dose` is `number | [number,number] | string` on purpose: real charts contain ranges (`5–13`), zeros that
mean stop (`8,8,8,8,8,0,0`) and literal strings (`"Flush only"`, `"water"`, `"Use as pH up"`). A scalar
model is wrong and would silently mangle them.

### 6.4 On the chart

- **Annotation rail row 1** gets a 💧 glyph per water event and a 🧪 per feed, clustered at 8–12 px bins
  with count badges. Tap → the entry.
- **A dedicated EC panel** appears whenever the device has ≥3 feed entries with EC: input EC as a filled
  dot, runoff EC as a hollow dot, and the schedule's `targetEc` band as a `markArea` that **steps along x**
  as the schedule advances. Divergence > 20 % between input and runoff draws a caret.
- **The verdict does not judge EC.** EC is not sampled continuously, so a time-in-range percentage over it
  would be a lie. The Journal shows it; the verdict stays silent about it. Naming this is more valuable than
  faking it.

### 6.5 Brand posture

**Build the engine brand-agnostic and user-editable first, and seed it with ownerless schedules.** Ships
with: Lucas Formula (0-5-10 / 0-8-16), Jack's 321, a generic coco EC ladder, a generic soil EC ladder — all
of which carry zero IP risk and are useful on day one with nothing borrowed.

Brand charts, **if the owner ever chooses them**, are a separate hot-swappable MongoDB content collection,
never baked into the bundle, each carrying `source_url` + `retrieved_at` + `chart_version` + `kind`, so any
single brand can be removed in one DB update. Word marks only — no logos, no brand colours, no bottle
photography. Never a feature named after a brand ("CANNA Modus" converts referential use into trademark use
and forfeits the Art. 14(1)(c) EUTMR defence). Never copy brand prose; paraphrase every description. Publish
a takedown address and a documented notice-and-action policy *before* shipping any of it.

**And the honest framing: this is not a design decision.** The EU sui generis database right (Directive
96/9/EC, UrhG §§ 87a–87e) requires no originality and bars extraction of a substantial part; shipping one
brand's complete chart is extraction of a substantial part, and Novazer GmbH is a far more reachable
defendant than an anonymous Play Store developer. Two hours of German IP counsel gate the brand layer. The
ownerless layer needs no gate and is what v1.3 ships.

**Why this is a Terp Control feature at all:** the chart data is the commodity; the closed loop is the
product. Every brand ships a calculator and **none of them can see the grow.** Terp Control can
**auto-detect the 18/6 → 12/12 flip from `out_light` history** and place the grower on the correct bloom
week, and can **move the EC/pH advisory bands as the schedule advances**. No bottle brand can do that,
because they have no device.

## 7. Camera & timelapse

Today: one webcam per device (`cloudSettings.rtspStream` is a single string), a still every 30 s over MQTT,
three timelapse durations built hourly, and `Image` carrying **no back-reference to any log, entry or
plant**. Timelapses have no relation to a cycle, phase or entry.

**The relation is time, and time is enough.** I add no plant foreign key to `Image`. A tent camera sees the
whole tent; asking a user to tag pictures is exactly the tax this concept refuses. Instead:

- **An image at time T belongs to whatever stage each plant was in at T**, derived from `PlantStageEvent`.
  Zero user work, zero join table, zero new field on `Image`.
- **Stage-bounded timelapses.** "Blüte" = the frames between the `flowering` stage event and the next one.
  This needs exactly one additive change: `Image.duration: '1d'|'1w'|'1m'|'stage'`. Generated on request by
  the existing mp4 pipeline, cached, and named in the UI as `Blüte · 42 Tage · 1:18`.
- **The film strip is an axis** on the Belege chart: thumbnails positioned by timestamp on the same x-scale
  so uneven capture intervals read honestly as *gaps*, sharing the chart's cursor. Delivered as **one sprite
  + JSON index per window** (50 tiles under 15 min of footage, 100 above, 256×160 px) rather than N image
  requests. mp4 entries — which already carry `timestampEnd` — render as a bracket, not a point.
- **The excursion thumbnail** (§3.5) is the camera's highest-value appearance in the whole concept: the
  picture from the minute the room peaked, next to the sentence that says it peaked.
- **Every journal entry with an image contributes to the strip too**, so a hand-held phone photo of a
  yellowing leaf sits on the same timeline as the tent cam.

Two hygiene fixes that become urgent the moment the diary is the product: `DELETE /image/:image_id` exists
and **is never called by the webapp**; retention/thinning filters `format:'jpeg'` only, so `user/jpeg` blobs
accumulate forever inside MongoDB documents capped by the 16 MB BSON limit, uploaded through
`express-fileupload` mounted **with no size limit**. And the unique index
`{device_id, format, timestamp, duration}` means two uploads in the same millisecond collide.

## 8. Multi-user, clubs, and the privacy posture

### 8.1 The authorisation rewrite

```ts
// server/src/middlewares/auth.middleware.ts:172  — THIS LINE IS THE ENTIRE AUTHORISATION MODEL TODAY
const devices = await deviceModel.find({ owner_id: req.user_id, device_id: device_id }, { device_id: 1 });
```

`Device.owner_id` is a single un-indexed `String`. Claiming is a **silent transfer** with no check on and no
notification to the previous owner. Share links are read-only, full stop.

```ts
interface DeviceMembership {
  membership_id: string; device_id: string; user_id: string;
  role: 'owner' | 'grower' | 'member' | 'viewer';
  displayName?: string;        // pseudonymous, room-scoped. NEVER a real name.
  invitedBy?: string; createdAt: number; revokedAt?: number;
}
```

| Role | Verdict & Evidence | Journal write | Goals / control | Members |
| --- | --- | --- | --- | --- |
| `owner` (exactly one) | ✓ | ✓ | ✓ | ✓, incl. transfer & delete |
| `grower` | ✓ | ✓ any plant | ✓ | — |
| `member` | ✓ | ✓ **own entries only** (`:self`) | — | — |
| `viewer` | ✓ | — | — | — |

The `member` `:self` tier is copied straight from Cannanas' `charges:create:self` /
`member:journals:self-checkin` pattern, and it is the **one legally-motivated multi-user feature worth
owning**: § 17 Abs. 2 KCanG requires members to participate *eigenhändig*, which is why every club platform
ships a member duty journal.

Cost, honestly: a new collection, rewriting `auth.middleware.ts:172` and `:207`, loosening ~10 owner-scoped
service queries, an `actor_id` on `JournalEntry` and on config-change `DeviceLog` rows, and an
**invite-by-code** flow. Not invite-by-email-lookup — an account-lookup-by-email endpoint does not exist and
designing one against enumeration abuse is its own project. A code is a string the owner pastes into
Telegram, which is where this community already is. **This cannot be bolted on as a flag** and it is not
in v1.

Prerequisite, and it is a **blocker**: `POST /device/claimcode` is unauthenticated for any device that has
not reported `hardwareInfo.claimcode_auth === 'on'`, and `claimDevice` overwrites `owner_id`
unconditionally. Knowing a `device_id` — which appears in every webapp URL — is enough to steal a device.
Nothing that widens device access ships before that is fixed.

### 8.2 Attribution

`JournalEntry.actor_id` is **always stored** and **conditionally displayed**:

- **Private mode (default):** attribution is stored but never rendered and never exported. A two-person
  household gets two logins, two notification targets, and one shared tent — the case *every* vendor fails
  (Pulse charges $10/user and got a public backlash thread; everyone else says share the password).
- **Club mode (opt-in, per device):** `displayName` renders on every entry, the participation log is
  visible, retention is longer, and exports gain a `NONE | PSEUDONYMIZED | ANONYMIZED` selector
  **defaulting to anonymised**.

### 8.3 The privacy line, as a design decision

| Keep (device-observed, thing-scoped) | Refuse (person-scoped, product-scoped) |
| --- | --- |
| Climate time series, setpoints, actuator states, alarms | Who consumed what, when |
| Watering/feeding events, EC/pH | Member identity, DOB, address, membership number |
| Photos the user chose to take | Per-member dispensing quantities and THC content |
| A task record with an optional actor | A permanent non-deletable inventory of grams |
| Harvest weights — **only if the user opts in** | Anything requiring a real name |

Concretely, in this concept:

1. **Jurisdiction mode on `/account`,** default **private**. Private = harvest weights off, plant count never
   prompted, attribution hidden, telemetry retention **12 months**, one-tap wipe.
2. **Telemetry retention is finite by default.** Today the InfluxDB bucket is created with **no retention**
   and there are **zero downsample tasks** — raw 5-second samples are kept forever. A light schedule
   flipping 18/6 → 12/12 is a legible harvest calendar. §26 KCanG is characterised in the German press as
   resembling *"einer Vorratsdatenspeicherung"*, and §28 Abs. 2 lets authorities seize digital data **with
   no prior judicial approval**. Infinite retention is a liability, not a feature.
3. **No location, ever.** No GPS, no IP-geolocation persistence, no "growers near you", no persisted
   timezone-from-IP. Timezone is a user setting.
4. **Do not become the club's system of record for § 26.** ~20 compliance SaaS products already serve that
   at €0.50–1.00/member/month; Cannanas claims >250 licensed clubs and ships a public OpenAPI with 185
   paths. Winning that race means owning 23 differing authority export formats and liability for wrong
   exports. **Be the device-attested environmental layer those systems consume instead** — Cannanas'
   `CreateDiaryRequest.measurements` has 40 numeric fields that read like a controller telemetry dump, and
   their zones carry `streams.video[].url` which Terp's webcam fills directly. There is **no sensor-ingestion
   endpoint in their public API. The IoT path is private and unclaimed.**
5. **Never ship a `KCanG-konform` badge or any compliance warranty.** Even Cannanas' own AI compliance
   endpoint says *"Not legal advice."*
6. **The audit log is deletable by the account owner.** Tamper-evidence protects a *regulated* club against
   its own staff; it **victimises an unregulated grower**. Immutability is an opt-in, club-scoped mode.
7. **No analytics or ad SDKs. EU hosting, stated plainly.**

## 9. Old devices (type 7) — exactly what they see

The reason this concept serves legacy hardware without special-casing it: **the verdict engine is
channel-driven, not device-driven.** A judged channel is `(something the device measures) ∩ (something with
a goal)`. Everything else follows.

All four devices get the same shell, the same four tabs, the same freshness pill, the same Journal, the same
new chart. Their existing settings components stay mounted under `/device/:id/settings` behind the
untouched `ngSwitch`. **No legacy device loses a screen.**

*because the controller stopped borrowing it* — today `overview.component.html:40` hard-codes
`{{'devices.fridge.title'|translate}}` for both, so a controller's dashboard card literally reads "Terp
Control FRIDGE GROW" and an unnamed controller is *named* that. The fix is a new `devices.controller.*`

### `light` — a dimmable lamp

Measures no climate. Judged channel: **photoperiod adherence** — did `out_light` actually run for

## 10. Onboarding

### 10.1 Capability is established by watching, not asking

The whole "how do we know what this user has" problem is already solved in the data and thrown away by the
code. `hardwareInfo.sockets` is a CSV of paired roles. `deviceControlCapability()` collapses it into three
buckets — `'full'` if *any* of dehumidifier/heater/co2 is paired — so **a heater-only tent is shown humidity
targets, a humidity-deviation warning and a "dehumidifier running non-stop" alarm preset it can never act
on**. And an absent key (older firmware) **fails open to `'full'`**.

Replace it:

```ts
interface DeviceCapability {
  canHeat: boolean; canCool: boolean; canDehumidify: boolean;
  canHumidify: false;                 // hardware truth: NO humidifier role exists. Typed as `false`.
  canEnrichCo2: boolean; canDim: boolean; canSwitchLight: boolean;
  measures: Set<'temperature'|'humidity'|'co2'|'lux'|'leaf_temperature'|'rpm'>;
  reportedAt?: number;
  unknown: boolean;                   // fail CLOSED, and say so
}
```

- `canCool` and `canDehumidify` both derive from the `dehumidifier` socket because **`out_dehumidifier`
  doubles as the cooler** in `temp`/`breed` workmodes — one socket, two meanings. The UI names it by what
  the current workmode makes it do.
- `unknown: true` renders a banner on Goals: *"Dieser Controller hat noch nicht gemeldet, was angeschlossen
  ist."* / *"This controller hasn't reported what's connected yet."* Controls stay visible but the verdict
  judges only measured channels. **Never silently show a control that does nothing.**

**And the rule that makes this visible in the verdict:** a channel the device **cannot change** is marked
`advisory`. It appears in the tiles and the scorecard with the label *"Nur zur Info — dieses Gerät kann das
nicht ändern"*, and **it does not drive the headline**. When *every* channel is advisory (a monitor-only
device), the headline uses the `verdict.monitor.*` copy. This is the whole answer to user type 3, expressed
inside the philosophy rather than as a settings toggle.

**Four dead controls are removed from the UI outright, not hidden behind Expert:** the entire
`daynight.floating` / `float_start` / `day_duration` / `light_duration` beta feature (**read by no firmware
anywhere — zero grep hits across `firmware/`**), plus `lights.maintenanceOn`, `co2.sunsetOff` and
`daynight.linearChange`, which the controller firmware silently ignores. A control that does nothing is
worse than a missing one in a product whose entire claim is that it tells you the truth. Removing
`floating` also deletes the live `simpleSettings.light.floatingNote` raw-key bug.

### 10.2 First run — three taps

```
1  Wie soll es heißen?         [ Zelt 1            ]   ← prefilled with the CORRECT type name
                               [ Weiter ]  [ Überspringen ]

2  Was steht drin?             ← stage-preset-picker, EXISTS TODAY
   ┌────────┬────────┬────────┐
   │ Sämling│  Veg   │ Blüte  │
   ├────────┼────────┼────────┤
   │Spätblüt│Trocknen│ Nur    │   ← the 6th card is NEW: "Nur messen" / "Just measuring"
   │        │        │ messen │
   └────────┴────────┴────────┘

3  Wie viele Pflanzen?
   [ 1 ] [ 2 ] [ 3 ] [ 4 ] [ mehr ] [ ist mir egal ]

   Fertig.
```

Step 2 is the **only mandatory question**, and it is the one that creates the `GrowGoal` — so a monitor-only
device with `workmode: 'off'` still gets a verdict. "Nur messen" writes a `GrowGoal` with
`source:'stage', stagePresetId: <last chosen or vegetative>` and **writes nothing to the device**, which is
what makes it work for a controller with no sockets at all.

Everything else — which sockets exist, whether the SCD4x is present, whether a camera is paired — is read
from `hardwareInfo` continuously and never asked. The existing `setup-wizard` already builds an adaptive
step list from hardware (`['name','connections','done']` for monitor-only); this keeps that machinery,
shortens it, gives it a route so it is re-runnable, and points its illustration slots at the **~30 MB of
already-shot wizard videos sitting unreferenced in `webapp/src/assets/wizard/`** (23 `.mp4`s copied into
every production build today and rendered nowhere).

## 11. Per-user-type walkthrough — the first week

### Type 1 — monitoring only, lazy

**Day 1.** Claims the controller, three taps, picks "Blüte". No sockets. The verdict card appears grey:
*"Zu wenig Daten für ein Urteil. Nur 4 % der letzten 24 Stunden wurden aufgezeichnet."* He closes the app.
**Day 2.** Opens it once from bed: green tick, *"Dein Klima passt. 22 Std 40 Min der letzten 24 Stunden im
Zielbereich."* plus *"Dieses Gerät misst nur."* Closes it. **Day 4.** Amber: *"Behalt es im Auge. Feuchte
war 3 Std 10 Min außerhalb. Am längsten 1 Std 20 Min, gestern Nacht."* He taps the tile once, sees the
night column at 61 %, understands it is a night problem, and cracks the tent open at lights-off. **Day 7.**
Green again. He has never opened the chart. **This is the type the concept is built for, and he is the type
the current app serves worst** — today he gets the full fridge dashboard with a dehumidifier tile he cannot
act on.

### Type 2 — the same, with a camera

Identical first three days. **Day 4**, the amber verdict's scorecard sheet shows *"1 Std 40 Min zu feucht,
gestern 21:10"* **with the tent photo from 21:10 next to it** — condensation visible on the plastic. That
is the moment this concept earns him. He opens Belege, the film strip is an axis, he scrubs to 21:10 and
the picture follows the crosshair. **Day 7** he opens Journal and plays the running "Blüte" timelapse.
*Honest caveat:* stage-bounded timelapses and the sprite film strip are **v1.1/v2**, so in October 2026 he
gets the excursion thumbnail and today's timelapses, and nothing more. He is the type this concept most
under-serves relative to what the owner asked for (§15).

### Type 3 — controls only CO₂ (or only heating)

**Day 1.** One `co2` socket paired. `hardwareInfo.sockets = "co2"`. Today that returns `'full'` and he is
shown humidity targets and a dehumidifier alarm preset. Under this concept the Status screen shows four
tiles: **CO₂ (judged, 91 %)**, temperature (advisory), humidity (advisory), VPD (advisory). The headline is
computed from CO₂ alone: *"Dein Klima passt."* **Day 3** temperature spikes to 31 °C. The temperature tile
turns amber and the scorecard says *"2 Std 05 Min zu warm · Nur zur Info — dieses Gerät kann das nicht
ändern."* The headline stays green. He is informed, not nagged. **Day 5** he buys a heater socket, pairs
it, and temperature silently becomes a judged channel the next time `hardwareInfo` arrives — no settings
change, no wizard re-run. **He is the second-best-served type.**

### Type 4 — the whole tent

**Day 1.** Heater, dehumidifier, two light sockets, CO₂ upgrade. Everything is judged. The Status screen is
dense with four green tiles and an outputs strip that shows the dehumidifier cycling. **Day 2** he taps
Belege and gets what he has wanted for a year: temperature with the stepped setpoint drawn on it, the
deviation shaded, the outputs lane underneath showing the heater firing four times an hour at 04:00. **Day
4** humidity sits at 42 % all week, below band, and there is **nothing he can do** — there is no humidifier
role in the firmware. The concept marks humidity advisory-below and the headline stays green, but the tile
is amber every single day (§15.3). **Day 6** he notices the verdict is single-climate and he has an
autoflower and a photoperiod in the same tent at different stages; the app judges against the more advanced
one and shows a small note *"2 Phasen im Zelt — beurteilt wird Blüte."* He is not fully served, and the
owner asked for exactly this (§15.8).

### Type 5 — closed-loop DIY, builds a fridge

**Day 1.** He does not want a verdict, he wants data. He finds `/account → Start auf → Belege` in the first
five minutes and never sees the Status tab again. **Day 2** he opens the scorecard once out of curiosity,
reads *"aus 17 214 Rohmessungen · 5-Sek-Raster"*, and decides the number is trustworthy. **Day 3** he wants
his own EC probe on the chart and cannot have it — `VALID_SENSORS` is hard-coded and the measure catalogue
is a literal array in a component, so his probe can only enter as a manual journal entry. **Day 5** he
looks for a write API and finds none. **This concept does nothing for him in v1** and I am not going to
pretend the "Start on" setting is a strategy (§15.5).

### Type 6 — a club with four rooms and eleven members

**Day 1.** The Vorstand claims four controllers. `/list` becomes the club's whole dashboard: four verdict
rows, one line each. *"Raum 1 · Alles in Ordnung · 97 % · live"* / *"Raum 3 · Da braucht dich was ·
Temperatur 2 Std 40 Min zu warm · live"*. He opens Raum 3, sees the excursion thumbnail, and calls whoever
is nearest. **Day 2** he switches the devices to club mode and invites members by code. **Day 3** a member
logs a watering: two taps, and it appears with her `displayName`. **Day 5** the Vorstand exports the week
anonymised for the club's compliance platform — a device-attested climate record that beats a hand-typed
diary number in an inspection **and contains zero personal data**. *Honest caveat:* multi-user is **v1.4**.
In October 2026 the club shares one login, which is what they do today anyway. The verdict board works for
them from day one; the roles do not.

### Type 7 — an old fan and two lights

**Day 1.** He updates the app expecting nothing and finds his fan has a Status tab. It says *"Nichts zu
beurteilen — dieses Gerät misst nichts. Lüfter lief 18 Std 20 Min (76 %)."* That is more than he had.
**Day 2** he opens a light and sees *"Licht lief wie geplant. 12 Std 00 Min gestern."* **Day 4** one light
reads *"Licht lief 9 Std 40 Min. Geplant: 12 Std."* — a loose plug he would otherwise have found in three
weeks. **Day 5** his plug's settings page stops rendering raw i18n keys on its checkboxes. Nothing he had
was taken away and one real fault was found. **He is better served than he expects to be, without being the
focus group.**

## 12. Stoner, normal, techie — one design

**The mechanism is progressive disclosure by depth, not a mode switch.** Nobody picks a persona. They stop
tapping when they have their answer.

| Depth | What you get | Who stops here |
| --- | --- | --- |
| 0 | The verdict card: a glyph, one sentence, one bar. | **Stoner.** |
| 1 | Three or four tiles: value, goal, TIR %. | Stoner, occasionally. |
| 2 | The scorecard sheet: in/above/below, day vs night, longest excursion as a duration, the photo. | **Normal.** |
| 3 | Belege: small multiples, setpoint band, outputs lane, annotation rail. | Normal, weekly. **Techie**, daily. |
| 4 | `[ Alle Messwerte ]`, `[ Als Tabelle ]`, raw sample count, band-source override, editable tolerances and verdict thresholds. | **Techie.** |

Specifics per lens:

**Stoner.** 28 px headline, 56 px glyph, everything ≥44 px, the FAB, two-tap watering, a three-tap
onboarding, and **no number in the headline ever**. The `rangeGuard` directive (slider inert until its row
is tapped, disarms after 8 s) already protects sliders from scroll-thumbs and stays. Colour is never the
only channel — every verdict state has a distinct glyph (`✓ ~ ! ?`), so a red/green-blind stoner reads the
same thing.

**Normal.** Gets the window switcher (24 h / 7 T / Phase), the journal, the feeding schedule card, and the
scorecard. Never has to configure a band — the priority chain picks one and labels it.

**Techie.** Gets: `?detail=` deep links on every scorecard; the raw sample count and the aggregation method
printed on the scorecard; editable tolerances and verdict thresholds under Ziele → Beurteilung; band-source
override per channel; the full measure picker; "view as table" on every panel (no OSS chart library matches
Highcharts' accessibility module, and Terp does not load that module today anyway); `/account → Start auf`
so the app opens on Belege; the existing Simple/Expert `ion-segment` kept for settings, with its
`localStorage['app-settings-expert']` persistence intact. And **the verdict is arithmetic, fully explainable,
with its inputs on screen** — which is the only version of this a sceptical engineer will tolerate. There
is no model, no score out of 100, no black box.

**What all three share:** exactly one mental model — *goal, measured, how much of the time in between*. The
stoner sees it as a colour, the normal user as a percentage, the techie as a dwell-time integral over raw
samples. Same object, three resolutions.

## 14. Non-goals

1. **No community feed.** ~200 App Store reviews across TrolMaster and VIVOSUN were read and **not one
   praised the feed each ships.** It is permanent moderation cost. A public diary *link* you can paste
   anywhere is not a feed you must moderate.
2. **No two-way sync with any grow-diary platform.** GrowDiaries has no public API and is Cloudflare-gated;
   Grow with Jane's ToS §(c)(7) bans scraping outright and its backend is Firebase; SeedFinder's API has
   been dead since 2024-07-01. The feature is called **"Woche exportieren" / "Export week"** and it never
   claims otherwise.
3. **Never Instagram, Threads, TikTok or Reddit auto-post.** A failed Discord post means a revoked webhook.
   A failed Instagram post means the **user** loses their account with no appeal and Terp Control was the
   proximate cause.
4. **No branded footer on user posts.** § 6 KCanG bans cannabis advertising and sponsoring with fines to
   €30,000, read broadly. This is the single riskiest string in the whole feature area.
5. **No compliance product and never a `KCanG-konform` badge.**
6. **No per-member consumption or dispensing records.** Arguably Art. 9 GDPR health data, for data a grow
   controller has no need for.
7. **No location, no real-name enforcement, no analytics SDK, no ad SDK.**
8. **No new firmware socket roles in v1.** The design lives inside the existing five
   (`dehumidifier`, `heater`, `light`, `secondary_light`, `co2`) and says out loud that there is no
   humidifier, no exhaust-fan and no chiller role.
9. **No irrigation or dosing automation.** There is no hardware for it. Watering is capture-and-recall.
10. **No offline mode, no native app.** There is no service worker, `capacitor.config.ts` is untouched
    scaffold (`io.ionic.starter`), and there are no `android/` or `ios/` projects.
11. **No AI grow advisor.** The verdict is arithmetic on the user's own declared goal, explainable in one
    sentence, with its inputs on screen. That is a feature, not a limitation.
12. **No score out of 100, no streaks, no gamification.** TIR is a percentage with a definition and a
    denominator.
13. **It will not hide the chart from people who want it.** `/account → Start auf → Belege`.
14. **It will not break a single existing share link or chart preset.** Route paths and query-string
    semantics are treated as persisted user data, because they are.

## 15. Honest weaknesses

**15.1 The verdict is only as good as the goal, and most goals will be our guesses.**
The band-source chain ends at `GROW_STAGE_PRESETS` — five rows of day/night temperature, humidity and a VPD
range with **no cited source anywhere in the repo**. A green tick against a wrong band is worse than no tick
at all, because it manufactures confidence. The mitigation (always label the source, always let the user
override) is real but it is a label, not a fix. **This is the deepest flaw in the concept and it is
structural.**

**15.2 Time-in-range is a proxy for climate control, not for plant health.**
96 % TIR against the wrong target grows bad weed, and a grower whose leaves are yellowing from a lockout
will see a green tick. I changed the headline copy to *"Dein Klima passt"* rather than *"Dein Grow ist
okay"* precisely because of this — which means the concept's own philosophy statement ("is my grow OK") is
answered by the product with a narrower question than the one it poses. A critic is right to call that a
bait-and-switch, and my defence is only that the narrower answer is the honest one.

**15.3 Humidity can only ever go down, and an always-amber channel trains people to ignore amber.**
There is no humidification path in the hardware. In a dry German winter tent RH will sit below band for
weeks. The advisory-channel rule keeps it out of the headline, but a tile that is amber every day for a
month is a tile people stop reading — and the alarm-fatigue failure mode is the exact thing this concept
claims to solve. A partial answer (auto-widen an advisory band's lower edge when the device demonstrably
cannot reach it) is inventing a heuristic to paper over a hardware gap.

**15.4 Six weeks means v1 ships the verdict on top of the chart the verdict is supposed to redeem.**
"Charts are the evidence you drill into, never the first thing you see" is only half true in October,
because the evidence is still fifteen translucent areas with hidden axes and hover-only events. The
concept's most quotable line is the part that ships last.

**15.5 The techie is actively annoyed by this design and "Start auf" is a thin answer.**
Type 5 writes their own Go apps rather than use anyone's. Telling them "we computed a verdict for you, but
here's a setting to skip it" is not a strategy — it is an apology. There is no write API, `VALID_SENSORS` is
hard-coded so their EC probe cannot enter the chart, and none of that changes before v2. If the owner
weights type 5 heavily, this is the wrong concept.

**15.6 The scorecard is computationally expensive and the cache is unbudgeted work.**
24 h × 5 s × 4 channels ≈ 69 k raw points per request, and the correctness requirement forbids the
`aggregateWindow` that would make it cheap. **There are zero Influx tasks in the repo today**, no retention
policy, and no downsampling. The v1 Mongo TTL cache is a stopgap; the real fix (an hourly in/above/below
rollup task) is v1.1 and I have not costed the operational work of running Influx tasks in this stack.

**15.7 An offline device destroys the concept's premise exactly when the user most wants it.**
The screen's entire job is to deliver a verdict. The only honest verdict for an offline device is *"I don't
know."* Every competitor's #1 complaint is showing stale data as live; the fix for that complaint is
admitting ignorance, and admitting ignorance is the one thing a single-answer home screen handles worst.
The offline card is well designed and it is still a blank where the product's value should be.

**15.8 Multi-plant fights the verdict, and the owner explicitly asked for multi-plant.**
The verdict is device-scoped because *climate* is device-scoped: one tent, one temperature. Plants at
different stages in one tent have different correct bands and one climate cannot satisfy both. This concept
judges against the most advanced plant's stage and prints a small note. That is a compromise, not a
solution, and the brief says *"maybe even at different stages"* in so many words. A concept organised around
plants rather than around a room would handle this better and would handle everything else worse.

**15.9 The verdict thresholds are invented and I have made them user-editable to hide that.**
AGP's ≥70 % has a consensus behind it. 90 % / 70 % / 60 min / 180 min for a grow room have nothing behind
them but my judgement. Making them editable is honest; it is also how a designer avoids defending a number.

**15.10 Two hard gates sit outside design's control.**
Open Question 2 (does Novazer hold a Highcharts licence, and does "quelloffen" still stand) gates §4.1
entirely. German IP counsel on UrhG §§ 87a–87e gates the brand-schedule layer in §6.5. Neither is a design
risk I can retire, and both are on the critical path of things I have put in the roadmap.

**15.11 It adds a fifth thing to a navigation that already had four too many, in a codebase with no test
baseline.** The device shell, the tab bar, the FAB, `GrowGoal`, the scorecard endpoint and the capability
rewrite all land in the same six weeks, on a repo whose CI never runs `ng test` and whose only meaningful
tests cover a function this concept plans to delete.
