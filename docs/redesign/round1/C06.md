# C06 — "Glance Tiles"

**Design philosophy:** a dashboard of live tiles, home-screen-widget philosophy.
**Status:** concept for the October 2026 release. Every claim about today's code is cited to a file.

---

## 1. Thesis

**The device home is a grid of self-contained tiles that each answer one question with goal-vs-actual and
each carry the age of the data that answers it — so the app is honest by construction, and the seven user
types are served by which tiles exist rather than by which mode you picked.**

The big idea: Terp Control's real failure today is not that it lacks features, it is that it *asserts*.
It asserts a fridge dashboard on a controller (`overview.component.html:40`). It asserts a humidity target
on a tent with no dehumidifier (`grow-presets.ts:143-173` fails open to `'full'`). It asserts that a value
is current when `/data/latest` cannot even tell you when it was measured — the endpoint runs
`range(start: -5m)` and returns a bare float, `NaN` otherwise (`server/src/services/data.service.ts:162-188`).
A tile is the smallest unit that can carry a *claim plus its warrant*: this number, this target, this age,
this proof that something can act on it. Build the home out of those units and the honesty problem, the
capability problem and the seven-user-types problem collapse into one mechanism: **a tile exists when the
evidence for it exists, and it looks alive only when it is alive.** Nobody configures anything. The board
assembles itself from what the hardware reported and what the user has actually done, and the only two
gestures a user ever needs are *drag to move* and *X to hide* — the most universally understood
configuration idiom on any phone on earth.

### 2.2 Navigation model

```
ion-split-pane
├── ion-menu          Devices · Shared links · Account · [Diagnostics · Fleet]  · dark mode · logout
└── router-outlet
      /device/:id  ── THE BOARD ───────────────────────┐
        │  tap a tile        →  /device/:id/t/<tile>   │  ion-back-button defaultHref = the board
        │  tile overflow "…" →  chart deep link        │
        │  header overflow   →  Settings · Setup · Share · Testmode
        └──────────────────────────────────────────────┘
```

- **The board is the root of the device.** Everything else is one level down, and everything one level down
  has a back button pointing at the board. This replaces today's six outline buttons in an
  `action-row` (`overview.component.html:219-248`) and the total absence of a back button (dossier §1.3).
- **No tab bar.** A tab bar and a tile grid are the same idea competing for the same screen. The grid wins.
- **Device switcher** in the header when the account has >1 device: an `ion-select`-style popover on the
  title. On desktop the menu lists devices directly.
- **Desktop (≥1200 px):** the board keeps a 4-column grid on the left and tile details open in a
  **right-hand rail** instead of navigating. Selecting Climate on a 27" monitor gives you the whole board
  *and* the climate panels at once. This is the "web app on a big screen" advantage stated concretely.
  Below 1200 px the rail becomes a navigation.

### 2.3 Restricted modes (constraint 8 — share / demo / public)

`resolveDeviceAccessInfo` (`devices.service.ts:202`) already yields `locked`, `canEdit`, `webcamAllowed`,
`chartsAllowed`. Board rules, stated once and enforced in `TileBoardComponent`:

| Condition | Board behaviour |
| --- | --- |
| `canEdit === false` | No drag, no hide, no `[+]` capture, no Settings/Setup in the overflow. Tiles render read-only. |
| `webcamAllowed === false` | Camera tile absent entirely (not greyed — absent). |
| `chartsAllowed === false` | Tiles do not navigate; tapping shows the value detail without panels. |
| `auth.isDemo` | Drag allowed, layout persisted to `localStorage` only, never `PUT`. |
| public/share view | Menu button swapped for the theme toggle (existing convention). |

New: `SharePage` gains `'board'`, so a share link can point at the board itself. That is the launch-day
stand-in for multi-user (§8).

### 3.2 Tile anatomy — identical on every tile, no exceptions

```
 ┌────────────────────────────┐
 │ EYEBROW              CHIP  │  11px 600 letter-spaced label · freshness chip (right)
 │                            │
 │ VALUE  UNIT     SPARKLINE  │  34px 600 value, 13px unit, 60×22px 24 h sparkline (no axis)
 │ CONTEXT LINE               │  13px muted — the target, or the next transition, or the last action
 │ ├─────────●────────┤       │  the GOAL BAR
 └────────────────────────────┘
```

**The goal bar is this concept's signature element and its whole answer to "goal-vs-actual at a glance".**
One horizontal track, always the same grammar:

- The **centre** is the setpoint (`day.temperature` / `night.temperature` picked by `is_day`, `co2.target`,
  the stage preset's VPD band midpoint, the feed regime's `ecTarget` midpoint).
- The **ends** are the user's own alarm thresholds for that `sensorType` if any exist
  (`Alarm.upperThreshold` / `lowerThreshold` — currently *unused by the chart*, dossier §1.6), otherwise
  setpoint ± a per-measure tolerance (±1.5 °C, ±7 %RH — the tolerances `grow-assistant-card` already uses).
- A **soft band** shading the middle third.
- A **dot** for the current value. Distance from centre is deviation; side is direction.

You learn one picture and it works on temperature, humidity, VPD, CO₂, fan RPM, EC and pH. The dot is
green inside the band, amber outside — **and grey whenever freshness is not `live`, without exception.**

> **A tile with no goal bar is making a deliberate statement:** nothing here can act on this number.
> That is how the fail-open capability bug (`grow-presets.ts:166-168`) becomes visible instead of silent.

### 3.3 Freshness — the honest-stale answer

Today the board cannot be honest even if it wanted to be: `/data/latest` returns a float or `NaN` with no
timestamp, and the overview infers "online" from *VPD not being NaN* (`overview.component.ts:100-114`).
A reading from 4 minutes 59 seconds ago is pixel-identical to one from 2 seconds ago.

**Required backend change (cloud only, no firmware):**

```
GET /data/board/:device_id
→ {
    serverTime: 1761300000123,          // authoritative clock — never trust the phone's
    lastseen:   1761299998000,          // Device.lastseen
    measures: {
      temperature: { v: 24.1, t: 1761299998000 },
      humidity:    { v: 58,   t: 1761299998000 },
      vpd:         { v: 1.31, t: 1761299998000 },   // derived, t = min(t of its inputs)
      co2:         null,                            // sensor absent
      lux:         { v: 18400, t: 1761299940000 }
    },
    outputs:  { light: {v:1,t:…}, heater: {v:0,t:…}, dehumidifier: {v:1,t:…}, co2: null },
    targets:  { temperature: 25, humidity: 60, co2: 1000, vpdBand: [1.2,1.5] },
    capability: { temperature: true, humidity: true, co2: false, light: true },
    image:    { image_id: "…", t: 1761299972000 }
  }
```

One request replaces the current per-measure polling loop that fires N requests every 10 s
(`data.service.ts:87-124`) — a strict improvement the dossier already flags as quadratic. Widen the Influx
range to `-48h` with `fn: last` so an old value comes back *with its age* instead of vanishing into `NaN`.
Fix the Flux injection (`data.service.ts:80-89`) in the same commit, because this endpoint widens the
measure vocabulary.

**Four states, per measure, never per device:**

| State | Rule | Rendering |
| --- | --- | --- |
| `live` | `serverTime − t ≤ 60 s` | Full-opacity value. Chip: a 6 px green dot + `vor 4 Sek` / `4 s ago`. Goal bar coloured. |
| `stale` | `60 s < age ≤ 600 s` | Value drops to `--tc-text-muted`; sparkline gets a 4 px diagonal hatch over its right edge; chip turns amber-outlined: `vor 6 Min` / `6 min ago`. **Goal bar dot goes grey.** |
| `offline` | `age > 600 s` | Whole tile gets `.tile--offline`: 1 px `--ion-color-medium` top border, value at 55 % opacity, context line replaced with `Zuletzt 24.1 °C · vor 2 Std` / `Last 24.1 °C · 2 h ago`. **Goal bar hidden entirely.** |
| `never` | No point in 48 h | `—` and `Noch keine Messung` / `No reading yet`. No sparkline, no bar. |

600 s is not a taste decision: it is `ONLINE_TIMEOUT = 10 * 60 * 1000` (`device.service.ts:46`), so the
board and the server never disagree about what "offline" means.

**Grey is reserved.** Grey means "I do not know". It is used for nothing else on the board — not for
disabled, not for secondary text inside a tile's value area. That single rule is what makes staleness
readable at arm's length without anybody reading a word.

**The status strip** at the top of the grid is the device-level truth and the only place a whole-board
statement is made:

| Situation | German | English |
| --- | --- | --- |
| all fresh | `● Live · vor 4 Sek` | `● Live · 4 s ago` |
| some stale | `● Letzte Messung vor 7 Min` | `● Last reading 7 min ago` |
| offline | `⊘ Offline seit 2 Std 14 Min — angezeigte Werte sind alt` | `⊘ Offline for 2 h 14 min — values shown are old` |
| `lastseen` fresh but no measures | `⚠ Verbunden, aber keine Messwerte` | `⚠ Connected, but no readings` |
| maintenance mode | `🔧 Wartungsmodus – noch 42 Min` | `🔧 Maintenance mode – 42 min left` |

The last one is a genuine diagnostic nobody surfaces today: `Device.lastseen` is stamped on any MQTT
traffic (`device.service.ts:236`) while the sensor may have failed. Today that shows a live-looking board
with `—` in every tile and no explanation.

When the board is offline, **the container dims once** (`.board--offline { filter: saturate(0.15) }` on the
grid, not on each tile) so it reads as one event, not twelve broken widgets. Today an offline device gets a
full-bleed click-to-dismiss overlay (`overview.component.html:1-8`) that hides the data entirely — worse in
both directions: it obscures the last known state *and* it can be dismissed, after which everything looks
fine again.

### 3.4 The tile catalogue and its evidence rules

**Nobody ever picks tiles from a list.** Each tile is a rule with a `showWhen(evidence)` predicate. Evidence
sources, in order of trust: `device.hardwareInfo` (firmware-reported), Influx "has this measure produced a
point in the last 48 h", `parseSocketRoles(hardwareInfo.sockets)`, cloud-side state (plants exist? regime
selected? alarms defined?), `device_type`.

| id | Tile | Shows when | Size | Detail route |
| --- | --- | --- | --- | --- |
| `status` | Status strip | always | full | — |
| `temperature` | Temperatur | `temperature` measure seen | 1x1 | `t/climate` |
| `humidity` | Luftfeuchte | `humidity` measure seen | 1x1 | `t/climate` |
| `vpd` | VPD | temp **and** humidity seen | 1x1 | `t/climate` |
| `co2` | CO₂ | `hardwareInfo.co2 !== 'off'` **and** a `co2` point seen | 1x1 | `t/co2` |
| `light` | Licht | `out_light` seen **or** a `light`/`secondary_light` socket | 1x1 | `t/light` |
| `machine` | Technik | ≥1 socket role paired **or** device_type has built-in actuators | 1x1 | `t/machine` |
| `camera` | Kamera | `hardwareInfo.webcam_did` set **or** an `Image` in 24 h | 2x2 | `t/camera` |
| `feed` | Gießen & Düngen | a `FeedRegime` exists **or** ≥1 `water`/`feed` entry ever | 2x1 | `t/feed` |
| `plants` | Pflanzen | ≥1 `Plant` **or** ≥1 lifecycle entry ever | 1x1 | `t/plants` |
| `alerts` | Alarme | ≥1 `Alarm` defined **or** ≥1 fired in 30 d | 1x1 | `t/alerts` |
| `leaf_temp` | Blatttemperatur | `hardwareInfo.leaf_temp === 'on'` | 1x1 | `t/climate` |
| `ppfd` | PPFD / DLI | `hardwareInfo.ppfd === 'on'` or `lux` seen | 1x1 | `t/light` |
| `rpm` | Lüfter | `rpm` seen | 1x1 | `t/machine` |
| `plug` | Steckdose | `device_type === 'plug'` | 1x1 | `t/machine` |
| `generic:<m>` | *(measure name)* | any measure with points but no rule above | 1x1 | `charts?measures=<m>` |

The last row matters more than it looks: **a device that reports something the catalogue does not know
about is never invisible.** It gets a value, a unit if the i18n bundle knows one, a sparkline, and no goal
bar. This is the failure mode the current app gets exactly backwards, where the measure catalogue is a
literal array inside a 1205-line component.

**Rank tiers** decide default order; user order is respected *within* a tier:

```
0 Alert (only while an alarm is active)   1 Action due (feed due today)
2 Live climate   3 Light   4 Machine   5 Media   6 Record (plants, journal)
```

An alert tile jumping to slot 1 and returning to its place when resolved is a documented, explainable
exception. **There is no learning algorithm and the layout never moves on its own otherwise** — a board
that rearranges itself based on what you look at is the single fastest way to make a user distrust it.

### 3.5 Tile configuration without a configuration chore

Three mechanisms and one prohibition.

1. **Auto-provisioning.** A tile appears the moment its evidence appears. Pair a heater socket in the
   wizard and the Technik tile grows a heater row within one status message. Buy the CO₂ upgrade, plug it
   in, and the CO₂ tile is there next time you open the app, announced by one dismissible toast:
   `Neue Kachel: CO₂` / `New tile: CO₂`. **This is the only "onboarding" the tile system has.**
2. **Two gestures, both borrowed from the phone home screen.** Long-press any tile (400 ms) → the grid
   enters arrange mode (tiles get a subtle scale-down and an `✕` badge; a `Fertig` / `Done` bar appears).
   Drag to reorder. Tap `✕` to hide. That is the complete interaction vocabulary.
3. **Hidden tiles go to a drawer, never to oblivion.** A collapsed `Ausgeblendet (2)` / `Hidden (2)`
   section at the bottom of the grid lists them as small chips; tapping one restores it. There is no
   separate "add tile" catalogue in the primary path, because auto-provisioning means "add" is only ever
   "un-hide".

**The prohibition: no tile has settings.** Expanding a tile navigates; it never opens a config sheet. A
tile's configuration *is* what it displays. Targets live in Settings, plants live in the journal, alarm
thresholds live in the alarm editor. The moment a tile grows a gear icon, this concept has failed.

Persistence:

```ts
TileLayout {
  layout_id: string; device_id: string; user_id: string;
  order: string[];        // tile ids, partial — unknown ids fall back to tier order
  hidden: string[];
  updatedAt: number;
}
```

Absent document → deterministic default from the tier table. A user who never touches anything always gets
a sane, evolving board; a user who arranges once gets it on every browser they log in from. `order` being
*partial* is deliberate: a tile invented in a later release slots into its tier rather than landing at the
end of a stale list.

## 4. The chart overhaul

The board's tile details and the workbench (`/device/:id/charts`) share one component, `<tc-panel-chart>`,
built on **Apache ECharts 6, tree-shaken, with a hand-rolled ~50-line Angular directive** — per the owner's
decision (`00-OWNER-DECISIONS.md` §2). Highcharts, `chart.js`, `ng2-charts` and `chartjs-adapter-luxon` are
deleted. Honest accounting: tree-shaken ECharts is **195.6 KB gz vs 132.7 KB gz** for Highstock; deleting
Chart.js repays 68.8 KB. The migration is justified by licence and by `markArea`/`markLine`/`grid[]`/
`sampling`/`darkMode:'auto'`, not by bundle size.

### 4.1 Panels and axes

Stacked small multiples on a shared x-axis with one linked crosshair (`grid[]` + `axisPointer.link`).
**At most two series per panel, and only when physically coupled.** No dual-scaled axes anywhere — Few's
paper is unqualified on this and Terp currently runs fifteen hidden scales as translucent areas.

**Axis labels are never hidden.** Below 320 px the axis is reduced to three ticks and the unit moves into
the panel title. Today they are suppressed entirely below 320 px, which produces an axis-less chart —
not a chart.

### 4.2 Goal-vs-actual on the chart

Three band sources, **one at a time, always labelled**, in this priority:

1. **Alarm thresholds** (`Alarm.upperThreshold` / `lowerThreshold` for that `sensorType`) — hard dotted
   edges. These are the user's own declared limits and they currently reach nothing.
2. **Setpoint ± tolerance** — soft `markArea`, and a **grey dashed stepped `markLine`** for the setpoint
   itself, stepping at `daynight.day` / `daynight.night` between `day.temperature` and `night.temperature`.
3. **Stage VPD sweet spot** — advisory, from `GROW_STAGE_PRESETS[].vpdRange`, and it **changes along the
   x-axis** as `Plant.stageHistory` moves through stages. This is the one chart in §7.2 nobody verifiably
   ships, and it costs a `markArea` with per-segment coordinates.

A **signed deviation fill** sits between actual and setpoint — never a fill to the axis. Today every series
is `type:'area', fillOpacity:0.1, threshold:null`, which encodes nothing and almost certainly fails WCAG
2.2 SC 1.4.11.

**Setpoints are always grey dashed, never a hue.** Hue is the measurement's identity; the target is a
different *kind* of thing and gets a different *channel*.

### 4.3 Day/night, outputs, annotations, camera

- **Day/night shading** derived from measured `out_light > 0`, falling back to the `daynight` schedule when
  the output series is missing, resolved **in an explicit timezone** (Grafana's time-regions model — a
  12/12 flip near a DST boundary otherwise drifts an hour). `lights.sunrise`/`sunset` render as gradient
  edges. **Where the schedule says day and `out_light` says off, the band is hatched** — a failed
  contactor becomes a visible diagnostic instead of nothing at all.
- **Outputs move to a state-timeline lane**, 28 px, below the value panels: region length = duration, null
  = gap, `out_light` shown as an intensity ramp rather than binary. They stop fighting for a value axis.
- **Annotations go to a rail under the x-axis**, max two rows: row 1 your entries (water, feed, training,
  photo, note), row 2 device events (boot, alarm, config change, socket lost). Pixel-proximity clustering
  in 10 px bins with count badges, severity ranking, category filter chips built on the existing
  `collectLogCategories` / `matchesLogCategory`. **Stage changes are full-height dashed verticals**, not
  rail marks — they are the grow's structure, not an event. Today events are height-1 columns readable only
  by hovering, which does nothing on touch, on a mobile-first product.
- **The film strip is an axis.** Thumbnails positioned by their own timestamp on the shared x-scale, so
  uneven capture reads honestly as gaps. Delivered as **one sprite + JSON index per window** (a new
  `GET /image/strip/:device_id?from&to` returning a 256×160 tile sheet), not N image requests.
  `Image.timestampEnd` already marks mp4 timelapses as spanning a range — those render as a bracket, not a
  point. Scrubbing the chart moves the strip cursor and vice versa; they share one x position.

### 4.4 Mobile touch

| Gesture | Result |
| --- | --- |
| one finger vertical | page scrolls (chart does not capture it) |
| two fingers | pan / zoom (`dataZoom: {type:'inside'}`) |
| tap / drag | crosshair; the **pinned scrub header** above the chart updates — one compact row per panel |
| long-press + drag | range selection |
| range chips | ≥44 px targets, the primary control |

**The floating tooltip is deleted.** There is no hover on touch and a fingertip occludes a tooltip.

**Interval is derived from the range**, which closes the `3y × 5s ≈ 18.9 M windows` self-DoS that is one
dropdown away today (`limit(n:50000)` is piped after `yield()` and does not bound anything). A techie
`Auflösung` override exists and is clamped so any request produces ≤ 5,000 windows.
`sampling: 'minmax'` for the plot — **LTTB smooths away the exact oscillation a grower is looking for in a
bang-bang controller** — LTTB only for the navigator. A `{mean,min,max}` combined response replaces three
round trips.

### 4.5 Colour and accessibility

Okabe-Ito, verbatim hex: temperature `#D55E00`, leaf temp `#E69F00`, humidity `#0072B2`, VPD `#009E73`,
CO₂ `#CC79A7`, lux/PPFD `#F0E442` (used for the day wash at 10 % rather than as a line on light
backgrounds), grey `#999999` for every setpoint and every unknown. Today `#e05a4e` sits next to `#b0743c`
(the classic deuteranopia collision), `Lights` and `Day` share `#c8a23c`, and `out_fan` and

library matches Highcharts' accessibility module, and Terp does not load that module today anyway.

Series names become translation keys. A German user currently gets `Temperature`, `Humidity` and
`Critical logs` in English inside a translated page.

## 5. The multi-plant diary

### 5.1 Why a new collection and not another `DeviceLog` category

Today a "diary entry" is a `DeviceLog` row whose `categories[0] === 'diary'`, in the same collection as
boot messages and MQTT errors, with a `Schema.Types.Mixed` `data` bag of ten flat optionals and zero
server-side validation. A grow's identity is the free-text `lifecycleName` on one row, and cycle boundaries
are **inferred in the browser** by `convertEventsToGrowCycles`, which starts a new cycle whenever the stage
ordinal rolls back **or the trimmed name string differs**. Renaming a plant forks its history. A re-veg
fabricates a plant. A per-plant diary cannot be layered onto this.

### 5.2 New entities

```ts
Plant {
  plant_id: string;                 // nanoid, stable forever
  device_id: string;                // one tent at a time
  owner_id: string;
  label: string;                    // "Blue Dream #1" — RENAMEABLE, renaming touches one field
  strain?: string;                  // free text (SeedFinder's API is dead since 2024-07-01)
  source?: 'seed' | 'clone' | 'unknown';
  motherPlantId?: string;
  startedAt: number;                // day 1
  stage: DiaryLifecycleStage | 'harvest';       // 'harvest' is NEW — today it is not even a stage
  stageHistory: { stage: string; at: number; note?: string }[];   // append-only
  medium?: string;                  // 'lightmix' | 'allmix' | 'coco' | 'soil' | free text
  potSizeL?: number;
  position?: string;                // "hinten links" — free text, never coordinates
  colorIndex?: number;              // stable chip colour
  archivedAt?: number;
}

JournalEntry {
  entry_id: string; device_id: string; owner_id: string;
  actor_id?: string;                // WRITTEN FROM DAY ONE even though nothing reads it until v1.1
  type: 'water'|'feed'|'measure'|'note'|'training'|'pest'|'transplant'
      | 'photo'|'stage'|'harvest'|'co2-refill'|'work';
  at: number;                       // when it happened — editable
  createdAt: number;                // when it was recorded — never editable
  plantIds: string[];               // [] means "the whole tent" and is the DEFAULT
  text?: string;
  images: string[];
  water?:   { volumeL: number; runoff?: boolean; runoffEc?: number; runoffPh?: number };
  feed?:    { regimeId?: string; stepIndex?: number; batchVolumeL: number;
              products: { name: string; mlPerL?: number; gPerL?: number; totalMl?: number }[];
              ecTarget?: number; ecMeasured?: number; ph?: number;
              ecBasis?: 'absolute' | 'delta_over_source'; deviatedFromStep?: boolean };
  measure?: { ph?: number; ec?: number; ppfd?: number; distanceCm?: number;
              heightCm?: number; outsideTemp?: number; substrateMoisture?: number };
  training?:{ kind: 'topping'|'lst'|'defoliation'|'supercrop'|'scrog'|'other' };
  harvest?: { wetG?: number; dryG?: number };   // fields HIDDEN unless privacy mode allows (§8)
  source: 'user' | 'device' | 'schedule';
  correctsEntryId?: string;         // club mode: corrections instead of edits
}
```

`DeviceLog` stays exactly as it is, for device events. Two collections, two purposes, one merged timeline
in the UI. The current single-collection design is why "Clear logs" deletes nothing from the diary
(`deleted` is a *visibility* flag and the diary always requests hidden rows) — that bug dies with the split.

**Server-side pagination is mandatory** on the journal (`?before=<ts>&limit=50`). Today
`getDeviceLogs` has no `.limit()`, no cursor and no count, and the Entries report fetches the device's
entire history on every open.

### 5.3 How plants get created

**Zero plants is a permanent, fully-supported state.** Every entry defaults to `plantIds: []` = "the tent".

1. **Never.** A monitoring-only user never creates a plant and is never asked to. The Plants tile is not in
   their layout because its evidence rule never fires.
2. **One field.** The first plant-shaped affordance a user touches — `+ Pflanze` in the Plants tile, or
   `Welche Pflanze?` when attaching a photo — asks for **a name and nothing else.** `startedAt = now`,
   `stage` = whatever the device's stage preset says, `medium` = the feed regime's medium.
3. **Three at once.** A `3 Pflanzen anlegen` / `Add 3 plants` quick action creates `Pflanze 1..3`, because
   the common case is n identical clones and typing three names is three chores.

### 5.4 Rename, re-veg, clone

| Case | Handling |
| --- | --- |
| **Rename** | `label` on a stable `plant_id`. One document write. History intact. This is the direct fix for `convertEventsToGrowCycles` forking on a string change. |
| **Re-veg** | Append `{stage:'vegetative', at:…}` to `stageHistory`. **No new plant.** The day counter reads `Tag 96 · Re-Veg Tag 12` because both the total day and the stage day are stored. |
| **Clone** | New `Plant` with `source:'clone'` and `motherPlantId`. Harvesting the mother does not touch the clone. |
| **Harvest** | `stage: 'harvest'` — a real stage, with a date. Weights are optional and privacy-gated (§8). "How did this grow do?" becomes answerable. |
| **Migration** | `convertEventsToGrowCycles` runs **once, server-side**, creating `Plant` documents from inferred cycles, stamped `Device.journalBackfilledAt`. Then the runtime algorithm is deleted. Per house style: optional fields, read-time normaliser, idempotent boot-time backfill — no migration tooling exists. |

### 5.5 Not taxing the user who does not care

- With zero plants, **the plant chip row in the capture sheet is not rendered at all.** Not disabled, not
  greyed — absent. There is nothing to skip.
- The Plants tile does not exist until a plant or a lifecycle entry does.
- No entry type ever requires a plant. `plantIds: []` is valid for every one of them.
- Plant filters appear in the journal only when `plantCount ≥ 2`.

## 6. Watering & fertilising

There is no irrigation or dosing hardware. This is capture-and-recall, and the entire design goal is
**capture speed** on one side and **reconstruction** on the other — the owner's two faces, the stoner who
wants it to think for them and the club that wants detailed logging.

### 6.1 Everyday capture — counted in taps

The Feed tile is the capture surface. It has two resting states:

```
 NOTHING DUE                          DUE
 ┌────────────────────────────┐      ┌────────────────────────────┐
 │ GIESSEN & DÜNGEN           │      │ GIESSEN & DÜNGEN    heute  │
 │ Zuletzt gegossen vor 2 Tg. │      │ Schritt 5 · Biobizz All-Mix│
 │ 💧 Wasser  🧪 Dünger   [+] │      │ [ Düngen – Schritt 5 ] [+] │
 └────────────────────────────┘      └────────────────────────────┘
```

**Plain water: 2 taps.**
1. Tap `💧 Wasser`. A sheet slides up **already filled**: type = Gießen, `at` = now, `volumeL` = last used,
   `plantIds` = all.
2. Tap `Speichern`.

**Feed following the schedule: 3 taps.**
1. Tap `Düngen – Schritt 5`. **The button is the step** — the schedule is never a table you navigate.
2. The sheet opens prefilled from the regime's step 5: product rows with ml/L, `batchVolumeL` from last
   time, computed totals (`2,0 L × 2 ml/L = 4 ml`), EC target with its basis, mixing order as an ordered
   checklist (silica → base A → base B → Cal-Mag → additives → **pH last**).
3. Tap `Gemacht`.

**Ad-hoc feed with no regime: 4 taps** (type → product from your last-used list → volume already filled →
save).

Every prefilled number is an existing `value-edit-row`: tap the row, it expands into `[−] ion-range [+]`,
fully ARIA-annotated, step-aware. **Deviating is the normal case, not the error case.** Editing a value
stores what actually happened and sets `deviatedFromStep: true`; it never "breaks" the schedule.

The stoner's version of this feature is: a tile that says `heute` and a button that says what to do.
They never see ml/L unless they tap `Details ▾` inside the sheet.

### 6.2 The schedule

```ts
FeedRegime {
  regime_id: string; device_id: string; owner_id: string;
  catalogId?: string;               // → FeedCatalogEntry, or null for a hand-made regime
  label: string;                    // "Biobizz All-Mix" — how the grower says it out loud
  medium: string;                   // the substrate IS part of the scheme, per the owner
  cadenceDays?: number;             // "every 3 days"
  waterEveryNFeeds?: number;        // plain water between feeds
  anchor: 'plantDay' | 'flipDate' | 'feedCount';
  startedAt: number;
  stepIndex: number;                // advances BY FEED EVENT, never by wall clock
  autoflowerMultiplier?: number;    // ×0.25–0.5, no 12/12 flip — no brand chart has an auto column
}
```

**The scheme is selected once and then prefills the log entry.** It is not a planner, not a calculator app.
The picker is a list of plain-text labels — `Biobizz Light-Mix`, `Biobizz All-Mix`, `Floragard Light`,
`Green House Feeding`, `BioTabs`, plus ownerless entries (Lucas Formula, Jack's 321, generic per-medium EC
ladders) — each with `Zuletzt geprüft: 14.03.2026` / `Last verified 14 Mar 2026` and a link to the brand's
own chart. Modelling substrate and feed line as **one selectable pair** is not a compromise, it is
horticulturally correct: All-Mix is heavily pre-fertilised, so a scheme that cannot express "don't feed yet"
is not modelling the domain.

`stepIndex` advances on a **saved feed event**. Skip a week and the schedule waits. Feed twice in a day and
one chip asks `Schritt 5 wiederholen` / `Schritt 6` — defaulting to repeat. Growers feed Tue/Fri and slip;
wall-clock advance is the failure that makes such features untrustworthy.

The one thing only a *controller* can do: **auto-detect the 18/6 → 12/12 flip from `out_light` history** and
offer `Auf Blüte-Woche 1 setzen?` / `Move to bloom week 1?`. No bottle-brand calculator can do this, because
none of them can see the tent.

### 6.3 What gets drawn on the chart

This is where "improve the visualisation of all things water and fertiliser related" is actually delivered.

- Water and feed events sit on **annotation rail row 1** as droplet / bottle glyphs, clustered.
- **EC and pH become real chart panels** — sourced from `JournalEntry.feed.ecMeasured` and
  `measure.ph` in MongoDB, not Influx — plotted as points joined by a step line.
- **The regime's `ecTarget` per step becomes a stepped band on the EC panel.** Target-vs-actual for a
  quantity the hardware cannot even measure, using the same grey-dashed-setpoint grammar as temperature.
  A grower sees their EC drifting under the schedule's band across three weeks. Nothing on the market draws
  this.
- Optional: cumulative water volume per week as a small bar panel; runoff EC vs input EC with a
  `> 20 % divergence` marker.

**EC is stored as EC, canonically.** A bare "ppm" number is never rendered: a per-user `ppmScale:
500 | 640 | 700` converts on display, because at EC 1.8 a Bluelab reads 1260 and a Hanna reads 900 for the
same liquid, and that is repeatedly cited as the #1 cause of accidental over/under-feeding.
`ecBasis: 'delta_over_source'` exists because CANNA publishes **EC+**, not EC — a UI that alarms against the
raw chart value is actively wrong.

### 6.4 Brand posture (invisible to the design)

```ts
FeedCatalogEntry {
  catalog_id: string; brandLabel: string; mediumLabel: string;
  steps: { phase: string; weekFrom?: number; weekTo?: number;
           products: { name: string; mlPerL?: number | [number, number]; note?: string }[];
           ecTarget?: [number, number]; ecBasis: 'absolute' | 'delta_over_source';
           phTarget?: [number, number] }[];
  source_url: string; retrieved_at: number; chart_version?: string;
  kind: 'official_pdf' | 'official_calculator' | 'ownerless';
}
```

- **MongoDB content collection, never baked into the webapp bundle**, so any brand is removable in one DB
  update.
- **Word marks as plain text only.** No logos, no brand colours, no bottle imagery, and never a brand name
  inside a Terp Control feature name. The feature is `Düngeplan` / `Feed schedule` — never "CANNA mode".
- Never copy brand prose. Every description is paraphrased.
- Seeded **only** from the brand's own chart or calculator, never from retailer or blog transcriptions —
  two sites disagree by ~3× on CANNA Terra Vega dosing, and wrong numbers here burn real crops.
- `Zuletzt geprüft` is a user-facing trust feature *and* the legal posture at the same time.
- Every computed dose carries a `Werte prüfen` / `Verify values` affordance. The app instructs people to
  apply chemicals to a crop, and with nine unit systems in circulation a conversion bug has physical
  consequences.
- Flush is presented as **"dein Plan sieht das vor" / "your schedule calls for this"**, never as necessary.

## 7. Camera & timelapse

- **The camera tile is subject to the same freshness law as every other tile.** A still from four hours ago
  is not shown as if it were now: `vor 4 Std` in the chip, the image at 55 % opacity, `Zuletzt aufgenommen`.
  This is the single most common way a camera UI lies.
- **Images join the timeline by their own timestamp.** `Image.timestamp` already exists. The film strip
  (§4.3) positions thumbnails on the chart's x-scale so uneven capture reads as gaps, and one cursor is
  shared between chart and strip. Scrub the chart at 03:40 and you see 03:40.
- **Images join plants by two new optional fields:** `Image.plantIds?: string[]` and
  `Image.entryId?: string`. A webcam still and a photo you attached to a feed entry become the same entity,
  which is what makes "show me this plant's photos" one query. Read-time normalised; existing rows have
  neither and render as tent-wide stills.
- **Images join stages through the plant, not through themselves.** The chart draws full-height dashed
  verticals from `Plant.stageHistory`; the camera detail offers `Zeitraffer: Blüte` / `Timelapse: flower`,
  a server render bounded by that stage's date range. That is a parameter on the existing hourly render
  job, cloud only. **v1 ships strip scrubbing and the existing 1d/1w/1m timelapses; stage-bounded renders
  are v1.1** if the render job proves cheap enough.
- Housekeeping the redesign must not inherit: `DELETE /image/:image_id` exists and is never called;
  retention filters `format:'jpeg'` only, so `user/jpeg` diary photos accumulate forever; the unique index
  `{device_id, format, timestamp, duration}` collides on two uploads in the same millisecond; and
  `express-fileupload` is mounted with no size limit against a 16 MB BSON ceiling. All four are in the v1
  journal work, because the journal is what will start producing photos in volume.
- Privacy: stills stay behind `imageToken`. A public diary link (v1.1) includes photos only per-photo,
  explicitly ticked.

## 8. Multi-user & clubs

### 8.1 Roles

```ts
DeviceMember {
  device_id: string; user_id: string;
  role: 'owner' | 'grower' | 'viewer';
  displayName: string;            // free text — "K." is a valid name
  addedAt: number; addedBy: string;
}
```

| Role | Board | Settings | Journal | Members |
| --- | --- | --- | --- | --- |
| `owner` | full | full | full | manage, transfer, delete device |
| `grower` | full | change setpoints, ack alerts | write own + read all | — |
| `viewer` | read | — | read | — |

`viewer` is the answer to "share the password", which is what every competitor tells two people with one
tent to do. Joining is by **invite code**, not by email lookup — an account-lookup-by-email endpoint does
not exist today and designing one against enumeration abuse is work this concept does not need. An invite
code is also the club-native idiom.

### 8.2 Attribution

`JournalEntry.actor_id` and a new optional `DeviceLog.actor_id` are **written from day one of v1**, even
though nothing renders them until v1.1. Losing the data is unrecoverable; not showing it is a UI change.

- **A solo grower never sees a person anywhere.** No "Owner: you" badge, no avatars, no initials. Attribution
  UI appears only when `memberCount ≥ 2`, as a small initials chip on journal rows and on the tile that
  something was done from.
- The board itself shows nothing about people, ever. It shows the tent.

### 8.3 Privacy posture

Two modes, per device, and **the privacy-maximal one is the default**:

**Privat (default).** Attribution stored, displayed only inside the device. No real name required anywhere.
Harvest weight fields hidden and not prompted. Telemetry retention default **12 months** — today the Influx
bucket has no retention and no downsample task, so raw 5-second samples are kept forever, which is both a
cost curve and, given § 28 Abs. 2 KCanG's power to seize digital data with no prior judicial approval, an
evidentiary liability. One-tap `Alles löschen` for the owner. A light schedule flipping 18/6 → 12/12 is a
legible harvest calendar.

**Vereinsmodus (explicit opt-in).** Enables the participation log (`JournalEntry.type: 'work'`, optional
`minutes`) serving § 17 Abs. 2's *eigenhändig* requirement — the one legally-motivated multi-user feature a
grow controller can credibly own. Makes entries append-only: an edit writes a **correcting entry**
(`correctsEntryId`) instead of mutating. Extends retention. Enables date-range export with a
`NONE | PSEUDONYMIZED | ANONYMIZED` selector **defaulting to pseudonymised**.

**Permanently refused**, regardless of mode: per-member dispensing or consumption records, grams handed
over, THC content, member DOB or address, membership numbers, any § 26 filing, location of any kind,
analytics or ad SDKs, and any "KCanG-konform" badge or compliance warranty. Winning the compliance race
would mean owning 23 differing authority export formats, 5-year retention, an Art. 28 AVV with every club
and liability for wrong exports, against ~20 incumbents at €0.50–1.00 per member per month. **Do not.**
What Terp Control has that they do not is a device-attested environmental record that requires storing zero
personal data — that is the thing to be good at, and it is the thing club software would consume.

EU hosting is stated plainly on the account page, because German advisers publish "servers outside Europe"
as the red flag when clubs choose software.

### 8.4 Honest cost

`DeviceMember` + rewriting `auth.middleware.ts:172` and `:207` from `find({owner_id, device_id})` to a
membership lookup + loosening ~10 owner-scoped service queries + the invite flow. **This is not a flag and
it is not in v1.** See §13 and §15.9.

## 9. Old devices — type 7 (fan, light, plug, fridge)

The board is **device-type-agnostic**, because tiles are evidence-driven. One `TileBoardComponent` renders
every device type; only which rules fire differs. The per-type overview components
(`fan-overview`, `light-overview`, `plug-overview`, `fridge-overview`) are deleted. Their **settings pages
are not touched in v1** — that is the honest scope line: board rewritten, settings kept.

**`device_type: 'fridge'`** — built-in actuators, `deviceControlCapability` returns `'full'` (unchanged).
Board: Temperatur, Luftfeuchte, VPD, Technik (Heizung / Entfeuchter / Licht), Kamera if paired, Alarme,
Pflanzen/Journal if used. Goal bars everywhere, because a fridge really does control. It **keeps** the label
`Terp Control Fridge Grow` — it is a fridge. The controller stops borrowing it.

**`device_type: 'fan'`** — reports `rpm` and `out_fan` / `out_fan-internal` / `out_fan-external`. Board:
Lüfter (RPM value, goal bar against the configured speed), Klima only if it has a sensor, Alarme, Journal.
No VPD tile without humidity. No Pflanzen tile unless they make one — and they can, which is the point: a
fan owner who wants a diary gets the same journal as everyone else.

**`device_type: 'light'`** — Board: Licht (on/off, %, `An bis 22:00`), Photoperiode (a 24 h ring showing the
measured on-window against the configured one — the failed-contactor check as a tile), PPFD/DLI if `lux`
exists, Alarme, Journal.

**`device_type: 'plug'`** — Board: Steckdose (on/off + `Heute 7 Std 20 Min an`), a Temperatur tile if it
reports one with its over/under-temperature limits as the goal-bar ends, Journal. The three broken
checkbox i18n keys (`settings.limits.overtemperature.enabled`, `.undertemperature.enabled`, `.time.enabled`)
that render raw today are fixed in the same commit, because a plug owner sees them.

**`device_type: 'dryer'`** — `AGENTS.md` says ignore it. It falls through to the generic board with
whatever measures it reports. Nothing is built for it and nothing breaks.

What type 7 concretely gains: honest freshness (they have the same "is this real?" problem and no fix
today), the goal bar, a chart that is not fifteen hidden axes, a journal, real alerts, and a back button.
What they concretely lose: nothing — no route they can reach today disappears. What they will notice: their
device stops looking like a stripped-down version of a bigger product and starts looking like a small one.

## 10. Onboarding

**First run, empty account** — keep what exists. `.tc-hero` with the three steps and the claim-code input
(`list.page.html:26-73`) works and is already translated.

**After claiming, the board opens immediately and builds itself in front of you.** Within one status
message (~5 s) Temperatur, Luftfeuchte and VPD are there with live chips. That moment — numbers appearing
on their own — is the onboarding.

Above the grid sits a **Einrichten strip** with at most three items, each one tap, each dismissible:

1. **`Wie heißt dein Zelt?` / `What's this tent called?`** — one text field. Skippable; default `Mein Zelt`.
2. **`Was ist angeschlossen?` / `What's connected?`** — the existing wizard `connections` step, which is
   **hardware-detected**: the user confirms roles the device already reported in `hardwareInfo.sockets`,
   they do not invent them. If the CSV is `'none'` this collapses to one line:
   `Nichts angeschlossen — nur Messung. OK.` If the key is **absent** (old firmware), this is the *only*
   time the app asks, because that is the one genuinely ambiguous case — and it replaces today's
   fail-open-to-`'full'` behaviour that shows a heater-only tent a dehumidifier alarm preset.
3. **`Wo bist du im Grow?` / `Where are you in the grow?`** — the existing `stage-preset-picker`: five
   cards, each showing its own numbers (`24/21 °C · 70 % · 18 h`, `VPD 0.4–0.8 kPa`). One tap writes
   day/night temperature, humidity, light hours, limit and the VPD band.

**Three taps to a configured controller**, and every one of them is a choice among visible options rather
than a number to type. The strip disappears when done and is re-openable from the header overflow
(`Einrichtung erneut` / `Run setup again`) — fixing the "wizard is barely discoverable" gap.

**Capability is never asked.** It is read from `hardwareInfo` and from Influx evidence. There is no
"are you a beginner or an expert?" question — the Simple/Expert segment stays in Settings where it already
lives and is already documented in German (`docs/einfach-modus.md`). **The board has no mode.**

Free win: the connections step gets the four relevant already-shot videos from
`webapp/src/assets/wizard/` (`sockettype_*.mp4`, `connect.mp4`). ~30 MB of those sit unreferenced in every
production build today. Reference four, delete the other nineteen.

## 11. Per-user-type walkthrough — first week

**Type 1 — monitoring only.** Unboxes, claims, board opens. Three tiles: Temperatur, Luftfeuchte, VPD.
Names the tent, taps "Nichts angeschlossen — nur Messung", skips the stage picker. **He sees no goal bars
and no targets** — the tiles carry a small `Nur Messung` chip instead, because nothing can act. Day 2 the
wifi drops overnight; he opens the app at breakfast to a grey board saying
`Offline seit 6 Std — angezeigte Werte sind alt`, which is the first time any grow app has told him the
truth. Day 4 he sets one alarm from the Alerts tile. Day 6 he taps Temperatur and gets a week of panels
with a min/max envelope and a coverage figure. He has configured nothing and hidden nothing.

**Type 2 — the same, with a camera.** Identical first day, plus the Kamera tile appears on its own the
moment `hardwareInfo.webcam_did` arrives (`Neue Kachel: Kamera`). He long-presses and drags it to the top,
because for him it *is* the product. Day 3 he opens the tile detail, scrubs the film strip, and watches the
last 24 h. Day 5 he opens the chart from the Klima tile and finds the strip **under the panels on the same
x-axis** — he scrubs to 04:00 and sees the picture and the temperature at 04:00 together. That correlation
is what he bought the camera for, and no competitor draws it. Day 7 he plays the 1-week mp4.

**Type 3 — controls CO₂ only.** Pairs a CO₂ socket. Board grows a CO₂ tile with a goal bar
(`Ziel 1000 ppm`) and a Technik tile with one row: `☁ CO₂`. **Temperature and humidity keep their tiles
but get no goal bar** — nothing can move them, so nothing pretends. Today the app would show him a humidity
target row, a humidity-deviation warning in the grow assistant and a "dehumidifier running non-stop" alarm
preset for hardware he does not own. Day 3 he logs a bottle refill from the CO₂ tile detail; day 6 the tile
estimates `noch ~11 Tage` from the refill history and the valve duty cycle.

**Type 4 — full tent.** Pairs heater, dehumidifier, light, CO₂. Board: five value tiles, a Technik tile
with four state rows, a goal bar on everything. Sets a stage preset in one tap. Day 2 he finds the chart's
Technik lane and sees the dehumidifier cycling every eleven minutes all night. Day 4 he creates three
plants and starts a Biobizz All-Mix regime. Day 5 he hits the design's honest wall: he wants a humidifier
and there is **no humidifier socket role in the firmware** — so no tile, and the Luftfeuchte goal bar's
lower half is drawn hollow with the caption `Nur Absenken möglich` / `Can only lower`. He is annoyed, but
he is not misled, and today he would be. Day 7 the time-in-range scorecard tells him he was in band 88 % of
day hours and 61 % of night hours, split, which is the number he actually wanted.

**Type 5 — closed-loop DIY, a fridge build.** Board is the fridge's. He immediately opens the chart, turns
on all measures, sets the resolution override, and reads the min/max envelope — which is the first thing in
this app that does not lie about a bang-bang controller. Day 2 he finds `Als Tabelle anzeigen` and copies
numbers out. Day 3 he wires a soil-moisture probe that Terp cannot ingest, so he logs it as a
`measure` journal entry and it appears on the annotation rail and as an EC/pH-style panel — a workaround,
and he knows it. **He is the type this concept serves least in v1** (see §15). What he gets on day one is a
board that never claims anything it cannot prove; what he wants is `/account/api`, and that is v1.1.

**Type 6 — a club with three people.** They claim the controller on one account. **At launch they share a
`viewer` board link with the other two** — which covers "let me look" and does not cover "who watered on
Tuesday". They log everything from the one owner account, and `actor_id` is stamped with that one user, so
when v1.1 lands the history is not lost, it is merely uniform. Their first week works; their central
question is deferred. This is the concept's biggest scope debt and §15.9 says so.

**Type 7 — an old plug owner.** Opens the app after the update and finds his plug's card replaced by a
board: Steckdose (`An · heute 7 Std 20 Min`), Temperatur with his over-temperature limit as the goal bar's
upper end, and Journal. The three checkboxes in his settings that used to render
`settings.limits.overtemperature.enabled` as literal text now render words. Nothing he could reach before
is gone. He hides the Journal tile and never thinks about it again — which took one long-press and one tap.

## 12. Stoner / normal / techie

**One board. Depth is behind a tap, never behind a mode switch.** The only persistent per-user difference
is tile order, which is exactly the widget metaphor and exactly what a phone home screen already teaches.

**Stoner.** The board *is* the product; they may never open a detail view. What carries them:

- Numbers at 34 px with a coloured dot on a bar. Green dot = fine. That is the entire literacy requirement.
- The status strip's `✓ 3/3` summary chip: everything with a goal is in band. One glance from the doorway.
- Grey means "don't trust this" — learned once, applies everywhere, never needs reading.
- The Feed tile tells them what to do today and takes two or three taps to do it. They never see ml/L.
- **Zero configuration is ever required.** If they never long-press anything, the board still evolves
  correctly as hardware appears.
- No mode to be in the wrong one of. No question they can answer wrong. No form.

**Normal.** Long-presses once, drags Kamera above Klima, hides Alarme. Opens tile details weekly. Reads the
time-in-range scorecard. Keeps three named plants and a feed regime. Uses the chart at 24 h / 7 d. Shares a
view-only board link with a friend.

**Techie.** Same board — and everywhere the stoner sees a number, they can get the machinery:

- The freshness chip's title attribute carries the exact sample timestamp and the server/browser clock skew.
- Every panel has `Als Tabelle anzeigen`, and the chart URL is a hand-editable view model
  (`panels=`, `band=`, `night=`, `lane=`, `strip=`, plus every legacy param).
- Resolution override, min/max envelope, raw-sample scorecard, day/night split.
- The workbench keeps the complete 15-measure catalogue behind `Alle Messwerte`.
- The Technik tile detail exposes socket roles, IPs (`socketIpFromCsv`), duty cycles and last-command
  failures.
- v1.1: `/account/api` with `x-api-key` scoped per device (copy Pulse Grow's shape) plus outbound webhooks
  on journal events — reusing `utils/webhookTemplate.ts`, which already does `{{placeholder}}`
  substitution in json and url modes. What is missing is only a non-alarm trigger, image attachment and a
  preset library. **Sharp edge to fix first: that code uses raw `http`/`https` `request()` with no timeout,
  no retry, no queue, no SSRF guard and no allowlist.**

The design's claim is narrow and testable: **a stoner and a techie look at the same first screen, and
neither is embarrassed by it.** The stoner is not shown a control panel; the techie is not shown a toy,
because every tile is a real measurement with its real age and its real target, and one tap deeper is a
real chart.

## 14. Non-goals

1. **No community feed.** ~200 App Store reviews across TrolMaster and VIVOSUN, both of which ship one, and
   not a single review praised it. It is permanent moderation cost. A shareable link is not a feed.
2. **No two-way grow-diary sync, and no GrowDiaries or Grow with Jane integration of any kind.** Every
   target is closed: no API, Cloudflare-hardened, or a ToS that forbids it outright. The feature will never
   be called "sync".
3. **No Instagram, Threads, TikTok or Reddit auto-posting. Ever.** A failed Discord post costs a webhook; a
   failed Instagram post costs *the user's account*, with Terp Control as the proximate cause.
4. **No "Powered by Terp Control" footer on user-generated posts.** § 6 KCanG bans cannabis advertising and
   sponsoring with fines to €30,000, read broadly. That string is the single riskiest one in the feature.
5. **No irrigation or dosing automation.** There is no hardware. Watering is capture-and-recall, and this
   concept will not imply otherwise with a "schedule" that cannot fire anything.
6. **No new socket roles and no firmware change in v1.**
7. **No compliance claims, no § 26 reporting, no per-member dispensing records, no KCanG badge.**
8. **No modes.** No beginner/advanced switch on the board, no "monitoring mode", no "club UI". The board
   differs by evidence, not by declaration.
9. **No tile settings.** A gear icon on a tile means this concept has failed.
10. **No adaptive or learned layout.** Tiles never rearrange themselves except the documented alert
    promotion.
11. **No commercial cultivation vocabulary** — rooms, zones, racks, benches, crop steering, cost-per-gram.
    The owner narrowed the market to hobbyists and clubs.
12. **No real names, no location, no analytics SDK, no non-EU hosting.**
13. **No user-editable tile sizes.** Order and visibility only.

## 15. Honest weaknesses

1. **A tile is a bad container for time, and growing is a process.** The board's unit of thought answers
   "now". Every genuinely differentiating insight in the dossier — time-in-range, goal-vs-actual across a
   week, the fused environment/machine/human timeline — lives *behind a tap*. I have bought glanceability
   by demoting the thing that actually makes this product unlike its competitors. A timeline-first concept
   would put the differentiator on the first screen. Mine puts a 60×22 px sparkline there.
2. **That sparkline is the weakest element in the design and it appears on every tile.** Unlabelled,
   axis-less, 22 px tall — decoration by §7.2's own standard. I keep it because nothing is worse and an axis
   does not fit. That is a compromise, not a solution, and a critic is right to call it one.
3. **Auto-provisioning is non-deterministic from the user's point of view.** A tile appearing on its own is
   delightful when it is right and alarming when it is wrong: "why is there a CO₂ tile? I don't have CO₂."
   The evidence sources are exactly the flaky things this codebase handles badly — `hardwareInfo` is a
   free-form `Record<string,string>` filled from MQTT log lines, and "has produced a point in 48 h" is a
   query that can flap. One wrong key produces a phantom tile, and a phantom tile is worse than a checkbox
   list would have been. A toast and a hidden drawer are mitigation, not a fix.
4. **The drag-and-drop grid is the most likely thing to be cut, and cutting it guts the concept's answer to
   the seven types.** 2D grid drag with long-press activation, autoscroll and drop animation on Angular 15
   / Ionic 6 means adding `@angular/cdk` (the repo has none) and fighting Ionic's own gesture layer. On
   mid-range Android it will be janky before it is good. If it goes, "users reorder and hide tiles — which
   is how one design serves seven user types without modes" degrades to "we picked a good default order",
   which is a much weaker claim.
5. **Freshness honesty makes the product look worse, and someone will ask to soften it.** Today every value
   looks live. Under this design a tent on flaky wifi shows a grey, uncoloured board a lot of the time —
   correct, and it will generate "the app is broken" tickets and demo badly in a shop. The 60-second `live`
   threshold in particular is aggressive. The moment it is relaxed to "look fine unless clearly dead", the
   feature is gone and only the cost remains.
6. **Two visual grammars for the same fact.** The board draws goal-vs-actual as a linear bar; the chart
   draws it as a dashed setpoint plus a band. A user must learn both. I retire the existing `valuedisplay`
   gauge from the board partly to avoid a *third* — which throws away a good, working 266-line SVG
   component with a value arc, limit arc, needle, 1 h average line and target line, and throws away the
   visual familiarity of every existing fridge customer.
7. **The board makes type 4's real problem legible instead of solving it.** The firmware has five socket
   roles and no humidifier; `out_dehumidifier` doubles as the cooler depending on workmode; there is no
   "cool *and* dehumidify". My design responds with an absent tile, a hollow half-bar and a
   `Nur Absenken möglich` caption. That is honest, and it is also resignation dressed as a feature. A grid
   of tiles cannot fix a five-role actuator model, and the marketing promise is *"ein Controller für dein
   ganzes Zelt"*.
8. **The design has no good answer for a second tent.** Tiles are device-scoped; a two-tent grower gets two
   boards and a device switcher. The obvious "all my tents on one wall" view is not designed here, and on a
   big screen it is arguably the more compelling thing to build than a right-hand rail.
9. **Type 6 is unserved at launch.** The club's central question — who did what — needs the auth rewrite,
   and I spent v1's budget on tiles, chart and journal. `actor_id` is written from day one so no history is
   lost, but nobody can read it until v1.1. A share link is not multi-user, and I should not pretend it is.
10. **The Feed tile nags, and hiding it is a gesture some users will never find.** The due reminder is the
    owner's explicit ask, but a reminder is an interruption. A monitoring-only user who logs one watering
    out of curiosity gets `Heute fällig` thereafter until they long-press and tap `✕`. The design's answer
    to unwanted nagging is a gesture, and gestures are discoverable only by the people who least need them.
11. **This concept changes everything at once against a red test suite.** Board, chart, journal, plants,
    feed and the latest-data endpoint all land for a fixed hardware date. The suite is 38 `it()` blocks, 24
    of which are `it('should create')`, `app.component.spec.ts` cannot pass, and CI never runs `ng test`.
    The only real safety net is `simulate-device.sh` — good, thorough, and entirely manual.
12. **The desktop rail is asserted, not designed.** I claim the big screen as an unexploited advantage and
    then spend one paragraph on it. The honest position is that I chose the cheap answer (board + rail)
    over the interesting one, and a critic should push on that.
