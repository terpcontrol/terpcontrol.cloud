# C04 — "Zweigang" (Two Gears)

*Radical progressive disclosure as the organising principle. Two apps, one login, one engine.*

---

## 1. Thesis

**Terp Control ships two complete applications behind one login — `Einfach` (3 screens, thumb-sized, verdicts instead of numbers) and `Profi` (everything) — and the user chooses which one they are in, explicitly, permanently, and reversibly, in one tap.**

The product's user population is genuinely bimodal and the owner said so in one sentence: *"All of these users might be very stupid (as they are often stoned) … But we also have very capable and techie users, that need to have the control they desire."* Every other resolution of that sentence is a compromise that fails both ends — an "Advanced" accordion still shows the stoner the door on every screen, and still charges the techie an extra tap forever. Zweigang refuses the compromise. It builds the simple app as a real app with its own routes, its own copy, its own information density and its own QA pass, and it builds the expert app as a real workbench, and it connects them with a switch that preserves context so crossing over costs nothing. The device, the data, the plants, the diary and the chart engine underneath are **one system**; only the cockpit differs. Critically, this also removes the worst question in onboarding — *"what kind of user are you?"* — because the answer is reversible and one tap away, so we never have to ask it.

## 2. Information architecture

### 2.1 The gear

```ts
// User (shared-types) — new optional field, read-time normalised, no migration needed
uiGear?: 'simple' | 'pro';
```

Server-side on `User` (so it survives a new phone — the techie's single most-cited annoyance), mirrored into `localStorage['tc-gear']` for instant first paint before `/auth/me` resolves.

**Default resolution order** (read-time normaliser, no backfill):
1. `user.uiGear` if set.
2. else `localStorage['app-settings-expert'] === 'true'` → `'pro'` — the existing settings-tab preference is *promoted* to a whole-app preference. A user who already told us they are an expert is believed.
3. else `'simple'`.

Gear is **per user, not per device**. See §15.7 for why, and why that is a real cost.

### 2.3 The switch, and why it is not a gimmick

Two placements, both permanent, neither modal:

- **Simple → Pro:** the last element on the `Jetzt` screen, below everything, a full-width outline button `Profi-Ansicht öffnen` / `Open Pro view`. Also in the account sheet.
- **Pro → Simple:** an `ion-segment` pinned at the top of the side menu: `[ Einfach | Profi ]` — the exact control the codebase already uses for simple/expert in fridge settings, promoted one level up.

**The switch preserves context.** This is the part that makes the two-shell design usable rather than a novelty. A static mapping table, one file, `util/gear-map.ts`:

| Simple location | ↔ | Pro location |
| --- | --- | --- |
| `/s/:id/now` | ↔ | `/pro/:id` |
| `/s/:id/diary` (+ plant filter, + date) | ↔ | `/pro/:id/diary?report=entries&plant=…&date=…` |
| `/s/:id/history?m=temperature&range=7d` | ↔ | `/pro/:id/charts?measures=temperature,humidity&timespan=7d` |
| plant sheet open on plant P | ↔ | `/pro/:id/plants/P` |
| due-feed card | ↔ | `/pro/:id/feeding` |

Reverse direction, for Pro screens with no simple counterpart (`/control`, `/alarms`, `/hardware`, `/access`): the segment's `Einfach` option is **disabled with a visible reason** — `Diese Seite gibt es nur in der Profi-Ansicht` / `This page only exists in the Pro view` — rather than silently dumping the user on `Jetzt`. Switching is never a trapdoor.

### 2.4 Navigation model, stated plainly

> One account → one gear → one device → three tabs (simple) or one menu + one device sub-nav (pro).
> No hamburger in simple. No tab bar in pro. The two navigation paradigms never appear on the same screen.

That last rule matters. Today's app has a menu, six outline buttons on the overview, and deep links, and no back button — three navigation systems and no primary one. Zweigang gives each gear exactly one.

**Design rules that are non-negotiable on this screen:**
- Exactly **one** ring. The ring is always the measure that the device can most directly *control* (temperature for a controller with a heater, RPM for a fan, dimming % for a light, socket state for a plug). Never two rings.
- Exactly **two** primary action buttons. Never three.
- No number appears without either a target beside it or the explicit absence of one.
- Every target shown is one the device can actually reach. Humidity target is **hidden** on a heater-only tent; humidity then renders as a plain reading with no verdict and no colour.
- No horizontal scrolling anywhere.

### 3.3 The four data states — drawn, not described

Dossier P0 #5 (*"nothing distinguishes live from stale from offline"* — the #1 complaint across all five consumer brands) is fixed once, in one shared component `<app-liveness [lastseen]>`, used by both gears and every device type.

Thresholds, from the existing server rule (offline = 10 min since last sample):

**1 — Live** (`age < 90 s`)
```
● Live · vor 4 Sek.        ← green dot #009E73
     24,3 °C     ✓ Passt   ← full opacity, solid ring
```

**2 — Stale** (`90 s ≤ age < 10 min`)
```
◐ Letzter Messwert vor 4 Min.     ← amber #E69F00
     24,3 °C                       ← 55 % opacity
     Ziel 25 °C · Tag              ← verdict text REMOVED
                                   ← ring stroke becomes dashed
```
The verdict disappears because a verdict on a four-minute-old number is a lie. The number stays because it is still the best we know.

**3 — Offline** (`age ≥ 10 min`)
```
○ Gerät offline seit 2 Std 14 Min.        ← grey #999999
              —                            ← the ring shows an em dash
     Zuletzt: 24,3 °C um 21:40             ← last known, demoted
              [ Was tun? ]                 ← 4-step checklist sheet
```
Outputs strip is replaced entirely by `Zustand unbekannt` / `State unknown`. **We never draw a heater as "off" when we cannot hear the device.** Settings remain editable and are queued — the existing behaviour documented in `einfach-modus.md`, kept.

**4 — Absent** (hardware not present)
The tile is **not rendered at all**. No `—`, no `-1`, no greyed placeholder for a CO₂ sensor the customer did not buy. Absence is invisible, not disabled.

This requires fixing dossier P0 #3: `deviceControlCapability()` collapses per-role truth into three buckets and **fails open** when `hardwareInfo.sockets` is absent. Zweigang replaces it with a per-role predicate `deviceRoles(device): Set<SocketRole>` reading the CSV directly, and **fails closed**: an absent key yields the empty set plus a one-time confirmation card (§10, screen 2). Fail-open is how a heater-only tent gets shown a dehumidifier target it can never reach.

## 4. The chart overhaul

Engine: **Apache ECharts 6, tree-shaken, hand-rolled ~50-line Angular directive** (owner decision, dossier §7.1). `chart.js` / `ng2-charts` / `chartjs-adapter-luxon` deleted from `charts.page.ts`, `charts.module.ts`, `diary.module.ts`, `diagnostics.*` in the same PR. Honest accounting: tree-shaken ECharts is **195.6 KB gz vs Highstock's 132.7 KB**; deleting Chart.js repays 68.8 KB. The migration is justified by **licence** and by `markArea`/`markLine`/`axisPointer.link`/`sampling`/`darkMode:'auto'`, **not** by bundle size, and it is not sold otherwise.

One engine, two chart *compositions*. This is the Zweigang Law (§13) applied to the hardest surface.

### 4.1 Simple gear — `/s/:id/history` — a verdict, not a workbench

```
┌──────────────────────────────────────────────┐

├──────────────────────────────────────────────┤

├──────────────────────────────────────────────┤

│  ░░░░░████████░░░░░░░░████████░░░░░  30      │  night = shaded markArea
│   ╭──╮                     ╭─╮       25 ┄┄┄  │  dashed stepped SETPOINT
│  ─╯  ╰─────╮   ╭───────────╯ ╰────    20     │  solid ACTUAL
│            ╰───╯                             │
│  ────────────────────────────────────  15    │
│  Mo    Di    Mi    Do    Fr    Sa    So      │  3 ticks min, NEVER hidden
├──────────────────────────────────────────────┤
│  Licht  ████████░░░░████████░░░░████████     │  outputs lane, 20px
│  Heizung ░░█░░░░░░█░░░░░█░░░░░░░█░░░░░░      │
├──────────────────────────────────────────────┤
│  💧 🌱      💧          📷💧                  │  annotation rail, 20px, 1 row
├──────────────────────────────────────────────┤
│  [img][img][img][img][img][img][img][img]    │  film strip, 44px, IS an axis
└──────────────────────────────────────────────┘
        ●  ○  ○  ○      ← page dots: temp / rF / VPD / CO₂
```

- **Swipe left/right** between measures. One `echarts.setOption` on one instance. This is the mobile-native gesture and it replaces the current 15-measure checkbox matrix entirely.
- **Long-press** → a pinned scrubbing header appears *above* the chart (never a floating tooltip — a fingertip occludes a tooltip and there is no hover on touch):
  `Do 21:40 · 24,3 °C · Ziel 25 °C · −0,7 · Licht an`
  and the film strip frame under the cursor pops to full width.
- One finger = page scroll. Two fingers = pan/zoom (`dataZoom: inside`). Tap = crosshair.
- **No interval control at all.** The server picks the aggregation window from the range. This kills the `3y × 5s` = 18.9 M-window self-DoS from the simple gear entirely, and the Pro gear gets a hard server-side cap.
- **Coverage guard:** if raw-sample coverage < 80 %, the scorecard greys and reads `Zu wenige Messwerte für eine Bewertung.` / `Not enough readings to judge.`
- **Time-in-range is computed server-side on RAW Influx samples**, in a new `GET /data/scorecard`. Never on `aggregateWindow(fn:mean)` output — averaging destroys the excursions the metric exists to count, and the error is invisible by eye.

### 4.2 Pro gear — `/pro/:id/charts` — the workbench

Stacked small multiples, shared x-axis, one linked crosshair (`grid[]` + `axisPointer.link` + `echarts.connect()`), 4–6 panels at 90–120 px mobile / 160–200 px desktop. Panel order and selection persist into the **existing query-string format**, extended additively so every preset and share link in circulation still parses.

Per panel:
- **Solid actual.** For the primary measure, a **min/max envelope** behind the mean, via `sampling: 'minmax'` — a single `mean` line is a lie about a bang-bang controller. LTTB is used only for the navigator, because LTTB smooths away the exact oscillation the grower is looking for.
- **Dashed stepped setpoint**, stepping at `daynight.day` / `daynight.night` between `day.temperature` and `night.temperature`. Read from `device.configuration` — **no new API, no new storage.** This is the single highest-leverage change in the whole redesign and it costs a parse.
- **Signed deviation fill** between actual and setpoint. Never fill to the axis; today's `type:'area', threshold:null, fillOpacity:0.1` encodes literally nothing and almost certainly fails WCAG 2.2 SC 1.4.11's 3:1 non-text contrast floor.
- **One target band at a time, labelled with its source**, priority: alarm thresholds (hard edge — the user's own declared acceptable) > setpoint ± tolerance (soft) > stage VPD sweet spot (advisory). A band whose source is not named is a band nobody trusts.
- **Day/night shading** as `markArea`, derived from measured `out_light > 0` where available, falling back to the `daynight` schedule, with `lights.sunrise`/`sunset` ramp gradients at the edges, **in an explicitly displayed timezone** (a 12/12 flip near a DST boundary otherwise drifts an hour and generates bug reports). A failed contactor then shows as a **missing band** — a diagnostic, not decoration.
- **Outputs in a state-timeline lane**, region length = duration, null = gap. Not 0/1 lines fighting for a value axis.
- **Annotation rail under the x-axis**, 12–20 px, max **two rows** (row 1 human `GrowEvent`s, row 2 device logs), 8–12 px pixel-proximity clustering with count badges, severity ranking, category filter chips reusing the existing `collectLogCategories` / `matchesLogCategory`. **Full-height dashed lines for stage changes and harvest.** Today's height-1 columns readable only by hovering are unusable on a mobile-first product.
- **Film strip as an axis.** Thumbnails positioned by timestamp on the same x-scale, so uneven capture intervals read honestly as gaps. Delivered as **one sprite + JSON index per window** (256×160, 50 tiles under 15 min / 100 above) instead of N image requests. `Image.timestampEnd` marks mp4 timelapses as spanning a range — those render as a **bracket**, not a point.
- **A dedicated `Wasser & Dünger` panel** — this is the owner's *"it should also be visualized in the graph"*, literally. Two series: watering volume as bars (L), measured EC as a line (mS/cm), plus the active regime's target EC as a dashed step line. Runoff EC as a second, lighter line when present.
- **Colour: Okabe-Ito** (`#E69F00 #56B4E9 #009E73 #F0E442 #0072B2 #D55E00 #CC79A7 #999999`). Today's `#e05a4e` red beside `#b0743c` brown is the textbook deuteranopia collision, and `Lights`/`Day` currently share `#c8a23c`. With small multiples, **position is the primary channel and colour is decoration** — itself an accessibility win. `darkMode: 'auto'` replaces the hand-maintained 30-property theme + `MutationObserver`.
- **"Als Tabelle anzeigen" / "View as table"** disclosure, because no OSS library matches Highcharts' accessibility module and Terp does not load that module today anyway.
- **DLI and dew point** added. Pure arithmetic on stored data (`DLI = PPFD × photoperiod / 1e6`) and it closes a named gap against Pulse Pro.
- Chart series names go through `translate` — today they are hardcoded English (`Temperature`, `Critical logs`) while the chrome is translated, which is what a German customer sees on the flagship screen.

## 5. The multi-plant diary

### 5.1 Why `DeviceLog` cannot carry this

Today every diary entry is a row in the one `DeviceLog` collection alongside boot messages and MQTT errors, with no `entry_type` discriminator; a "grow cycle" is inferred **in the browser** by `convertEventsToGrowCycles()` scanning lifecycle rows and forking whenever the stage ordinal rolls back **or the trimmed `lifecycleName` string differs**. Renaming a plant mid-grow forks its history. A re-veg fabricates a new plant. Cycle identity in share-link URLs is the cycle's *start timestamp*, so editing an entry's time breaks links already in circulation. A per-plant diary cannot be layered on that. It needs real entities.

### 5.2 New entities — all cloud-side MongoDB, keyed by `device_id`

`device.configuration` cannot carry new keys (firmware strips unknown keys on echo), so none of this goes near the device. All fields optional, read-time normalised, backfilled by an idempotent boot-time job — the house style, since there is no migration tooling.

```ts
// collection: plants
interface Plant {
  plant_id: string;              // nanoid, stable forever — identity is NOT a string label
  device_id: string;             // index {device_id, archivedAt}

  schemaVersion: 1;

  event_id: string;

```

**`Image` gains two optional fields** (`plant_ids?: string[]`, `event_id?: string`) rather than a sidecar collection — optional field + read-time normaliser is the house style and cheaper than a join. `GrowEvent.images` gives the forward direction; the film strip needs the reverse.

**Backfill.** `convertEventsToGrowCycles()` stops being a runtime browser algorithm and becomes a **one-time server-side migration**: read `DeviceLog` rows whose `categories` match `diary*` (both `diary-plant-lifecycle` and the legacy `plant-lifecycle`), create one `Plant` per inferred cycle with `label = lifecycleName`, emit `PlantStageEvent`s and `GrowEvent`s with `legacyLogId` set, skip anything already backfilled. It also fixes P0 #7 in passing: the server's own stage entries written with `categories: ['diary-plant-lifecycle']` (missing the `'diary'` prefix, therefore invisible in the Entries report and not editable) become first-class `PlantStageEvent`s like every other.

### 5.3 How a plant is created

Three paths, increasing effort. **The default path creates nothing.**

1. **Never.** On the first `GrowEvent` for a device, the server lazily creates one implicit plant, `plant_id = 'tent:' + device_id`, `label = 'Das Zelt' / 'The tent'`, `isImplicit: true`. Every event attaches to it. **The word "plant" never appears in the UI while `plants.length === 1 && isImplicit`.** No plant chips, no plant filter, no plant tab. This is the tax-free path and it is what types 1, 2, 3 and 7 get for free.
2. **`+ Pflanze`** in the capture sheet or on the Pro plant board: one required field (label). Everything else optional. On the first explicit plant, the implicit tent plant is renamed `Ganzes Zelt` / `Whole tent` and stays as the "applies to everything" bucket.
3. **From a photo**: shoot, tap `+ Pflanze`, name it, the photo becomes `coverImageId`.

### 5.4 How entries attach

The plant selector appears **only when `plants.length > 1`**, as a horizontal chip row directly above the sheet's keyboard:

```
[ Alle ]  [ ● Blue Dream ]  [ ● #2 ]  [ ● Auto ]  [ + ]
   ^ default selection, because watering usually is
```
Chips carry the plant's `colorIndex` dot. Multi-select. `Alle` writes `plant_ids: []`, which is semantically "the tent", not "each plant" — so adding a plant later does not retroactively rewrite history.

### 5.5 Re-veg, clone, rename — the three cases that break today

| Case | Today | Zweigang |
| --- | --- | --- |
| **Rename** | `lifecycleName` string differs → `convertEventsToGrowCycles` **forks the history into two cycles** | `Plant.label` update. Identity is `plant_id`. History is untouched. Share links keep working. |
| **Re-veg** | stage ordinal rolls back → **a new plant is fabricated** | A `PlantStageEvent{stage:'vegetative'}` after a flowering one. Stages are append-only, so backwards is legal and expected. The plant timeline renders a second veg segment with a `Re-Veg` marker. Same plant, same id, same photos. |
| **Clone** | no concept | `POST /plants` with `motherPlantId` + `origin:'clone'`; strain copied from the mother; `startedAt = now`; mother untouched. The plant board indents clones under their mother. |
| **Harvest** | **not even a lifecycle stage** (`flowering → drying`) | `PlantStageEvent{stage:'harvest'}` + optional `GrowEvent{kind:'harvest'}`. Full-height dashed line on the chart. Sets `archivedAt` when curing completes or on demand. Archived plants leave the board into `Abgeschlossen` / `Finished`. |

2. A sheet rises with two commit buttons and a volume stepper prefilled from the user's last event:

### 6.2 The schedule model — "grow medium + feed regime", the way growers say it

The owner's own examples settle the model: *Light-Mix* and *All-Mix* are **substrates**, *Floragard Light* is a substrate, *Green House Feeding* and *BioTabs* are **feed products** — and that is horticulturally correct, because the substrate changes the schedule more than almost anything else. Light-Mix is lightly pre-fertilised → feed from ~week 2. All-Mix is heavily pre-fertilised → feed from ~week 3–4, and feeding early burns plants. BioTabs is slow-release → almost no liquid feeding; the "schedule" is re-tabbing every 4–6 weeks. **A model that cannot express "All-Mix, so don't feed yet" is not modelling the domain.**

```ts
// collection: growregimes — CONTENT. Seeded, versioned, hot-swappable, never in the webapp bundle.
interface GrowRegime {
  regime_id: string;
  label: string;                 // "Biobizz All-Mix" — plain-text word mark, no logo, no brand colour
  medium: string;                // 'soil-prefertilised-heavy' | 'soil-prefertilised-light' | 'coco' | ...
  kind: 'liquid' | 'slow_release' | 'hybrid';
  feedStartsAt?: { stage: DiaryLifecycleStage; dayOfStage: number };   // All-Mix: veg, day 21
  strengthAxis?: Array<'light'|'medium'|'heavy'>;
  autoflowerMultiplier?: number; // 0.25–0.5; no manufacturer chart has an auto column
  ecBasis: 'absolute' | 'delta_over_source';   // CANNA publishes EC+, not EC
  steps: RegimeStep[];
  source_url: string; retrieved_at: number; chart_version: string;
  sourceKind: 'official_pdf' | 'official_calculator' | 'ownerless' | 'user';
  owner_id?: string;             // set = a user's private copy, invisible to everyone else
  removedAt?: number;            // one DB update removes any brand entirely
}
interface RegimeStep {
  index: number;
  anchor: { stage: DiaryLifecycleStage; weekOfStage: number };  // phase-relative, never wall-clock
  products: Array<{ name: string; mlPerL?: number | [number, number]; gPerL?: number;
                    everyNthFeed?: number; note?: string }>;
  ecTarget?: [number, number]; phTarget?: [number, number];
  action?: 'water_only' | 'flush' | 'retab';
}
```

**Correctness rules baked into the schema, because a conversion bug here burns a crop:**
- **EC is canonical in mS/cm. A bare "ppm" is never rendered.** Three scales are in circulation (500/640/700); at EC 1.8 a Bluelab reads 1260 and a Hanna reads 900 for the same liquid. `measure.tdsScale` is mandatory whenever `tds` is set.
- `ecBasis: 'delta_over_source'` regimes render the arithmetic explicitly, never the bare number:
  `Ziel 1,8 + deine Wasser-EC 0,4 = **2,2**` / `Target 1.8 + your source EC 0.4 = **2.2**`
- **A dose can be a range or a word.** `mlPerL` accepts `[5, 13]`; `action` covers `Flush only` / `water_only` / `retab`. A range prefills its midpoint and shows the range beneath.
- **The schedule advances by feed events, not by wall-clock weeks.** `Schritt 4 von 11` / `Step 4 of 11`, with a soft calendar mapping. Growers feed Tuesday and Friday and they slip.
- **The 18/6 → 12/12 flip is auto-detected from `out_light` history** to place the grower on the correct bloom week. **No bottle brand's calculator can do this, because none of them can see the device.** This is the one thing that makes feeding a *Terp Control* feature rather than a worse version of a free web calculator.
- **Flush means three different things** (pre-harvest, corrective, routine leaching to run-off) and the UI never conflates them. Pre-harvest flush is always phrased `Dein Plan sieht das vor` / `Your chosen plan calls for this` — never "this is necessary". The evidence does not support the stronger claim.

### 6.3 Brand posture — invisible, and it costs the design nothing

1. Brand names are **plain-text labels only**. No logos, no brand colours, no bottle imagery, no trade dress. **Never inside a Terp Control feature name** — the feature is `Düngeplan` / `Feeding plan`, never "CANNA Mode". That distinction is what keeps the use referential (Art. 14(1)(c) EUTMR, *Gillette* C-228/03) rather than trademark use.
2. Numbers live in the MongoDB content collection with `source_url` + `retrieved_at`, so any brand is removable in one DB update. **Never baked into the webapp bundle.**
3. **Sourced from the brand's own chart or calculator, never from retailer or blog transcriptions** — hyjo.co.uk and veridiangrow.com disagree by ~3× on CANNA Terra Vega. Wrong numbers here reach a plant.
4. The picker shows `Zuletzt geprüft: 12.03.2026` / `Last verified: 12 Mar 2026` under each regime. This is simultaneously the legal posture and a genuine user-facing trust feature, which is why FeedSchedules.com does the same thing.
5. Never present a computed dose as an instruction. Every prefilled value is editable and the sheet footer reads `Richtwert. Prüfe selbst, fang niedrig an.` / `Guideline. Check yourself, start low.`
6. A takedown address and a published notice-and-action policy exist **before** the first brand ships. A brand that can email you and get removal in 48 hours sends an email; one that cannot sends a lawyer.
7. Seed set: the owner's named list (Biobizz Light-Mix, Biobizz All-Mix, Floragard Light, Green House Feeding, BioTabs) **plus** ownerless schedules (Lucas Formula, Jack's 321, generic per-medium EC ladders), which cost nothing legally and make the feature useful the day a brand is pulled.

### 6.4 Drawn on the chart

- **Pro:** the `Wasser & Dünger` panel (§4.2) — volume bars, measured EC line, target EC dashed step line, runoff EC lighter line.
- **Simple:** blue droplet glyphs on the annotation rail of the History chart, tappable → the event card. **No EC panel appears until the user has entered an EC value at least once** — progressive by *data*, not by a setting. The stoner never sees a table of ml/L; the club sees all of it.

## 7. Camera & timelapse

Terp Control already pulls a still every 30 s over MQTT and builds `1d`/`1w`/`1m` timelapses hourly. What it lacks is any **relation** between an image and a time, a plant, or a stage.

**Images relate to time** — they always did, via `Image.timestamp`. What changes is that time becomes a *shared axis*: the film strip in both gears is positioned on the chart's x-scale, so a 6-hour capture gap reads as a 6-hour gap and not as two adjacent thumbnails. `Image.timestampEnd` (already present, already marking mp4 spans) renders as a bracket. One cursor drives chart, scrubbing header and film strip together.

**Images relate to plants** via the two new optional fields on `Image` (`plant_ids`, `event_id`). A photo shot from the capture sheet inherits the sheet's plant chips. A webcam still inherits `plant_ids: []` (the tent) and can be adopted into an event by long-pressing a film-strip frame → `Zu Eintrag hinzufügen` / `Add to entry`.

**Images relate to stages** via a new timelapse span. The existing hourly job gains one more duration alongside `1d|1w|1m`:

```ts
duration: '1d' | '1w' | '1m' | 'stage'
```
computed from consecutive `PlantStageEvent`s on the device's primary plant. The result: `Deine Blüte in 90 Sekunden` / `Your bloom in 90 seconds`, which is a shareable artefact rather than a rolling window nobody ever watches. This is the single feature type 2 buys the camera for and today it does not exist.

**In the Simple gear**, the camera is: a 16:9 latest-still card on `Jetzt` **with its own age line** (a stale camera is exactly as misleading as a stale sensor), and the 44 px film strip on `Verlauf`. Type 2 additionally gets one extra card on `Jetzt`:

```
┌──────────────────────────────────────┐
│  Heute      │      vor 7 Tagen       │
│  [ image ]  │      [ image ]         │
│         [ Teilen ]                   │
└──────────────────────────────────────┘
```
Two frames, one axis, one share button. That is the whole monitor-plus-camera product for a user who does not control anything.

**In the Pro gear**, additionally: the storyboard sprite endpoint, per-stage timelapse downloads, camera diagnostics (RTSP URL, tunnel, error log), and the existing hover-to-load behaviour on desktop.

**Privacy:** images are never fetched by a third party. This alone rules out the Meta platforms independent of their cannabis policy — the Instagram Graph API requires the media to sit on a publicly accessible unauthenticated URL for Meta to pull. Sharing is a Terp-hosted link the user copies, or a file they save.

## 8. Multi-user / clubs

**v1.1, not v1.** It is an authorisation rewrite, and a bad authorisation rewrite is a data leak. Stated up front rather than promised and slipped.

### 8.1 The model

```ts
// collection: memberships
interface Membership {
  device_id: string; user_id: string;           // unique index {device_id, user_id}
  role: 'owner' | 'operator' | 'logger' | 'viewer';
  displayName?: string;                          // opt-in; absent → "Mitglied 3"
  invitedBy: string; createdAt: number; revokedAt?: number;
}
```

| Role | Reads | Writes settings | Writes events | Manages access | Default gear on invite |
| --- | --- | --- | --- | --- | --- |
| `owner` | all | ✅ | ✅ all | ✅ + delete + transfer | Profi |
| `operator` | all | ✅ | ✅ all | ❌ | Profi |
| `logger` (**`:self` tier**) | room + own events | ❌ | ✅ own only, edit/delete own only | ❌ | **Einfach** |
| `viewer` | room | ❌ | ❌ | ❌ | Einfach |

**This is the cleanest argument for Two Speeds in the whole concept.** A twenty-member Anbauverein has one admin who lives in Profi and twenty members who live in Einfach, and neither has to negotiate with the other's interface. A single blended UI would have to be simultaneously safe for a stoned member with write access to a €289 controller and rich enough for the person answering to the Landesamt. Zweigang does not have to solve that; it routes around it.

**The work, costed honestly:** `auth.middleware.ts:172` and `:207` change from `find({owner_id, device_id})` to a resolver returning an effective role; ~10 owner-scoped service queries loosen; `GrowEvent.actor_id` is populated; an account-lookup-by-email endpoint has to be designed against enumeration abuse; `PUT /users/:id` is currently broken and `RecipeTemplate.name` is globally unique across all users, both of which need repair first. That is not a flag. It is a release.

### 8.2 Attribution

`GrowEvent.actor_id` is **always stored** (you need it to answer "who changed my setpoint at 3 a.m.") but **rendering depends on the jurisdiction mode**:
- Private mode: `du` / `you` vs `jemand anderes` / `someone else`. No names.
- Club mode: `displayName` if opted in, else `Mitglied 3` / `Member 3`.

### 8.3 Privacy posture — a device-scoped mode, default privacy-maximal

| | `Privat` (default) | `Verein` (opt-in, DE/MT) |
| --- | --- | --- |
| Attribution rendered | pseudonymous | display names |
| Harvest weight | **never prompted**; an off-by-default disclosure `Gewicht erfassen?` | prompted |
| Plant count in exports | omitted | included |
| Participation log (§ 17 Abs. 2 *eigenhändig*) | off | `PLANNED → PENDING → COMPLETED → REJECTED`, `regulatoryRelevance` flag |
| Telemetry retention | **12 months**, then downsampled to 15-min means | 5 years |
| Export anonymisation | `ANONYMIZED` default | `NONE \| PSEUDONYMIZED \| ANONYMIZED`, default anonymised |
| One-tap `Alles löschen` | ✅ in account | ✅ (audit log is opt-in immutable, never global) |

The reasoning is not squeamishness. Harvest weights and plant counts are the exact facts separating a lawful three-plant hobby from a prosecutable offence in many jurisdictions, § 28 Abs. 2 KCanG lets German authorities seize digital data with **no prior judicial approval**, and a light schedule flipping 18/6 → 12/12 in an unbounded Influx bucket is a legible harvest calendar. Today the bucket is created with **no retention and zero downsample tasks** — raw 5-second samples kept forever. That is both a cost curve and an evidentiary liability, and setting a retention policy is v1 work.

**Refused outright** (§14): per-member consumption or dispensing records, grams inventory, membership numbers, DOB, addresses, location of any kind, being the club's system of record for § 26, and any `KCanG-konform` badge. Even Cannanas' own compliance endpoint says *"Not legal advice."*

## 9. Old devices — `fan`, `light`, `plug`, `fridge` (type 7)

Not hand-waved. Two concrete promises and one concrete refusal.

**Promise 1 — the Pro gear for an old device is today's screens, moved and left alone.** `fan-settings`, `light-settings`, `plug-settings`, `fridge-settings` keep their components verbatim; only their route changes (`/device/:id/settings` → `/pro/:id/control`) and the shell around them. No redesign, no regression risk, no re-QA of five device types' settings forms in one release. `dryer` stays dead per `AGENTS.md` and continues to resolve to `fridge-settings`.

**Promise 2 — the Simple gear works for all of them, because the `Jetzt` screen is composed from *capability*, not from `device_type`.** It shrinks; it never fakes:

| Type | Ring (primary) | Secondary tiles | Output strip | Tabs |
| --- | --- | --- | --- | --- |
| `plug` | socket state, `An` / `Aus` | none | schedule / timer state | **2** — `Jetzt`, `Tagebuch` (no chartable series → no `Verlauf`) |
| `fan` | `rpm` | temp + humidity **if reported** | fan lane | 3 |
| `light` | dimming % | **a 24 h photoperiod bar as the hero element**, DLI | light lane | 3 |
| `fridge` | temperature + verdict | humidity, VPD | heater / dehumidifier / light | 3 |
| `controller` | temperature + verdict | humidity, VPD, CO₂ if present | capability-filtered | 3 |

The `light` row is the interesting one: a light-only owner today gets `out_light` plotted as a 0–100 line on a value axis, `is_day` inferred from `out_light >= 0.5` rather than from the configured photoperiod, no day/night shading, no DLI anywhere in the repo, and a failed contactor that is completely invisible. Zweigang gives them a photoperiod bar, day/night shading derived from measured light (so a failed contactor is a **missing band**), and DLI. **A type-7 light owner gains more from this redesign than a controller owner does**, which is the honest way to serve a non-focus group: not by special-casing them, but by making the general mechanism cover them.

**Promise 3 — plants, diary, feeding and photos work on every device type**, because they are cloud-side and keyed by `device_id`. A `plug` owner can keep a full per-plant grow diary with feeding schedules. That is free, it required no thought about type 7 specifically, and it is the nicest thing the concept does for them.

**Refusal:** old devices get **no new firmware capability, no new socket roles, no new sensors**. Anything they cannot do today, they still cannot do. Where the app previously implied otherwise (a `plug` shown a humidity target, `fans.external`/`internal` offered to a controller and read by no firmware, the entire `daynight.floating` beta that **zero firmware anywhere reads**, `lights.maintenanceOn`, `co2.sunsetOff`, `daynight.linearChange`), the control is **removed from Einfach entirely and marked `Ohne Funktion in dieser Firmware` / `No effect on this firmware` in Profi.** Shipping dead controls as if they work is a credibility bug, and the Simple gear's whole claim is that everything on it does something.

Also fixed here, because it is embarrassing and cheap: a controller's dashboard card today literally reads **"Terp Control FRIDGE GROW"**, and an unnamed controller is *named* `devices.fridge.title`. There is no `devices.controller` block in `en.json` or `de.json`. Zweigang adds it and reads the type label through a lookup, so the flagship product stops describing itself as a converted refrigerator.

Checkmarks are pre-ticked from `hardwareInfo.sockets`. One button. Each row can be tapped to open the pairing help — **illustrated with the `sockettype_*.mp4` clips already sitting unreferenced in `assets/wizard/`**, ~30 MB of already-shot video currently copied into every production build and used nowhere.

**This screen is also the fail-closed fallback.** When `hardwareInfo.sockets` is absent (old firmware), every row is unticked and the copy becomes `Was hast du angeschlossen?` / `What do you have connected?` — **exactly one question, with pictures**, instead of assuming full capability and then showing a humidity target the tent cannot reach.

**Screen 3 · Stage.**
> `Wo stehst du gerade?` / `Where are you right now?`
The existing `stage-preset-picker`: five large cards over `GROW_STAGE_PRESETS`, each with its subtitle `24/21 °C · 70 % · 18 h` and `VPD 0,4–0,8 kPa`. Sets the targets. **Skippable** → monitor-only, no targets, no nagging.

**Done.** Lands on `Jetzt` in the **Einfach** gear. One non-modal hint bubble points at the Pro button — `Alles im Detail: Profi-Ansicht` — dismissed forever on first tap or after three sessions.

**Three screens. Three taps minimum. No self-description question.**

The last point is the concept's onboarding thesis: because the gear is reversible and one tap away, **we never have to ask "are you a beginner?"** — the worst question in software onboarding, which every user answers wrongly and defensively. We default to Einfach and let behaviour, not self-report, decide.

**Deliberately NOT in onboarding:** plants, feeding regimes, alarms, camera setup, share links. Each appears at its first point of need:
- Plants: on the second `+ Pflanze` tap.
- Feeding: the first time `Gegossen / Gedüngt` is tapped — a two-question sheet (`Substrat?` / `Düngeplan?`) with `Weiß ich nicht` / `Not sure` as a first-class answer on both. Skipping gives the 2-tap water flow, forever, with no nagging.
- Alarms: three toggles in the account sheet (§15.5), on by default for `Gerät offline`.

**Re-running setup** gets a menu entry in both gears — today the wizard is barely discoverable and has no "re-run" path at all.

## 11. Per-user-type walkthrough — the first week

### Type 1 — Lazy, monitoring only
Claims the controller, names it `Zelt`, taps `Passt` on a screen showing only `✓ Temperatursensor  ✓ Feuchtesensor`, **skips** the stage screen. Lands on `Jetzt`: one ring reading `24,3 °C`, no verdict, the words `Nur Messen`, two tiles, and the line `Keine Steuerung — dieses Gerät misst nur.` He does not open the app again for four days. On day five he taps `Verlauf`, `7 Tage`, and reads one sentence: `86 % im Zielbereich` — except he set no target, so it reads `Ø 24,1 °C · 21,0–27,4 °C`, with the swipe dots offering humidity and VPD. He swipes twice, sees the VPD line, closes the app. **He never saw a plant, a schedule, a socket, an alarm editor or the word "expert".** Total interface surface consumed in week one: one ring, two tiles, three chips, one sentence.

### Type 2 — Same, with a camera
Identical, except screen 2 shows `✓ Kamera` and `Jetzt` carries the latest still with its own age line, plus the `Heute | vor 7 Tagen` card. On day seven that card has two genuinely different pictures in it and he taps `Teilen`, which copies a Terp-hosted link. On `Verlauf`, the 44 px film strip runs under the chart on the same axis; he long-presses a frame from the night of day four and the pinned header reads `Do 03:12 · 19,8 °C · Licht aus`. **The image and the number are the same moment for the first time in this product's life.** At the end of week two the `stage`-span timelapse appears in the diary feed as a card: `Deine Blüte in 90 Sekunden`.

### Type 3 — Controls certain aspects (CO₂ or heating only)
Heater on socket 1, no dehumidifier. Screen 2 shows `✓ Heizung` and `○ Entfeuchter — nicht gefunden`. He taps `Passt`. On `Jetzt`, the ring is temperature with `Ziel 25 °C · Tag` and a green `Passt`; humidity appears as a **plain tile with no target and no colour**. The output strip lists `🔥 Heizung aus` and nothing else. Today this user is shown a humidity target row, a grow-assistant humidity-deviation warning and a "Dehumidifier running non-stop" alarm preset, all for hardware he does not own, because `deviceControlCapability()` returns `'full'` the moment any climate socket is paired. Under Zweigang **the app never mentions a capability he does not have.** Mid-week he crosses to Profi once to set the heater hysteresis, lands on `/pro/:id/control`, changes one value, taps the `Einfach` segment and is back on `Jetzt`. Round trip: four taps.

### Type 4 — Whole tent
Heater, dehumidifier (doubling as the cooler), light on PWM, secondary light, CO₂. He is in Profi by day two and stays there. He gets: six-panel small multiples with the setpoint drawn against every actual, day/night bands from measured light, the outputs state-timeline lane showing exactly when the dehumidifier fought the heater, the annotation rail, and the scorecard split day/night. In week one he discovers from the outputs lane that his dehumidifier runs 40 minutes every night at lights-off, which no chart in this product could previously show him.
**What he does not get, and is told plainly:** there is no humidifier role, no exhaust-fan role, no AC role. `dehumidifier` *is* the cooler in `temp`/`breed` workmodes — one socket, two meanings, one chart series — and the chart labels it `Entfeuchter / Kühler` rather than pretending. `fans.external`/`internal` are not offered at all, because no firmware reads them. **This concept adds no socket roles and requests no firmware change**; the marketing promise *"ein Controller für dein ganzes Zelt"* is beyond what the firmware can express today, and pretending otherwise in the UI is how you get a one-star review that says the app lies.

### Type 5 — Closed-loop DIY (the fridge builder)
Day one he finds Profi and the `Hardware` page. Day two he asks for the API. **v1 gives him the read API** — a documented `x-api-key` surface shaped like Pulse Grow's (keys scoped per device, quotas in datapoints, OpenAPI + Redoc), plus the **generic outbound webhook** decoupled from alarms so a diary entry, a stage change or a feed event can POST anywhere. That transitively unlocks n8n, Make, Home Assistant, ntfy and Matrix and moves the entire platform-policy problem to his side of the trust boundary. He builds his own Grafana panel in week one and stops complaining. **What v1 does not give him:** a write API for outputs (`POST /device/test/:id` remains the admin harness it is), custom sensor measures (`VALID_SENSORS` stays hard-coded; his soil-moisture probe enters as a `GrowEvent.measure` and charts on the `Wasser & Dünger` panel), or custom `device.configuration` keys, which the firmware strips. He is the segment most likely to be disappointed and the one most likely to write a blog post about it; §15 owns that.

### Type 6 — Cannabis grow club
**v1: they use share links and one shared login, exactly as today, and we say so.** v1.1 gives them `memberships`. The admin is `owner`, in Profi, with the feed history table, the participation log, the CSV export with the anonymisation toggle, and the `Verein` jurisdiction mode. The twenty members are `logger`s, land in **Einfach**, and their week is: open the app, tap `Erledigt` on the due-feed card, shoot a photo, done. Their events carry `actor_id`; they see the room and their own entries and nobody else's identity. When the admin later asks "who fed room 2 on the 14th and how did the plants react", the answer is a `GrowEvent` with an actor, a volume, an EC, a plant list, and a chart with all three drawn on one x-axis. **Terp Control never stores a member's name, DOB, address, membership number or dispensed grams**, and never becomes the § 26 system of record — that market has ~20 products at €0.50–1.00/member/month, Cannanas alone claims >250 licensed clubs with a 185-path public API, and it is not winnable. What is winnable is being the **device-attested environmental layer** those systems consume, which requires storing zero personal data.

### Type 7 — Owner of an old device (fan / light / plug)
She has a `light` from the previous generation. She updates and finds the app changed. Her settings page is **byte-identical**, at a new URL. What is new: a `Jetzt` screen with a 24-hour photoperiod bar as the hero element and the dimming % in the ring, a `Verlauf` tab with day/night shading derived from her lamp's *measured* output (so the evening she lost a contactor shows as a missing band — she would never have found that before), DLI as a number, and a diary she can put plants and photos and a feeding schedule into, on a device that has no sensors at all. **Nothing was taken away and the general mechanism happened to cover her.** She is not the focus group, she is not special-cased, and she is better off — which is exactly the brief.

## 12. Stoner / Normal / Techie

### Stoner
Lives in Einfach and never leaves. Concretely, what that means:
- **Three tabs, 64 px. One ring. Two action buttons. One primary CTA per screen.** No horizontal scroll, no accordion, no tab-within-tab.
- **Verdicts, not interpretations.** `Passt`, `Zu warm`, `Zu kalt`. The number is present but the judgement is made for her.
- **One-tap confirms instead of forms.** `Erledigt` on the due-feed card writes a nine-field `GrowEvent`.
- **It thinks for her and it reminds her** — the two things the owner named. The regime knows what she was going to write; the due card knows when.
- **No destructive action without hold-to-confirm.** No "delete history", no workmode dropdown, no threshold matrix.
- **Nothing on screen that does nothing.** Dead controls are removed, not disabled.
- **The Pro button is one button at the bottom of one screen** — visible, ignorable, not a nag, never automatic.

### Normal
The one the *switch* is actually for. He lives in Einfach and crosses over two or three times a grow: to set a heater hysteresis, to look at a real chart on a laptop, to read the grow report. **The switch has to be cheap enough that "occasionally" works**, which is why context is preserved (§2.3): switching from `Verlauf` at 7 days lands on the Pro chart at 7 days with the same measures, and switching back returns him where he was. If crossing over cost him his place, he would stop crossing over, and the Pro gear would become a feature nobody uses.
He is also the reason the web app matters: AC Infinity, TrolMaster, Mars Hydro, Spider Farmer and VIVOSUN are **phone-only**. The Pro gear on a 27" monitor — six panels, a linked crosshair, a film strip and a feed table — is a structural advantage the Angular/Ionic stack gives for free, and it is where growers actually analyse.

### Techie
Lives in Profi permanently, and — this is the load-bearing claim — **his power never leaks into the stoner's screens.** In a single-shell design every expert feature is a compromise negotiated against the beginner: an accordion, a "show advanced" toggle, a settings flag, a tooltip. Every one of those compromises makes the expert feature slightly worse and the beginner screen slightly more cluttered. Two shells means the alarm editor can be a dense matrix with no apology, and `Jetzt` can have two buttons on it.
He also gets: gear preference stored **server-side** so a new phone does not reset him; the read API; the generic webhook; `Als Tabelle anzeigen`; the timezone printed on the chart; and the honest labelling of `Entfeuchter / Kühler` and `Ohne Funktion in dieser Firmware`.

### Why not one shell with an "Advanced" accordion
Because an accordion is a door, and **a door on the screen is a screen with a door on it.** The stoner sees it on every screen, wonders every time whether the thing she needs is behind it, and occasionally opens it and gets lost. The techie pays an extra tap and a collapse animation forever, on every visit, for the rest of the product's life. And the copy has to serve both audiences in one string, which means it serves neither.
**You cannot make a screen simple by hiding things on it. Only by not putting them there.**

## 13. The engineering law that makes this affordable

The brief asks the hard question directly: does a two-shell design double the maintenance burden?

**Answer: no, and here is the mechanism that makes "no" true rather than aspirational.**

> **The Zweigang Law.** Every piece of UI is a component declared and exported in `components.module.ts` and it **knows nothing about gear**. A gear is a *page* that composes components. If a component ever needs `if (gear === 'simple')` inside it, the split is in the wrong place: extract two components, or move the branch up to the page.

Three named exceptions, costed rather than hidden: `value-edit-row`, `tc-tile` and `annotation-rail` take a `density: 'compact' | 'roomy'` input, because touch-target size genuinely is a rendering concern and duplicating those three would be worse than parameterising them. `density` is **not** `gear` — a Pro page on a phone may pass `roomy`.

**The actual duplication, counted:**

| | Count |
| --- | --- |
| Shared components (single source of truth) | ~28 |
| Simple-gear page shells | 3 (+ 5 sheets) |
| Pro-gear page shells | 12 |
| Genuinely duplicated code | **3 page templates + 3 page classes ≈ 600 lines of HTML/TS** |
| Extra i18n keys (simple-gear copy is deliberately different, not a subset) | ~120 keys × 2 languages |
| Extra test matrix | 2 gears × 6 device types × 3 access modes = 36 cells |

The 600 lines are real and cheap. **The 120 keys and the 36 cells are the honest cost**, and §15 owns them.

**What makes October 2026 believable is the asymmetry of the two builds:** the Simple gear is **genuinely new but tiny** (3 screens), while the Pro gear is **largely a re-roof of what already exists** — the expert settings tab, the charts page, the diary, the alarm editor, the five device settings components — moved under new routes with a new shell. We are not building two apps. We are building one small new app and re-shelving the existing one, plus one shared chart engine migration that was required regardless.

## 15. Non-goals — what this concept refuses to do

1. **No accordion, no "Advanced" toggle, no progressive-disclosure-within-a-screen anywhere.** The disclosure boundary is the shell. That is the whole concept.
2. **No automatic gear switching.** No "we noticed you're an advanced user". The UI never changes underneath a person.
3. **No adaptive or learning layout.** A screen that rearranges itself is unlearnable, and this product's core users are, by the owner's own description, sometimes impaired.
4. **No per-device gear.** One user, one gear. See §16.7 for the cost.
5. **No firmware change, no new socket roles, no new MQTT topics, no new `device.configuration` keys.** Everything new is cloud-side MongoDB keyed by `device_id`.
6. **No claim of irrigation or dosing automation.** Watering and feeding are capture-and-recall. The word "automatic" never appears near them.
7. **No two-way sync with any grow-diary platform.** GrowDiaries has no public API and is Cloudflare-hardened; Grow with Jane's ToS §(c)(7) forbids it outright and its backend is Firebase; SeedFinder has been dead since July 2024. The feature is `Woche exportieren` / `Tagebuch teilen`, and it is named that.
8. **No auto-posting to Instagram, Threads, TikTok, Reddit or Facebook.** A failed Discord post means a user revokes a webhook; a failed Instagram post means the user loses their Instagram account with no appeal and Terp Control was the proximate cause.
9. **No "Powered by Terp Control" footer on user-generated posts.** § 6 KCanG bans cannabis advertising and sponsoring with fines to €30,000, read broadly. That string is the single riskiest one in the feature and it earns nothing.
10. **No community feed.** Zero of ~200 App Store reviews across TrolMaster and VIVOSUN praised theirs; it is permanent moderation cost. A link you can paste anywhere is not a feed you must moderate.
11. **No compliance system of record.** No § 26 export, no grams inventory, no per-member dispensing, no `KCanG-konform` badge, no member identity data of any kind.
12. **No location, ever.** No GPS, no IP-geolocation persistence, no "growers near you", no persisted timezone-from-IP.
13. **No analytics or ad SDKs.**
14. **No strain database.** `Plant.strain` is free text, because every candidate API is dead or closed.
15. **No AI recommendations.** The app states what happened and what the target was. It does not tell anyone what to grow.
16. **No subscription gate on alerts, control, or seeing your own current data** — whatever the business model turns out to be.

## 16. Honest weaknesses — where this concept is worst

**16.1 The switch is a confession.** A critic will say: a genuinely good design does not need two of itself; you built two apps because you could not decide. The defence — the population is bimodal, the owner said so, and clubs make it structurally bimodal — is a defence, not a disproof. If the population turns out to be a smooth gradient rather than two clusters, this concept is wrong at the root, and no amount of polish on either shell fixes it.

**16.2 The middle user is served worst, and the middle is large.** Types 3 and much of type 4 sit exactly on the boundary: they want three things from Profi and everything else from Einfach. They will ping-pong. Context-preserving switching softens this; it does not fix it. **This is the concept's worst structural flaw.** The competing concepts that do one adaptive shell serve this person better and I cannot claim otherwise.

**16.3 Two shells is two shells, and governance rots.** The Zweigang Law is a rule in a document. Every new feature triggers a placement argument, and placement arguments have no objectively right answer. The 120 extra i18n keys × 2 languages are real, permanent, and exactly the kind of thing that drifts — the bundle is 885/883 today with a 2-key drift, and this concept puts pressure on that number in both languages simultaneously.

**16.4 The Simple gear can lie by omission.** By showing a mean line and hiding capabilities, it can conceal a real oscillation. My mitigation — render the min/max envelope only when an excursion crosses the band — is a heuristic, and heuristics have false negatives. A controller cycling ±0.4 °C inside a ±1.5 °C band is invisible in Einfach, and that is exactly the signal that a heater is short-cycling itself to death.

**16.5 Discoverability becomes a funnel problem, and it forced a scope addition.** In the original shape of this concept, alarms lived only in Profi. But the research is unambiguous that Spider Farmer users are *begging for any push notification at all*, and a stoner who never opens Profi would never get an alert. So three toggles — `Hitze melden` / `Kälte melden` / `Gerät offline melden` — ship in the Simple account **sheet**. That is a real scope addition, and it means the "three screens" claim is already "three screens plus five sheets" on day one. Sheets are screens with better PR (§16.10).

**16.6 The test matrix is 36 cells on a codebase with 38 `it()` blocks**, 24 of which are a lone `it('should create')`, a suite that is RED, an `app.component.spec.ts` that still asserts an Ionic scaffold menu containing 'Inbox' and cannot pass, and a CI that never runs `ng test`. Two gears multiply that by two. The only honest mitigation is that `simulate-device.sh` can drive all six device types end to end over real MQTT, so release should be gated on a **scripted walkthrough per type per gear**, not on unit tests. That is a manual gate, and manual gates get skipped under deadline pressure.

**16.7 Gear is per-user, not per-device.** A user with one controller and three plugs gets one gear for all of them. Per-device gear was considered and rejected because a switch that means different things in different places is worse than one that means one thing — but the club logger with two rooms and the DIY builder with a controller plus three plugs will both feel it, and neither has a workaround.

**16.8 The ECharts migration and the Simple gear compete for the same October.** If one slips, the honest sacrifice is the Pro chart workbench (keep Highstock one more release) rather than the Simple gear — but that reopens the licence question the owner has already decided, on a repo with no LICENSE file whose marketing calls the cloud *"quelloffen"*, and Highcharts source cannot be redistributed under an OSS licence regardless of how many seats are bought. There is no clean fallback here, only a less-bad one.

**16.9 Feeding is the feature most likely to be wrong in a way that hurts a plant.** Nine unit systems in active circulation (including drops/10 L and 1:5000 dilution ratios), `EC+` versus `EC`, three ppm scales that differ by 40 % on the same liquid. I require every prefilled dose to show its source, remain editable, and never drive an alarm — but a wrong seeded number still reaches a crop, and the amplification factor of a unit-conversion bug in this feature is the whole point of the feature.

**16.10 "Three screens" is a slogan and slogans erode.** The due-feed card, the plant picker, the device picker, the account sheet, the alert toggles and the capture sheet are already modals on top of three screens. In two years the Simple gear will be three tabs and eleven sheets unless somebody defends the line every sprint. **Nothing in this document defends it except this paragraph**, and this paragraph will not be in the room.

**16.11 Type 5 is under-served and vocal.** The read API and the generic webhook are real, but the DIY closed-loop builder wants a **write** API for outputs, custom sensor measures and custom config keys, and gets none of the three in v1 — the first is a real safety question, the second requires widening a hard-coded Influx allowlist that is currently a Flux-injection surface, and the third the firmware physically strips. This is the highest-advocacy, most sceptical segment in the market, they write their own Go apps rather than use anyone's, and they will notice.

**16.12 Type 4 is promised more by the marketing than the firmware can deliver, and this concept does not fix that.** There is no humidifier role, no exhaust-fan role, no AC role; `dehumidifier` doubles as the cooler; the workmodes are mutually exclusive so there is no "cool AND dehumidify". Zweigang's answer is to label the ambiguity honestly rather than paper over it — which is correct, and which also means the app now visibly admits that *"ein Controller für dein ganzes Zelt"* is aspirational. That is a marketing conversation this concept starts and cannot finish.
