# C01 — "Loupe" (die Lupe)

**Philosophy:** One Timeline, pushed to its extreme.
**Author's stance:** this document is written to be attacked. Section 15 attacks it first.

---

## 1. Thesis

**Terp Control has exactly one screen — a single time axis — and the only navigation verb is zoom.**

Everything the product knows is a fact about a moment: a temperature sample, a socket switching on, a
camera frame, a setpoint change, a watering, a stage transition, an alarm. Today those facts are scattered
across a charts page, a diary page, a grow report, a device overview and a log stream, each with its own
time window, its own filters and its own idea of what "now" means. Loupe deletes all of them and replaces
them with one horizontally-zoomable, vertically-stacked timeline whose x-scale every element shares. The
chart *is* the diary. Zooming out from six hours to a whole grow does not navigate anywhere — it changes
the **representation** of the same object, from continuous curves to daily columns to run-over-run bands.
That is the entire information architecture. Rules about the *future* — targets, alarms, schedules, feed
plans, who has access — live in a drawer off the side, because a rule is not a moment.

The name is the mechanic: you do not open pages, you move a magnifier over one continuous record.

## 2. Information architecture

### 2.1 The two-part model

```
        PAST + PRESENT                          FUTURE
   ┌──────────────────────────┐        ┌────────────────────┐
   │      DIE ZEITLEISTE      │◀──────▶│      REGELN        │
```

This maps onto the company's own marketing line — *"Messen. Regeln. Ruhig schlafen."* The timeline is
**Messen**. The drawer is **Regeln**. Nothing else exists.

### 2.3 Navigation model

- **The `ion-menu` (start) becomes the device switcher only.** Devices, plus Konto/Teilen/Abmelden at the
  bottom. No more Diagnostics/Fleet using the `mail` icon.
- **A second `ion-menu side="end"` is the Drawer (Regeln).** On ≥1024 px it is `ion-split-pane`-docked and
  permanently visible. On mobile it is a swipe-from-right / gear-button menu.
- **The zoom bar is the primary navigation control** and it is pinned to the bottom of the timeline —
  thumb reach, ≥44 px targets, five segments. It is not a page switcher. It is a magnification switcher.
- **No tab bar.** A tab bar implies peer destinations; there is one destination.
- **Back button semantics:** the browser back button steps through *zoom/time states*, not pages. Each
  zoom change is a `router.navigate` with `replaceUrl: false`; each pan is `replaceUrl: true` (debounced
  400 ms) so scrubbing does not flood history.

### 2.4 View state = query params (extended, back-compatible)

The URL query string is already the view model, the on-disk format of every `ChartPreset` and the frozen
content of every `ShareLink.query`. Constraint 9 says extend, do not redefine. So:

**Kept verbatim, still parsed:** `measures`, `date`, `dateEnd`, `vpdMode`, `autoUpdate`, `useCustom`,
`timespan`, `interval`, `logs`, `share`.

**Added:**

| Param | Values | Meaning |
| --- | --- | --- |
| `zoom` | `6h` \| `1d` \| `1w` \| `cycle` \| `runs` | the magnification regime |
| `t` | epoch ms | the cursor / window centre |
| `lanes` | csv | superset of `measures`: adds `out:light`, `out:heater`, `ec`, `ph`, `cam`, `events`, `daynight` |
| `plant` | csv of `plant_id` | filter events + stage bands to these plants |
| `axis` | `clock` \| `day` | wall-clock x-axis vs day-of-cycle x-axis (Runs zoom) |
| `band` | `alarm` \| `setpoint` \| `stage` \| `off` | which target band is drawn (one at a time, §4.3) |
| `actor` | csv of `user_id` | club filter: "who did what" |
| `precision` | `0` \| `1` | techie mode |

**Back-compat rule in `applyViewParams`:** if `lanes` is absent, build it from `measures`. If `zoom` is
absent, derive it from `timespan` (`6h→6h`, `1d→1d`, `1w→1w`, `1m|3m|1y|3y→cycle`). If `t` is absent, use
`date`/`dateEnd`. **Every preset and share link in circulation therefore opens on the timeline showing what
it always showed.** The redirect from `/charts` and `/diary` passes the query string through untouched;
`/diary?report=growreport&cycle=<ts>` maps to `?zoom=cycle&t=<ts>`.

### 3.4 Stale / offline / absent — the honest answers

This is P0 gap 5 and the #1 complaint across all five consumer brands. Loupe's answer is structural, not a
badge:

1. **Liveness chip, header right.** Three states off `Device.lastseen` and the newest Influx sample:
   `● Live` (< 60 s, `--tc-text-success`), `◐ vor 7 Min` (60 s – `ONLINE_TIMEOUT` 10 min, warning),
   `○ Offline seit 14:20` (> 10 min, muted). Tap → a sheet with last sample, last MQTT contact, uptime.
2. **The timeline draws the gap.** No sample means no pixel. Every lane physically stops where the data
   stopped. The region between the last sample and *now* is filled with a 45° hatch in `--tc-surface-subtle`
   and labelled **"Keine Daten"**. A grower does not read a badge; they see a hole. Nothing is ever
   extrapolated or carried forward, and no lane ever draws a line across a gap larger than 3× the sample
   interval.
3. **The scrub header greys out** when the cursor sits inside a gap: values become `—`, target values stay.
4. **Absent data** (a device claimed 20 seconds ago): lanes render as empty framed axes with the
   `timeline.empty` copy. Never a full-page spinner, never a skeleton that looks like data.
5. **Absent capability**: a lane the hardware cannot produce is **not rendered at all**. No CO₂ upgrade →
   no CO₂ lane, no CO₂ target, no CO₂ alarm preset. This replaces `deviceControlCapability()`'s
   three-bucket fail-open model (P0 gap 3) with lane-level truth derived from `hardwareInfo.sockets` +
   observed Influx fields; **absent `hardwareInfo.sockets` now fails CLOSED to monitoring**.
6. **Present but unactionable**: a measure with a sensor but no actuator (humidity with no dehumidifier
   socket) draws its lane normally and its band **in grey with the label `nur Beobachtung`**. The user is
   never nagged about a deviation they cannot fix, and the grow-assistant humidity warning is suppressed.

## 4. The chart overhaul

### 4.1 Library and engineering primitive

**Apache ECharts 6, tree-shaken, with a hand-rolled ~50-line Angular directive.** Reasons, in the order
that decides it: (a) Highcharts Stock is proprietary, needs a quote-only SaaS licence for a public
`/demo`, and cannot be redistributed under the "quelloffen" claim on terpcontrol.com — buying seats does
not cure redistribution; (b) `grid[]` + `axisPointer.link` + `markArea`/`markLine` + `dataZoom:'inside'` +
`sampling:'minmax'` are exactly the primitives this design needs, as configuration rather than plugins;
(c) 148 ms / 17 MB peak vs Highcharts 10.3.3's 416 ms / 97 MB on the 166 k-point benchmark, which is the
whole game on a mid-range Android in a tent.

**Be honest about the cost:** tree-shaken ECharts is **195.6 KB gz vs Highstock's 132.7 KB gz**. The
migration makes the bundle *bigger*. 68.8 KB of that is repaid by deleting the entirely unused
`chart.js` / `ng2-charts` / `chartjs-adapter-luxon` stack from `charts.page.ts`, `charts.module.ts`,
`diary.module.ts` and `diagnostics.*`. Do not sell the migration on size; sell it on licence and memory.

**And carry the warning forward:** Highstock's implicit `dataGrouping` — configured nowhere — is currently
the only thing keeping a 4,320-point render cheap. Switching libraries silently removes that safety net.
`sampling: 'minmax'` on every value series is therefore **not polish, it is the replacement for a
load-bearing default nobody knew was there.**

**The primitive that makes the fusion possible: a shared `TimeScale`.**

```ts
// webapp/src/app/device/timeline/time-scale.ts
export class TimeScale {
  constructor(public from: number, public to: number, public pxWidth: number, public pxLeft: number) {}
  x(t: number): number;      // epoch ms -> px within the timeline column
  t(x: number): number;      // px -> epoch ms
  bucketMs(): number;        // the current aggregation window
  readonly changes: Observable<TimeScale>;
}
```

One `TimeScale` instance per timeline, injected into: the single ECharts instance (as its `dataZoom`
source of truth), the day/night lane (DOM), the output state lane (DOM), the film strip (DOM), and the
event rail (DOM). Canvas and DOM stay aligned because they read the same `x(t)`; ECharts' `dataZoom`
events feed back into it. The chart's `grid.left`/`grid.right` are **fixed pixel values**, not `'10%'`, so
the DOM lanes can use the identical inset. This is the single most important implementation detail in the
concept and the first thing a critic should test.

### 4.2 Panels (lanes) and axes

**Small multiples, one shared x-axis, one linked crosshair.** Adopted wholesale (§7.2 #1). The current
design — up to 15 measures on 15 independent hidden y-axes, all as `type:'area', fillOpacity:0.1,
threshold:null`, with axis labels suppressed below 320 px — is indefensible. Stephen Few, verbatim: *"When
lines are associated with different quantitative scales, their intersection means nothing."* Terp renders
fifteen such scales at once, as translucent fills, with the axes programmatically hidden on a phone.

Rules:

- One unit per lane. Two units on one lane only when physically coupled and only two: `temperature +
  leaf_temperature`, or `temperature + humidity` when the user explicitly enables "koppeln".
- ~104 px per lane on mobile, ~140 px on desktop. 3–4 lanes visible without scrolling.
- **Axis labels are never hidden.** Below 360 px they reduce to **three ticks** (min, mid, max) and the
  unit moves into the lane title (`Temperatur °C`). An axis-less chart is not a chart.
- `sampling:'minmax'` on the plot, LTTB only for the (desktop-only) navigator.
- **Min/max envelope on the primary measure**: `aggregateWindow` already supports `min`/`max`, so a single
  extra query per lane buys a shaded envelope behind the mean line. A lone mean line is a lie about a
  bang-bang controller. Backend: one combined `{mean,min,max}` response instead of 3× round trips.

### 4.3 Goal vs actual — the highest-leverage change in the product

Setpoints, alarm thresholds and per-stage `vpdRange` all already exist client-side. Nothing draws them.
Loupe draws all three, **one at a time, labelled, with an explicit priority** (`band` query param):

| `band` | Source | Rendering |
| --- | --- | --- |
| `alarm` | `Alarm.upperThreshold` / `lowerThreshold` for that `sensorType` | **hard edges**, 1 px solid `--tc-text-danger` at 45 % — the user's own declared acceptable |
| `setpoint` (default) | `day.temperature`/`night.temperature`, `day.humidity`/`night.humidity`, `co2.target` ± tolerance | soft filled band, lane hue at 12 %, plus a **dashed stepped setpoint line** that steps at `daynight.day`/`daynight.night` |
| `stage` | `GROW_STAGE_PRESETS[...].vpdRange` | advisory band, dotted outline, no fill, only on the VPD lane |
| `off` | — | nothing |

**Deviation fill, not area fill.** The fill is between *actual* and *setpoint*, signed:
`#D55E00` @ 22 % when above, `#0072B2` @ 22 % when below, nothing when inside the band. Never fill to the
axis — `threshold: null` encodes nothing and today's `fillOpacity: 0.1` almost certainly fails WCAG 2.2 SC
1.4.11's 3:1 non-text contrast requirement.

**The moving VPD band.** The `stage` band **changes along the x-axis** as `PlantStage` rows advance
(seedling 0.4–0.8 → veg 0.8–1.1 → flower 1.2–1.5 → late flower 1.3–1.6). That is a stepped `markArea`,
free to draw, and it is the one chart in this market nobody verifiably ships. **The leaf-temperature offset
is printed on the lane itself** — `VPD kPa · Blatt = Luft − 2,0 °C` — because VPD is entirely an artefact
of that assumption; when a real MLX90632 exists the label reads `Blatt gemessen`.

### 4.4 Day/night shading

Promoted to **its own 16 px lane at the very top**, because in a fused timeline the photoperiod is the
master rhythm everything else is read against.

- Derived from measured `out_light > 0` where available; falls back to the `daynight.day`/`daynight.night`
  schedule when `out_light` is absent.
- `lights.sunrise`/`lights.sunset` render as gradient ramps at the band edges.
- **Explicit timezone**, named in the lane tooltip. `daynight` is seconds-of-day **UTC**; a 12/12 flip near
  a DST boundary otherwise drifts an hour and generates bug reports.
- **A failed contactor shows as a missing band** while the schedule ghost stays drawn behind it — a
  diagnostic, not decoration. This is a feature that light-only and old-plug owners have never had from
  anyone.

### 4.5 Annotations — the event rail

An annotation rail **under the lanes**, never columns inside the plot. Today's three `column` series of
constant height 1 on hidden 0..1 axes, readable only by hovering, are unusable on a mobile-first product.

- **Exactly two rows**, 22 px each. Row 1 = `👤` human (`GrowEvent`). Row 2 = `🤖` machine (`DeviceLog`).
- Pixel-proximity clustering at 10 px bins with a count badge (`💧3`). Severity ranks which glyph wins a
  cluster.
- **Spans, not just points.** An alarm renders as a bracket `▲▬▬▬▬▬` whose length *is* its duration —
  Mean Kinetic Temperature's lesson: excursions must be reported as duration, not as a count of alarms. A
  drying period, a 3-day dry-back and an mp4 timelapse are all spans (`GrowEvent.at_end`,
  `Image.timestampEnd`).
- **Full-height dashed vertical lines** for stage changes and for the detected 12/12 flip, labelled at the
  top.
- **Optional full-height whisper ticks** for human actions (1 px, 12 % opacity, across *all* lanes) behind
  a toggle `Aktionen zeigen`. This is the fusion payoff in one gesture: turn it on and you see the humidity
  bump three hours after every watering.
- Category filter chips reuse the existing `collectLogCategories` / `matchesLogCategory` /
  `filterLogsByCategory` helpers from `LogEntryViewerModule`.
- Tap an event → a sheet, never a hover. Tap a cluster → a list sheet.

### 4.6 The outputs lane

A **state-timeline**, Grafana's state-regions model: one thin row per *paired* role, region length =
duration, `null` renders as a gap, not as zero. Rows exist only for roles present in
`hardwareInfo.sockets`, plus `out_light` (the one physical PWM output) which renders as a **height-mapped
band** (0–100 %) rather than binary, because it is dimmable.

The `dehumidifier`-doubles-as-cooler ambiguity is named rather than hidden: in `temp`/`breed` workmode the
row is labelled `Entfeuchter / Kühler` with a `ⓘ` explaining that one socket serves both meanings. Lying
about it is worse.

### 4.7 The camera film strip

**A film strip that is an axis** (§7.2 #9). Thumbnails positioned by timestamp on the shared `TimeScale`,
so uneven capture intervals read honestly as gaps. One cursor with the chart: scrubbing the chart moves the
highlighted frame; scrubbing the strip moves the chart crosshair.

- **Delivery (v1.1): one sprite + JSON index per window.** `GET /image/strip/:device_id?from&to&cols=N`
  → a single JPEG sprite of 256×160 tiles (≤ 50 tiles under a 15-minute window, ≤ 100 above) plus
  `GET /image/strip/index/:device_id?from&to` → `[{t, col}]`. Mux's storyboard pattern. **v1.0 ships
  without it**: at most 12 thumbnails per window fetched by the existing
  `GET /image/:device_id?timestamp=` endpoint. This keeps a backend endpoint off the launch critical path.
- mp4 timelapses (`Image.timestampEnd`) render as a **bracket** under the strip, not a point. Tap plays
  inline in the lane.
- **Diary photos and webcam stills share the lane**: user photos sit *above* the centre line with a 2 px
  border in the plant's colour; webcam stills sit below. One lane, two origins, visually distinct.

### 4.8 Mobile touch interaction

| Gesture | Effect |
| --- | --- |
| one finger vertical | page scroll (never zoom) |
| one finger horizontal on a lane | pan time |
| two fingers | pinch-zoom time (`dataZoom: {type:'inside', zoomOnMouseWheel:false, moveOnMouseMove:true}`) |
| tap | place the crosshair; scrub header updates |
| long-press + drag | fine scrub with a 1 px cursor |
| tap the zoom bar | change regime |
| long-press the zoom bar | **Präzision** — exact from/to, interval, method, table view, CSV |
| double-tap a lane | solo that lane (full height) |

## 5. The multi-plant diary

### 5.1 The hard invariant, first

> **A user who does not care about plants never sees the word "Pflanze".**

Every event's `plant_ids` defaults to `[]`, which means "the room". The plant chip row is **not rendered
when the device has zero plants**. The capture sheet shows no plant selector. The stage bands lane does
not exist. `Drawer › Pflanzen` exists but shows an empty state. Types 1, 3 and 7 can use this product for
a year and never encounter the plant model. Multi-plant is **opt-in by creation**, and nothing in the
product ever prompts for it except the single onboarding question in §10.

### 5.2 Entities (all MongoDB, cloud-side, keyed by `device_id`)

`device.configuration` cannot carry new keys — the firmware strips unknown keys when echoing config back.
So all of this is server-side, all fields optional, with read-time normalisers and idempotent boot-time
backfills, per the house migration style.

```ts
// collection: plants
interface Plant {
  plant_id: string;                 // nanoid — the stable identity that fixes the forking bug
  device_id: string;                // home device
  owner_id: string;
  name: string;                     // renameable, freely
  strain?: string;                  // free text. No SeedFinder — its API has been dead since 2024-07.
  source?: 'seed' | 'clone' | 'unknown';
  mother_plant_id?: string;
  started_at: number;               // epoch ms — day 1 of the day counter
  archived_at?: number;             // set on harvest; NEVER deleted
  colour: string;                   // from an 8-entry Okabe-Ito-derived palette; the plant's identity everywhere
  emoji?: string;                   // optional, low-effort identity
  position?: string;                // "hinten links" — free text. No coordinates, no map.
  potLitres?: number;
  medium?: 'soil' | 'coco' | 'hydro' | 'other';
  createdAt: number; updatedAt: number;
}

// collection: plant_stages — APPEND-ONLY. A re-veg is simply another row.
interface PlantStage {
  stage_id: string; plant_id: string; device_id: string;
  stage: DiaryLifecycleStage | 'harvest';   // 'harvest' added to the shared union (cloud-only, diary-only)
  started_at: number;
  note?: string; actor_id?: string;
  createdAt: number;
}

// collection: events — the ONE new event collection. DeviceLog is NOT touched.
interface GrowEvent {
  event_id: string; device_id: string;
  plant_ids: string[];              // [] = the room. THE multi-plant hinge, and the anti-tax mechanism.
  kind: 'water'|'feed'|'measure'|'train'|'pest'|'photo'|'note'|'transplant'|'harvest'|'stage'|'task';

  feed?: {
    plan_id?: string; run_id?: string; step_index?: number;
    batchLitres?: number;
    doses: { productName: string; mlPerL?: number; gPerL?: number; ml?: number; g?: number }[];
    ecTarget?: [number, number]; phTarget?: [number, number];
  };
  readings?: {
    ph?: number;
    ec?: number;                    // ALWAYS mS/cm. Canonical.

// collection: week_rollups — "that table IS the export"
interface WeekRollup {
  rollup_id: string; device_id: string; plant_id?: string;

  dayFrom: number; dayTo: number;   // Grow-with-Jane-style day counter — BOTH, so no export is lossy
  from: number; to: number;
```

`DayRollup` is the same shape at day granularity, and is what the Day Sheet reads.

### 5.3 Why a new collection instead of extending `DeviceLog`

`DeviceLog` is one collection holding boot messages, MQTT errors, alarm transitions, recipe steps, config
diffs *and* diary entries, discriminated by a string prefix in `categories[0]`, with `deleted: true`
meaning "visible in the diary", `Schema.Types.Mixed` data with zero validation, and no server-side
pagination. A per-plant diary cannot be layered onto it. **`DeviceLog` stays exactly as it is** and keeps
feeding **row 2 (machine)** of the event rail. `GrowEvent` feeds **row 1 (human)**. Two sources, two rows,
one x-axis — which is precisely §7.2 #5's recommendation, arrived at for a second, independent reason.

Consequence: the `deleted`-does-not-mean-deleted trap and the invisible server-written stage entries
(P0 gaps 6 and 7) still have to be fixed, but they no longer sit under the product's centrepiece.

### 5.4 Backfill

`convertEventsToGrowCycles()` (currently a 57-line runtime algorithm in the browser that forks history on
rename) becomes a **one-time, idempotent, boot-time migration** in the events service constructor:

1. For each device, read `diary-plant-lifecycle` + legacy `plant-lifecycle` rows in time order.
2. Apply the existing cycle-boundary heuristic (stage ordinal rollback, or trimmed `lifecycleName`
   change) **once**, and materialise one `Plant` per detected cycle (`name = lifecycleName || 'My Strain'`,
   `started_at` = first row time, `archived_at` = last row time if a later cycle exists).
3. Emit `PlantStage` rows.
4. Convert every `diary-*` row to a `GrowEvent` with `legacy_log_id` set; the unique sparse index makes
   re-running a no-op.
5. Old `?cycle=<startTimestamp>` share links resolve via a `legacy_cycle_start` field on `Plant`.

The heuristic runs once, on data that already exists, and never again. Renaming after the migration cannot
fork anything, because identity is `plant_id`.

### 5.5 Creating a plant, re-veg, clone, rename

- **Create**: `Drawer › Pflanzen › + Pflanze`. Two required fields — name and start date (defaulting to
  today). Colour is auto-assigned. Everything else optional. Or: in the capture sheet, if the user taps the
  plant selector and no plants exist, an inline "+ neue Pflanze" row creates one from a name alone.
- **Rename**: edit `Plant.name`. History does not fork. A `GrowEvent{kind:'note', source:'device'}` records
  `„Blue Dream #1" → „BD Pheno A"` so the rename is itself on the timeline.
- **Re-veg**: append `PlantStage{stage:'vegetative'}` after a `flowering` row. The stage band draws a second
  vegetative segment. **No new plant, no new cycle.** This is the case that currently fabricates a phantom
  plant.
- **Clone**: new `Plant` with `source:'clone'` and `mother_plant_id`. At Runs zoom a clone's band draws a
  1 px connector back to its mother's band (v1.1).
- **Harvest**: `PlantStage{stage:'harvest'}` + `GrowEvent{kind:'harvest'}` + `Plant.archived_at`. Weights
  are §8-gated. A harvest without weights is still a first-class, dated, photographed event — which is what
  makes "how did this grow do?" answerable at all.

### 5.6 Attaching events to plants

The plant chip row sits directly above the event rail and is a filter *and* a default:

```
 Pflanzen:  [● BD #1] [● BD #2] [○ Auto #3] [ Raum ]
```

Selected chips (a) filter the event rail and stage bands and (b) become the **default `plant_ids` for the
next captured event**. So a user who is currently working on BD #1 taps its chip once, and every subsequent
watering attaches to it with zero extra taps. The `Raum` chip clears to `[]`.

### 6.3 What is stored, and the two facts everyone gets wrong

- **EC is canonical in mS/cm.** A bare "ppm" number is never stored and never rendered. If the user enters
  ppm they must pick their meter scale (500 / 640 / 700); at EC 1.8 a Bluelab reads 1260 and a Hanna reads
  900 for the same liquid, and this is repeatedly cited as the #1 cause of accidental over- and
  under-feeding.
- **`FeedPlan.ecBasis: 'absolute' | 'delta_over_source'`.** CANNA publishes **EC+**, verbatim: *"Add the EC
  of the tap water that is used to the recommended EC."* A UI that alarms against the raw chart number is
  actively wrong. When `delta_over_source`, the sheet prints both numbers (see the mock above) and the EC
  target band on the chart is drawn at source + plan.
- **`readings.where`** is mandatory for any EC/pH entry — `input` / `runoff` / `reservoir` / `soil`. Today
  the app stores three bare numbers with no notion of what was measured. A runoff EC of 2.4 and an input EC
  of 2.4 mean opposite things.

### 6.4 Model

```ts
interface FeedPlan {
  plan_id: string; owner_id?: string;         // null owner = library plan
  name: string; origin: 'terp' | 'user' | 'library';
  medium?: 'soil'|'coco'|'hydro'|'other';
  strength?: 'light'|'medium'|'heavy';
  waterBasis: 'any'|'tap'|'ro'; sourceEc?: number;
  ecBasis: 'absolute' | 'delta_over_source';
  steps: FeedStep[];
  library?: { source_url: string; retrieved_at: number; chart_version: string;
              kind: 'official_pdf'|'official_calculator'|'manual_transcription';
              takedown_contact: string };
}
interface FeedStep {
  index: number;
  anchor: 'abs_week' | 'veg_week' | 'flower_week' | 'event';   // the four incompatible time schemes
  anchorValue: number;
  label?: string;
  doses: { productName: string; mlPerL?: number; gPerL?: number;
           range?: [number, number]; literal?: string; note?: string }[];  // a dose is NOT a scalar
  ecTarget?: [number, number];
  phTarget?: [number, number];
  phTargetByMedium?: Record<string, [number, number]>;
  flush?: 'preharvest' | 'corrective' | 'leach';               // three different meanings, never conflated
}
interface FeedPlanRun {
  run_id: string; device_id: string; plan_id: string; plant_ids: string[];
  startedAt: number; flipAt?: number;
  currentStepIndex: number;          // advanced by FEED EVENTS, not wall clock — growers feed Tue/Fri and slip
  batchLitres: number;               // batch volume, not reservoir size: serves a 10 L can and a 100 L DWC alike
  strengthMultiplier: number;        // 0.25–0.5 for autoflowers — no manufacturer chart has an auto column
}
```

`doses[].literal` exists because real charts contain `"water"`, `"Flush only"`, `"Use as pH up"` and
`"1-2× a week"`. `range` exists because they contain `5–13` and `"12–18"`. `flush` is a three-valued enum
because pre-harvest flush, corrective flush and routine leaching are different acts — and the flush step is
labelled **"Dein Plan sieht das vor"** / **"Your chosen plan calls for this"**, never "this is necessary",
because the Rx Green Technologies 2019 trial found no significant difference in terpenes, THC, yield or
minerals and the taste panel statistically preferred un-flushed samples.

### 6.5 What only Terp Control can do

The chart data is a commodity; every brand ships its own calculator. **None of them can see the grow.**

- **Auto-detect the 18/6 → 12/12 flip from `out_light` history** and offer to place the run on flower week 1:
  a full-height dashed line labelled `12/12`, plus a proposal card at that x-position —
  `Lichtwechsel erkannt am 12.03. — Blütewoche 1 starten?` / `Light flip detected on 12 Mar — start flower
  week 1?` with `Ja` / `Nein`. Proposed, never asserted.
- **Move the EC/pH target bands as the run advances** instead of setting them once. This is the strongest
  argument for the feature living in a *controller* rather than a standalone app.
- **Runoff-vs-input EC divergence > 20 %** → a device event on rail row 2.

### 6.6 How it is drawn

- A watering is `💧` on rail row 1, sized by cluster count.
- A feed is `🧪`; if it carried EC/pH readings it grows a 1 px **stem** into the EC & pH lane.
- **EC & pH is a lane like any other** — sparse: discrete points on a thin dashed connector, with the
  plan's target band drawn behind it by **the same code path as the temperature setpoint band**. One
  mechanism, two uses. That is the answer to "it should also be visualized in the graph."
- With `Aktionen zeigen` on, every watering draws a 1 px 12 %-opacity tick across all lanes, so the
  humidity response to a watering is directly legible.

### 6.7 Brand posture

**v1 ships zero brand charts.** The engine is brand-agnostic and user-editable first, because that is the
durable asset and it carries zero IP risk. It is seeded with **ownerless** plans authored by Terp Control:

1. Lucas Formula (0-5-10 and 0-8-16)
2. Jack's 321
3. Generic EC ladder — Erde / soil
4. Generic EC ladder — Coco
5. Generic EC ladder — Hydro / DWC

Plus **`Plan importieren`**: the user types their own numbers from their own bottle's chart, in a grid that
takes the four anchor schemes and nine unit systems. Plus a **`Hersteller-Rechner`** list that *links* to
each brand's own calculator and reproduces nothing — FeedSchedules.com's posture, verbatim: *"We link
directly to each brand's official source… We don't reproduce the charts themselves."*

If brand charts ever ship, they ship as `feed_plan_library` — a separate, versioned, hot-swappable MongoDB
collection, **never baked into the webapp bundle**, so any single brand is removable in one DB update.
Every entry carries `source_url`, `retrieved_at`, `chart_version`, `kind` and `takedown_contact`, and the
"zuletzt geprüft am" line is shown to the user as a *feature* — protection against the ~3× transcription
divergences found in the wild (hyjo.co.uk 30–50 ml/10 L vs veridiangrow.com 10–30 for the same CANNA Terra
step). Word marks only: no logos, no brand colours, no bottle photography, no "CANNA-Modus" feature name —
that would move referential use into trademark use and forfeit the Art. 14(1)(c) EUTMR defence. Never copy
brand prose; paraphrase every description. Publish a takedown address and a notice-and-action policy
**before** shipping any brand entry. And this is the one place where German IP counsel on UWG § 4 Nr. 3 and
UrhG §§ 87a–87e is worth a couple of hours *before*, not after.

A liability line sits under every computed dose, in Terp Control's own words, never CANNA's:
`Richtwerte. Zelt, Sorte und Substrat entscheiden. Niedrig anfangen und nachmessen.` /
`Guide values. Your tent, strain and substrate decide. Start low and measure.`

## 7. Camera & timelapse

**Images relate to time by their timestamp on the shared `TimeScale` — that is the whole relationship.**

- **To plants:** transitively. A webcam still has no plant, because one camera sees the whole tent. A
  *user* photo taken from the capture sheet is a `GrowEvent{kind:'photo'}` and inherits the selected
  `plant_ids`, so it shows a coloured border and filters with the plant chips. This finally gives `Image` a
  back-reference (it currently has none), which means deleting the event deletes the images and closes the
  leak where `DELETE /image/:image_id` exists and is never called.
- **To stages:** transitively, via `PlantStage.started_at` ranges. `Timelapse dieser Phase` is just a
  `from`/`to` pair, so a per-stage timelapse needs no new relationship, only a render job. **v1 ships the
  existing 1d/1w/1m mp4s as brackets on the strip; per-stage timelapses land in v1.1** when the render job
  is generalised past its three fixed durations.
- **Cycle zoom picks one frame per day**, the still nearest local solar noon *while the light is on*, so a
  90-day scroll is a legible growth sequence rather than a strobe of light and dark frames.
- **The camera is never a separate page.** The current "hover a point for 500 ms to load a still, and when
  no measure is enabled swap to an mp4" behaviour is replaced by: the strip is always there, the cursor
  always selects a frame, and tapping a frame opens it full-screen in the existing
  `app-image-viewer-modal`.
- `Image` blobs still live inside MongoDB with a 16 MB BSON ceiling and `express-fileupload` mounted with
  no size limit. **Cap uploads at 8 MB with a real error message** — this is a launch-blocking one-liner,
  not a redesign.

## 8. Multi-user / clubs

### 8.1 Model

```ts
interface DeviceMembership {
  membership_id: string; device_id: string; user_id: string;
  role: 'owner' | 'operator' | 'member' | 'viewer';
  createdAt: number; invitedBy: string; acceptedAt?: number;
}
interface DeviceInvite {
  invite_id: string; device_id: string; code: string;      // 8 chars, single use
  role: 'operator'|'member'|'viewer'; expiresAt: number; usedBy?: string;
}
```

| Role | Timeline | Events | Targets/alarms | Access | Delete device |
| --- | --- | --- | --- | --- | --- |
| `owner` | read | all | yes | yes | yes |
| `operator` | read | all | yes | no | no |
| `member` (`:self`) | read | **own only** — create, edit, delete | no | no | no |
| `viewer` | read | none | no | no | no |

The `:self` tier is copied from Cannanas' `charges:create:self` / `member:journals:self-checkin` pattern: a
member logs their own work, sees the room, changes nothing. **This is the one legally-motivated multi-user
feature a grow controller can credibly own** — § 17 Abs. 2 KCanG requires members to participate
*eigenhändig*, which is why every club platform ships a participation journal.

**Invitation is by code, not email.** No account-lookup-by-email endpoint is built, because it does not
exist today and designing one against enumeration abuse is a project. The owner generates a code with a
role and an expiry; the invitee pastes it — the same mental model as claiming a device.

**Auth rewrite:** `auth.middleware.ts:172` and `:207` become membership lookups with an `owner_id`
fallback normaliser, plus loosening ~10 owner-scoped service queries. An idempotent boot-time backfill
writes one `owner` membership per existing device. This cannot be bolted on as a flag, which is why it is
**v1.1**, not v1.

### 8.2 Attribution on the timeline

`GrowEvent.actor_id`. On the rail, an event carries a 16 px initial-avatar **only when the device has more
than one member**. A solo grower never sees attribution and is never taxed by it.

The club payoff is the `actor` query param: filter the rail to one member, and the day columns at Cycle
zoom show the initials of everyone who touched the room that day.

```
 👤  │ CG │    │ MK │    │    │ CG │ MK │
```

That is the owner's question — *"Who did what? How did the plants react?"* — answered in one view, because
the environment lanes sit directly above the action row. No other product in this market can draw that
picture, because no other product owns both halves.

### 8.3 Privacy posture

`Device.privacyMode: 'private' | 'club'`, a Mongo field on the device document (not `device.configuration`).
**`private` is the default**, and the default is the privacy-maximal one.

| | `private` (default) | `club` |
| --- | --- | --- |
| Attribution | stored, rendered only to members | rendered everywhere |
| Harvest weights | **never prompted**; fields hidden | prompted, opt-in per event |
| Telemetry retention | raw 90 days → 5-min rollups 12 months → daily rollups forever | raw 12 months, then rollups |
| Participation tasks | off | on (`kind:'task'`, `regulatory_relevance` flag) |
| Export | on, anonymised by default | on, `NONE / PSEUDONYMISIERT / ANONYMISIERT`, default anonymised |
| One-tap wipe | **yes** — `Drawer › Konto › Alles löschen`, which actually deletes events, images and the Influx range | yes |

**Refused, permanently:** per-member consumption or dispensing records; member identity beyond a display
name (no DOB, no address, no membership number); payments, credits, quotas, POS; real-name enforcement;
location of any kind (no GPS, no IP-geolocation persistence, no persisted timezone-from-IP); a public feed
with real identities; an undeletable audit log for the account owner; analytics or ad SDKs; hosting outside
the EU; and any `KCanG-konform` badge or compliance warranty. § 28 Abs. 2 KCanG lets German authorities
seize digital data with **no prior judicial approval**, and § 26 Abs. 5 contains an explicit nemo-tenetur
carve-out — the legislator itself flagged the documentation duty as a self-incrimination hazard.
Tamper-evidence protects a *regulated* club against its own staff; it *victimises* an unregulated grower.
Immutability is opt-in and club-scoped, never global.

**Terp Control does not become a club's system of record.** ~20 compliance SaaS products already serve that
at €0.50–1.00/member/month, and winning it would mean owning 23 differing authority export formats,
5-year retention, an Art. 28 AVV with every club and liability for wrong exports. Instead Terp Control is
the **device-attested environmental layer those systems consume** — Cannanas' `CreateDiaryRequest.
measurements` has 40 numeric fields that read like a controller telemetry dump, its zones carry
`streams.video[].url` which the webcam fills directly, and **it has no sensor-ingestion endpoint. That path
is private and unclaimed.** P3, business development, not a sprint.

## 10. Onboarding

**Zero questions to see data. One question to be configured.**

1. **Claim.** Unchanged flow (claim code), on `/list`. **Prerequisite fix:** `POST /device/claimcode` is
   unauthenticated for any device that has not reported `hardwareInfo.claimcode_auth === 'on'`, and
   `claimDevice` overwrites `owner_id` with no check and no notification. Knowing a `device_id` — which
   appears in every webapp URL — is enough to steal a device. This concept surfaces device ids in share
   links and invite flows, so **this is a launch blocker, not a nice-to-have.**

2. **Straight to the timeline.** No wizard modal in front of it. The screen is honest and empty:
   *"Noch keine Messwerte. Der Controller sendet alle 5 Sekunden."* The first sample lands within seconds
   and the first lane draws itself. **The first thing a new owner sees is their own data appearing.**

3. **Capability is established by observation, not interrogation.** Over the first minutes the device
   reports `hardwareInfo.sockets` and Influx starts carrying fields. Lanes appear as evidence arrives. Each
   detection posts a machine event on rail row 2:
   `Steckdose erkannt: Heizung` / `Socket detected: heater`. The user confirms nothing, answers nothing,
   and can watch their tent assemble itself on screen. When `hardwareInfo.sockets` is absent (old firmware)
   the app **fails closed to monitoring** and says so once.

4. **One question, and only one, and only after data exists.** A non-blocking card slides into the timeline
   at `now`:

   ```
   ┌──────────────────────────────────────────┐
   │  Was wächst da?                          │
   │  [ Nur beobachten ]  [ Ich steuere ]     │
   │                             Später       │
   └──────────────────────────────────────────┘
   ```

   `Nur beobachten` / `Just monitoring` → `cloudSettings.intent = 'monitor'`: no target bands, no stage
   picker, no plants, no grow assistant, never asked again. `Ich steuere` / `I'm controlling it` → the
   `stage-preset-picker` (which already exists, already carries a VPD band, and is already good) appears
   inline in `Drawer › Ziele`, pre-scrolled. `Später` dismisses for 7 days.

5. **The existing 289-line `setup-wizard` is retained but demoted** to `Drawer › Geräte › Einrichtung
   wiederholen` — which also fixes the "barely discoverable, no re-run" gap. And the **30 MB of already-shot
   wizard videos** currently copied into every production build and referenced nowhere (`connect.mp4`,
   `teachin.mp4`, `sockettype_*.mp4`, `overview.mp4`, …) finally become the illustrations inside the socket
   pairing step. Either use them or delete them; shipping them unused is indefensible either way.

**Score:** 0 questions to first data. 1 question to be configured. 2 taps to log a watering. That is the
stoner test, and it is the acceptance criterion.

## 11. Per-user-type walkthrough — the first week

### Type 1 — lazy, monitoring only
Day 1: claims the controller, lands on the timeline, watches temperature draw itself. Taps
`Nur beobachten`. Never sees a plant, a stage, a feed plan or a target band. Day 2: opens the app in bed,
sees `● Live · 24,5 °C · 58 %` in the scrub header and a day's curve underneath — one screen, no taps.
Day 4: the router reboots; the timeline shows a hatched hole and `○ Offline seit 03:12`. He does not have
to work out whether the app is lying. Day 7: taps `Woche`, sees seven day/night cycles and notices the
humidity climbing every night. He sets one alarm from `Drawer › Alarme`. **What he gets that he does not
have today:** he can tell live from stale, and the chart has axes on his phone. **What he does not get:**
much of anything else — see §15.8.

### Type 2 — the same, with a camera
Identical first two days, plus the film strip lane is populated from the first hour. Day 3 he taps `Woche`
and swipes the strip: 168 hours of tent, aligned to the temperature curve above it. Day 5 he taps a
1-week mp4 bracket and it plays inline. Day 7 he taps `Zyklus` and gets one frame per day at solar noon —
a growth sequence, not a strobe. He shares a link to the timeline in a Telegram group; the recipient sees
the frozen window, the film strip and nothing else (webcam toggle honoured). **This is the type the concept
serves best per unit of effort**, because the film-strip-as-an-axis is pure fusion and costs him zero taps.

### Type 3 — controls certain aspects (CO₂ or heating)
Claims; sockets detected; **only a heater is paired.** The temperature lane gets a live band and a dashed
stepped setpoint. The humidity lane gets a **grey** band and the label `nur Beobachtung`. No dehumidifier
row appears in the outputs lane. No humidity deviation warning. No "Dehumidifier running non-stop" alarm
preset in the list. Day 3 he sees the deviation fill go warm every afternoon and drops the day setpoint by
1 °C from `Drawer › Ziele`; the setpoint line steps down on the timeline at that instant and the config
change lands as a machine event with his name on it. **What is fixed:** today he is shown humidity targets,
a humidity deviation warning and a dehumidifier alarm preset he can never act on, because a heater alone
returns capability `'full'`.

### Type 4 — the whole tent
Six sockets paired: heater, dehumidifier, light, secondary light, CO₂. Outputs lane has five rows. He
steers by VPD: the VPD lane's stage band moves as `PlantStage` advances. Day 2 he notices the `Entfeuchter
/ Kühler` label and reads the `ⓘ` — one socket, two meanings, depending on workmode. He is annoyed, but he
was going to be confused by it anyway; now at least the confusion is named. Day 4 he wants "cool AND
dehumidify" and the product cannot do it — **the concept surfaces that limit instead of hiding it**
(`Drawer › Ziele` shows which targets the current workmode actually regulates). Day 6 he turns on
`Aktionen zeigen` and sees the humidity spike after every watering, then correlates it against the
dehumidifier row directly below. **He is the type the marketing promise is written for and the type the
firmware cannot fully express; no cloud-side concept fixes that, and this one says so.**

### Type 5 — closed-loop DIY (the fridge builder)
Claims a controller wired into his own build. Day 1 he long-presses the zoom bar and finds `Präzision`:
exact from/to, interval, `mean|min|max|raw`, `Als Tabelle anzeigen`, and **CSV export of the visible window
including actuator state** — which no vendor in this market provides and an AC Infinity 4★ reviewer asked
for by name. Day 2 he adds a lane by raw Influx field name (anything in `VALID_SENSORS`). Day 3 he finds
the webhook editor in `Drawer › Alarme` and points it at his own ntfy instance. Day 5 he asks for a write
API and finds `Drawer › Konto › API` — which in v1 is an honest "kommt" page with the read endpoints and
the documented cloud-outage behaviour, and in v2 is an `x-api-key`, per-grow, quota-metered API modelled on
Pulse's shape. **He is the most sceptical, highest-advocacy segment and the product currently has nothing
for him; Präzision + CSV is the cheapest meaningful down-payment.**

### Type 6 — the club (shared controllers)
Owner claims; invites three members with `member` codes from `Drawer › Zugriff`. Each member installs
nothing (it is a web app), pastes a code, and sees the same timeline. Day 2, member MK waters and feeds;
her initials appear on rail row 1. Day 3 the owner filters `actor=MK` and sees exactly what she did and
what the room did in response — the environment lanes are directly above her actions. Day 5 he switches
`privacyMode` to `club`, which turns on participation tasks (`✅ Aufgabe`, § 17 Abs. 2 *eigenhändig*) and
the anonymised date-range export. Day 7 he exports a week; the file contains room climate, setpoints,
actuator state, tasks and pseudonymous actor ids — and **no member identity, no dispensing, no grams**,
because Terp Control refuses to be the § 26 system of record. **This concept's single best fit** — the
fused timeline is literally the answer to "who did what, and how did the plants react?". It is also, per
§13, v1.1 and not v1.

### Type 7 — old devices (fan, light, plug)
Opens the app on a light and sees a real light page for the first time: a day/night lane driven by his
schedule, a PWM lane, and a ghost band that would reveal a failed contactor. He is not asked about plants,
stages, feeding or clubs. His device stops being called something it is not. Two of his settings checkboxes
stop rendering raw i18n keys. Nothing he had is taken away except the six-button overview screen, which is
replaced by a header and a drawer. **He is explicitly not the focus and explicitly not broken.**

## 12. Stoner / normal / techie

One design, three depths, and the depths are **layered, not moded** — there is no "advanced mode" toggle
that hides the product from itself.

**Stoner (the default surface).**
- One screen. Five zoom buttons. One FAB.
- The scrub header answers "is it OK right now" in three numbers with their targets underneath. Colour and
  shape carry the verdict: inside the band = no fill; outside = a coloured wedge.
- Two taps to log a watering. Zero typing anywhere except a plant name.
- **No confirmation dialogs.** Every destructive action is an immediate action plus a 6-second
  `Rückgängig`. A native `confirm('You have unsaved changes…')` currently exists in the diary modal; it
  dies.
- Copy is short, concrete and past tense: `Gegossen ✓ 14:32`, not `Bewässerungsereignis gespeichert`.
- Nothing on the default surface can break the grow. Targets are one drawer away, behind the existing
  `rangeGuard` directive (a slider is inert until its row is tapped, and disarms 8 s after the last
  interaction).

**Normal (discovered by use, not by a switch).**
- Lane collapse/expand and reorder; the `⌄` on each lane title.
- The Day Sheet time-in-range scorecard, reached by tapping any day column.
- Plants and plant chips, created when they are wanted.
- Feed plans and the step-by-step mixing sheet.
- Share links; the weekly digest note that writes itself.

**Techie (behind one long-press and one drawer page — costing the stoner zero pixels).**
- **Präzision** (`?precision=1`): exact from/to, arbitrary interval with a **clamp** (windows/interval is
  bounded server-side; `3y × 5s` ≈ 18.9 M aggregation windows is currently one dropdown away and the
  `limit(n:50000)` guard is piped *after* `yield()` so it does not bound anything), aggregation method
  including `raw`, per-lane axis min/max override, `Als Tabelle anzeigen`, and a copyable box containing
  the live query string.
- CSV export of the visible window **including actuator state**.
- Lanes by raw field name from `VALID_SENSORS` / `VALID_OUTPUTS`.
- Webhooks, alarms with custom headers and payloads, the API page, firmware channel.
- Reuses the existing `localStorage['app-settings-expert']` flag rather than inventing a second one.

The rule that keeps this coherent: **a techie affordance may never add a control to the default surface.**
It may only add depth behind a long-press, a disclosure triangle, or a drawer page.

## 14. Non-goals

This concept deliberately refuses to:

1. **Have a charts page or a diary page.** Not as a fallback, not as a preference, not for "power users".
2. **Have a dashboard of gauges as the home screen.** The `value-display` SVG gauge — 266 lines, genuinely
   good — is demoted to `Drawer › Ziele` where it belongs (it is a *rule* editor's preview, not a record).
   This is a real loss and §15.5 owns it.
3. **Have a tab bar or a bottom nav.** There is one destination.
4. **Two-way sync with any grow-diary platform.** GrowDiaries has no public API and is Cloudflare-hardened;
   Grow with Jane's ToS §(c)(7) bans scraping and its backend is Firebase; SeedFinder has been dead since
   2024-07-01. The honest feature is export + a shareable link + a post generator. The word "Sync" does not
   appear in this product.
5. **Auto-post to Instagram, Threads, TikTok or Reddit.** A failed Discord post means a revoked webhook. A
   failed Instagram post means the *user* loses their account with no appeal and Terp Control was the
   proximate cause.
6. **Ship a "Powered by Terp Control" footer on user posts.** § 6 KCanG bans cannabis advertising and
   sponsoring with fines to €30,000, read broadly; this is the single riskiest string in the feature.
7. **Build a community feed.** ~200 App Store reviews across TrolMaster and VIVOSUN, both of which ship
   one, contain zero praise for it. It is permanent moderation cost. (A link you can paste anywhere is not
   a feed you must moderate — the public diary URL is v2 and is not this.)
8. **Request any firmware change.** No new socket role, no new sensor field, no new MQTT topic. Everything
   here is cloud-side. If Type 4 needs a humidifier role, that is a separate, costed, firmware-gated
   decision and this concept does not smuggle it in.
9. **Automate watering or dosing.** There is no irrigation hardware. Capture and recall, never control.
10. **Give each plant its own climate.** One tent, one environment. Plants are a *labelling* dimension over
    a shared climate, not a control dimension. The concept can show a grower that their seedling and their
    flowering plant want different things; it cannot give them both.
11. **Be a club's § 26 system of record.** No member ledger, no dispensing, no grams, no identities.
12. **Ship brand feed charts in v1.**
13. **Build a native app or a service worker.** Capacitor is untouched scaffold; there is no `android/` or
    `ios/`; there is no service worker. "Works on the tent floor with bad wifi" is not a claim this concept
    makes.
14. **Ship a `KCanG-konform` badge or any compliance warranty.**

## 15. Honest weaknesses

**15.1 Horizontal time is a hard sell for reading a diary on a phone.** Every diary app in this market is a
vertical feed, because reading a journal is a vertical act. Loupe makes "what did I do in week 3" a
sideways scroll through a 14 px-per-day strip. The Day Sheet mitigates it and the plant chips filter it,
but the friction is real and it is at the centre of the concept, not the edge. **If usability testing shows
growers cannot find their own entries, the premise fails**, and the fallback — a vertical entry list — is
precisely the thing this concept refuses to build. This is the single biggest bet in the document.

**15.2 Semantic zoom is a second chart engine.** Five regimes × N lanes × 5 device types × 3 restricted
modes (share/view-only, demo, public) is a combinatorial surface, and the Cycle-zoom daily-column renderer
shares almost no code with the curve renderer. Against 38 `it()` blocks, a red suite and a CI that never
runs tests, this is a lot of untested branches shipping on a hardware date.

**15.3 One screen, one performance budget.** ECharts canvas + DOM film strip + DOM event rail + DOM output
lanes + a 10-second live refresh all compete on the same frame. Today's app at least degrades page by page:
a slow chart does not slow the diary. Loupe has no such firebreak. On a €150 Android in a tent on two bars
of wifi this is the riskiest screen in the product, and the mitigation (virtualise off-screen lanes, cap
concurrent requests, pause live refresh when the tab is hidden) is engineering discipline that has to hold
under deadline pressure.

**15.4 Canvas/DOM alignment is fragile.** The shared `TimeScale` must survive `dataZoom`, rotation, lane
collapse, font loading and Ionic's own layout passes. Any sub-pixel drift and the thumbnails lie about when
a picture was taken — which is strictly worse than not showing thumbnails at all. The obvious hardening
(render *everything* inside ECharts using `graphic` image elements) trades one fragility for another and
makes the event rail's tap targets and accessibility markedly worse.

**15.5 The gauge dies.** `value-display` is the nicest component in the codebase — value arc, limit arc,
needle, 1-hour average, target line, HSL interpolation, honest `—` for missing data — and existing users
will miss the at-a-glance dial on the device card. The scrub header is strictly more informative and
strictly less pleasant. Some users will read this as a downgrade, and they will not be wrong about the
feeling.

**15.6 Share links get much harder.** Today a `ShareLink.query` is `measures=temperature,humidity&
timespan=1d`. Under Loupe it can encode a zoom regime, a lane set, a plant filter, an actor filter, a band
choice and an axis mode — a far larger back-compat surface, in a ≤2000-character field, that must keep
resolving correctly for years. The translation layer in `applyViewParams` is where this concept will
accumulate its ugliest code.

**15.7 Multi-plant is a label, not a control — and the concept makes that more visible, not less.** A
grower with a seedling and a flowering plant in one tent will see two stage bands with two different VPD
targets and one environment that can only satisfy one of them. Every competitor has the same physical
limitation; this concept is the one that draws it. Expect that to be read as a shortcoming of the product
rather than of physics.

**15.8 The concept is weakest for the most common user.** For Type 1 — the lazy monitoring-only user the
owner listed *first* — Cycle zoom is 90 columns of climate with an empty human row, and the entire fusion
premise (environment × machine × human) has only two of its three terms. He gets a much better chart and an
honest liveness model, which is genuinely valuable, but he does not get the thing that makes this concept
distinctive. Conversely the concept is strongest for **Type 6, clubs**, which the owner did not rank first
and which §13 puts in v1.1. **The concept's peak value and the owner's stated priority are not aligned**,
and no amount of arguing changes that.

**15.9 It bets the launch on one screen with no fallback.** Once `/charts` and `/diary` are redirects,
there is no degraded mode. Keeping the old pages behind a feature flag until the last minute doubles the
maintenance surface through exactly the months when the team has least slack — and a flag that is never
flipped off is a permanent fork.

**15.10 Time-in-range and retention are in direct tension, and the resolution is more work than it looks.**
The scorecard must be computed on raw samples, and the retention policy must delete raw samples. That
forces a nightly `DayRollup` job that has to run *before* the downsample task, be idempotent, be
backfillable over existing history, and be correct across DST and device clock skew. Get the ordering wrong
once and historical scorecards change silently — the same class of invisible error the raw-samples rule
exists to prevent.

**15.11 The drawer is where I hid the mess.** "Everything else is a drawer off it" is a clean sentence
covering a settings page that still `ngSwitch`es across five device types, still saves settings + recipe +
alarms + cloud settings in one full-page action, still navigates away to `/list` on save, and still
duplicates four workmode gating truth tables. The timeline does not fix any of that. It just stops the mess
being the first thing you see.

**15.12 "One Timeline" is a philosophy, and philosophies resist exceptions that are actually correct.**
The VPD matrix (§4.10 #8b) is genuinely the best diagnostic in the dossier and it cannot go on a time axis.
I put it in the drawer and called that principled. A fair critic will say I put it there because my rule
forbade the better answer.
