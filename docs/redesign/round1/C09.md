# C09 — "The Tent" / **Das Zelt**

A spatial concept for Terp Control. The home screen is a live cross-section of the grower's actual
tent, containing exactly the kit they actually own, rendered in its real state, at a real point in time.

Written against `/home/user/terpcontrol.cloud` (branch `claude/controller-software-user-types-wc1jxn`),
the grounding dossier, and the owner decisions memo. Every claim about today's code carries a file
reference. Where the concept requires something the code cannot do, it says so before a critic has to.

---

## 1. Thesis

**The home screen is a picture of your tent with your kit in it — so "what do I own", "what is it doing
right now", "is that number fresh", and "what did it look like on day 34" all become the same picture,
and the app can no longer show you a control for a machine that is not in the room.**

The big idea: Terp Control's deepest bug is not visual, it is epistemic. `deviceControlCapability()`
(`webapp/src/app/util/grow-presets.ts:155-173`) collapses per-role hardware truth into three buckets and
**fails open** when `hardwareInfo.sockets` is absent, so a heater-only tent is offered humidity targets,
a humidity-deviation warning and a dehumidifier alarm preset it can never act on. Meanwhile a controller
is labelled `devices.fridge.title` — "Terp Control FRIDGE GROW" (`overview.component.html:40`) — and every
value on the dashboard is rendered as though it were current whether it arrived four seconds or four days
ago. The app is confidently wrong about the room. A picture of the room cannot be confidently wrong in
the same way: an object that is not in the picture has no controls, and an object whose state is old is
*drawn* old. The Tent makes capability, freshness and ownership properties of the rendering instead of
properties of a helper function nobody reads. Everything else — plants as pots on the floor, the camera
still as the tent's backdrop, the time slider that turns the scene into a scrubbable film — falls out of
that one commitment.

### The single fact that makes this buildable

The hardware envelope is *tiny and fixed*. `firmware/src/wifi.cpp:1694-1704` defines the entire universe
of smart-socket roles:

```cpp
const std::vector<std::string>& getSocketRolesList() {
  static const std::vector<std::string> roles = {
    "back", "dehumidifier", "heater", "light", "secondary_light", "co2",
  };
  return roles;
}
```

`"back"` is skipped in the reported CSV (`connectedSocketRolesCsv()`), and the whole stack is **keyed by
role, one socket per role**: `SmartSocketsComponent.freeSocketRoles` filters roles that are not yet
connected, the add-flow picks a *role*, and `sendAuxDeviceCommand` validates against the same five
(`server/src/services/device.service.ts:859`). The marketing line "up to 32 Tasmota sockets" does not
describe 32 independently addressable things in the UI; it describes what the radio can talk to.

**So a fully loaded controller tent contains at most: 1 PWM output + 5 role sockets + 1 camera +
1 sensor cluster + 1 bed. Nine objects.** A spatial metaphor over nine fixed objects is not a scaling
problem — it is a *layout*. This is the reason The Tent is not a gimmick: the scene never has to solve
the hard version of its own problem. (§15 is honest about where it does.)

## 2. Information architecture

### 2.1 The model in one line

**One device = one scene. The scene is the home. Everything else is a view *of* the scene, sharing one
cursor (`?t=`) and one selection (`?sel=`).**

### 2.2 Route map

New canonical routes. Ionic 6 / Angular 15, `NgModule` + `loadChildren` for every page (constraint 1 —
no standalone components anywhere in this concept).

**Legacy route preservation is mandatory, not optional.** `ShareLink.query` and `ChartPreset.query` are
*persisted user data* holding the frozen chart query string (constraint 9). Therefore:

```ts
// app-routing.module.ts
{ path: 'device/:device_id/charts',   canActivate: [LegacyRedirectGuard], component: NoopComponent },
{ path: 'device/:device_id/diary',    canActivate: [LegacyRedirectGuard], component: NoopComponent },
{ path: 'device/:device_id/settings', canActivate: [LegacyRedirectGuard], component: NoopComponent },
{ path: 'list', canActivate: [LegacyRedirectGuard], component: NoopComponent },
```

`LegacyRedirectGuard` re-navigates to the `/tent/...` equivalent **carrying `route.queryParams`
untouched**, because Angular's `redirectTo` does not preserve them. `applyViewParams` in the chart page
keeps parsing every existing key (`measures`, `date`, `dateEnd`, `vpdMode`, `autoUpdate`, `useCustom`,
`timespan`, `interval`, `logs`, `share`) and only *adds* `t`, `panels`, `plant`. **No existing share link
or preset breaks.** This is stated up front because it is the cheapest way for this concept to die.

### 2.3 Navigation model — there is no tab bar and no new global chrome

The scene contains its own navigation. Below the tent floor sits **der Sockel / the plinth**, a fixed
strip that is part of the scene, not a bar bolted on top of it:

```
┌──────────────────────────────────────────────┐
│                                              │
│                THE SCENE                     │
│         (tent interior, objects)             │
│                                              │
├──────────────────────────────────────────────┤   ← tent floor line
│ ◀━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━●   │   ← time slider ("Jetzt" at the right end)
│  💧 Gießen & Düngen        ✎ Notiz    📷      │   ← the two capture actions + camera
│  Verlauf     Tagebuch     Einstellungen      │   ← three flat links
└──────────────────────────────────────────────┘
```

Rationale: the dossier records that today there is **no tab bar, no FAB, no back button, no device
switcher** (`§1.3`) and that cross-navigation happens through six outline buttons. The plinth replaces
those six buttons with three links plus the two verbs the owner explicitly asked to make cheap. Adding
an `ion-tab-bar` would compete with the scene for the "where am I" job; the plinth *is* furniture.

Sub-pages (`/chart`, `/diary`, `/settings`, `/people`, `/furnish`) get a real `ion-back-button` that
returns to the tent, preserving `?t=`. The existing `ion-split-pane` + `ion-menu` stays exactly as it is
for Account / Shared links / dark mode / Logout / admin entries — this concept does not touch it beyond
fixing the two menu items that wrongly use the `mail` icon.

**Desktop (≥ 992 px):** the split-pane's main area becomes two columns — the scene pinned left at its
natural tall aspect (max 420 px wide), the active sub-view right. Selecting a kit object on the left
scrolls/highlights its panel on the right; scrubbing the chart on the right re-renders the scene on the
left. That is the "big screen is an unexploited advantage" answer: **tent and chart side by side sharing
one cursor.** No phone-only competitor can show that.

### 2.4 Screens, named

1. **Empty tent / Leeres Zelt** — no devices claimed. Illustrated empty tent, claim-code field on the floor.
2. **The Shelf / Das Regal** (`/tents`) — thumbnails, one per device.
3. **The Tent / Das Zelt** (`/tent/:id`) — the home screen. §3.
4. **Kit sheet / Geräte-Blatt** — bottom sheet over the tent for one object. Not a route; `?sel=<slot_id>`.
5. **Plant sheet / Pflanzen-Blatt** — bottom sheet for one pot. `?sel=plant:<plant_id>`.
6. **Water & Feed sheet / Gießen & Düngen** — the capture flow. §6.
7. **Furnish / Zelt einrichten** (`/tent/:id/furnish`).
8. **Chart / Verlauf** (`/tent/:id/chart`). §4.
9. **Diary / Tagebuch** (`/tent/:id/diary`). §5.
10. **Settings / Einstellungen** (`/tent/:id/settings`) — the existing expert form, unchanged.
11. **People / Leute** (`/tent/:id/people`). §8.
12. **Contents list / Inhalt** — the accessible, non-spatial twin of the scene (§15.5). Reached from the
    tent header menu and used automatically when `prefers-reduced-motion` is set or the viewport is
    landscape-short.

## 3. The home screen

### 3.1 Portrait phone, controller with a camera, everything healthy

A real grow tent is 80×80×180 cm — aspect ratio **0.44**. A phone viewport is ~0.46. The tent fits the
phone better than it fits a desktop. This is the concept's luckiest structural break and it is why the
scene is portrait-first rather than portrait-tolerated.

Layout rules, concretely:

- The scene is **one inline `<svg viewBox="0 0 440 780">`** with fixed slot coordinates per template.
  **There is no free placement and no drag-and-drop in v1.** Each `kind` has a fixed home in the
  template; furnishing decides *whether* a slot is occupied, not *where*. This removes the single most
  expensive part of a spatial UI and costs the user nothing they asked for.
- The camera still is an `<image>` element clipped to the interior rect, `preserveAspectRatio="xMidYMid
  slice"`, `opacity: 0.85`, with a `--tc-gradient-panel` scrim behind the sensor chips so text stays
  readable over arbitrary photos. No camera → the illustrated interior (a flat two-tone tent liner) shows
  instead. **Both paths must be designed; the illustration is not a fallback afterthought.**
- Sensor chips are `<foreignObject>` wrapping the existing `.tc-pill` classes so typography and dark
  mode come from `theme/variables.scss` for free.
- Kit objects on the wall rail are 56×56 px hit targets (≥ 44 px, constraint 7), each with a 2-line
  label: name + state.
- Pots are 64 px wide, up to 5 across; a 6th+ collapses into a `( +7 )` chip that opens the contents list
  filtered to plants.
- The verdict line under the tent is one string. Nothing else.

### 3.2 Object state vocabulary — the whole design rests on this table

Every object in every scene renders in exactly one of six states. This is the fix for dossier P0 #5
("nothing distinguishes live from stale from offline" — the #1 complaint across all five consumer brands).

| State | Condition | Drawn as | DE | EN |
| --- | --- | --- | --- | --- |
| **live** | value age ≤ 2 × sample interval | full colour, solid, state text + `✓ 4 s` | `vor 4 Sek.` | `4 s ago` |
| **stale** | age > 2 × interval, device seen < 10 min | colour desaturated 40 %, value in `--tc-text-warning`, age shown | `vor 6 Min.` | `6 min ago` |
| **offline** | `Date.now() - lastseen > 10 min` | whole scene at 55 % opacity, greyscale, banner across the tent | `Keine Verbindung seit 14:20` | `No connection since 14:20` |
| **absent** | slot not furnished | dotted outline, no state colour ever | `Hier ist nichts` | `Nothing here` |
| **unverified (prop)** | furnished but hardware cannot report it | flat outline, **never a state colour** | `Nur ein Merkzettel — Terp Control sieht das nicht.` | `Just a note — Terp Control can't see this.` |
| **discrepancy** | reported ≠ furnished (either direction) | amber dashed outline + `!` badge | see §3.4 | |

`DEVICE_ONLINE_TIMEOUT_MS = 10 * 60 * 1000` already exists in
`webapp/src/app/components/aux-devices/smart-sockets.component.ts:7` — reuse it, do not invent a second
threshold. Age comes from `Device.lastseen` for the device and from the newest Influx point for a measure.

**The rule that makes the picture honest: colour encodes state, and only verified things get colour.**
A prop is never green. This is the whole answer to "a picture is more persuasive than a list, so a wrong
picture is worse than a wrong list" (§15.4).

### 3.4 What it looks like when things are not fine

**Stale.** One sensor stops updating while the device is still online: that chip alone desaturates and
switches to `vor 6 Min.`. The rest of the tent stays live. Today every value is rendered as if current
regardless of age — this is the cheapest credibility fix in the document and the scene gets it by
construction.

**Offline.** `lastseen` older than 10 min:

```
┌────────────────────────────────────┐
│ ╔══════════════════════════════╗   │
│ ║░░░░ (whole scene greyed) ░░░░║   │
│ ║  ┌────────────────────────┐  ║   │
│ ║  │ Keine Verbindung seit  │  ║   │
│ ║  │ Do, 14.03. um 14:20    │  ║   │
│ ║  │ Zuletzt: 25.8 °C, 54 % │  ║   │
│ ║  │ [ Was tun? ]           │  ║   │
│ ║  └────────────────────────┘  ║   │
│ ╚══════════════════════════════╝   │
```

The scene still renders the last known state underneath, greyed — because "what was it doing when it
went dark" is the actual question. Today's `offline-overlay` (`overview.component.html:1-8`) is
dismissible by clicking it, which un-greys stale data; that behaviour is removed.

**Absent / never furnished.** The wall rail draws dotted outlines with `Hier ist nichts` and a `+`. The
kit sheet for an empty slot contains *no controls at all* — only "Was ist das?" explaining what would go
there. **This is the capability fix**: a humidity target row physically cannot appear because the
dehumidifier object it belongs to is not in the scene. Compare `simple-settings.component.ts:65` today,
which reaches for `deviceControlCapability()` and gets `'full'` from a heater-only tent.

**Discrepancy — the fail-closed replacement for fail-open.** Two directions, both drawn:

- *Ghost*: `hardwareInfo.sockets` contains `heater` but no heater is furnished → an amber ghost heater
  appears in its slot with `Etwas hängt dran, das nicht im Zelt steht` and a `Reinstellen` button.
- *Silent*: a heater is furnished but the CSV does not contain it → drawn hollow with `Antwortet nicht`
  and a `Kurz testen` button (fires the existing `socket_test` aux command).
- *Unknown firmware*: `hardwareInfo.sockets === undefined` (old firmware, the case that today returns
  `'full'`) → the scene renders **only what the user furnished**, plus a one-time banner:
  `Dein Controller ist zu alt, um zu melden, was angeschlossen ist. Ich zeige, was du reingestellt hast.`
  / `Your controller is too old to report what's connected. I'll show what you put in.` **Fails to the
  user's declaration, never to "everything".**

**Absent data / brand-new device.** Claimed, online, no Influx points yet: full-colour scene, chips read
`—` (the existing `value-display` already renders `—` for missing values), verdict line
`Noch keine Werte — das Zelt füllt sich gerade`.

**Maintenance mode.** `maintenance_mode_until` in the future → the tent's door illustration swings open,
the interior dims, all kit greys, banner `Tür offen bis 14:35 · Wartungsmodus. Nichts wird geregelt.`
This reuses `MaintenanceService.promptFor` (already wired at `overview.component.ts:345`). It is the
clearest example of the metaphor doing work a tile grid cannot: an open door means "the room is not
sealed, do not trust the numbers".

### 3.5 The two skins

`?skin=tent` (default) and `?skin=schema`, persisted in `localStorage['tc-scene-skin']` — the same
convention as `localStorage['app-settings-expert']` (`§1.7`).

`./simulate-device.sh configure` takes and what the REST API documents. A techie reading Schema can
drive the device from a shell.

## 4. The chart overhaul

The chart is the analysis surface. **The Tent does not try to be the chart** — it is the "now" and the
"replay"; the chart is the "why". They share one cursor and one colour system.

### 4.1 Library

Per the owner decision: off Highcharts. **Apache ECharts 6, tree-shaken, with a hand-rolled ~50-line
Angular directive** (not `ngx-echarts`, which ships a major per Angular major and would pin the chart to
the framework upgrade path). Delete `chart.js` / `ng2-charts` / `chartjs-adapter-luxon` from
`charts.page.ts`, `charts.module.ts`, `diary.module.ts` and `diagnostics.*` — they are imported alongside
Highcharts and used for nothing.

Honest cost, stated in the PR description and not softened: **tree-shaken ECharts ≈ 195.6 KB gz vs
Highstock 132.7 KB gz. The bundle gets bigger.** Deleting Chart.js repays 68.8 KB of it. The migration is
justified by licence (`highcharts/highstock` is Core+Stock, $732/seat/yr plus a quote-only SaaS licence,
against a repo with no LICENSE file and a public demo at `terpcontrol.cloud/demo`) and by capability
(`markArea`/`markLine`, `grid[]` + `axisPointer.link`, `sampling`, `darkMode:'auto'`). Not by size.

One deviation from the dossier's §7.1 shopping list: I use **a single ECharts instance with `grid[]` +
`axisPointer.link`, not `echarts.connect()` across instances.** Connect multiplies instances, each with
its own canvas and its own resize observer, on the exact mid-range Android where the memory argument was
the reason to migrate.

Replacing Highstock removes an implicit safety net: **Highstock's `dataGrouping` — never configured
anywhere in this repo — is the only thing keeping a 4,320-point render cheap** (dossier Appendix A #1).
So `sampling: 'minmax'` on every series is **not polish, it is the replacement for a load-bearing
default**, and it is written into the directive as a default rather than left to each call site.

Two server fixes are prerequisites, not nice-to-haves (dossier P0 #8):
`from`, `to`, `interval` and `measure` are interpolated raw into Flux in
`server/src/services/data.service.ts:80-89`, and the `limit(n: 50000)` guard is piped *after* `yield()`
and therefore bounds nothing. Any concept that widens the measure vocabulary — this one does, with EC/pH
— must fix both first.

### 4.2 Panels

Stacked small multiples, shared x-axis, one linked crosshair. ~110 px each on mobile. Adopted from
dossier §7.2 #1 without reservation: Few's *Dual-Scaled Axes* verdict is unqualified, and today's chart
runs **fifteen independent hidden y-axes as translucent area fills with the axis labels programmatically
suppressed below 320 px** (`charts.page.ts`). Small multiples let you see RH lagging temperature at
lights-on, which the overlay destroys.

Panel order is not arbitrary: **it mirrors the tent, top to bottom.** Lamp is at the top of the tent, so
Licht is the top panel after Klima; the outputs lane lists kit in the same order as the wall rail.
Scrubbing either surface highlights the corresponding object in the other.

| # | Panel | Series | Shown when |
| --- | --- | --- | --- |
| 0 | **Film** | camera thumbnails positioned by timestamp | camera paired and stills exist in window |
| 1 | **Klima** `°C / %` | temperature (solid), humidity (solid, right axis), leaf_temperature (dashed grey) | always |
| 2 | **VPD** `kPa` | vpd | always (derived server-side today) |
| 3 | **Licht** `% · DLI` | out_light duty, lux/PPFD if present, cumulative DLI as a step | lamp or light socket furnished |
| 4 | **CO₂** `ppm` | co2 | `deviceHasCo2()` true |
| 5 | **Wasser & Dünger** `EC · pH · l` | EC in (filled dot), EC runoff (hollow dot), pH (marker), volume (bottom bars) | ≥1 water/feed event in window |
| 6 | **Geräte** | state-timeline lane, one row per furnished kit object | ≥1 output furnished |
| 7 | **Spur** | annotation rail, 2 rows | always |
| 8 | **Urteil** | time-in-range scorecard | ≥ 80 % data coverage |

Panels 3–6 appear only when the tent contains the thing they describe. `?panels=` records which are
open, appended to the existing query format.

Two units on one panel are allowed only when physically coupled (temp + RH; temp + leaf temp), per §7.2
#1. Everything else gets its own panel.

### 4.3 Goal vs actual — how it is actually drawn

The dossier's most important finding for this section: **"goal vs actual" is a presentation gap, not a
data-collection gap.** `GROW_STAGE_PRESETS` already carries per-stage day/night temperature, day/night
humidity, light hours, light limit, CO₂ and a **VPD band** (`grow-presets.ts:37-118`), and the live
setpoints sit in `device.configuration`. None of it reaches the chart today.

Per measure, three layers, drawn back to front:

1. **Target band** (`markArea`, 12 % opacity of the series hue). Source priority, **one at a time and
   labelled in the legend** so the reader knows which promise they are looking at:
   - `Alarm` — the user's own `Alarm.upperThreshold` / `lowerThreshold` for that `sensorType`. Hard edge,
     drawn with a 1 px solid boundary. (These fields exist and the chart ignores them today.)
   - `Ziel ± Toleranz` — setpoint ± the tolerances already used by the grow assistant (±1.5 °C, ±7 % RH).
     Soft edge, no boundary line.
   - `Empfehlung` — the stage preset's advisory range, e.g. `vpdRange`. Dotted boundary, lowest opacity.
2. **Setpoint line** — **dashed, stepped** (`step: 'end'`). It steps at `daynight.day` / `daynight.night`
   (seconds-of-day, UTC) between `day.temperature` and `night.temperature`. For VPD it is the stage
   band's midpoint and it **moves along the x-axis as the plant's stage changes** (§4.6).
3. **Actual** — solid, `sampling: 'minmax'`, plus a **min/max envelope** as a 20 %-opacity band around it
   on the primary measure. `aggregateWindow` already supports `min`/`max`; a single `mean` line is a lie
   about a bang-bang controller, and the whole point of a controller chart is seeing the oscillation.
4. **Signed deviation fill** between actual and setpoint — warm tint above, cool tint below. **Never fill
   to the axis.** Today every series is `type: 'area', fillOpacity: 0.1, threshold: null`, which encodes
   nothing at all and, at 0.1 opacity, almost certainly fails WCAG 2.2 SC 1.4.11's 3:1 non-text contrast
   requirement.

Legend strings: `Ist` / `Actual`, `Ziel` / `Target`, `Alarm`, `Empfehlung` / `Guideline`. These are
translated — today the series names (`Temperature`, `Humidity`, `Critical logs`) are **hardcoded English**
while the page chrome is translated, so a German user gets English legends.

### 4.4 Day/night shading

A vertical `markArea` spanning **all** panels, so the eye reads one photoperiod across the whole stack.

- Primary source: **measured** `out_light > 0`. A failed contactor then shows as a *missing band* — a
  diagnostic, not decoration.
- Fallback when `out_light` is absent from the window: the configured `daynight.day` / `daynight.night`
  schedule, drawn with a hatched edge to say "this is the plan, not the observation".
- `lights.sunrise` / `lights.sunset` ramps render as a gradient at each edge.
- **Explicit timezone.** Grafana's time-regions model. `daynight` is seconds-of-day in UTC; a 12/12 flip
  near a DST boundary drifts an hour and generates bug reports. The chart header states the zone
  (`Zeiten in Europe/Berlin`).

**The honesty case that no other concept will catch:** the PWM output is named `out_light` but is
*freely assignable to a dimmable lamp or an exhaust fan*, and `is_day` is inferred from
`out_light >= 0.5` (`overview.component.ts:123`). If the grower hangs an exhaust fan on the dimmer, both
the day/night shading and the overview's day/night state become nonsense. The Tent asks this exactly once
during furnishing (§10) and stores `TentScene.pwmUse`. When `pwmUse === 'exhaust'`, day/night shading
falls back to the schedule permanently, the Licht panel is relabelled **Abluft**, and the tent's lamp
object becomes a fan. Nobody else in this bake-off is positioned to notice this, because it only becomes
visible when you have to draw the thing.

### 4.5 Outputs lane, annotation rail, film strip

**Geräte lane** (dossier §7.2 #6, adopted). One row per furnished kit object, in wall-rail order. Region
length = duration; `null` renders as a **gap**, not as off — the distinction between "off" and "we don't
know" is the same distinction the tent's stale state draws. Rows are labelled with the same dynamic name
the tent uses, so `Kühler*` appears with a footnote `* dieselbe Steckdose wie der Entfeuchter`.

Colour for outputs is **not** from the measure palette: off = `--tc-surface-subtle`, on = brand green
`#50a030`, unknown = 45° hatch in step-300, fault = `#D55E00`.

**Spur / annotation rail** (dossier §7.2 #5, adopted with two deliberate rejections). 20 px, under the
x-axis, **max two rows**: row 1 = human actions (water, feed, note, photo, training, transplant,
harvest), row 2 = device events (alarms, boots, config changes, recipe steps). Stage changes are
**full-height dashed vertical lines across every panel** with a label on the rail
(`Blüte ab hier` / `Flower starts here`) — they are context, not points.

*Rejected #1:* the dossier's pixel-proximity clustering with count badges. At 12 px a count badge is
unreadable, and a stoned user tapping a `14` and getting a modal of boot messages has been punished for
curiosity. **Instead: row 2 is off by default.** The rail opens showing human actions only. A single
`Geräte-Ereignisse` chip turns row 2 on. Within a row, overlapping glyphs collapse to the highest
severity plus a hairline tick for the others, and tapping opens a *list scoped to that time bin* using
the existing `app-log-entry-viewer` — which already does pagination, category collection and image
thumbnails (`LogEntryViewerModule`).

*Rejected #2:* Highcharts `flags`. Irrelevant post-migration, but for the record `stackDistance: 12` does
not survive 90 days of logs.

Today events are three plain `column` series of constant height 1 on hidden 0..1 axes, readable **only by
hovering** — on a mobile-first product. That is the defect being removed.

**Film strip** (dossier §7.2 #9, adopted). Thumbnails positioned by timestamp on the *same x-scale* as
the panels, so an uneven capture interval reads honestly as a gap. `Image.timestampEnd` already marks the
mp4 timelapses as spanning a range; those render as a bracket, not a point.

Delivery is a new endpoint, and it is the single most important backend addition in this concept because
the tent's time slider needs it too:

```
GET /image/strip/:device_id?from=<ms>&to=<ms>&cols=<n>&token=<imageToken>
→ { sprite: "/image/strip/<id>.jpg", cols, rows, tileW: 256, tileH: 160,
    frames: [{ i: 0, t: 1742000000000 }, …] }
```

One sprite JPEG + a JSON index, Mux's storyboard pattern (50 tiles under 15 min, 100 above). Scrubbing
then costs zero network requests. Today the chart loads a still per hover after a 500 ms debounce.

### 4.6 The differentiating chart: a VPD band that moves

Adopted from §7.2 #8, and it is the one place where the plant model (§5) pays for itself in the chart.

The VPD panel's target band is **not constant across the window**. It is a step function driven by the
active plant's stage history: seedling 0.4–0.8 → vegetative 0.8–1.1 → flowering 1.2–1.5 → late flowering
1.3–1.6 kPa, straight out of `GROW_STAGE_PRESETS[].vpdRange`. When plants at different stages share the
tent (§5), the band shows the **intersection** and, where the intersection is empty, draws two hatched
bands with a label `Zwei Ziele — Sämling und Blüte` / `Two targets — seedling and flower`. That is a real
horticultural conflict; showing it beats hiding it.

The leaf-temperature assumption is drawn **on the chart**, not buried in settings:
`Blatt = Luft − 2,0 K (geschätzt)` / `Leaf = air − 2.0 K (estimated)`, replaced by
`Blatt gemessen` when an MLX90632 is present. VPD is entirely an artefact of that offset.

*Deferred to v1.1:* the VPD temperature × RH **matrix** with the last-24 h trajectory plotted on it. It
is the best diagnostic in the dossier ("you drift into the too-humid corner every night") and it is a
second chart type with its own interaction model. Techies will love it; nobody else will open it. It does
not earn a slot in an October launch.

### 4.7 The verdict / Urteil

The AGP scorecard (§7.2 #3), adopted, with the correctness trap treated as a blocker:

**Time-in-range is computed server-side on RAW Influx samples.** Never on `aggregateWindow(fn: mean)`
output — averaging destroys the excursions the metric exists to count, and the error is invisible by eye.
New endpoint:

```
GET /data/scorecard/:device_id?measure=temperature&from&to&band=alarm|setpoint|stage
→ { inRange: 0.84, above: 0.11, below: 0.05,
    day: { inRange: 0.91 }, night: { inRange: 0.71 },
    longestExcursion: { ms: 7800000, direction: 'above', at: 1742… },
    mean, min, max, madFromSetpoint, coverage: 0.97 }
```

Rendered as one stacked bar plus four numbers:

```
Im Zielbereich  84 %
▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▁▁▁▁▂▂
Tag 91 %   ·   Nacht 71 %
Längste Abweichung: 2 Std. 10 Min. zu warm
Daten: 97 % vorhanden
```

Excursions are reported **as a duration, not as a count of alarms** (Mean Kinetic Temperature's lesson).
Below 80 % coverage the whole card greys out and reads `Zu wenig Daten für ein Urteil` / `Not enough data
for a verdict` — a scorecard computed over a gap is worse than no scorecard.

`Tag 91 % · Nacht 71 %` is the line that sells the product. It says: your dehumidifier cannot keep up at
night. No competitor in the research reports it.

### 4.8 Mobile touch interaction

Adopted wholesale from §7.2 #10, because today's chart on a phone requires Ctrl to pan and Shift to zoom.

- **One finger = page scroll.** Non-negotiable; the chart lives in a scrolling page.
- **Two fingers = pan and zoom** (`dataZoom: { type: 'inside', zoomOnMouseWheel: false, moveOnMouseMove: false }`).
- **Tap or long-press = crosshair**, which sets `?t=` and therefore also moves the tent and the film strip.
- **Range presets stay the primary control**, ≥ 44 px: `24 Std · 7 Tage · 30 Tage · Eigen`.
- **The interval dropdown is constrained by the timespan.** Today `3y × 5s` ≈ 18.9 M aggregation windows
  is one dropdown away and the limit guard does not bound it.
- **Axis labels are never hidden.** Below 320 px: three ticks and the unit moves into the panel title.
  An axis-less chart is not a chart.
- **Replace the floating tooltip with a pinned scrub header** on mobile — a fingertip occludes a tooltip
  and there is no hover on touch. *Nuance:* on desktop the scrub header is **suppressed**, because the
  tent is already on screen at the left rendering the scrubbed state, which is a strictly better readout
  than a table of numbers. That is the concept's structural payoff for the big screen.
- Live mode stops re-fetching everything every 10 s with a `router.navigate` (today: all series + all
  logs + a navigation, no `?since=`). Incremental append with `?since=`, and the tent's chips subscribe
  to the same stream.

## 5. The multi-plant diary

### 5.1 What has to be replaced and why

Today **there is no diary data model.** Every entry is a row in the single `DeviceLog` collection whose
`categories[0] === 'diary'`, sharing that collection with boot messages, MQTT errors, alarm transitions
and config diffs. A "grow cycle" is **inferred in the browser at runtime** by
`convertEventsToGrowCycles()` (`grow-report.component.ts:691-747`), which starts a new cycle whenever the
stage ordinal rolls back **or the trimmed `lifecycleName` string differs**. Consequences, all real today:

- **Renaming a plant mid-grow forks its history into two cycles.**
- **A re-veg fabricates a new plant.**
- Cycle identity in URLs and share links is the cycle's *start timestamp*, so editing an entry's time
  breaks share links that are already in circulation.
- The server's own stage-transition entry is written with `categories: ['diary-plant-lifecycle']`
  *without* the `'diary'` prefix (`device.service.ts:714`) — invisible in the Entries report and not
  editable, while the identical manual entry is both.
- `deleted: true` means "hide from the overview stream", and manual diary entries are *created* with it
  (`diary.page.ts:112`), so **"Clear logs" deletes nothing from the diary**.

A per-plant diary cannot be layered on this. It needs persisted entities.

### 5.2 New MongoDB entities

All cloud-side, keyed by `device_id` — `device.configuration` cannot carry new keys because the firmware
strips unknown keys when echoing config back (`grow-presets.ts:31-34`). All new fields are **optional**
with read-time normalisers, because there is no migration tooling in this repo (no migrate-mongo, no
versioned migrations, no `schemaVersion`); the house style is optional field + normaliser + idempotent
boot-time backfill in a service constructor, and this concept follows it.

```ts
// ---- the scene itself -------------------------------------------------
export type SceneTemplate = 'tent' | 'fridge' | 'fan' | 'light' | 'plug';
export type SlotKind = 'pwm' | 'socket' | 'sensor' | 'camera' | 'bed' | 'prop';

export interface SceneSlot {
  slot_id: string;              // stable, e.g. 'socket:heater', 'pwm', 'bed', 'prop:1'
  kind: SlotKind;
  role?: string;                // one of SOCKET_ROLES, or 'pwm'
  label?: string;               // user override; else i18n from role
  iconId?: string;              // for props
  placedAt: number;
  verified: boolean;            // false ⇒ NEVER drawn with a state colour
}

export interface TentScene {
  device_id: string;            // 1:1 with Device
  template: SceneTemplate;
  slots: SceneSlot[];
  pwmUse?: 'lamp' | 'exhaust';  // the one question hardware cannot answer
  backdrop: 'illustration' | 'camera';
  privacyMode: 'private' | 'club';   // §8
  updatedAt: number;
  schemaVersion: 1;
}

// ---- plants -----------------------------------------------------------
export interface Plant {
  plant_id: string;
  device_id: string;
  slot_id?: string;             // which bed; v1 always the single 'bed'
  name: string;                 // mutable, does NOT fork history
  previousNames?: { name: string; until: number }[];
  strain?: string;
  source?: 'seed' | 'clone' | 'unknown';
  parentPlantId?: string;       // clone lineage
  startedAt: number;
  stage: DiaryLifecycleStage;
  stageSince: number;
  medium?: string;              // FeedRegime.medium id, e.g. 'biobizz-allmix'
  potLitres?: number;
  regime_id?: string;
  regimeAnchor?: { at: number; stepIndex: number };  // where the schedule was pinned
  colorIndex: number;           // stable pot colour, 0..7
  archivedAt?: number;          // ends the cycle. absent ⇒ alive
  harvest?: { at: number; wetG?: number; dryG?: number };  // §8 privacy
  notes?: string;
}

// ---- events (the diary) ----------------------------------------------
export type PlantEventType =
  | 'note' | 'water' | 'feed' | 'measure' | 'train' | 'pest'
  | 'transplant' | 'stage' | 'harvest' | 'photo' | 'co2refill' | 'kit';

export interface PlantEvent {
  event_id: string;
  device_id: string;
  plant_ids: string[];          // [] ⇒ tent-scoped. THIS is the no-tax path.
  type: PlantEventType;
  at: number;
  actor_id?: string;            // §8 attribution
  actorHandle?: string;         // per-tent pseudonym, never an email
  source: 'user' | 'device' | 'schedule';
  data?: PlantEventData;
  images?: string[];            // image_id, with a BACK-reference (Image gains event_id)
  correctionOf?: string;        // append-only corrections, never destructive edits
  deletedAt?: number;           // real deletion, unlike DeviceLog.deleted
}

export interface WaterFeedData {
  volumeL?: number;
  perPlant: boolean;            // true ⇒ volumeL applies to EACH plant in plant_ids
  runoff?: boolean;
  ecIn?: number; ecOut?: number;      // mS/cm canonical, ALWAYS
  phIn?: number; phOut?: number;
  waterTempC?: number;
  products?: { label: string; amountMl?: number; amountG?: number; perLitre: boolean }[];
  regime_id?: string;
  regimeStepIndex?: number;
  regimeDeviated?: boolean;     // set automatically when the user edits a prefill
}
```

`Image` gains one optional field, `event_id?: string`, which is the back-reference it has never had. The
unique index `{device_id, format, timestamp, duration}` gains a `format: 'user/jpeg'` collision guard —
two uploads in the same millisecond currently collide.

### 5.3 How plants are created

Three ways, none of them a form:

1. **Tap `[+]` on the bed.** A sheet: name (prefilled `Pflanze 1`), optional strain, `Aus Samen` /
   `Steckling` / `Weiß nicht`, and a stage chip row reusing `stage-preset-picker`. **Two required taps**
   (add, confirm) — name and stage are prefilled.
2. **From the mother.** Plant sheet → `Steckling nehmen` / `Take a clone` → creates a `Plant` with
   `parentPlantId`, `source: 'clone'`, `stage: 'seedling'`, `startedAt: now`. Drawn as a small pot beside
   the mother with a hairline linking them.
3. **Backfill, once, server-side.** On first boot after deploy, `PlantBackfillService` runs
   `convertEventsToGrowCycles()` **once per device** and materialises one `Plant` per inferred cycle,
   `name = lifecycleName`. Every `DeviceLog` row with a `diary*` category inside a cycle's window is
   mirrored into a `PlantEvent`. Where the device had exactly one cycle running at that time, the event
   gets `plant_ids: [that plant]`; otherwise `plant_ids: []`.
   The user is shown the result, once, with an undo:
   `Ich habe deine alten Einträge zu {{n}} Pflanzen zusammengefasst. Passt das?` /
   `I grouped your old entries into {{n}} plants. Does that look right?` → `Passt` / `Rückgängig`.
   **The backfill is lossy and is presented as lossy.** `convertEventsToGrowCycles` then becomes dead
   runtime code and is deleted — its five existing spec tests move onto the backfill service, which is
   the only real test coverage in this repo and worth keeping (`grow-report.component.spec.ts`).

`DeviceLog` is **not** deleted. Device-generated log rows continue to land there; the diary reads
`PlantEvent`. The two are unioned only in the Spur (§4.5), where row 1 = `PlantEvent`, row 2 = `DeviceLog`.
This keeps the alarm/boot/config machinery untouched.

### 5.4 How entries attach to plants

**Spatially, and by default.** The capture sheets open with pots pre-selected:

```
Welche Pflanzen?
[✓ Amnesia] [✓ Zkittlez] [✓ #3]      Alle   Keine
```

- Opened from the plinth → **all live plants selected**.
- Opened by tapping a pot → **that pot only**.
- Opened with zero plants existing → the chip row is **not rendered at all** and the event is stored with
  `plant_ids: []`.

Deselecting is one tap per pot. There is no "assign to plant" step anywhere, ever.

### 5.5 Rename, re-veg, clone — the three cases today's code gets wrong

| Case | Today | The Tent |
| --- | --- | --- |
| **Rename** | `lifecycleName` differs ⇒ `convertEventsToGrowCycles` forks the history into two cycles | `Plant.name` is mutable; the old name is appended to `previousNames[]` with an `until`. Identity is `plant_id`. **Nothing forks.** The diary shows `Amnesia (früher: Nr. 3)` for 30 days, then just the new name |
| **Re-veg** | stage ordinal rolls back ⇒ a new cycle is fabricated | `stage` moves `flowering → vegetative`, `stageSince` resets, a `PlantEvent{type:'stage'}` records it. **Stage regression is legal and creates nothing.** The chart's stage band simply shows veg again, and the VPD target band steps back with it |
| **Clone** | impossible to express | new `Plant` with `parentPlantId`. The chart can show `Mutter: Amnesia` on the clone's stage band |
| **End of grow** | implicit, inferred | explicit `archivedAt`. That, and only that, ends a cycle. Archived pots leave the tent and appear under `Tagebuch → Abgeschlossen` |

### 5.6 The user who does not care about plants

This is the acceptance test for the whole section, and the answer must be precise.

The tent always has **one bed slot**. If no `Plant` exists for the device:

- The bed renders as plain substrate with **one 40 px `[+ Pflanze]` chip**. That chip is the entire tax.
- Every capture sheet omits the plant chip row; events store `plant_ids: []`.
- The diary shows entries with no plant column and no plant filter.
- The chart's stage band is derived from the device's own `newLifecycleStage` history exactly as today,
  so the VPD target band still moves. **Stage does not require a plant.**
- `Tagebuch` has no "per plant" tab. No plant appears in any menu, export, or share link.
- The grow report's cycle picker is replaced by a date-range picker.

Measured: **one chip, ~40 × 28 px, on one screen.** A monitoring-only user (type 1) never touches it and
never sees the word "Pflanze" again after onboarding, where it is also skipped (§10).

### 5.7 The diary screen

`/tent/:id/diary`. Three reports, preserving the existing `report=` query convention
(`diary-query-params.ts` — `mergeDiaryQueryParams`, `parseDiaryReport`):

- **`entries`** — the stream. `app-log-entry-viewer` reused wholesale (severity colours, repeat counts,
  `data` list with units, image thumbnails → fullscreen modal, category chips, edit/delete). Now over
  `PlantEvent` with **server-side pagination** (today `getDeviceLogs` has no `.limit()`, no cursor and no
  count, and the Entries report fetches the device's *entire* history on every open). New filter row:
  plant chips + type chips. Entries carry an actor chip when attribution is on.
- **`grow`** — per-plant. Day counter (`Tag 47`), week bucket (`Woche 7`), stage timeline, the plant's
  photos as a strip, its water/feed table, and a `Woche exportieren` button. The 370 lines of
  DOM-measuring scroll-linked scrubber code in `grow-report.component.ts` are **deleted**; the film strip
  and time slider replace them with one shared cursor.
- **`co2`** — unchanged.

Both a **day counter and derived week buckets** are stored (`Plant.startedAt` + computed), because
GrowDiaries is week-bucketed and Grow with Jane is day-indexed, and storing only one makes one export
permanently lossy.

## 6. Watering & fertilising

There is no irrigation or dosing hardware. **This is capture-and-recall, not automation**, and the design
is judged on taps and on recall quality, not on cleverness.

### 6.1 The everyday capture flow — counted

**Scenario A — a feed is due and a regime is selected (the "it thinks for me" case).**

The plinth button already carries the state: `💧 Gießen & Düngen · fällig`.

1. **Tap** `Gießen & Düngen`.
2. Sheet opens **fully prefilled**: all pots selected, volume = last used, products = this step's
   products with computed millilitres, EC/pH blank.
3. **Tap** `Passt` (the big green primary — brand green `#50a030` is already the CTA colour).

→ **2 taps.** Toast: `Gegossen. 3 Pflanzen, je 2 l.` / `Watered. 3 plants, 2 L each.`

**Scenario B — no regime, plain watering.** Identical, minus the products block. **2 taps.**

**Scenario C — deviating.** Each edit is one `value-edit-row` interaction (tap the row → it expands into
`[−] ion-range [+]`, ARIA-annotated, step-aware — the canonical numeric row that already exists). Volume
+ one product amount + confirm = **4–5 taps**.

**Scenario D — the club / detailed case.** `Mehr` expands EC in, EC runoff, pH in, pH runoff, water
temperature, runoff yes/no, note, photo. ~10 taps, and that is the correct number for a user who wants
that record.

The sheet:

```
┌── Gießen & Düngen ────────────────── ✕ ──┐
│ Welche Pflanzen?                          │
│ [✓ Amnesia] [✓ Zkittlez] [✓ #3]  Alle Keine│
│                                           │
│ Wie viel?         2,0 l   je Pflanze ⇄    │
│ ┌───────────────────────────────────────┐ │
│ │  Biobizz All-Mix · Woche 4 Blüte      │ │
│ │  Bio-Grow      2,0 ml/l   → 4,0 ml    │ │
│ │  Bio-Bloom     2,5 ml/l   → 5,0 ml    │ │

│ │           + Leitungswasser 0,4)       │ │

```

Strings: `feed.due` DE `fällig` EN `due`; `feed.sameAsLast` DE `So wie letztes Mal` EN `Same as last
time`; `feed.confirm` DE `Passt` EN `Looks right`; `feed.perPlant` DE `je Pflanze` EN `each`;
`feed.total` DE `insgesamt` EN `total`; `feed.lastVerified` DE `Zuletzt geprüft: {{date}}` EN `Last
verified: {{date}}`; `feed.notYet` DE `Noch nicht düngen — {{medium}} ist vorgedüngt` EN `Don't feed yet
— {{medium}} is pre-fertilised`.

### 6.2 What is stored

**One `PlantEvent` per event, never N events for N plants.** `plant_ids` carries the selection and
`perPlant: true` means `volumeL` applies to each. If plants genuinely got different amounts, a
`unterschiedlich` / `different amounts` toggle splits the sheet into N rows and writes N events. This is
the difference between a diary that stays readable at 200 events and one that doesn't — and the log
endpoint has no server-side pagination today, so row explosion is a real cost, not a theoretical one.

EC is stored **canonically in mS/cm**, always. `ppm` is never stored and never rendered as a bare number:
at EC 1.8 a Bluelab (700 scale) reads 1260 and a Hanna (500 scale) reads 900 for the same liquid, and
this is repeatedly cited as the #1 cause of accidental over- and under-feeding. If the user's meter is a
ppm meter they set the scale once in `/account`, and the UI renders `1,8 mS/cm (1260 ppm · 700)` — the
scale is always in the string.

### 6.3 The schedule-following flow

Per the owner's correction: **a scheme is selected once, then it prefills the log entry.** It is not a
planner, not a calculator, not a compliance engine.

Selection lives on the plant sheet, and it is one control, labelled the way growers speak:

```
Erde & Dünger
[ Biobizz All-Mix ▾ ]
```

with options grouped: `Biobizz Light-Mix`, `Biobizz All-Mix`, `Floragard Light`, `Green House Feeding
(Powder Feeding)`, `BioTabs`, then `Ohne Plan`, `Nur Wasser`, `Lucas Formula`, `Jack's 321`,
`Kokos — EC-Leiter`, and `Eigener Plan …`.

The model — deliberately much smaller than the dossier's nine-axis matrix, because the owner rejected
that framing:

```ts
export interface FeedStep {
  stage: DiaryLifecycleStage;   // which stage this step belongs to
  week: number;                 // week WITHIN the stage, 1-based
  labelKey?: string;            // e.g. 'feed.step.noFeedYet'
  products?: { label: string; mlPerL?: number; gPerL?: number; noteKey?: string }[];
  ecTarget?: [number, number];
  phTarget?: [number, number];
  flush?: boolean;
  reminderKey?: string;         // BioTabs: 'feed.reminder.retab'
}

export interface FeedRegime {
  regime_id: string;
  owner_id?: string;            // '' or absent ⇒ catalogue; else the user's own
  label: string;                // PLAIN TEXT. Never inside a Terp feature name.
  medium?: string;              // 'biobizz-allmix' | 'coco' | 'soil' | …
  brand?: string;
  steps: FeedStep[];
  stepIndexBy: 'stage_week' | 'feed_count' | 'interval_days';
  ecBasis: 'absolute' | 'delta_over_source';
  intervalDays?: number;        // for BioTabs-style regimes
  source_url?: string;
  retrieved_at?: number;
  chart_version?: string;
  kind: 'ownerless' | 'official_pdf' | 'official_calculator' | 'user';
}
```

Three things this model has to survive, all from the owner's own examples:

- **All-Mix is heavily pre-fertilised.** Its first steps have `products: []` and
  `labelKey: 'feed.step.noFeedYet'`. The due pill then reads
  `Noch nicht düngen — All-Mix ist vorgedüngt` and the confirm button logs a **water-only** event. A model
  that cannot say "don't feed yet" is not modelling the domain.
- **Light-Mix is lightly pre-fertilised** and starts feeding around week 2 — same structure, different
  first non-empty step.
- **BioTabs is a slow-release tablet regime**: `stepIndexBy: 'interval_days'`, `intervalDays: 35`,
  steps carrying `reminderKey: 'feed.reminder.retab'` and no `mlPerL` at all. It produces a **reminder**,
  not a dose. If the schema handles BioTabs it handles the shape of the problem.

**`ecBasis: 'delta_over_source'` is the correctness feature.** CANNA and others publish `EC +`, not EC:
*add the EC of your tap water to the recommended EC*. If source water is 0.4 and the chart says 1.4–1.8,
the meter should read 1.8–2.2. The UI shows the arithmetic rather than the answer alone:
`Ziel-EC 1,8–2,2 (Plan 1,4–1,8 + Leitungswasser 0,4)`. Source-water EC is asked once, on the plant sheet,
with `Weiß ich nicht` as a valid answer that switches the regime to `absolute` and says so.

**Where the step index comes from.** `stepIndexBy: 'stage_week'` uses `Plant.stage` and
`Plant.stageSince` — which the device itself can advance. This is the one thing no bottle-brand
calculator can do, because they have no device: **the 18/6 → 12/12 flip is detectable from `out_light`
history**, so when the photoperiod changes the app offers
`Du hast auf 12/12 umgestellt. Blüte ab heute?` / `You switched to 12/12. Flower starts today?` — one tap
to advance every plant's stage, and with it the feed step, the VPD band and the alarm bands.

**Advance by feed events where the regime says so.** `stepIndexBy: 'feed_count'` counts confirmed feed
events, not wall-clock weeks, because growers feed Tuesday and Friday and slip. `Plant.regimeAnchor`
pins where the schedule started so a mid-grow switch does not restart it.

**Autoflowers**: a `× 0.5` strength multiplier on the plant, no 12/12 flip event, stage advanced by
day counter. Essentially no manufacturer chart has an auto column, so this fills a real gap with nothing
borrowed.

**Every prefilled value stays editable, and deviating is normal.** Editing sets `regimeDeviated: true`,
which is recorded and never scolded. The next prefill uses **what you actually did last time**, not the
chart — this is the difference between a schedule that helps and one that nags.

### 6.4 How it is drawn on the chart

Panel 5, **Wasser & Dünger**, present only when the window contains water/feed events:

```
┌ Wasser & Dünger   EC mS/cm · pH · l ─────────────────────┐
│ 2.5 ┤   ░░░░░ Ziel-EC (Plan + Quellwasser) ░░░░░         │
│     │      ●        ●        ●        ●                  │  ● EC rein
│ 1.5 ┤      ○        ○         ○       ○                  │  ○ EC Ablauf
│     │   ╌╌╌ pH 6.2 ╌╌╌                                   │
│ 0   ┤ ▁▁▁    ▁▁▁     ▁▁▁▁     ▁▁▁                        │  Liter
└──────────────────────────────────────────────────────────┘
```

- The regime's `ecTarget` per step draws as a **stepped band** — the exact same visual language as the
  temperature setpoint band, which is the point: goal-vs-actual is one idea applied everywhere.
- EC in (filled) vs EC runoff (hollow) on one axis makes divergence legible. A `> 20 %` divergence draws
  the pair in `#D55E00` and adds a Spur marker `Ablauf-EC weicht ab` / `Runoff EC diverging`.
- Volume renders as bars at the panel floor. Cumulative volume per plant is available in the plant sheet.
- Feed events also appear on the Spur row 1 as a droplet glyph, so they are visible even with panel 5
  collapsed.

### 6.5 Brand posture

Invisible in the UI and it costs the design nothing:

- Brand names are **plain-text labels only**. No logos, no brand colours, no bottle imagery, no trade
  dress. Never inside a Terp Control feature name — the feature is `Dünge-Plan` / `Feeding plan`, and the
  control is labelled `Erde & Dünger` / `Medium & feed`.
- Numbers live in a **MongoDB content collection**, never baked into the webapp bundle, each carrying
  `source_url` + `retrieved_at` + `chart_version` + `kind`. Any single brand is removable in one DB
  update.
- Every regime card shows `Zuletzt geprüft: 12.03.2026` with a link to the brand's own chart. That is
  simultaneously the legal posture, a genuine trust feature, and protection against transcription errors
  — two retailer sites disagree by ~3× on CANNA Terra Vega dosing, and wrong numbers here burn real crops.
- Never seed from retailer or blog transcriptions. Source from the brand's own chart or calculator.
- Never *drive* a brand's server-side calculator to harvest outputs.
- A standing disclaimer, paraphrased and never quoted: `Richtwerte. Fang niedrig an und schau dir deine
  Pflanzen an.` / `Guidelines. Start low and watch your plants.`
- A published takedown address and a documented 48-hour notice-and-action policy shipped **before** the
  first brand entry.

## 7. Camera & timelapse

The camera is the reason this concept is worth building rather than merely arguable.

### 7.1 The camera still *is* the tent

When `hardwareInfo.webcam_did` is set and a recent still exists, `TentScene.backdrop = 'camera'` and the
tent interior renders **the actual photograph**, updating with the 30-second MQTT still capture the cloud
already performs. Kit objects, sensor chips and pots draw as overlay chips on top of it.

For user type 2 — "the same values, but correlated with his camera" — the home screen *is* the
correlation. There is no tile to open and no correlation to construct. The chip that says `54 %` sits on
top of the leaf it is describing.

Cost: near zero. `Image` rows already exist at 30 s cadence; `getDeviceImage` already accepts a share
token and an `imageToken`; the charts page already loads stills on hover.

Failure handling, because a photo backdrop can fail in ways an illustration cannot:
- No still newer than 10 minutes → backdrop fades to the illustration, with a small camera chip reading
  `Letztes Bild vor 2 Std.` / `Last picture 2 h ago`. **The scene never shows an old photo as if it were
  now.**
- Lights off → the still is nearly black. The backdrop applies a `--tc-gradient-panel` scrim so the chips
  stay readable, and the tent's night state is drawn regardless. A black backdrop is *correct* at night
  and reads as such.
- Share/public views: the backdrop respects `ShareLink.webcam`. If false, illustration only. This is
  checked in the scene component, not in a parent, so no share path can leak a frame.

### 7.2 The time slider is the timelapse

Dragging the plinth slider sets `?t=`. Everything re-renders at that instant:

- backdrop → the sprite tile nearest `t` (§4.5's `/image/strip` endpoint, so scrubbing costs no requests)
- sensor chips → the value at `t`, with the label changing from `vor 4 Sek.` to `Do, 14.03. 21:40`
- kit objects → their state at `t` (from the `out_*` series)
- pots → the plants that existed at `t`, at their stage at `t`; a plant started later fades out
- the plinth's capture buttons **disable**, replaced by `Zurück zu Jetzt` / `Back to now`

Releasing at the right end snaps to live. A double-tap on the slider jumps to `Jetzt`.

**This is the honest answer to "how do you show 30 days spatially": you don't — you show one moment
spatially and let the user move the moment.** Spatial layout carries *state at a time*; the chart carries
*change over time*. The tent is a film; the chart is the analysis. `Verlauf öffnen` on the slider opens
the chart at the same `t` with the crosshair already placed. One cursor, two views, one URL parameter.

The scrub range is bounded to what the sprite service can serve cheaply: **7 days on mobile, 30 on
desktop**, with a `Weiter zurück im Verlauf` link past that. Pretending the slider scales to three years
would be a lie the first time someone tried it.

### 7.3 Images, plants and stages

- **Time**: `Image.timestamp`, already there.
- **Plants**: a 30-second automatic still is **not** tagged with plants — tagging 2,880 frames a day per
  plant is absurd. Instead, attribution is *contextual*: opening any still shows which plants were alive
  and their stage at that timestamp, derived from `Plant.startedAt`/`archivedAt` and the stage events.
  A **user photo** taken through a capture sheet (`format: 'user/jpeg'`) carries `event_id`, and through
  it `plant_ids` — so "photos of Amnesia" is a real, cheap query.
- **Stages**: the film strip and the time slider both draw the stage dashed lines, so `Blüte ab hier`
  is visible while scrubbing. Seeing the plant change at the line it changed on is the payoff.

### 7.4 Timelapses

Today `Image.duration` is `'1d' | '1w' | '1m'` and timelapses have **no relation to a cycle, phase or
entry**. v1 keeps the three durations and adds nothing to the enum — the film strip plus the slider
already deliver "scrub your grow" without a new render pipeline.

v1.1 adds `duration: 'stage' | 'grow'`, generated server-side on stage transition and on
`Plant.archivedAt`, with the plant's name in the file. That extends the `duration` enum **and** the
unique index `{device_id, format, timestamp, duration}` — cloud-only work, no firmware, but not free, and
it is the honest place for it.

Retention is a design decision here, not an afterthought: diary photos currently leak forever
(`DELETE /image/:image_id` exists and the webapp never calls it; thinning filters `format: 'jpeg'` only,
so `user/jpeg` accumulates). The Tent ships a **`Bilder` section in `/account`** with a size figure and a
`Alles löschen` action, and the thinning job is extended to `user/jpeg` with a user-set retention
(default: keep everything attached to an event, thin unattached stills after 12 months).

## 8. Multi-user and clubs

A tent is a **place**. Places have people in them. That is the whole model.

### 8.1 Roles

New collection, because `Device.owner_id` is a single unindexed `String` and the authorisation model is
literally one equality test (`server/src/middlewares/auth.middleware.ts:172`):

```ts
export interface Membership {
  device_id: string;
  user_id: string;
  role: 'owner' | 'grower' | 'viewer';
  handle: string;          // per-tent pseudonym. NEVER an email, never a real name.
  attribution: boolean;    // may this member's actions be labelled with their handle
  createdAt: number;
  invitedBy?: string;
}
```

| Role | Can |
| --- | --- |
| **owner** | everything, incl. invite/remove, delete the tent, change privacy mode, unclaim |
| **grower** | change settings, control kit, add/edit plants, log events, upload photos |
| **viewer** | read the tent, the chart, the diary. No writes. |

Implementation reality, stated plainly: this is **not a flag**. It means writing
`isUserDeviceMiddelware` as *real* Express middleware (today it is an awaited helper each controller must
remember to call — `DELETE /device/logs/:device_id` already forgot), rewriting `auth.middleware.ts:172`
and `:207`, and loosening ~10 owner-scoped service queries. Budget it as ~3 weeks with tests, and it is
the riskiest single line item in the v1 scope.

Two deliberate simplifications that cut real work:

- **Invitation is a one-time link, not an email lookup.** `POST /tent/:id/invite` returns a single-use
  URL with a 7-day expiry. There is no account-lookup-by-email endpoint (there isn't one today), so
  there is no enumeration surface to design against. The inviter pastes the link into whatever they
  already use — which, for this community, is Telegram.
- **Roles are per device, not per organisation.** No teams, no org hierarchy, no seats. A club with three
  tents grants three memberships. The dossier's market narrowing ("only grow clubs", "a club is one or a
  few tents in one place") makes this correct rather than lazy.

### 8.2 Attribution

`PlantEvent.actor_id` + `actorHandle`. In the tent, an action logged in the last hour shows a small
handle chip on the affected pot. In the diary: `Gegossen · 2 l · Kim`. In the Spur, the glyph carries a
one-letter avatar.

`DeviceLog` gains an optional `actor_id` too, so "who changed the settings" is answerable — today with
several writers it is not.

**Attribution is a per-tent switch, defaulting off in `private` mode and on in `club` mode.** With it off,
`actor_id` is not written at all — not written and hidden, *not written*.

### 8.3 Privacy posture

`TentScene.privacyMode` is a real design decision with real consequences:

| | `private` (default) | `club` |
| --- | --- | --- |
| Attribution | off | on |
| Harvest weight prompt | never shown; the field exists but is only reachable through `Mehr` | shown |
| Plant count | shown to members only | shown to members only |
| Telemetry retention | 12 months, then downsampled to hourly | 5 years, opt-in |
| Export | `ANONYMISIERT` default | `PSEUDONYMISIERT` default |
| Delete | `Zelt löschen` wipes scene, plants, events, images in one action | same, with a 24 h grace |

`Ernte`: the harvest sheet asks for a date and, separately and optionally,
`Gewicht speichern? Du musst nicht.` / `Save a weight? You don't have to.` Harvest weights and plant
counts are the exact facts separating a lawful hobby from an offence in many jurisdictions, and
§ 28 Abs. 2 KCanG lets German authorities seize digital data with no prior judicial approval. The
resolution the dossier could not make is made here: **harvest is a first-class event with a date; the
weight is an optional field that is never prompted in `private` mode.**

**What this concept refuses to build**, explicitly, per §6.3 of the dossier:

- No per-member consumption or dispensing records (§ 26 Abs. 1 Nr. 5/6 KCanG — arguably Art. 9 GDPR
  health data, for data a grow controller has no need of).
- No grams ledger, no member directory, no real names, no date of birth, no membership numbers.
- No location of any kind: no GPS, no IP-geolocation persistence, no persisted timezone-from-IP, no
  "growers near you".
- No public feed with identities. A public **diary link** (v1.1) is not a feed: it is a URL you paste,
  with no identity attached and a revoke button. Zero of ~200 competitor App Store reviews praised a
  community feed; it is permanent moderation cost.
- No undeletable audit log by default. Tamper-evidence protects a *regulated* club against its own staff
  and **victimises an unregulated grower**. `club` mode uses append-only corrections
  (`PlantEvent.correctionOf`) rather than destructive edits; `private` mode allows real deletion.
- No `KCanG-konform` badge, no compliance claim, ever.
- No analytics or ad SDKs. EU hosting, stated plainly in `/account`.

The § 17 Abs. 2 participation log — the one legally-motivated multi-user feature worth owning — is
**v1.1**, built as a `PlantEvent` view filtered to `regulatoryRelevance: true`, not as a new subsystem.


`rpm` is already an allowed sensor in `VALID_SENSORS`. The fan object shows live RPM with the same

### 9.4 `light` — a lamp

Lamp object, glow keyed to `out_light`, photoperiod / sunrise / sunset / dim limit in its sheet. If a
VEML7700 is present, **DLI appears on the object itself** (`DLI = PPFD × photoperiod / 1e6`) — pure
arithmetic on stored data, and it closes a named competitive gap. A bed is offered, because a lamp over
a bed is a real setup.

### 9.5 `dryer`

`AGENTS.md` says the dryer type is dead. It keeps the `fridge` template and receives no further work.
Stated so nobody has to guess.

### 9.6 The non-regression promise

Nothing a fan / light / plug / fridge owner can do today disappears. The expert settings page keeps its
existing `ngSwitch` shell and its per-type components verbatim, reached from the plinth's
`Einstellungen`. What changes for them:

- their device stops borrowing another device's identity and gets its own i18n block
  (and, critically, **a controller stops being called "Terp Control FRIDGE GROW"** — an unnamed
  controller is currently *named* `devices.fridge.title` at `overview.component.ts:91-94`, and no
  `devices.controller` block exists in either language file)
- stale / offline / absent become visible for the first time
- the chart overhaul applies to them unchanged, including the setpoint band and the verdict
- the diary, plants and feeding are available if they want them and invisible if they don't
- back buttons and a language switcher exist

**What they lose:** the tent illustration, which was never theirs. Their scenes need their own art — four
extra illustration sets — and that is a real line item in §15.1.

The setup wizard already exists and is genuinely good (289 lines, adaptive step list
`name → [connections] → stage → plan → done`, hardware-aware, real error text). The Tent replaces its
`connections` step with **furnishing**, and keeps the rest.

**Step 1 — Name.** One field, prefilled `Mein Zelt`.

**Step 2 — Furnish.** The empty tent plus a shelf of kit along the bottom:

```
╔════════════════════════════════╗
║   Was steht bei dir im Zelt?   ║
║                                ║
║   ┌ gefunden ────────────────┐ ║
║   │ 🔥 Heizung   ❄ Entfeucht.│ ║   ← already placed, marked "gefunden"
║   └──────────────────────────┘ ║
║   (tent with those two in it)  ║
╚════════════════════════════════╝
 ─────────── Regal ────────────────
 [💡Lampe] [💡2.Lampe] [CO₂] [📷Kamera]
 [🌀Abluft] [🌿Pflanzen] [✎ Etwas anderes]
```

Tapping a shelf item places it in its fixed slot. **There is no drag-and-drop.**

The critical behaviour: **anything `hardwareInfo.sockets` already reports is pre-placed and badged
`gefunden` / `found` before the user touches anything.** A grower who paired their sockets on the device
itself — which is how Terp sockets pair — taps **nothing** at this step. `hardwareInfo.webcam_did`
pre-places the camera. `hardwareInfo.co2 !== 'off'` pre-places the CO₂ sensor.

`onboard.furnish.title` DE `Was steht bei dir im Zelt?` EN `What's in your tent?`
`onboard.furnish.found` DE `Das habe ich schon gefunden.` EN `I found these already.`
`onboard.furnish.shelf` DE `Stell dazu, was du sonst noch hast.` EN `Add whatever else you have.`
`onboard.furnish.skip` DE `Passt so` EN `That's it`

**The one question hardware cannot answer.** If the PWM output is in use, exactly one question appears:

```
Am Dimm-Ausgang hängt …
  ( ) eine Lampe          ( ) eine Abluft
```

If `Abluft` is chosen, the tent says so honestly:
`Dann weiß Terp Control nicht mehr sicher, wann Tag ist. Ich nehme deinen Zeitplan.` /
`Then Terp Control can't tell day from night for certain. I'll use your schedule.`
This sets `TentScene.pwmUse` and permanently changes day/night shading (§4.4).

**Step 3 — Stage.** `stage-preset-picker` reused verbatim: a grid of `.tc-preset-card`s with the
subtitle `24/21 °C · 70 % · 18 h` and `VPD 0,4–0,8 kPa`. `Wo bist du gerade?` One tap.

**Step 4 — Plants (skippable, and skipped by default).**
`Willst du deine Pflanzen einzeln führen?` / `Do you want to track plants individually?`
`[ Später ]` `[ Ja, anlegen ]` — `Später` is the primary. This is where type 1 opts out of §5 forever.

**Step 5 — Done.** `Fertig. Dein Zelt ist eingerichtet.` → the live tent.

**Tap count: 3 in the common case** (name accepted, kit all found, stage picked, plants skipped);
**~7 worst case**. The wizard's own step list already adapts by hardware, so a monitor-only device skips
step 2's shelf entirely.

The **30 MB of already-shot wizard videos** sitting unreferenced in `webapp/src/assets/wizard/`
(`connect.mp4`, `teachin.mp4`, `sockettype_*.mp4`, `overview.mp4`) finally get used: each shelf item's
"Wie geht das?" plays the matching clip inline. They are already in every production build; using them
costs nothing and removes ~30 MB of pure waste from the "unused" column.

`Zelt einrichten` gets a permanent entry in the plinth's Settings and in the side menu — today the setup
wizard is barely discoverable and there is no "re-run setup".

### 10.3 Language

A **language switcher** ships with this (`de` / `en`, persisted in `localStorage['tc-lang']`). Today
language is the browser language with no switcher and no persisted preference, in a product whose
primary market is Germany and whose owner is a German GmbH. A German grower on an English-locale phone
currently cannot get German. This is four lines of code and it has to stop being missing.

## 11. Per-user-type walkthrough

### Type 1 — Monitoring only, lazy

*Day 1.* Claims the controller. Wizard: name, nothing found on the shelf (no sockets paired), stage
`Vegetativ`, skips plants. The tent renders: an empty box, two sensor chips reading 24,1 °C and 61 %, a
VPD line, dotted outlines everywhere else labelled `Hier ist nichts`. The verdict says `Alles gut`.
He notices there is no dehumidifier control anywhere — correct, he has no dehumidifier — where today the
app would have offered him a humidity target, a deviation warning and a dehumidifier alarm preset.

*Day 2–6.* He opens the app maybe twice. The chips are current or they say how old they are. That is the
whole interaction. One night the tent greys out and reads `Keine Verbindung seit 03:12`; the last known
values are still visible underneath, greyed. He power-cycles the router.

*Day 7.* Curious, he taps `Verlauf`. Klima, VPD, day/night shading, and a verdict card:
`Im Zielbereich 84 % · Tag 91 % · Nacht 71 % · Längste Abweichung 2 Std. 10 Min. zu warm`. This is the
first thing the app has ever told him that he did not already know. He taps the tent's time slider back
to that excursion and sees the room at 03:00.

**Honest assessment: he is over-served by the picture and under-served by its cost.** An empty tent with
two chips is a lot of illustration for two numbers. The verdict card and the staleness vocabulary are
what he actually got; both would work in a list. §15.2.

### Type 2 — The same user, with a camera

*Day 1.* Same wizard, except `Kamera` is already on the shelf badged `gefunden` because
`hardwareInfo.webcam_did` is set. He taps nothing. The tent opens and the interior **is his tent**, a
30-second-old photograph, with `24,1 °C` and `61 %` floating over the leaves.

*Day 2.* He shows someone. This is the screenshot that sells the product.

*Day 5.* He drags the slider and watches four days pass in three seconds: the lamp glow rising and
falling, the plants standing up. The slider *is* the timelapse; he never learns there is a timelapse
feature.

*Day 7.* He opens `Verlauf`. The film strip sits above the panels on the same x-axis; uneven capture
gaps read as gaps. He drags the crosshair to the moment the temperature spiked and the picture above it
shows the tent door half open — his own hand in frame. **That is the correlation he wanted, and the app
did not make him construct it.**

**Best-served type in this concept, by some distance.**

### Type 3 — Controls certain aspects (CO₂ and heating)

*Day 1.* Pairs a heater socket and a CO₂ socket on the device. The wizard shows both badged `gefunden`.
He adds nothing else. His tent contains: lamp, heater, CO₂, sensors. **No dehumidifier appears
anywhere** — no object, no humidity target row, no humidity deviation warning, no dehumidifier alarm
preset. The humidity chip is still there because he still *measures* humidity, and tapping it explains:
`Ich messe die Luftfeuchte, aber ich kann sie nicht ändern — dafür steht nichts im Zelt.` /
`I measure humidity but I can't change it — there's nothing in the tent for that.`

*Day 3.* He taps the heater. The sheet says `Heizung · aus · vor 4 Sek.` and contains the day and night
temperature rows — because those are what the heater obeys. He also finds `Kurz testen`, taps it, and
hears the socket click in the next room. That is when he starts believing the picture.

*Day 6.* The heater socket loses wifi. `hardwareInfo.sockets` drops `heater`. The tent draws it hollow
with `Antwortet nicht` and a test button. Today this failure is completely invisible.

**Second-best-served type. The concept's central argument is written for him.**

### Type 4 — The whole tent

*Day 1.* Lamp on the dimmer, heater socket, dehumidifier socket, CO₂ socket, second lamp socket. All five
pre-placed. He also owns a humidifier and an exhaust fan — and here the concept has to be honest:
**there is no humidifier role and no exhaust role in the firmware.** The shelf offers `Etwas anderes` and
he places two props. They draw as flat outlines and **never take a state colour**, with the sheet reading
`Nur ein Merkzettel — Terp Control sieht dieses Gerät nicht.` He can log `Luftbefeuchter eingeschaltet`
as a note against them, and the note lands on the Spur.

That is unsatisfying, and it is the truth. Humidity can only ever go down in this system; there is no
humidification path. The alternative — drawing a humidifier that looks controllable — is exactly the
fail-open lie this concept exists to remove.

*Day 2.* The dehumidifier object is labelled `Kühler / Entfeuchter — dieselbe Steckdose`, because
`workmode` is `temp` and `out_dehumidifier` doubles as the cooler. He learns from the app, for the first
time, that his cooling and his dehumidifying are the same relay.

*Week 2.* His tent screen shows five live objects, three pots and a photo backdrop. He checks it the way
people check a fish tank. The chart's Geräte lane lists his kit in the same top-to-bottom order as the
tent wall, so the lane needs no legend.

**The metaphor is the product for him — and it also delivers him the clearest bad news in the app.**

### Type 5 — Closed-loop DIY (the fridge builder)

*Day 1.* He has a controller in a converted fridge with a compressor on the dehumidifier socket, a
heater mat, a DIY airflow fan on a dumb timer, and a soil-moisture probe on an Arduino he wrote himself.

He furnishes: heater and dehumidifier `gefunden`, fan as a prop, probe as a prop. Half his tent is
outline. He immediately switches to **Schema**, which is the first screen in this app that has ever shown
him `socket dehumidifier 192.168.1.45 ON 3:12` and `day.temperature=25`. He copies the dotted keys into a
shell script.

*Day 3.* He wants his probe on the chart. He cannot have it: `VALID_SENSORS` is a hard-coded allowlist in
`data.service.ts:12` and anything else is silently dropped. He logs readings as `measure` events, which
do appear on the Spur and in the Wasser & Dünger panel, and he is not happy about typing them.

*Week 2.* He writes a script that POSTs `measure` events through the API and stops thinking about the UI.

**Worst-served type, and this concept does not pretend otherwise.** His need is a documented read/write
API with custom measures — the highest-advocacy, most sceptical segment in the market, currently writing
their own Go apps — and The Tent gives him a picture of things it cannot see. Schema is a consolation,
not an answer. §15.9.

### Type 6 — A grow club with three people on one controller

*Day 1.* The club's grow lead claims the controller, furnishes it, sets `privacyMode: club`. Attribution
switches on. She creates six plants in the bed with strain names and sets `Biobizz All-Mix` on each.

*Day 2.* She sends two one-time invite links over Telegram. Kim and Ali join, pick handles `Kim` and
`Ali`, and land on the tent. Nobody typed an email address into a search box; there is no member
directory to enumerate.

*Day 4.* Ali waters. Three taps: `Gießen & Düngen`, deselect two pots that were done yesterday, `Passt`.
The event carries `actorHandle: 'Ali'`.

*Day 5.* The lead opens `Tagebuch`: `Gegossen · 2 l je Pflanze · Ali · Do 14.03. 19:02`. She filters by
`Kim` to see what Kim did last week. **"Who did what, and how did the plants react" is one screen**, and
the plants' response is the chart directly under it on the same x-axis.

*Week 3.* An `Ernte` on two plants. The sheet asks for a date; the weight field is present but optional
and unprompted. Nothing about grams per member, nothing about who consumed anything, no real names
anywhere in the system.

**Third-best-served. The spatial model earns it: a tent is a place, and shared places want to know who
was in them.** The § 17 Abs. 2 participation log is v1.1.

### Type 7 — A user with an old fan and an old plug

*Day 1.* Opens the app after the update. Two scenes on the shelf: a duct with a fan, and a wall socket.
Neither is a tent. Nothing he could do before is missing; the settings form is one tap away on the
plinth.

*Day 2.* His plug's schedule checkboxes finally have labels instead of `settings.limits.time.enabled`.

*Day 4.* The fan's RPM chip says `vor 11 Min.` and he realises the app has been showing him a stale
number for months.

*Week 2.* He opens `Verlauf` out of curiosity and finds an actual chart with an axis on his phone.

**Honestly served, not centrally served.** He is served by the *renderer*, not by the *idea*. If the tent
illustration is the concept's soul, he never sees it. That is acceptable per the owner's framing, and it
is also a real weakness (§15.3).

## 12. Stoner, normal, techie

One design, three depths, and the depth control is **not** a mode switch the user has to understand.

### Stoner

The picture. That is the whole product for them.

- **Colour and shape carry the state.** Green glow = lamp on. Grey object = off. Amber = look at me. They
  never have to read a number to know whether the tent is fine.
- **One sentence, ever**: `Alles gut` / `Ich behalte es im Auge` / `Da stimmt was nicht`.
- **Tap the thing to reach the thing.** No menu path, no settings tree, no vocabulary. The lamp is at the
  top of the tent because the lamp is at the top of the tent.
- **Two verbs on the plinth**, always in the same place: `Gießen & Düngen` and `Notiz`. Watering is two
  taps from cold start.
- **It thinks for them**: the plinth button carries `fällig`, the sheet arrives prefilled, and `Passt`
  is a big green button. They never see a table of ml/L.
- **It reminds them**: a due feed, a re-tab reminder, `Du hast auf 12/12 umgestellt. Blüte ab heute?`
- **Nothing they cannot act on is shown.** No target for a machine that is not in the picture.
- **Nothing is presented as current when it isn't.** The most stoner-hostile thing an app can do is lie
  quietly; staleness is drawn, not written in small print.

### Normal

- The kit sheets hold the actual targets, using `value-edit-row` — tap the row, `[−] slider [+]`, which
  is already the canonical numeric control and already has the `rangeGuard` directive that keeps a slider
  inert until deliberately touched (mobile scroll protection).
- The stage picker with its VPD subtitles.
- Plants as pots, with a feeding plan that prefills and never nags when you deviate.
- The chart with panels, target bands and a verdict card — five stacked panels with axes, not fifteen
  invisible ones.
- The diary, filterable by plant and type, with photos.
- Share links and week export.

### Techie

- **Schema skin.** The same scene, same layout, rendered as an engineering diagram: role identifiers,
  socket IPs from `socket_ips`, duty cycles, ages in seconds, `workmode`, the dotted configuration keys
  verbatim, firmware id, camera did, `lastseen`. One toggle in the header, persisted.
- **Expert settings survive untouched** — the existing `ion-segment` Simple/Expert with the recipe editor,
  the full settings form, aux devices, cloud settings and the full alarm editor.
- **The chart tells the truth about its own data**: min/max envelope rather than a lone mean line, the
  leaf-temperature offset printed on the VPD panel, `Daten: 97 % vorhanden`, band provenance labelled
  (`Alarm` vs `Ziel ± Toleranz` vs `Empfehlung`), and the interval dropdown constrained so `3y × 5s`
  cannot be requested.
- **`Als Tabelle anzeigen`** on every panel, and CSV export including actuator state — which an
  AC Infinity reviewer asked for by name and no vendor provides.
- **Honesty about limits, in the UI**: props say the app cannot see them; `Antwortet nicht` says the
  socket is silent; unknown-firmware says the scene is the user's declaration.

**Why one design instead of three:** the three depths are the *same objects at three resolutions*, not
three information architectures. The stoner sees a glowing lamp; the normal user taps it and gets a
photoperiod; the techie flips to Schema and gets `PWM out_light 80.0 % t+4s`. Nobody navigates anywhere
different, so nobody can be lost in a mode they didn't choose, and support can say "tap the lamp"
regardless of who is asking.

## 13. Scope

### v1 — ships with the hardware, October 2026

**Prerequisites (P0 — the product is not credible without them, and three of them block the rest):**

1. Controller identity: `SceneTemplate` + a `devices.controller` i18n block in `en.json` and `de.json`.
   A controller stops being called a fridge.
2. Freshness: the live/stale/offline/absent vocabulary, everywhere, from one shared helper.
3. Capability: per-role truth from `hardwareInfo.sockets` reconciled against `TentScene.slots`, failing
   **closed** to the user's declaration. `deviceControlCapability()`'s three buckets are deleted.
4. Dead controls removed from the UI: the entire `daynight.floating` / `float_start` / `day_duration` /
   `light_duration` beta (read by **no firmware anywhere** — zero grep hits across `firmware/`), plus
   `lights.maintenanceOn`, `co2.sunsetOff`, `daynight.linearChange` for controllers.
5. Flux injection + the unbounded `limit`-after-`yield` in `data.service.ts` — **blocks §6's EC/pH
   measures**.
6. Server-side log pagination — **blocks §5's event volume**.
7. InfluxDB retention + a downsample task — raw 5 s samples are currently kept forever.
8. The six live i18n bugs, and translated chart series names.
9. `/classes` gets its missing route guard.

**The concept proper:**

10. Scene renderer + `tent` template + `fridge` / `fan` / `light` / `plug` templates.
11. Furnish flow + wizard integration + the wizard videos + the language switcher.
12. Time slider bounded to 7 days mobile / 30 desktop, `/image/strip` sprite endpoint, camera backdrop.
13. Schema skin.
14. Chart v2: ECharts migration, panels 1/2/3/4/6/7, setpoint bands, day/night shading, outputs lane,
    annotation rail, film strip, scorecard endpoint + verdict card, mobile interaction rules, Okabe-Ito.
15. Plants + `PlantEvent` + the backfill, with the "does this look right?" confirmation.
16. Water & feed capture, panel 5, and the regime engine with **ownerless schedules + the owner's five
    named media/regimes** in a MongoDB content collection.
17. Membership (owner / grower / viewer) + attribution + invite links + `privacyMode`.
18. `Woche exportieren` as JSON + Markdown, and a CSV export including actuator state.

**Cut from v1, deliberately:** free placement / drag-and-drop, the VPD matrix, stage and grow timelapses,
the public diary URL, Discord/Telegram/webhook update destinations, the § 17 participation log,
brand-schedule expansion beyond the seed list, the Home Assistant integration, offline/service worker,
native apps.

**Realism check.** This is a large v1 for a small team over ~13 months, and items 5, 6, 14 and 17 are the
ones that will slip. The honest de-scope order, in order:

1. **Membership (17)** slips first. It is ~3 weeks of authorisation-model surgery and clubs are the one
   user type that can wait a point release. Ship a read-only share link for them in the meantime — that
   already exists.
2. **Schema (13)** slips second. It is cheap but it is not load-bearing for launch.
3. **The camera backdrop (12)** must **not** slip — it is the concept's single most demonstrable idea.
4. **Freshness (2) and capability (3)** must not slip under any circumstance. They are the reason for the
   redesign.

### v1.1 — first half of 2027

Public diary URL (`/d/{slug}-{5char}`), Markdown + BBCode post generator with hot-linked images,
Discord / Telegram / generic webhook update destinations (decoupled from alarms — `webhookTemplate.ts`
already does `{{placeholder}}` substitution in json and url modes, and `alarm.service.ts` already
supports GET/POST/PUT with custom headers, so what is missing is a non-alarm trigger, image attachment
and a preset library — plus an SSRF guard, a timeout and a retry queue, none of which exist today).
Stage/grow timelapses. The VPD matrix. The § 17 participation log. Run-over-run comparison
("day 34 of this grow vs day 34 of the last"). Free placement in the furnish editor, if anyone asks.

### v2 — 2027+

The documented public read/write API with `x-api-key` scoped per tent (Pulse's shape, plus writes, which
no monitoring vendor can offer because they do not own the hardware). Home Assistant. Cannanas /
420cloud as a device-attested environmental layer. Brand-schedule expansion behind written permission.

### Firmware asks — one, and it is optional

**Add `other1`, `other2`, `other3` to `getSocketRolesList()`.** The NVS key helpers for them already
exist at `firmware/src/wifi.cpp:1680-1682` (`sock_oth1`, `sock_oth2`, `sock_oth3`); they are simply not
in the roles vector. That is a handful of firmware lines plus the server whitelist at
`device.service.ts:859` plus three shelf items, and it converts type 4's humidifier and exhaust fan from
**props** (drawn flat, never a state colour, un-actuatable) into **objects that at least report their
switch state**. It does not give them a control law — a humidifier on `other1` would be a dumb on/off
that nothing regulates — so it is a genuine but partial improvement, and it is the only firmware line
item this concept asks for. If the answer is no, the props path is the design and §11's type 4
walkthrough stands unchanged.

## 14. Non-goals

1. **Not a dashboard.** No configurable widget grid, no "add a tile", no layout editor. The layout is the
   room.
2. **Not free placement.** Slots are fixed per template in v1. Dragging a lamp two pixels left is not a
   feature; it is a support burden and a migration.
3. **Not a 3D tent.** No perspective, no rotation, no WebGL. A flat cross-section is legible at 320 px
   and 3D is not.
4. **Not a facility manager.** No rooms, zones, racks, benches, crop steering, labour tracking or
   cost-per-gram. The owner narrowed the market to hobbyists and clubs; a club is one or a few tents in
   one place.
5. **Not a compliance system.** No per-member dispensing, no grams ledger, no authority export formats,
   no `KCanG-konform` badge. Winning that race means owning 23 differing authority formats, 5-year
   retention, an Art. 28 AVV per club and liability for wrong exports.
6. **Not a community.** No feed, no comments, no follows, no discovery, no "growers near you". A public
   diary *link* (v1.1) is a URL you paste, not a place you moderate.
7. **Not two-way diary sync.** No grow-diary platform can be 2-way synced: GrowDiaries has no public API
   and is Cloudflare-hardened, Grow with Jane's ToS §(c)(7) forbids automation and its backend is
   Firebase, and SeedFinder's API has been dead since July 2024. The feature is called
   `Woche exportieren` / `Export week`, and it is honest.
8. **Never auto-post to Instagram, Threads, TikTok or Reddit.** A failed Discord post means a revoked
   webhook. A failed Instagram post means the **user** loses their account with no appeal, and Terp
   Control was the proximate cause.
9. **No branded footer on user posts.** § 6 KCanG bans cannabis advertising and sponsoring with fines to
   €30,000, read broadly. An auto-appended "Powered by Terp Control" on thousands of German growers'
   cannabis posts is the single riskiest string in the feature.
10. **No irrigation automation.** There is no irrigation or dosing hardware. Watering and feeding are
    capture-and-recall. The app will never claim to have watered anything.
11. **No brand logos, colours, bottle imagery, or brand names in Terp Control feature names.** Word marks
    as plain text labels only.
12. **No harvest weight prompting in `private` mode.** The field exists; it is never asked for.
13. **No location, no analytics SDK, no ad SDK, no real-name enforcement, no non-EU hosting.**
14. **Not offline-capable.** There is no service worker and adding `@angular/service-worker` is a new
    dependency and a build change. This concept does not claim to work on the tent floor with bad wifi.
15. **Not a native app.** Capacitor 4 is present but `capacitor.config.ts` is untouched scaffold
    (`io.ionic.starter`) and there are no `android/` or `ios/` projects.
16. **Does not preserve `convertEventsToGrowCycles` as runtime behaviour.** It becomes a one-time
    backfill. Renaming a plant must stop forking its history.
17. **Does not use `device.configuration` for anything new.** Every new entity is cloud-side.

## 15. Honest weaknesses

Ordered by how badly they hurt.

### 15.1 The art is a hard dependency, and it has no graceful degradation

Five scene templates × two skins × light and dark × legible at 320 px is a real illustration
commission — the largest single non-engineering line item in this concept, and no competing concept in
this bake-off carries it. If the illustration set is late, the concept does not ship in a reduced form;
it ships as boxes, and boxes are worse than today's gauge grid.

Mitigation, partial and honest: Schema is a *complete alternative rendering* built from CSS and text
only, so a delayed illustration set degrades to "the techie skin is the default for a while" rather than
to nothing. It is a lifeboat, not a plan. And the four legacy templates (§9) are pure cost with no
strategic upside — they exist so type 7 is not abandoned, and they will be the first art to be cut and
the first thing critics point at.

### 15.2 A picture is less information-dense than a list

Today's overview shows four `value-display` gauges — each with a value arc, a limit arc, a needle, a 1 h
average line and a target line — in a 2×2 grid. That is a lot of information per pixel. The tent spends
pixels on *background*: liner, floor, walls, the space between objects. For a user who opens the app to
read numbers and leave, the tent is **strictly worse than what exists**.

That is the real cost of the metaphor and it is not recoverable by tuning. Schema recovers density for
techies; the contents list recovers it for accessibility; neither recovers it for a normal user who just
wants four numbers. Type 1 pays this cost for the least benefit.

### 15.3 It does not compose upward, and type 7 is served by the exception path

Three tents means three pictures and a picker. There is no "house view" worth building — a room
containing rooms is not a useful drawing. `/tents` is a shelf of thumbnails and it works to perhaps eight
before it should honestly become a list. A club with a dozen devices gets a list, which means the
concept's central idea evaporates exactly where the club user type needs it most.

And type 7 never sees the idea at all. A plug is not a tent. He is served correctly, by the renderer,
which means the concept's answer to a whole user type is "our exception path is good". That is defensible
and it is also thin.

### 15.4 A wrong picture is more harmful than a wrong list

Pictures are persuasive. A user who furnishes their tent wrong now has a *convincing* wrong model. The
reconciliation machinery (§3.4) only covers the five roles the firmware reports; a fan on a dumb socket,
a passive intake, a DIY reservoir are invisible to it forever.

The mitigation is the prop rule — unverifiable objects are drawn flat and **never take a state colour** —
and it is a real mitigation, but it depends on users reading a visual convention. Some fraction will see
a humidifier drawn in their tent and believe the app is managing it. That fraction is not zero, and the
consequence is a dead crop and a support ticket that begins "your app said".

### 15.5 It is hostile to screen readers by construction

An SVG scene is a poor semantic surface. The **Contents list** (`Inhalt`) is a first-class alternate
view, not an `aria-label` bolted on: a plain `ion-list` of every object with its state, age and controls,
reachable from the header, auto-selected for `prefers-reduced-motion` and short landscape viewports.

That is a second UI to build, translate and keep in sync forever. Every change to the scene is two
changes. Concepts built on lists get accessibility approximately for free; this one buys it.

### 15.6 Landscape phone does not work

The tent is tall. In landscape on a phone the scene is ~200 px tall and everything collides. The
concept's answer is to switch to the contents list below 480 px of height — which is a correct answer and
also an admission that the home screen has a device orientation in which it does not exist.

### 15.7 Scrubbing is delightful and analytically weak

The time slider is the demo. It is also a low-information way to inspect history: you can see one moment
at a time, and finding the interesting moment requires the chart anyway. A critic will say the tent is a
launcher with an expensive background, and for the analysis task they are right. The defence is that the
tent is not the analysis surface and never claims to be — but "the beautiful screen is not where the work
happens" is a genuine structural weakness, not a positioning statement.

### 15.8 Performance is a real risk, not a formality

An inline SVG with live-updating `<foreignObject>` chips, a photographic backdrop, and a scrub interaction
that re-renders the whole scene, on a mid-range Android, in an Angular 15 app with default change
detection. The mitigations are known — `OnPush` on the scene component, the sprite endpoint so scrubbing
costs no network, `requestAnimationFrame`-throttled scrub, `KeyedCache` for every derived template
getter (mandatory in this codebase or `ngFor` rebuilds the DOM every change-detection cycle) — but this
has to be measured on real hardware early, and if scrubbing stutters the concept's best feature is its
worst.

Component SCSS budget is **2 kB warn / 4 kB error**. A scene component's styles will not fit; the scene's
CSS has to live in `theme/` as shared classes, which is a small architectural imposition worth naming.

### 15.9 Type 5 is served badly and the concept knows it

The DIY closed-loop builder's kit is invisible to the firmware, so his tent is mostly props. His actual
need — custom measures, a documented read/write API, MQTT, Home Assistant — is v2 in this concept and is
not helped at all by drawing pictures. `VALID_SENSORS` is a hard-coded allowlist; his soil probe can only
enter as a manual event. Schema is a consolation prize.

This is the highest-advocacy segment in the market. A concept that under-serves it under-serves the
people who write the forum posts.

### 15.10 It might read as a toy

€289 hardware, a German market, `Messen. Regeln. Ruhig schlafen.` A cartoon tent risks reading as
unserious to exactly the buyer who is comparing this against TrolMaster. The camera backdrop is the
strongest defence — a photograph of your actual tent is not a cartoon — but that defence only exists for
camera owners, which is a paid upgrade. For a €289 controller with no camera, the home screen is an
illustration, and the illustration style will decide whether this concept is loved or mocked. That
decision is not an engineering decision and it is not recoverable in code.

### 15.11 Two things in this document are asserted, not measured

- The claim that Okabe-Ito plus small multiples is *more* readable than today's overlay is well
  supported by the dossier, but it has not been tested with an actual German hobby grower on an actual
  phone. It should be, before the chart is built.
- The claim that furnishing takes 3 taps in the common case assumes `hardwareInfo.sockets` is populated
  and accurate for a freshly claimed device. That is verifiable in an afternoon with
  `./simulate-device.sh setup` + `hwinfo sockets=heater,light` and **must be verified before this
  concept's onboarding claim is repeated to anyone**. There is no excuse for an unverified UI claim in a
  repo that ships a full device simulator.
