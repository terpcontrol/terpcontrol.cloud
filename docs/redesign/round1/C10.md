# C10 — "Durchgang" (Run Over Run)

**Design philosophy:** the app is about comparing grows.
**Author's stance:** the current run is one of many. The x-axis is day-of-run, not wall-clock. The killer
view is this run drawn on top of your last one. And the comparison is built on *climate execution*, not on
grams — because grams are the number that turns a hobby into a criminal file.

---

## 1. Thesis

**Terp Control's root object is a `Durchgang` — a run — and every number the app shows carries a second
number beside it: what that same number was at the same day of your last run.**

The big idea. Every competitor, and Terp Control today, models a grow tent as a *device with a live
reading*. That framing has no memory: the chart resets when you scroll, the diary is an undifferentiated
log stream back to 2024, and the question a repeat home grower actually asks — *"is this one going better
than the last one?"* — is not answerable from any screen in any product on the market. C10 makes the run
the spine of the information architecture. A run has a day 0, a stage sequence, a day counter, a set of
per-day summary statistics, optional plants, and an ending. Because runs are objects, they can be laid on
top of each other: the same day-of-run x-axis, the same panels, the same targets, this run solid and the
last one a grey ghost. And because the comparison substrate is a tiny per-day summary row (~200 bytes)
rather than raw telemetry, **the product can delete aggressively and still compare** — which is how a
comparison product survives the fact that harvest weights and plant counts are legally dangerous data in
the primary market. The privacy answer is not a checkbox. It is the storage architecture.

## 2. Information architecture

### 2.1 The one new object, and what it replaces

Today a "grow cycle" is *inferred in the browser* by `convertEventsToGrowCycles()`
(`grow-report.component.ts:691-747`): it scans lifecycle log rows and starts a new cycle whenever the stage
ordinal rolls back or the trimmed `lifecycleName` string differs. A re-veg fabricates a plant. A rename
forks the history. Cycle identity in URLs is a *start timestamp*, so editing an entry's time breaks share
links.

C10 deletes that function from the client and makes it a **one-time server-side backfill** that writes real
`Run` rows. Everything else in this document depends on that single change.

All three restricted modes must keep working (`resolveDeviceAccessInfo`: `locked`, `canEdit`,
`webcamAllowed`, `chartsAllowed`; `auth.isDemo`; public view). Rules:

- A share link opens **without** the tab bar. It renders exactly the page it was cut for, as today.
- The demo session gets the full tab bar with `Vergleich` populated from the demo device's seeded runs —
  the demo is the one place a first-time visitor can see the thesis before owning hardware.
- `Vergleich` is hidden entirely when `chartsAllowed === false`.

### 3.2 Block D is the thesis, and it is one line of copy

`Lauf 2 an Tag 34: 74 %` is the entire concept compressed into a home-screen row. It is computed from a
`RunDayStat` row that already exists (§5.2), costs one indexed lookup, and it is the reason a user opens the
app on day 34 of run 3 rather than glancing at the device's own display. Tapping it goes to `Vergleich`.

When there is no previous run, the row is replaced — not hidden, replaced — by:

> **Erster Durchgang.** Ab Lauf 2 steht hier, wie es beim letzten Mal lief.
> *(First run. From run 2 on, this row shows how the last one went.)*

That is an honest promise, and it is also the retention hook: the app tells you, on day one, that it gets
better if you come back.

### 3.4 Stale, offline, absent — four states, never faked

The dossier calls this the **#1 complaint across all five consumer brands**. C10 treats freshness as a
property of the screen, not a badge in a corner.

| State | Condition | Block B | Tiles (C) | Verdict (D) | Capture (E) |
| --- | --- | --- | --- | --- | --- |
| **Live** | last sample < 2 × expected interval | `● Live · vor 12 s`, `--tc-text-success` | full colour, goal row shown | shown | enabled |
| **Stale** | 2 × interval … 10 min | `◐ Stand von 14:02`, `--tc-text-warning` | value at 65 % opacity; sparkline tail drawn with a 4 px dashed stroke instead of solid; goal row stays | shown, with `Abdeckung 91 %` beneath | enabled |
| **Offline** | > 10 min since last sample | `○ Offline seit 14:02 (vor 3 Std)`, `--tc-text-danger`, full-width tinted band | value rendered in outline text with the reading time under it; **goal rows are hidden** — a target is meaningless when nothing is regulating | greyed with `Daten unvollständig`, percentage suppressed below 80 % coverage | **still enabled** — you can log a watering while the wifi is down |
| **Absent** | no sample of that measure ever, or `hardwareInfo` says no sensor | — | `—` (the `value-display` component already renders this) plus subtitle `Kein Sensor`; tile is not removed, so the layout is stable | measure excluded from the verdict | — |

Two rules that follow from capability, not from data:

- A tile shows a **goal row only if something can act on it**. Per-role truth from
  `parseSocketRoles(hardwareInfo.sockets)`, not the three-bucket `deviceControlCapability()` that fails open
  on missing keys. No dehumidifier socket → the humidity tile shows the reading and the subtitle
  `Kein Gerät dafür angeschlossen`, and the humidity measure is excluded from the in-range verdict. This
  single change kills gap P0 #3.
- Because **humidity can only ever go down** (there is no humidification path in the hardware), the humidity
  goal is drawn as a **ceiling**, `max. 55`, not as a centred target with a band on both sides. Drawing a
  symmetric band around a number the device can only approach from one side is a lie about the machine.

## 4. The chart overhaul — `Verlauf`

Library: **Apache ECharts 6, tree-shaken, hand-rolled ~50-line Angular directive** (owner decision;
`chart.js` / `ng2-charts` / `chartjs-adapter-luxon` deleted at the same time). Honest cost: ~195.6 KB gz vs
~132.7 KB gz for Highstock, ~68.8 KB repaid by the Chart.js deletion. The justification is licence and
capability (`markArea` / `markLine` / `grid[]` / `axisPointer.link` / `sampling`), not bundle size.

**Replacement for a load-bearing default:** Highstock's implicit `dataGrouping` is the only reason a
4,320-point render is currently cheap. ECharts has no equivalent by default, so `sampling: 'minmax'` on
every value series is not polish — it is mandatory, and it is also the right choice, because LTTB smooths
away exactly the bang-bang oscillation a grower is looking at.


X-axis primary labels in run mode: `T30`, `T31`, `T32` …, with a second, smaller ruler under it showing
`Blüte 8` / `Blüte 9` (day-of-stage) and, greyed at the far bottom, the wall-clock date. Switching the

Timespan presets gain a fourth: `Lauf` (the whole run so far). `3y × 5s` is removed from the reachable
combinations — interval is now constrained by timespan, which also closes the self-DoS half of gap P0 #8.

### 4.3 How goal-vs-actual is drawn — precisely

Three sources of "goal", drawn one at a time, **labelled**, in this priority:

1. **Alarm-Schwelle** — the user's own declared unacceptable. Hard edge: a 1 px solid line in
   `--tc-text-danger` at `Alarm.upperThreshold` / `lowerThreshold` (today these are read by nothing in the
   chart pipeline). No fill.
2. **Sollwert ± Toleranz** — from `device.configuration` `day.temperature` / `night.temperature`, drawn as a
   **dashed stepped line** that steps at `daynight.day` (21600 s) and `daynight.night` (79200 s) *in the
   device's local timezone*, with a soft `markArea` band at ±1.5 °C / ±7 % RH (the tolerances the existing
   `grow-assistant-card` already uses for its green/warning pills).
3. **Stufen-Empfehlung** — the stage preset's advisory range, including `vpdRange`. Faintest tint, and the
   only band shown for VPD, because VPD is never a device setpoint.

The **deviation fill** is the signed area between the actual line and the setpoint line — warm tint above,
cool tint below. It is **never** a fill to the axis. Today's `type:'area', fillOpacity:0.1, threshold:null`
encodes nothing at all and is deleted.

The **min/max envelope** is drawn only on the panel the user has designated primary (three Influx queries
instead of one, for one measure). A single `mean` line over a bang-bang controller is a lie.

### 4.4 Day/night shading

Derived from **measured `out_light > 0`** where the series exists, falling back to the configured
`daynight` schedule, with `lights.sunrise` / `lights.sunset` rendered as gradient edges. Explicit timezone,
stored per device — a 12/12 flip near a DST boundary otherwise drifts an hour.

Diagnostic value: because the band is *measured*, a failed contactor shows up as a **missing band** while
the schedule says it should be there. The chart draws a hairline "geplant" outline where the schedule
disagrees with reality. That is a whole class of silent hardware failure made visible for free.

In `Tag des Laufs` mode the shading repeats per day-column, which makes the 18/6 → 12/12 flip visible as a
step change in band width across the whole run — and that step is what auto-detects `photoperiodFlipAt`
(§6.3).

### 4.5 Mobile interaction and colour

- One finger = page scroll. Two fingers = pan/zoom (`dataZoom: {type:'inside'}`). Tap or long-press = pin
  the crosshair.
- **No floating tooltip.** A **pinned scrubbing header** sits above the chart: a compact two-column table,
  one row per visible panel, updating as you drag. A fingertip occludes a tooltip; it cannot occlude a
  header.
- Range presets are ≥44 px targets and stay the primary control.
- **Axis labels are never hidden.** Below 320 px the axis drops to 3 ticks and the unit moves into the panel
  title. An axis-less chart is not a chart, and today's `<320 px` suppression produces exactly that.
- Colour: **Okabe-Ito**. Temperatur `#D55E00`, Feuchte `#0072B2`, VPD `#009E73`, CO₂ `#CC79A7`,
  Licht `#E69F00`, Blattemperatur `#56B4E9`.
  **`#999999` grey is reserved, product-wide, for "a different run".** That is a semantic rule, not a
  palette entry: grey never means a measure, so a ghost is always legible as a ghost. Setpoint lines are the
  measure's own hue at 60 % lightness, dashed. `darkMode:'auto'` replaces the hand-written 30-property
  Highcharts theme and the `MutationObserver`.
- A `Als Tabelle anzeigen` disclosure under every panel. No OSS charting library matches Highcharts'
  accessibility module, and Terp does not load that module today anyway.

opacity, `z: 1` (behind everything), no fill, no markers, excluded from the crosshair table unless the
scrubbing header is expanded. A legend chip reads `Lauf 2 (Ghost)` with an `×`.

thing in the concept.

### 4.7 §7.2 techniques — adopt / reject

| # | Technique | Verdict |
| --- | --- | --- |
| 1 | Stacked small multiples, shared x, linked crosshair | **Adopt.** Fifteen hidden scales as translucent areas is indefensible; Few's dual-axis paper is unqualified. At most two units per panel, only when physically coupled (air + leaf temp). |
| 2 | Draw the setpoint, banded, signed deviation fill | **Adopt.** Highest-leverage change in the whole document and it needs no new API — the setpoints are already in `device.configuration` on the client. |
| 3 | AGP-style scorecard | **Adopt, reshaped.** The scorecard is per **run-day**, persisted as `RunDayStat`, not computed for the visible window. A window-scoped scorecard cannot be compared to anything. Computed **server-side on raw Influx samples** — `aggregateWindow(fn:mean)` destroys the excursions the metric exists to count. Grey out below 80 % coverage. |
| 4 | Day/night shading from measured `out_light`, explicit tz | **Adopt**, plus the "geplant vs. gemessen" hairline diagnostic. |
| 5 | Annotation rail under the axis, clustered, max 2 rows | **Adopt.** Today's height-1 hover-only columns are unusable on touch, on a mobile-first product. |
| 6 | Outputs as a state-timeline lane | **Adopt.** Also the substrate for the per-output runtime totals in the compare scorecard. |
| 7 | Min/max envelope | **Adopt**, primary panel only, 3 queries. |
| 8 | Moving VPD band + temp×RH matrix with trajectory | **Adopt the moving band** (it is literally day-of-stage and is the same idea as this concept). **Reject the matrix for v1.** It is a second mental model, it does not fold onto a day-of-run axis, and it cannot be compared run-over-run — which makes it off-thesis. Defer to v2 as a panel in `Vergleich`. Leaf-offset assumption ("Blatt = Luft − 2.0 °C") is printed on the VPD panel header, and disappears when a real MLX90632 is present. |
| 9 | Film strip as an axis, sprite + index | **Adopt**, and it is cheaper here than anywhere else because a run is a natural sprite window. `Image.timestampEnd` (mp4) renders as a bracket, not a point. |
| 10 | Mobile rules, pinned scrubbing header, stop hiding axes | **Adopt wholesale.** |
| 11 | Okabe-Ito | **Adopt**, plus the reserved-grey rule for ghosts. |
| 12 | DLI and dew point | **Split.** DLI **only when a VEML7700/PPFD sensor exists** — computing DLI from `lights.limit` percentage would be inventing a number with a unit on it, and this concept's comparisons must survive being checked. When there is no sensor, show **`Lichtstunden/Tag`** integrated from `out_light`, which is honest, free, and a better run-over-run metric anyway. **Reject dew point for v1** — it adds a series without adding a comparison. |

## 5. The multi-plant diary

### 5.1 New entities

All cloud-side in MongoDB, keyed by `device_id`. All new fields optional, with read-time normalisers and one
idempotent boot-time backfill — the house style, because there is no migration tooling.

```ts
// collection: runs
interface Run {
  run_id: string;                 // nanoid, stable, safe in URLs and share links
  device_id: string;
  owner_id: string;
  name?: string;                  // user-editable; renaming NEVER forks anything
  index: number;                  // 1,2,3… for "Lauf 3" without a count query
  startedAt: number;              // day 0 anchor, epoch ms
  endedAt?: number;
  timezone: string;               // IANA, captured at start; day boundaries depend on it
  stageChanges: { stage: DiaryLifecycleStage; at: number }[];  // authoritative, ordered, repeatable
  photoperiodFlipAt?: number;     // detected from out_light, user-confirmable
  expectedFlowerDays?: number;    // for "Tag 34 von ~63"; from the preset or the user
  contributeAnonymously: boolean; // default false
  summaryOnly: boolean;           // true once reduced to a summary (§8.3)
  createdAt: number; updatedAt: number;
}

// collection: plants
interface Plant {
  plant_id: string;
  run_id: string;
  device_id: string;              // denormalised for the owner-scoped query
  label: string;                  // "A", "2", "Gorilla links" — what the user actually says
  strain?: string;                // free text. NEVER required. NEVER a dropdown from a strain DB.
  source?: 'seed' | 'clone' | 'unknown';
  startedAt?: number;             // staggered plants
  position?: string;              // free text
  previousPlantId?: string;       // clone lineage / carried into the next run
  archivedAt?: number;            // removed mid-run without deleting its history
}

// collection: rundaystats — the comparison substrate
interface RunDayStat {
  run_id: string; day: number;    // day-of-run integer, 0-based
  date: string;                   // YYYY-MM-DD in Run.timezone
  stage: DiaryLifecycleStage; stageDay: number;
  coverage: number;               // 0..1
  day:   { tMean; tMin; tMax; rhMean; vpdMean; co2Mean; inRangePct; abovePct; belowPct; longestExcursionSec };
  night: { …same };
  lightHours: number;
  dli?: number;                   // only when a real PPFD sensor exists
  outputSeconds: { light; heater; dehumidifier; co2 };
  eventCounts: { watering; feeding; training; issue; entry };
  waterLiters?: number; feedEcInput?: number;
  computedAt: number; statVersion: number;
}
```

`DeviceLog` gains three optional fields — `run_id?: string`, `plant_ids?: string[]`, `actor_id?: string` —
and `DiaryEntryData` gains optional keys (§6.2). `DiaryEntryData` is already `Schema.Types.Mixed` with zero
server-side validation, so this is additive with no schema migration. **New validation is added at the same
time**, per-category, because an unvalidated Mixed bag is how the ten-optional-field mess happened.

New diary categories, following the existing `diary-*` prefix convention so `collectLogCategories` and
`matchesLogCategory` keep working unchanged: `diary-watering`, `diary-feeding`, `diary-training`,
`diary-issue`, `diary-harvest-note`.

### 5.2 Backfill and the two legacy traps

- `convertEventsToGrowCycles()` becomes a **server-side one-time backfill** producing `Run` rows from
  historic `diary-plant-lifecycle` logs, then is deleted from the client. Every existing log row gets a
  `run_id` stamped by timestamp containment. Old share links keyed by cycle-start timestamp resolve through
  a `?cycleStart=` → `run_id` lookup for one release.
- `RunDayStat` is backfilled from Influx for the last N runs at first request, not at boot, and marked with
  `statVersion` so a formula change recomputes rather than silently disagreeing with the chart.
- **`deleted` is fixed, and it must be, before the diary becomes the centrepiece.** Today manual diary
  entries are *created* with `deleted: true` and "Clear logs" therefore deletes nothing. C10 introduces
  `hiddenFromStream: boolean` alongside, backfills it from `deleted`, and makes `deleted` mean deleted. A
  data-loss-shaped bug is fatal for a product whose pitch is "it keeps the record for you".
- The server's own stage-transition entry is written with `categories:['diary-plant-lifecycle']` — missing
  the `'diary'` prefix — so it is invisible in the Entries report and not editable. Fixed to
  `['diary','diary-plant-lifecycle']` with the old form still matched on read.

### 5.3 How plants are created — and how a user who does not care is not taxed

**A run starts with zero plants.** Nothing asks "how many plants?" — ever.

The capture sheet has a plant row that reads `Alle` and nothing else. `Alle` means "attach to the run", i.e.
`plant_ids` is left `undefined`. A user who never presses `+ Pflanze` sees the word *Pflanze* exactly once
in their entire life with the product, on a button they can ignore, and every entry they write attaches to
the run. **That is the whole tax.**

The first time they press `+ Pflanze`, a one-field sheet asks for a label, prefilled `A`. Press it again and
it prefills `B`. There is no strain field on this sheet — strain is behind `Details` on the plant page,
because a stoned user naming a plant does not want to fill in a form, and because a strain name is a
volunteered fact we would rather not require.

```
Capture sheet, plant row:
┌─────────────────────────────────────────────┐
│ Pflanzen   [● Alle] [ A ] [ B ] [ + ]       │   ← chips; Alle preselected
└─────────────────────────────────────────────┘
```

Chip behaviour: selecting any named plant deselects `Alle`. Selecting `Alle` deselects the rest. Multi-select
across named plants is allowed (fed A and B, not C).

The `Tagebuch` tab shows a `Pflanzen` sub-segment **only when the run has at least one plant**. Zero plants
means the sub-segment does not exist, so nothing about multi-plant is visible to a single-plant grower.

### 5.4 Re-veg, clone, rename — the three cases that break the current model

| Case | Today | C10 |
| --- | --- | --- |
| **Re-veg** (flowering → vegetative) | stage ordinal rolls back → `convertEventsToGrowCycles` **fabricates a new grow cycle**; the history forks | `Run.stageChanges` simply appends `{stage:'vegetative', at}`. The day counter continues. The second flowering boundary is labelled `Blüte 2` and the VPD band steps back down. Nothing forks. |
| **Rename** | trimmed `lifecycleName` differs → **forks the history** | `Run.name` is a field on an object with a stable `run_id`. Renaming is a `PATCH`. Nothing forks, no share link breaks. |
| **Clone taken into the next run** | not expressible | new `Plant` in the new run with `previousPlantId` pointing at the mother. The plant page shows `Steckling von Gorilla links (Lauf 2)`, and `Vergleich` can filter to lineage. |
| **Plant dies / is culled mid-run** | not expressible | `Plant.archivedAt` set. Its entries stay, its chip greys out, it is excluded from per-plant averages after that date. |
| **Stage set by mistake** | edit the log row's time, breaking any share link keyed to a cycle start | edit `Run.stageChanges` on the run page. `RunDayStat.stage` recomputes; `run_id` never changes. |

## 6. Watering & fertilising

There is **no irrigation or dosing hardware**. This is capture-and-recall, and the only thing that matters
is how many taps it costs on a Tuesday evening in a dark tent.

### 6.1 Everyday watering — 2 taps

```
Tap 1: [ 💧 Gießen ] on Jetzt
        ↓  sheet slides up, everything already filled in
┌─────────────────────────────────────────────┐
│  Gießen                            jetzt ▾  │
│                                             │
│         [ − ]      4,0 L      [ + ]         │   prefilled: last watering's volume
│                                             │
│  Pflanzen  [● Alle] [ A ] [ B ] [ + ]       │
│                                             │
│  ⌄ Details (EC, pH, Ablauf, Notiz, Foto)    │   collapsed
│                                             │
│              [   Speichern   ]              │
└─────────────────────────────────────────────┘
Tap 2: [ Speichern ]
```

**Two taps, no typing.** The volume stepper uses the existing `value-edit-row` component and the
`rangeGuard` directive (slider inert until tapped, disarms after 8 s) so it survives being in a scroll view
on a phone. The `Details` disclosure holds `ecInput`, `phInput`, `ecRunoff`, `phRunoff`, `runoffPercent`,
free text and a photo — everything the techie and the club need, none of it in the stoner's way.

`jetzt ▾` opens a time picker for "I watered last night and forgot" — one tap to `gestern Abend`.

### 6.2 What is stored

A `DeviceLog` row, `categories: ['diary','diary-watering']`, `run_id`, `plant_ids`, `actor_id`, and:

```ts
// added to DiaryEntryData, all optional
waterLiters?: number;
waterPerPlantLiters?: number;   // derived when plant_ids.length > 1, stored for reporting
runoffPercent?: number;
ecInput?: number;               // mS/cm — canonical unit, always
ecRunoff?: number;
phInput?: number; phRunoff?: number;
feedProgramId?: string; feedStepIndex?: number;
feedProducts?: { label: string; mlPerLiter?: number; note?: string }[];
trainingType?: 'topping'|'lst'|'defoliation'|'transplant'|'other';
```

**EC is stored canonically in mS/cm and a bare "ppm" is never rendered.** Three PPM scales are in
circulation and at EC 1.8 a Bluelab reads 1260 while a Hanna reads 900 — for the same liquid. Where a ppm
figure is shown at all it carries its scale: `1260 ppm (700)`. This is the single most consequential unit
decision in the feature and it is invisible in the UI, which is correct.

### 6.3 Following a schedule

The scheme is **selected once and then prefills the log entry**. It is not a planner, not a calculator, not
a compliance engine.

The selectable thing is a **medium + feed regime pair, labelled the way growers say it out loud**:

```
┌─────────────────────────────────────────────┐
│  Düngeplan wählen                           │
│                                             │
│  ○ Biobizz Light-Mix                        │
│    Leicht vorgedüngt · ab Woche 2           │
│  ○ Biobizz All-Mix                          │
│    Stark vorgedüngt · ab Woche 4            │
│  ○ Floragard Light                          │
│  ○ Green House Feeding — Short Flowering    │
│  ○ BioTabs                                  │
│    Kaum Flüssigdünger · alle 4–6 Wochen     │
│  ─────────────────────────────────────────  │
│  ○ Lucas-Formel        ○ Jack's 321         │
│  ○ Eigener Plan                             │
│                                             │
│  Zuletzt geprüft: 12.03.2026  ·  Quelle ›   │
└─────────────────────────────────────────────┘
```

A plan that cannot express *"All-Mix, so don't feed yet"* is not modelling the domain. So the model is:

```ts
FeedProgram { program_id; brand?; name; medium; strengthAxis?: 'light'|'medium'|'heavy';
              source_url; retrieved_at; chart_version; kind; steps: FeedStep[] }
FeedStep    { index; phase: 'veg'|'flower'|'flush'; phaseWeek;
              products: { label; mlPerLiter?; note? }[];
              ecTarget?; ecBasis: 'absolute'|'delta_over_source'; phTarget?; note? }
RunFeedPlan { run_id; program_id; strengthMultiplier; medium; sourceWaterEc?;
              currentStepIndex; startedAt }
```

Three domain facts the model has to carry or the feature is actively wrong:

- **`ecBasis`.** CANNA publishes `EC +`, not EC: *"add the EC of the tap water that is used to the
  recommended EC."* A UI that alarms against the raw chart number with tap water at EC 0.4 is telling the
  user to underfeed by 20 %.
- **Advance by feed events, not by wall-clock weeks.** `currentStepIndex` moves when you log a feed. Growers
  feed Tue/Fri and slip; a calendar-driven plan desynchronises within two weeks and is then noise.
- **Autoflower multiplier.** `strengthMultiplier` 0.25–0.5 with no 12/12 flip event. Essentially no
  manufacturer chart has an auto column, so this fills a real gap without borrowing anything.

**Schedule-following flow — 1 tap.** The `Als Nächstes` card on `Jetzt` shows the due step. `[ Erledigt ]`
commits the entry with every prefilled value as-is. `[ Ändern ]` opens the same watering sheet with the
products and ml/L filled in, all editable — because **the grower who deviates is the normal case, not the
error case**.

Due-detection is soft: a step is due when `daysSinceLastFeed >= program.stepIntervalDays` (default 3, from
the program). It never nags twice and it never blocks. The stoner sees `Düngen fällig` and a green button;
they never see a table of ml/L. The club treasurer opens `Details` and gets product, dose, volume, EC in,
EC runoff, pH, per-plant split, and an actor.

**The one thing only a controller can do:** the app auto-detects the 18/6 → 12/12 flip from `out_light`
history and offers, once, `Blüte gestartet? Düngeplan auf Blüte Woche 1 setzen. [Ja] [Nein]`. No
bottle-brand calculator can do this, because none of them can see the tent. This is the argument for the
feature living in a controller.

### 6.4 On the chart

- Watering → blue drop marker, annotation rail row 1. Marker size scales with litres (3 steps, not
  continuous).
- Feeding → green flask marker, same row. Tapping it shows the products and dose in the scrubbing header.
- **EC gets a panel** when the run has ≥3 EC readings: measured `ecInput` as dots, `ecRunoff` as hollow
  dots, and the program's `ecTarget` as a **stepped dashed line** — the identical goal-vs-actual grammar as
  temperature. When `ecBasis === 'delta_over_source'` the drawn target is `ecTarget + sourceWaterEc` and the
  panel header says so.
- Cumulative litres per week appears as a small bar row in `Vergleich`, which is where it earns its place:
  *"Lauf 3: 84 L bis Tag 34. Lauf 2: 97 L."*

### 6.5 Brand posture

Brand names are **plain text labels only** — no logos, no brand colours, no bottle imagery, and never inside
a Terp Control feature name. The numbers live in a **MongoDB content collection, never in the webapp
bundle**, each entry carrying `source_url` + `retrieved_at` + `chart_version` + `kind`, so any single brand
is removable in one DB update. `Zuletzt geprüft: 12.03.2026` is shown to the user, which doubles as a
genuine trust feature (two retailer sites disagree by ~3× on CANNA Terra Vega dosing — wrong numbers here
burn real crops). Nothing is seeded from retailer or blog transcriptions. A takedown address and a
notice-and-action policy ship before the first brand chart does.

## 7. Camera & timelapse

Images today are `{image_id, device_id, timestamp, data, format, duration}` with **no back-reference to
anything**, and a unique index on `{device_id, format, timestamp, duration}`. C10 does not touch that
collection — the buffers are 16 MB BSON documents and the index is load-bearing. Instead:

```ts
// collection: imagemeta — sidecar, one row per image, cheap to query and cheap to delete
ImageMeta { image_id; device_id; run_id?; day?; stage?; plant_ids?: string[];
            kind: 'auto'|'user'|'timelapse'; timestamp; timestampEnd? }
```

- **Time:** the film strip positions thumbnails by real timestamp on the chart's x-scale, so an uneven
  capture interval reads honestly as a gap rather than being evened out. Delivery is **one sprite + JSON
  index per window** (Mux's storyboard pattern, 50–100 tiles at 256×160), not N image requests — otherwise
  a 30-day run is 86,400 stills' worth of requests.
- **Plants:** a photo taken from the capture sheet inherits the sheet's `plant_ids`. Auto-captured stills
  never get plant ids, because the camera sees the whole tent and guessing would be a fabricated fact.
- **Stages:** timelapses are cut **per stage of a run** — `Blüte, Tag 1–34` — in addition to the existing
  `1d`/`1w`/`1m` durations, which stay because share links reference them. A stage-close event triggers one
  render. That is the first time a timelapse in this product has any relationship to what the plant was
  doing.
- **Run over run:** the `Am selben Tag` block in `Vergleich` (§4.6) picks the auto-still nearest to
  `startedAt + day × 86400s + 12h` (mid-photoperiod) for each run, so the two images are lit the same way
  and are actually comparable. If lights-on differs between runs it picks mid-photoperiod per run, not the
  same wall-clock hour.
- Scrubbing the chart moves the film strip cursor and vice versa — one shared cursor, both directions.

Housekeeping that has to ship with this: `DELETE /image/:image_id` exists and **is never called by the
webapp**; retention filters `format:'jpeg'` only, so `user/jpeg` diary photos accumulate forever.
`express-fileupload` is mounted with no size limit. All three are fixed as part of this feature, not later.

## 8. Multi-user, clubs, and the privacy posture

### 8.1 Roles

`Device.owner_id` is a single unindexed string and that one equality test
(`auth.middleware.ts:172`) is the entire authorisation model. It cannot be flagged around.

```ts
// collection: memberships
Membership { device_id; user_id; role: 'owner'|'grower'|'viewer';
             invitedBy; createdAt; displayName?: string }   // displayName is a NICKNAME, never a real name
```

- **owner** — settings, alarms, members, delete, export. Exactly one.
- **grower** — writes diary entries, starts/ends runs, confirms feeds, uploads photos. Cannot change
  setpoints or delete.
- **viewer** — read-only, same as a share link but with an account and its own notification preferences.

Invitation is by a short code the owner generates and reads out loud, **not by email lookup** — an
account-lookup-by-email endpoint does not exist and designing one against enumeration abuse is work that
buys nothing here.

`actor_id` is stamped on every log row. Whether it is *displayed* is a device setting.

### 8.2 Attribution, and the honest tension

`Device.showActors` — default **off**. When off, entries render as `Gegossen · 4 L`. When on, they render
as `Gegossen · 4 L · Micha`.

Club mode turns it on, adds a `Wer hat was gemacht` view on the run page grouped by member and by week, and
sets `regulatoryRelevance` on task records so § 17 Abs. 2 KCanG's *eigenhändig* participation requirement is
evidenced. That is the **one legally-motivated multi-user feature worth owning**.

What C10 refuses, permanently: per-member dispensing quantities, THC content, member identity/DOB/address,
membership numbers, payments and quotas. Those are § 26 KCanG's list, they are arguably Art. 9 GDPR health
data, and a grow controller has no need for any of them. Terp Control is the **device-attested
environmental layer** those platforms consume — a value the controller recorded with its own clock beats a
hand-typed number in an inspection, and it requires storing zero personal data. If integration ever happens
it is with Cannanas / 420cloud (`POST /v1/clubs/{clubId}/diaries` with a `measurements` payload; the device
registers as a `zone`; the camera publishes as `zones.streams.video[].url`), not with commercial platforms.

No compliance claim, no `KCanG-konform` badge, ever.

### 8.3 The privacy problem this concept creates, and the architecture that answers it

**The problem, stated plainly.** A comparison product wants outcomes. Harvest weight and plant count are the
exact facts separating a lawful three-plant hobby from a three-year offence in many jurisdictions.
§ 28 Abs. 2 KCanG lets German authorities seize digital data with **no prior judicial approval**. A cloud
that stores "Lauf 2: 6 Pflanzen, 412 g" is building a case file with a nice chart on it.

**The architectural answer, in four parts.**

**(1) The comparison substrate is summaries, not raw data.** `RunDayStat` is ~200 bytes per day. A 90-day
run is ~18 KB. Everything in `Vergleich` — the scorecard delta, the day profile, the "was war anders" diff —
reads `RunDayStat` and `Run`, never raw Influx. Therefore **the product can delete raw telemetry and
photos and still compare**, which is not a compromise, it is a better architecture: the compare screen is
fast because it never touches Influx.

This makes retention a *feature*:

```
Wenn ein Durchgang endet:
  ┌───────────────────────────────────────────────┐
  │  Lauf 2 abschließen                           │
  │                                               │
  │  ○ Alles behalten                             │
  │  ● Auf Zusammenfassung reduzieren             │  ← DEFAULT
  │      Tageswerte, Zielerreichung und Stufen    │
  │      bleiben. Messreihen, Fotos und Notizen   │
  │      werden gelöscht. Vergleiche funktionieren│
  │      weiter.                                  │
  │  ○ Komplett löschen                           │
  │                                               │
  │  … in [ 30 Tagen ▾ ]                          │
  └───────────────────────────────────────────────┘
```

Default account-wide: raw telemetry 180 days, auto-stills 90 days, run summaries indefinitely (they are
~18 KB and contain nothing incriminating). Today the Influx bucket is created with **no retention and zero
downsample tasks** — raw 5-second samples kept forever — so this is a fix, not an addition.

**(2) Rank, don't weigh.** The default outcome field is an **ordinal**, not a mass.

```
┌───────────────────────────────────────────────┐
│  Wie lief Lauf 2?                             │
│      ☆ ☆ ☆ ☆ ☆                                │
│  Verglichen mit Lauf 1:                       │
│      [ besser ] [ gleich ] [ schlechter ]     │
│  Notiz (optional)                             │
└───────────────────────────────────────────────┘
```

A five-point rating and a three-value comparison give you almost everything run-over-run comparison needs —
*which run was better* — and they are close to worthless as evidence of anything. There is no gram figure to
seize, and no plant count in the outcome record at all. This is the sharpest single decision in C10 and it
is deliberately a product sacrifice: grams are more motivating than stars.

**(3) Weights exist, but only where the user put them, and they are shreddable on their own.**

`/account/privacy` → `Ernte-Daten`:

| Option | Behaviour |
| --- | --- |
| **Nicht speichern** *(default)* | The weight field does not exist in the UI. Not asked, not stored. |
| **Nur auf diesem Gerät** | Stored in `localStorage` under `tc.outcome.<run_id>`. Never leaves the browser. **Honest cost, stated in the UI: "Zahlen sind nur in diesem Browser sichtbar und gehen verloren, wenn du die Website-Daten löschst."** Comparisons that use it are computed client-side. |
| **In der Cloud** | A `RunOutcome` row with `dryWeightGrams` / `plantCountAtHarvest`, deletable per run with one button that is not buried, and excluded from every export unless separately confirmed. |

Weights live in `RunOutcome`, **never in a `DeviceLog` row** — that is the whole reason they are a separate
entity. A log row is entangled with the chart, the annotation rail and the share link; a `RunOutcome` row
can be dropped without leaving a hole anywhere.

**(4) Two modes and a panic button.**

- **Privat** (default, and the default is the privacy-maximal one): attribution off, outcomes off, short
  retention, no community contribution, no location ever collected or inferred, pseudonymous account, no
  analytics or ad SDKs, EU hosting stated plainly on the page.
- **Club (DE/MT)**: explicit opt-in with a plain-language list of exactly what changes. Attribution on,
  participation log on, longer retention, export tooling, audit view for the Vorstand. Immutability is
  **club-scoped and opt-in** — tamper-evidence protects a regulated club from its own staff and victimises
  an unregulated grower, so it is never global.
- **Alles löschen** on `/account/privacy`: one confirm, no undo, removes runs, plants, entries, photos,
  outcomes, memberships and telemetry. Two taps from anywhere. Not a support ticket.

**The community median, and why it is not in v1.** The `[ Median ▾ ]` selector in `Vergleich` compares your
run to the median of contributed runs. It is built from `RunDayStat` rows only — climate metrics, never
outcomes, never strain, never location, never identity — from runs whose owner set
`Run.contributeAnonymously` (per-run, off by default, one toggle). A band is suppressed entirely unless it
is computed from **≥25 runs** at that day-of-run, and the underlying rows are never queryable individually.
Even so it ships **after** v1, because a k-anonymity threshold with fewer than a few hundred contributing
runs is a promise you cannot keep, and 150 units ship in October.

## 9. Old devices — type 7 (fan, light, plug, fridge)

They are not the focus group; they must not be broken; and the honest generalisation is cheap.

**The generalisation: the comparison engine's unit is a *period*. A run is just the interesting kind of
period.** Everything in `Vergleich` works on `(start, end, per-day stats)`. If a device has no runs, the
period is a rolling 7 days and the tab reads `Diese Woche vs. letzte Woche`. Same code, same panels, same
ghost, same grey.

What each type actually sees:

| Type | `Jetzt` | `Verlauf` | `Tagebuch` | `Vergleich` |
| --- | --- | --- | --- | --- |
| **plug** (smart socket) | one tile: on/off + Laufzeit heute; freshness; no goal row (nothing to aim at) | one panel: the output state lane, full width | free-text entries + photos | `Laufzeit pro Tag: diese Woche vs. letzte` |
| **fan** | RPM tile, no goal row (there is no fan setpoint the firmware reads) | RPM panel + output lane | free text | RPM/day, week vs week |
| **light** | on/off + `Lichtstunden heute 12,0` + `Ziel 12` | photoperiod band panel + output lane; the "geplant vs. gemessen" hairline is the headline feature here — a failed contactor is visible | free text | `Lichtstunden pro Tag` week over week; if the owner started a run, day-of-run |
| **fridge** (real fridge builds, type 5) | temp + humidity tiles with goal rows, same as the controller | full small-multiples chart | full diary, plants optional | **runs work fully.** A fridge build is a closed loop with a start and an end. |
| **dryer** | dead type per `AGENTS.md`; left exactly as-is, no new work | | | |

Two concrete wins for the old fleet, not hand-waved:

1. **Trocknungs-Lauf.** A fridge or a controller in `dry` workmode can start a run of type `drying`: day
   counter, the 18 °C / 58 % targets drawn on the chart, and **run-over-run comparison of drying curves**.
   Growers argue about dry-downs constantly and nobody ships a comparison of two of them. This is real value
   delivered to the type explicitly excluded from focus, using machinery built for someone else.
2. **The naming bug is fixed for everyone.** `overview.component.html:40` hard-codes
   `{{'devices.fridge.title'|translate}}` → *"Terp Control FRIDGE GROW"*, and an unnamed controller is
   *named* that. A `devices.controller.*` i18n block is added in both languages, the label is driven by
   `device_type`, and the `ngSwitchCase` lines gain a real `controller` case. That is the cheapest
   credibility fix in the whole document and it also removes the fridge's workmode vocabulary ("Kleine
   Pflanzen", "Gewächshaus") from a device that is not a fridge.

## 10. Onboarding

The existing 289-line `setup-wizard` is kept and restructured to **three questions and one confirmation**,
and the ~30 MB of already-shot wizard videos sitting unreferenced in `assets/wizard/` finally get used — one
4-second silent loop per step, which is what they were shot for.

```
① Wie soll dein Zelt heißen?          [ Zelt 1 ]              ← prefilled, Weiter is one tap
② Das haben wir gefunden:                                     ← DETECTED, not asked
     ✓ Licht (Steckdose)          ✓ Heizung (Steckdose)
     ✓ Entfeuchter (Steckdose)    ✓ Temperatur / Feuchte
     ✗ CO₂-Sensor (Upgrade)
   Stimmt das?     [ Passt ]   [ Ändern ]
③ Was läuft gerade?
     [ Sämling ] [ Wachstum ] [ Blüte ] [ Trocknung ]
     [ Ich fange gerade an ]  [ Weiß ich nicht ]
④ Fertig. Lauf 1 läuft. Tag 0.
```

**Capability is established without asking a stoned user twenty questions, by reading
`hardwareInfo.sockets` and asking one yes/no about the result.** This is the same data the current wizard's
`connections` step already reads — it is just promoted from a one-time step to the thing that drives every
goal row in the app forever. `Ändern` opens per-role checkboxes for the case where the CSV is stale.

Three tails:

- **No sockets found** → `Nur messen` path. Zero goal rows appear anywhere in the app, alarm presets that
  require an actuator are hidden, and the copy is explicit: *"Dieses Gerät misst nur. Ziele erscheinen,
  sobald du eine Steckdose verbindest."* This is what type 1 should have been getting all along.
- **Missing `hardwareInfo.sockets`** (old firmware) → **fail closed to monitor**, with a one-line banner
  offering `Ich habe Steckdosen verbunden ›`. Today this case fails **open to `'full'`**, which is how a
  heater-only tent gets shown a dehumidifier alarm preset it can never act on.
- **`Weiß ich nicht`** → run starts, stage `vegetative`, **no targets are pushed to the device**. The app
  does not pretend to know. The stage picker sits on `Jetzt` until answered.

**The second onboarding is the one that matters.** When a run ends, `Neuen Lauf starten` offers
`Wie letztes Mal` — one tap copies the stage plan, expected flower length, feed program and plant labels
from the previous run. That is the retention loop, and it is also how run 2 becomes comparable to run 1
without the user doing anything deliberate.

## 11. Per-user-type walkthrough — first week

**Type 1 — monitoring only, lazy.**
Day 1: wizard finds no sockets, says so, and shows him a `Nur messen` device. No goal rows, no dehumidifier
tile, no humidity target he cannot act on — the first time this product has told him the truth about itself.
He taps `Ich fange gerade an`; a run starts at day 0. Days 2–6 he opens the app maybe twice, sees
`● Live · vor 8 s`, four numbers, and `Heute im Zielbereich — nicht bewertbar (keine Ziele gesetzt)`. Day 7
he opens `Verlauf`, drags two fingers, and sees a week at 15-minute resolution with day/night shading he did
not configure, because it was derived from his lamp. Nothing has nagged him. **The comparison payoff is
three months away and this concept is honest that he gets nothing from it in week one beyond a chart that
finally has axes.**

**Type 2 — same, with a camera.**
Identical first day, plus `run --camera` equivalent: the wizard sees the paired cam and enables the
`Kamera` panel. Day 3 he scrubs the chart and the film strip follows his finger — the first time an image in
this product has had anything to do with sensor time. Day 7 the first stage timelapse is not yet cut (that
happens at stage close), so what he gets in week one is the existing 1d/1w timelapse *plus* a film strip
that is an axis. Week one is honestly modest for him; the payoff is day 34 of run 2, when `Am selben Tag`
puts two pictures side by side. **He is the type this concept eventually serves best and week-one serves
worst.**

**Type 3 — controls CO₂ or heating only.**
Wizard finds `heater` and nothing else. Only the temperature tile gets a goal row. The humidity tile reads
`57 %` with `Kein Gerät dafür angeschlossen` underneath, and humidity is excluded from `Heute im
Zielbereich` — so his 82 % is a real number about the thing he actually controls, not a number diluted by a
target he cannot hit. No dehumidifier alarm preset is offered. Day 4 he adds a CO₂ socket; the wizard is not
re-run — `hardwareInfo.sockets` changes, and a toast says `Neue Steckdose erkannt: CO₂. Ziel setzen? ›`. By
day 7 he has two goal rows and two panels and a chart that draws both setpoints.

**Type 4 — full tent.**
Wizard finds light, heater, dehumidifier, CO₂. Four goal rows. He picks `Blüte`; the stage preset writes
`day.temperature 25 / night 20 / dayHumidity 50 / lights 12 h / limit 100 / co2 1000` into
`device.configuration`, and the chart immediately draws all four setpoints as stepped dashed lines with
bands. Day 2 he notices from the `Ausgänge` lane that the dehumidifier ran 41 minutes straight at 03:00 and
the temperature panel shows a matching dip — because `out_dehumidifier` doubles as the cooler, and the lane
makes that double meaning legible for the first time. Day 5 he sets a feed program. Day 7 his verdict line
reads `Heute im Zielbereich 88 %` and, beneath it, `Erster Durchgang.` He is the type with the most goal
rows and therefore the type for whom the second run will say the most.

**Type 5 — closed-loop DIY (fridge build).**
He does not use the wizard; he claims the device and goes straight to `⋮ → Einstellungen`. What he actually
wants is the API, and C10's answer is that `RunDayStat` is a documented, versioned, exportable schema —
`GET /run/:run_id/stats.json` and `.csv`, including **actuator state**, which no vendor in the market
exports. He starts a run for his fridge, gets the day counter and the drying comparison, and treats the
webapp as a viewer over an API he trusts. **Week one he mostly reads documentation; if that documentation is
not written, this type gets nothing from C10 at all.**

**Type 6 — club.**
The Vorstand claims the device, opens `⋮ → Mitglieder`, generates two codes and reads them out at the
Tuesday meeting. Two growers join as `grower`. The owner switches the device to `Club-Modus` and reads the
plain-language change list: attribution on, retention 5 years, export enabled, participation log on. From
day 2 every watering carries a nickname. Day 4 someone fed with the wrong step; the run page's `Wer hat was
gemacht` view shows it in eight seconds, which is the actual daily value — not compliance, but *knowing
whether the plants were watered on Thursday*. The club creates four plants with labels `1`–`4` because two
different people need to know which ones got the fish emulsion. **Nothing about members' consumption,
identity or dispensing exists anywhere in the product, and the export defaults to anonymised.**

**Type 7 — old devices.**
A light owner opens the app after the update. His device is still there, still called what he called it, and
the fridge-branded label is gone. `Jetzt` shows on/off, `Lichtstunden heute 12,0 / Ziel 12`, and a freshness
line. `Verlauf` shows the photoperiod band with a hairline where the schedule and the measurement disagree —
which is how he discovers, in week one, that his timer has been firing 20 minutes late since March.
`Vergleich` shows `Diese Woche vs. letzte Woche`. He never sees the word `Lauf` unless he starts one.
**Nothing was taken away and one real bug in his tent became visible.**

## 12. Stoner / normal / techie in one design

The resolution is **not** a mode switch. It is that density is a property of the screen, not of the user,
and the run gives every screen a natural "one number" summary to lead with.

| | Stoner | Normal | Techie |
| --- | --- | --- | --- |
| **Lands on** | `Jetzt` | `Jetzt` | `Jetzt`, then lives in `Verlauf`/`Vergleich` |
| **Reads** | one line: `Heute im Zielbereich 82 %` and the ghost line under it | the four tiles with goal rows | the scorecard delta table |
| **Does** | `[ Erledigt ]` on the task card, or `💧 Gießen → Speichern` | opens the sheet, adjusts litres, adds a note | opens `Details`, records EC in/out, runoff %, pH |
| **Chart** | never opens it; the sparkline in the tile is his chart | 2 panels, `1 T` / `7 T` presets | 7 panels, reordered, min/max envelope, ghost on, table view, CSV |
| **Feeding** | sees `Düngen fällig` and a green button. **Never sees a ml/L table.** | picks a program once, follows it, deviates freely | edits the program, sets `strengthMultiplier`, sets `sourceWaterEc`, sets `ecBasis` |
| **Plants** | never presses `+ Pflanze`; the word appears once, on a button | 2–3 labelled plants | plants with lineage and per-plant EC history |
| **Comparison** | the one ghost line on `Jetzt` | `Vergleich` scorecard | `Vergleich` + exported `RunDayStat` in a spreadsheet |

Concrete mechanisms rather than adjectives:

1. **Progressive disclosure is always a `⌄ Details` on the same sheet**, never a different screen and never a
   persisted mode. The existing `Einfach/Experte` segment (persisted in
   `localStorage['app-settings-expert']`, simple by default) is kept **only** in device settings, where it
   already exists and is already documented in `docs/einfach-modus.md`. It is not extended to the new
   screens, because a mode you have to be in is a mode you can be lost in.
2. **Every destructive or committing action has a prefilled happy path.** `[ Erledigt ]` with no further
   input is always a legal move. The techie's extra fields are all optional and all remembered.
3. **The stoner is served by defaults; the techie is served by the fact that the defaults are visible and
   editable.** The `Zuletzt geprüft` line, the `ecBasis` note on the EC panel, the "Blatt = Luft − 2.0 °C"
   header, the `Abdeckung 91 %` under a suppressed percentage — each is one line that a casual user's eye
   skips and a sceptical user's eye stops on.
4. **Nothing that cannot act is ever shown as a control.** `daynight.floating` / `float_start` /
   `day_duration` / `light_duration` are read by **no firmware anywhere** (zero grep hits across
   `firmware/`), and `lights.maintenanceOn`, `co2.sunsetOff`, `daynight.linearChange` are silently ignored
   by the controller. All are removed. A techie who finds one dead control stops trusting every number in
   the app, and this concept's entire pitch is a comparison he has to trust.

## 13. v1 scope for October 2026

The hardware ships 2026-10 with 150 units and there is essentially no test baseline. So v1 is deliberately
narrow and the cut is stated, not implied.

### Ships in v1

**Foundation (must, or nothing else works)**
- `Run` entity + server-side backfill from `convertEventsToGrowCycles`; that function deleted from the client.
- `RunDayStat` computed **server-side on raw Influx samples**, `statVersion`-tagged, backfilled lazily.
- `DeviceLog.run_id` / `plant_ids` / `actor_id` (optional, normalised on read).
- Fix `deleted` vs `hiddenFromStream`; server-side log pagination; Flux parameter allowlisting + timespan/
  interval constraint; Influx retention + one downsample task.

**Screens**
- Tab bar; `Jetzt` with the four freshness states, per-role goal rows, the today verdict and **the one ghost
  line**; `Verlauf`; `Tagebuch`; `Vergleich` with scorecard delta, day profile, `Am selben Tag`, and
  `Was war anders`.
- Legacy `/charts` and `/diary` redirects preserving every query param.

**Chart**
- ECharts 6 migration, `sampling:'minmax'`, small multiples, linked crosshair, stepped setpoint + band +
  signed deviation fill, day/night shading with the geplant-vs-gemessen hairline, outputs state lane,
  annotation rail, film strip with sprites, pinned scrubbing header, Okabe-Ito, axes never hidden.
  Chart.js / ng2-charts deleted.

**Diary & feeding**
- Two-tap watering, one-tap feed confirm, `⌄ Details` with EC/pH/runoff.
- Plants: optional, chip-based, zero-plant default. Plant page with rename, strain, archive, lineage.
- **Five feed programs**, seeded from brand-owned sources with `source_url` + `retrieved_at`, plus Lucas and
  Jack's 321, plus `Eigener Plan`. The engine is user-editable from day one.
- 12/12 flip auto-detection offering to advance the program.

**Privacy**
- `/account/privacy`: Privat (default) / Club, retention defaults, outcome storage mode (default
  **Nicht speichern**), panic delete.
- Run-close flow with `Auf Zusammenfassung reduzieren` as the default.
- Ordinal outcome (rating + better/same/worse).

**Credibility fixes that cannot wait**
- `devices.controller.*` i18n block in de+en; the fridge label and fridge workmode vocabulary removed from
  controllers; the six live raw-key i18n bugs; chart series names translated; dead controls removed;
  capability fails **closed**; `/classes` gets a route guard; image delete + upload size limit.
- Tests written in the `grow-report.component.spec.ts` style (plain class construction with stubs) for:
  run boundary derivation, `RunDayStat` aggregation, day-of-run axis mapping, the four freshness states,
  and feed-step advancement. CI does not run `ng test` today; that is fixed as part of this.

### Explicitly NOT in v1

- **Community median.** Needs volume before a k-anonymity promise is keepable. 150 units is not volume.
- **Multi-user / club mode.** `Membership` + rewriting `auth.middleware.ts:172` and `:207` + loosening ~10
  owner-scoped queries + repairing the broken `PUT /users/:id` and the globally-unique `RecipeTemplate.name`
  is a release of its own. v1 stamps `actor_id` and ships the schema so v1.1 is additive, and ships nothing
  user-visible. **This is the biggest thing being cut and type 6 is the type that pays for it.**
- Public shareable diary URL, Markdown/BBCode post generator, Discord/Telegram/generic update destinations.
  (Cheap and high-ROI, but off-thesis; v1.1.)
- VPD temp×RH matrix; dew point; DLI without a real PPFD sensor.
- Per-plant charts (per-plant *entries* ship; per-plant *series* do not — there is one sensor per tent).
- Cannanas / 420cloud integration (business development, not a sprint).
- Offline / service worker; native app; Capacitor configuration.
- Any brand chart beyond the seeded five, until German IP counsel has looked at UrhG §§ 87a–87e and
  UWG § 4 Nr. 3.

## 14. Non-goals

1. **No community feed.** ~200 App Store reviews across TrolMaster and VIVOSUN were read and not one praised
   theirs. It is permanent moderation cost, and with real identities on cannabis grows it is a target list.
   A pasteable link is not a feed.
2. **No two-way sync with any grow-diary platform.** GrowDiaries has no public API and is Cloudflare-hardened;
   Grow with Jane's ToS forbids it and its backend is Firebase; SeedFinder has been dead since 2024-07.
   Nothing in this concept promises sync, in copy or in a feature name.
3. **No auto-posting to Instagram, Threads, TikTok or Reddit.** A failed post there costs **the user** their
   account and Terp Control is the proximate cause. Not "later" — never.
4. **No irrigation or dosing automation.** There is no hardware for it. Watering and feeding are capture and
   recall, and pretending otherwise would be the same lie as the dead `daynight.floating` control.
5. **No yield accounting, no cost-per-gram, no € per watt.** Grams are refused by design (§8.3); the
   economics of a hobby grow are not this product's business.
6. **No strain database and no strain dropdown.** SeedFinder's API is dead, strain is a volunteered fact we
   would rather not require, and a dropdown makes it feel mandatory. Free text, optional, always.
7. **No compliance product.** Not the club's system of record for § 26 KCanG, not 23 authority export
   formats, not per-member dispensing. No `KCanG-konform` badge.
8. **No second app.** No permanent Einfach/Profi split beyond the settings segment that already exists.
9. **No plant count as a headline.** The plant list exists because two people in a club need to know which
   plant got what. It is never rendered as a count badge, never in an export header, never in a share
   preview.
10. **No `Powered by Terp Control` footer on user-generated posts.** § 6 KCanG bans cannabis advertising and
    sponsoring with fines to €30,000, read broadly; that string is the single riskiest one in the whole
    integration surface, and this concept does not ship it.

## 15. Honest weaknesses

Written to be found here first.

1. **The core value arrives at run 2, three to five months after purchase.** Every other concept in this set
   delivers on day one. C10's day-one experience is "a chart with axes and a good watering button", and its
   headline row says *"Erster Durchgang"* — an IOU. For a product shipping 150 units in October 2026 into a
   market where people churn out of apps in a week, **this is the most serious objection and the mitigations
   (stage-vs-stage within one run, the drying comparison, the demo device's seeded runs) are thin.** A critic
   is right to say the thesis is a retention feature masquerading as a product.

2. **Run-over-run comparison is deeply confounded and the app cannot say so loudly enough.** Different
   genetics, pot size, lamp, medium, phenotype, ambient season. Climate is one of twenty variables. `Was war
   anders` lists the four differences the product happens to know and is silent about the sixteen it does
   not. A user will conclude "the 20 °C nights did it" with our chart as the evidence, and be wrong. Any
   copy that implies causation is a defect; keeping that discipline across two languages and a hundred
   strings is harder than it sounds.

3. **The privacy stance removes the most motivating number in the product.** Stars are not grams. A
   five-point rating typed three days after harvest while stoned is noisy to the point of uselessness, and a
   critic can fairly say C10 solved a legal problem by deleting the feature that made comparison worth
   doing. The counter-argument — that "which run was better" is ordinal anyway — is true and also
   convenient.

4. **`localStorage`-only harvest weights are a bad half-measure.** They do not sync, they vanish with site
   data, they cannot be compared across devices, and a user who chooses that option will lose them and blame
   us. It is honest and it is still bad.

5. **Autoflowers, perpetual grows and sea-of-green break the run model.** One active run per device with one
   day-0 is wrong for a tent with staggered plants at three different stages — which is *explicitly* the
   owner's multi-plant scenario ("maybe even at different stages"). C10's answer is per-plant `startedAt`
   and per-plant day counters on the plant page, but the **chart's x-axis, the stage bands and the whole
   `Vergleich` screen remain run-scoped**, so a staggered grower gets a comparison axis that does not match
   any of his plants. This is a real hole in the concept's coverage of the owner's own brief.

6. **Day-of-run is the wrong axis for types 5 and 7**, and the "a run is just a period" generalisation is a
   patch over that, not a design. A plug owner comparing this week to last week is a thin feature wearing
   the clothes of a thick one.

7. **`RunDayStat` is a derived cache and inherits every derived-cache problem.** It can disagree with the
   chart (different aggregation), it needs `statVersion` recomputation on every formula change, backfilling
   a year of Influx for a new metric is expensive, and the day boundary depends on `Run.timezone` — which,
   if a user travels or the device's tz is wrong, silently shifts every daily number by hours.

8. **`Auf Zusammenfassung reduzieren` is irreversible and it is the default.** A user who reduces run 2 and
   then wants the photo from day 41 has lost it permanently. Making the privacy-maximal choice the default
   means some users will be surprised by their own settings, and the 30-day grace period is the only thing
   between them and a support ticket we cannot fix.

9. **The tab bar is new navigation in an app that has none, with no test baseline to catch what it breaks.**
   Three restricted modes (share, demo, public) must behave correctly on four new routes, and the existing
   suite is 38 `it()` blocks, 24 of which are `it('should create')`, with `app.component.spec.ts` unable to
   pass at all.

10. **Cutting multi-user from v1 means type 6 — the club, one of only two segments in the narrowed market —
    gets nothing in October** beyond `actor_id` sitting unused in the database. That is a defensible
    sequencing call and it is still a segment shipped empty.

11. **The ECharts migration removes Highstock's implicit `dataGrouping` safety net**, which nobody
    configured and everybody depends on. `sampling:'minmax'` is the replacement and it is a config line that
    can be forgotten on a new panel; the failure mode is a phone that locks up on a 17,280-point series,
    which is exactly the user who will not file a bug.

12. **Club attribution and the privacy posture are in genuine tension and §8.2 is a mitigation, not a
    resolution.** A participation log is a per-person record of who touched cannabis plants and when. Making
    it opt-in, thing-scoped, nickname-only and club-mode-only reduces the exposure; it does not remove it.
    If a German authority seizes a club's Terp Control account under § 28 Abs. 2 KCanG, that log is in it.
