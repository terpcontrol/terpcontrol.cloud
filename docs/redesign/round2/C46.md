# C46 — Der Kalender

**Family:** structure · **Centre of gravity:** the calendar is the app.

---

## 1. Thesis

**A grow is a calendar, so make the calendar the product: one time-grid that holds the past (what the room
did, what you did, what it looked like) and the future (what is due) in the same cells, and let the size of
a cell — chosen by the hand, never by a setting — decide how much of the truth it shows.**

Every other concept in this bake-off invents a new organising idea and then has to teach it. A calendar needs
no instruction: my mother can read one, and so can a person at 2 a.m. with a head full of their own product.
But a calendar is not just a familiar skin — it is *structurally* the right shape for this domain, for four
reasons the current app throws away:

1. **A grow room is periodic.** Photoperiod is a 24 h cycle; feeding is a ~3–7 day cycle; stage changes are a
   ~10 week cycle. A grid that wraps time at 24 h and 7 days makes all three visible as *shape*. The current
   chart, a continuous scroll of 15 translucent areas, destroys exactly this.
2. **A calendar has a future.** Every one of the ten round-one concepts is a rear-view mirror. "Düngen fällig
   Fr 29." is not a notification that interrupts you; it is a cell you can already see on Tuesday.
3. **A calendar makes the double feed structurally visible.** Anna's 💧 chip is already sitting in today's
   cell before Ben reaches for the watering can. The confirm-dialog guard (§9) is the backstop, not the
   defence.
4. **A calendar of photographs is a contact sheet.** The camera stops being a tile in the corner and becomes
   the *background of the month*. That is the single screenshot that sells the €289 box.

The one thing I am not building is a scheduler/automation product. There is no irrigation hardware. The
future half of this calendar is *reminders and prefills*, not commands.

## 2. Information architecture

### 2.1 The navigation model in one sentence

**You navigate time, not pages.** Inside a device there is exactly one persistent control — the *Zeitkopf* —
and it moves you along one axis (‹ ›) and one depth (Jahr · Monat · Woche · Tag). Everything else is a sheet
that opens over the grid and closes back onto it.

The existing `ion-split-pane` + `ion-menu` stays as-is (Geräte / Geteilte Links / Konto / Dark-Mode /
Abmelden). No tab bar is introduced. No FAB.

### 2.2 Routes

| Path | Status | What it is |
| --- | --- | --- |
| `/list` | **kept, extended** | Device list. Each card gains a 14-day mini-band (§3.6). One device → straight to its calendar. |
| `/device/:id/kalender` | **new — the device home** | The grid. Query params below. |
| `/device/:id/kalender?tag=2026-08-27` | new (route-modal) | *Tagesblatt* — the day sheet. |
| `/device/:id/film` | new | Film builder, player, export. |
| `/device/:id/pflanzen` | new, **conditional** | Only linked when ≥1 `Plant` exists. |
| `/device/:id/charts` | **kept unchanged** | Deep-linked from the Tagesblatt ("Als Diagramm öffnen"). Every existing share link and `ChartPreset` keeps working. |
| `/device/:id/diary` | **kept unchanged** | `entries` / `growreport` / `co2report`. The calendar is a new *view*, not a replacement. |
| `/device/:id/settings` | kept unchanged | Including all five `ngSwitchCase` device types. |
| `/device/:id/testmode`, `/shares`, `/account`, `/classes`, `/demo` | kept unchanged | |

`/device/:id` (bare) redirects to `/kalender`.

### 2.3 The calendar's query params (extends `diary-query-params.ts` conventions)

```
?zoom=monat|woche|tag        default: woche
&von=2026-08-24&bis=2026-08-30
&tag=2026-08-27              opens the Tagesblatt over the grid
&spuren=temp,rh,vpd,co2,light   which lanes are drawn (default = all the device can produce)
&pflanze=<plant_id>          filter chips + Summenleiste to one plant
&akteur=<actor_id>           filter to one person
&grow=<grow_id>
```

Shareable, bookmarkable, and it is how a techie pins the view they want without a preference existing.

### 2.4 Screen inventory

1. **Geräteliste** (`/list`) — existing + mini-band.
2. **Kalender · Monat** — photo contact sheet, 7×5 cells.
3. **Kalender · Woche** — the default home. 7 day-rows on an hour axis.
4. **Kalender · Jahr** — 12 month blocks, grow spans as bars. *(stretch, §12)*
5. **Tagesblatt** — the day sheet: chart, film strip, event list, device state.
6. **Erfassen-Sheets** — Gießen · Düngen · Notiz/Foto · Messung · Zustand · Phase.
7. **Film** — builder + player + export.
8. **Grow-Kopf** — start/end a run, medium+regime, expected flower length, timezone.
9. **Pflanzen** — flat list of labels, only if any exist.
10. **Akteure** — name list, only rendered when >1 exists.
11. Existing: Charts, Diary reports, Settings, Testmode, Shares, Account.

## 3. The home screen — `/device/:id/kalender?zoom=woche`

### 3.1 Phone layout (390 px), fully specified

On a phone a 7-column week grid gives 55 px columns — useless. So **on a phone the week runs down and the
hours run across**: y = day, x = 0–24 h. On ≥768 px the identical component flips to the familiar 7-column
grid with hours vertical (`@media` only, one template). This is the big-screen advantage the dossier says is
unexploited: on a laptop you get a real week wall.

**A — Gerätekopf.** `{{device.name}} · Tag {{dayOfRun}} · {{stageLabel}}`. If no Grow is running:
`Zelt 1 · kein Grow`. `⋮` opens Einstellungen / Charts / Tagebuch / Film / Grow / Teilen.

**B — Jetzt-Zeile.** The one non-calendar element on the calendar, and I am not going to pretend it isn't a
compromise (§13.1). It carries the current reading, the light state, and *the age of the data as a clock
time*, never as "live". Rules:

| Condition | Copy |
| --- | --- |
| sample < 2 min old | `24,8 °C · 52 % · VPD 1,31 · Licht 100 %   14:22` |
| 2–10 min | same, timestamp in `--tc-text-warning`: `… 14:12` |
| >10 min, device seen | `Letzter Wert 13:40 · vor 42 Min` (values greyed) |
| device offline | `⚠ Keine Verbindung seit 11:08 · vor 3 Std 14` (values greyed, no ° shown) |
| never any data | `Noch keine Messwerte. Das Gerät meldet sich alle 30 Sekunden.` |
| demo / share | identical; there is no privileged path |

**C — Zeitkopf.** `‹` / `›` step one week. Tapping the label opens a date picker. `KW 35` is included because
German growers and every club roster speak in Kalenderwochen.

**D — Tiefe.** Four words, current one boxed. Tapping a word re-renders the same range at that depth. Pinch
does the same on the grid. **Zoom is never persisted:** the calendar opens at *Woche* for every user, every
session, forever (§4.2).

**E — Zustände.** Open `Condition` rows, one per line, max 3 then `+n weitere`. `✕` closes the condition and
stamps `closedBy`. If there are none, the row does not exist (no empty state, no "keine Zustände").

**F — Stundenlineal.** Drawn once, at the top, in the grow's timezone (`Grow.tz`, default the browser's).
A thin vertical `now` line runs down through all rows.

**G — Tagesreihe.** Two lines, 48 px total.
- *Line 1, the band (28 px):* background = photoperiod. `████` night, `░░░` day, derived from measured
  `out_light > 0` where present, falling back to `daynight.day/night` from `device.configuration`; a
  **missing band is drawn as missing**, which is how a failed contactor becomes visible. Ramp minutes from
  `lights.sunrise/sunset` render as a 2-stop gradient. On top of that background sits the **deviation tint**:
  neutral where the measured primary lane was inside its band, `--tc-text-warning` where outside, and
  `▓▓▓` (a solid red-tinted block) for an excursion longer than 10 minutes. Colour comes from the server-side
  raw-sample scorecard (§5.4), never from averaged chart data.
- *Line 2, the Ereignisspur:* day-of-run `d43` in `--tc-eyebrow` style, then chips. Chips: `💧` water,
  `🧪` feed, `📷` photo, `✎` note, `⚗` measurement, `🌱` stage change, `✂` harvest, `⚠` alert.
  A chip carries the actor initial when >1 actor exists (`🧪A`). Max 3 chips + `+2`; overflow opens the day.
  Future days show **hollow** chips: `○ Düngen fällig`.
- *Today's row:* marked `▸`, and everything after `now` is hatched `▒▒▒` — the calendar draws the future as
  future and never extrapolates a measurement into it.

**H — Erfassen-Leiste.** Fixed, 56 px, thumb-height, always in the same four places. `(B)` is the actor
avatar (32 px, coloured) and only appears when >1 actor exists; tapping it switches actor.

### 3.4 Stale / offline / absent — the rules, once, everywhere

- **Never draw a value you did not measure.** No interpolation across a gap > 3× the sample interval; the
  band simply stops and the remainder is an outlined rectangle.
- **Offline:** every affected day row keeps its outline and gains a single inline sentence in the event
  line: `⚠ Offline seit Mi 11:08`. The Jetzt-Zeile carries the duration. The webcam still keeps the existing
  server-side "Offline since …" overlay, which already exists (`imageService.addOfflineOverlay`).
- **Camera silent:** grey camera glyph on affected days + a `Condition`-styled row:
  `⚠ Kamera stumm seit Mi 09:40` (§8.5).
- **Absolutely no data:** the grid renders 7 outlined rows and one line under the Zeitkopf:
  `Noch keine Messwerte. Sobald das Gerät online ist, füllt sich der Kalender von selbst.`
  Below it, the existing setup-wizard link.
- **Demo / share link:** identical rendering; the Erfassen-Leiste is replaced by a single disabled row
  `Nur-Lesen-Ansicht`. `resolveDeviceAccessInfo`'s `locked` / `canEdit` / `webcamAllowed` /
  `chartsAllowed` gate lanes and the film strip exactly as they gate the charts page today.

## 4. NO-MODES MECHANISM

### 4.1 One component, four sizes: **size is the only variable**

There is exactly one cell component in this product:

```ts
@Component({ selector: 'tc-zeitzelle' })
export class ZeitzelleComponent {
  @Input() von!: number; @Input() bis!: number;
  @Input() roll!: DayRoll | RangeRoll;     // precomputed aggregate, §5.4
  @Input() ereignisse!: GrowEvent[];
  @Input() hoehePx!: number;               // ← the ONLY thing that decides content
}
```

The render ladder is a pure function of `hoehePx`:

| height | shows |
| --- | --- |
| 12 px (`/list` band, Jahr) | photoperiod background + deviation tint. Nothing else. |
| 28 px (Woche band) | + excursion blocks, + now-line |
| 48 px (Woche row) | + day-of-run, + up to 3 event chips |
| 52 px (Monat cell) | + Tagesbild as background, + ≤2 event dots |
| full screen (Tag) | + the chart panels, film strip, output lane, event list, numbers |

**Nobody chooses a level of detail for themselves.** They choose how much *screen* one day gets, with a pinch
or by tapping a word in the Zeitkopf, and the answer arrives instantly for the range they are already looking
at. The stoned user never pinches and lives at Woche. The techie pinches to Tag and then taps a number to get
the raw series. Both used the same control on the same object. This is *reveal by depth* taken literally:
simple is the top of a deep screen — here, the top of a zoom stack.

### 4.2 The commitment that stops it being a mode: **zoom is never persisted**

A preference that survives a session is a mode with a different name. So:

- The calendar **always opens at Woche, centred on today**, for every user, every device, every session.
- Zoom lives in the URL and in the session's back stack only. Nothing is written to `localStorage`.
- Consequence, stated plainly: two people describing the app to each other are describing the same screen.
  A support answer that starts "open the calendar" is always true.
- The cost, stated plainly: a techie who lives at Tag re-pinches once per session. The mitigation is the URL —
  every zoom state is a bookmarkable, shareable link, and `ChartPreset`'s existing query-string format is the
  precedent for it.

The one thing that *is* persisted is the actor (`localStorage['tc-actor-<device_id>']`), because a signature
is not a level of detail, and it is visible at all times as a coloured avatar in the Erfassen-Leiste.

### 4.3 Three more non-mode reveals, applied consistently

**Reveal by capability.** Lanes exist only if the device can produce them. No SCD4x → there is no CO₂ panel,
no CO₂ ring in the band, no CO₂ alarm preset, anywhere, ever. Not greyed out, not behind a chevron: absent.
Source is `hardwareInfo` per-role (`parseSocketRoles`), **not** the three-bucket `deviceControlCapability()`,
whose fail-open behaviour on missing `sockets` is the bug that shows a heater-only tent a dehumidifier tile.
Fail-open is replaced by fail-honest: unknown sockets → show the measured lanes, show no control affordances,
show one line `Gerät meldet seine Steckdosen nicht — Firmware zu alt.`

**Reveal by data.** Plant chips exist iff `Plant` docs exist. The actor avatar exists iff >1 `Actor` exists.
The Zustände bar exists iff an open `Condition` exists. The Summenleiste exists iff a range is selected. The
Düngen sheet's regime block exists iff `Grow.regimeId` is set. **The taxation of a feature is proportional to
your use of it, and it is zero at zero.**

**Progressive precision, one rule everywhere.** Every quantity in this product renders as
**Urteil → Zahl → Serie**: the band's colour is the verdict, the Tagesblatt puts the number beside it
(`92 % im Band · 40 Min darüber`), and tapping the number opens the panel with the raw series and a
`Als Tabelle` disclosure. Nobody is denied the number; nobody is forced to read it.

**What I explicitly refuse:** adaptive reordering by behaviour. A calendar's whole value is that Wednesday is
where Wednesday was yesterday. The grid never rearranges. Ranked density is applied only *inside* a cell's
chip overflow (severity, then recency), never to the cells themselves.

## 5. The chart

### 5.1 Where charts live

At Tag depth, and only there. Apache ECharts 6, tree-shaken, driven by a hand-rolled ~50-line directive
(owner decision). The Tagesblatt is the first ECharts surface in the codebase; `/charts` stays on Highcharts
for this release so that no existing share link or preset breaks. **That means one release ships both
libraries.** It is ugly, it costs ~130 KB gz, and it is the honest price of not breaking user data (§13.7).

### 5.2 Goal vs actual, drawn

Per measure, one panel, ~110 px tall, stacked, shared x-axis, one linked crosshair
(`axisPointer.link` + `echarts.connect`). Never two scales in one panel except temp + leaf-temp.

- **Setpoint:** a `line` series with `step: 'end'`, `lineStyle: { type: 'dashed', width: 1.5 }`, built from
  `device.configuration.day.temperature` / `night.temperature` and the `daynight` seconds-of-day pair. It
  steps at lights-on and lights-off, which is exactly what the controller does.
- **Tolerance band:** `markArea` behind it. Source priority, one at a time, and *labelled in the panel
  header* so the reader knows which promise they are being shown:
  1. the user's own `Alarm.upperThreshold/lowerThreshold` for this `sensorType` — hard edges;
  2. setpoint ± tolerance (±1,5 °C / ±7 % RH, the values `grow-assistant-card` already uses);
  3. the stage's `vpdRange` from `GROW_STAGE_PRESETS` — advisory, dashed edge.
- **Actual:** `line` with a `min`/`max` envelope drawn as a translucent `custom` band, `sampling: 'minmax'`
  (never LTTB in the plot — a bang-bang controller's oscillation is the signal). Deviation is encoded by
  `visualMap.piecewise` colouring the line where it leaves the band. **No fill to the axis, ever** — the
  current `type:'area', threshold:null` encodes nothing.
- **Day/night:** `markArea` per photoperiod block, derived from measured `out_light > 0`, falling back to the
  schedule. Ramp edges get a 2-stop gradient from `lights.sunrise/sunset`.
- **Annotations:** the Ereignisspur from the calendar row *is* the annotation rail — literally the same
  component, re-parented under the x-axis. 20 px, one row of user events, one row of device events, 10 px
  pixel-proximity clustering with count badges, full-height dashed line for a stage change. Tap, not hover.
- **Outputs:** a state-timeline lane under the panels; region length = duration; a gap is a gap.

### 5.3 Mobile interaction

One finger scrolls the page. Two fingers pan/zoom (`dataZoom: { type: 'inside' }`). Tap or drag = crosshair,
and the readout is a **pinned header row above the panels** (one line per panel), not a floating tooltip a
fingertip covers. Axis labels are never hidden — below 320 px they degrade to 3 ticks with the unit moved
into the panel title.

### 5.4 The number behind the colour (`DayRoll`) — and the correctness trap

The calendar band's colour comes from **raw Influx samples**, computed server-side, never from
`aggregateWindow(fn: mean)` — averaging destroys the excursions the metric exists to count, and the error is
invisible by eye.

```ts
DayRoll {
  device_id, date: '2026-08-26', tz: 'Europe/Berlin',
  measure: 'temperature' | 'humidity' | 'vpd' | 'co2',
  inBandPct, abovePct, belowPct, coveragePct,
  longestExcursionMs, mean, min, max,
  dayInBandPct, nightInBandPct,          // split, because they are different problems
  lightOnAt, lightOffAt, lightMinutes,
  eventCount, pickImageId
}
```
Computed by a nightly job for closed days; today's row is recomputed on read with a 5-minute cache. New
endpoint `GET /data/roll/:device_id?von&bis` returns the range in one request. This collection is also
the CSV/JSON export (§12) and it is what makes a Jahr zoom cheap.

`coveragePct < 80` greys the cell and prints `Nur 63 % Daten an diesem Tag — Werte mit Vorsicht lesen.`

## 6. The diary and multi-plant

### 6.1 The diary *is* the calendar

There is no "diary tab" in this concept. Writing an entry means putting something in a day. Reading the diary
means looking at the grid. The existing `/diary` reports survive as a *list rendering* of the same events for
people who want to scroll and for the grow report's phase summary.

### 6.2 New entities (all cloud-side MongoDB, all optional fields, house style)

```ts
Grow      { grow_id, device_id, name, startedAt, endedAt?, flipAt?,
            expectedFlowerWeeks?, mediumId?, regimeId?, tz, createdBy?, createdAt }
Plant     { plant_id, device_id, grow_id, label, strain?, source?, potLiters?,
            startedAt, archivedAt?, createdAt }
Actor     { actor_id, device_id, name, initials, color, active, createdAt }
GrowEvent { event_id, device_id, grow_id?, plant_ids: string[], type, at,
            actor_id?, note?, images: string[], data: object,
            source: 'user'|'device'|'schedule', supersedes?, clientKey, createdAt }
Condition { condition_id, device_id, grow_id?, plant_ids: string[], text,
            severity: 0|1|2, openedBy?, openedAt, closedBy?, closedAt? }
Due       { due_id, device_id, grow_id?, kind: 'water'|'feed'|'task',
            rule: { everyDays } | { regimeStep }, dueAt, plant_ids: string[],
            doneEventId?, skippedAt? }
Film      { film_id, device_id, grow_id?, von, bis, cadence, frames, burnIn,
            status, image_id?, createdAt }
Regime    { regime_id, medium, feedLine, label, steps: [...],
            source_url, retrieved_at, chart_version, kind }
```

`GrowEvent.type ∈ water | feed | note | photo | measure | stage | harvest | train | pest | transplant`.

Indexes: `{device_id, at}`, `{device_id, clientKey}` **unique** (idempotency, §9.4),
`{grow_id, plant_ids, at}`.

**`DeviceLog` is untouched.** Device-generated events (boot, alarm, socket, recipe) stay where they are and
are read into the same lane; the calendar merges two sources at read time. This avoids a migration of the
one collection everything already depends on, and it means the legacy `deleted`-flag oddity and the seven
legacy prose regexes stay contained in `LogTranslateService` where they already live.

`convertEventsToGrowCycles()` (the browser-side string-comparison cycle inference) becomes a **one-time
backfill** into `Grow` + `GrowEvent`, run idempotently at boot, keyed by the cycle's start timestamp so
existing share-link cycle ids keep resolving.

### 6.3 How a user who ignores plants is untaxed

`plant_ids: []` means *the whole tent*, and it is the default on every capture sheet. A user who never taps
"Pflanzen anlegen":

- never sees a plant chip row (reveal by data),
- gets `Gegossen · 8 l` instead of `Gegossen · 8 l · A1–A3`,
- gets a Summenleiste that says `3 Gaben · 14 l` with no per-plant breakdown,
- and can add plants later without invalidating a single earlier event — `[]` stays `[]` and reads as
  "everything at that time", which is true.

Plants are created in one place: the Grow-Kopf → `Pflanzen anlegen` → a number pad (`Wie viele? 3`) that
mints `A1 A2 A3` with editable labels. Ten seconds, or never.

### 6.4 Harvest and weights — privacy without a mode

`type: 'harvest'` exists with `data: { wetGrams?, dryGrams?, plant_ids }`. **The weight fields are not
rendered until a weight has been entered once for that device.** The harvest sheet ships with
`Erntedatum` + `Notiz` + `Foto` and one small text link: `Gewicht notieren`. Tapping it reveals the field
*and* prints one honest line: `Nur auf unserem Server in Deutschland. Du kannst es jederzeit löschen.`
No jurisdiction switch, no "Klub-Modus" — reveal by data does the work, and the default is the
privacy-maximal one.

## 7. Watering & fertilising

### 7.1 The capture flow, counted in taps

The Erfassen-Leiste is fixed at the bottom of every calendar depth. Nothing moves.

| Goal | Sequence | **Taps** |
| --- | --- | --- |
| "I watered." (stoner, 2 a.m., dark tent) | `💧` → done. Chip lands in today, Snackbar `Gegossen 14:22 · Rückgängig` for 6 s. | **1** |
| "I watered, 8 l" | `💧` long-press → sheet opens with `8 l` prefilled from your last volume → `Speichern` | **3** |
| "I fed, per the plan" | `🧪` → sheet opens prefilled from the regime's due step → `Übernehmen` | **2** |
| "I fed, but 3 ml instead of 4" | `🧪` → tap `Bio-Bloom 4 ml/l` → number pad `3` → `Übernehmen` | **4** |
| Club: fed A1–A3, 20 l, EC 1,8 | `🧪` → `A1` `A2` `A3` → tap `20 l` → pad → tap `EC` → pad → `Übernehmen` | **9** |
| Confirming a due chip from the future | tap the hollow `○ Düngen fällig` chip → `Übernehmen` | **2** |

**The one-tap water is a real, complete, honest record** — `{type:'water', at:now, plant_ids:[],
volume_l:null, actor_id}`. A null volume is not a defect; it is what the person knew. The Summenleiste says
`3 Gaben · 2× ohne Menge` rather than inventing a number.

### 7.2 The Düngen sheet

```
┌────────────────────────────────────────────────┐
│ Düngen                             Fr 28. 14:26│
├────────────────────────────────────────────────┤
│ Pflanzen   [ganzes Zelt] A1  A2  A3            │  chips; only if plants exist
├────────────────────────────────────────────────┤
│ Nach Plan · Bio-Bloom · Blüte Woche 3          │  ← from Grow.regimeId
│   Bio-Grow      2 ml/l                    ✎    │
│   Bio-Bloom     4 ml/l                    ✎    │
│   Top-Max       1 ml/l                    ✎    │
│   Menge         10 l              = 40 ml      │
│   ────────────────────────────────────────     │
│   Reihenfolge: Silizium → Basis → Cal-Mag →    │
│   Zusätze → pH zuletzt                          │
├────────────────────────────────────────────────┤
│ EC 1,8   pH 6,2   (optional)              ✎    │
│ Notiz …                                    📷  │
├────────────────────────────────────────────────┤
│           Abbrechen        Übernehmen          │
└────────────────────────────────────────────────┘
```

- Every prefilled number is editable in place; an edited value renders in `--tc-text-info` with a small
  `≠ Plan` marker, and the deviation is stored (`data.deviatedFrom`), because *deviating is the normal case*.
- `= 40 ml` recomputes live. Nine unit systems exist in the wild; **only ml/l and g/l are ever displayed**,
  and the total is always shown in ml or g so a conversion bug is visible.
- `EC` is stored canonically in mS/cm with `ec_basis: 'absolute' | 'delta_over_source'` carried from the
  regime — because a chart that publishes `EC+` and a UI that alarms on the raw value is actively wrong.
  A bare "ppm" number is never rendered.
- **All-Mix behaviour:** a regime whose medium is heavily pre-fertilised renders, for the first weeks:
  `Nach Plan · All-Mix · noch nicht düngen` with the product rows collapsed to one line
  `Woche 1–3: nur gießen. All-Mix ist vorgedüngt.` and `Übernehmen` writing a `water` event instead. That is
  the test of whether the domain is modelled: a schedule that cannot say "don't feed yet" is not a schedule.
- **BioTabs behaviour:** the regime's steps are `re-tab alle 6 Wochen`; the calendar shows one hollow chip
  every six weeks and nothing in between.

Brand names are plain text labels. No logos, no brand colours, no bottle imagery, never inside a Terp Control
feature name. Numbers live in the `Regime` collection with `source_url` + `retrieved_at`, surfaced as
`Zuletzt geprüft 06/2026` under the plan header — the legal posture doubles as a trust feature.

### 7.3 Schedule following

When `Grow.regimeId` is set, `Due` rows are generated for the whole run and drawn as hollow chips in future
cells. Rules:

- An overdue `Due` **stays in the day it was due** and turns amber: `○ Düngen überfällig seit 2 Tagen`.
  It never migrates to today. A calendar that moves the past is not a calendar.
- The schedule advances by **feed events, not wall-clock weeks** — completing step *n* schedules step *n+1*
  at `+intervalDays` from the actual event. Growers feed Tue/Fri and slip.
- The 12/12 flip is **detected from `out_light` history** (a sustained drop from ≥16 h to ≤13 h over 3 days)
  and offered, never applied: a `Condition`-styled row `Sieht nach 12/12 seit Fr 21. aus. Blüte starten?`
  with `Ja` / `Nein, weiter vegetativ`. No bottle-brand calculator can do this because none of them can see
  the lamp.
- Autoflower: `Grow.autoflower` sets a strength multiplier of ×0.5 on regime doses and suppresses the flip
  detection entirely.
- A `Due` is never a push notification unless the user turns one on (`Erinnerung` toggle in the Grow-Kopf,
  delivered through the existing `Alarm.actionType: 'email'` machinery — no new notification stack).

### 7.4 The cumulative question — the Summenleiste

Dragging across day rows (or tapping the Zeitkopf label at Woche/Monat depth) selects a range, and the
Zeitkopf becomes:

```
│ 24. – 30. Aug · 3 Gaben · 14 l · 2× ohne Menge │
│ Bio-Grow 20 ml · Bio-Bloom 40 ml · Top-Max 10 ml│
│ Anna 2 · Ben 1                            ✕    │
```

Tapping a plant chip first (`?pflanze=A3`) scopes it: *"How much Bio-Bloom has A3 had this cycle, and from
whom?"* is a range selection plus a chip. The whole-grow answer is the same interaction at Jahr depth or via
`Grow-Kopf → Bilanz`.

## 8. Camera, timelapse and image correlation

This is the headline. What exists today: a still every 30 s over MQTT/RTSP into Mongo, three rolling
timelapses (`1d`/`1w`/`1m`) rebuilt hourly with `libx265 -crf 30` at 25 fps, progressive thinning of stills,
3-year retention. **ffmpeg, sharp and imagemagick are already server dependencies** — this feature is
mostly content logic, not new infrastructure.

### 8.1 The camera is the calendar's background

`Image` gains two optional fields:

```ts
Image { ..., pick?: 'daily', qc?: { lum, sd, r, g, b, hash /* 64-bit dHash */ }, lit?: boolean }
```

`qc` is computed at capture with `sharp(buf).stats()` plus an 8×8 greyscale resize for the dHash — ~5 ms per
frame, ~14 s of CPU per device per day, ~36 min/day across the whole first series of 150 units. ~40 bytes
per document.

One frame per day is elected `pick: 'daily'`. That frame is the Monat cell background, the `/list` band's
thumbnail on hover, and the film's frame. **The camera is not a tile; it is the surface the data is
printed on.**

### 8.2 Culling — the content problem, specified

A tent timelapse is mostly garbage. The rules, in order, run nightly over the day's frames:

1. **Lit window only.** Keep frames with `out_light > 0` (from Influx) or, failing that, inside the
   `daynight` schedule. This alone removes ~half the frames and all of the black ones.
2. **Same phase of the photoperiod.** Target `lightOnAt + 0.5 × lightMinutes` — the "Fotostunde". Candidates
   are ranked by distance from it. *This single rule removes most of the flicker in a tent timelapse and
   nobody wrote it down in round one*: the lamp is at the same dim level and the same angle every day.
3. **Exposure outlier.** Drop frames whose `qc.lum` is outside ±25 % of the day's median (door open, camera
   IR cut-over, a phone torch).
4. **Contrast collapse.** Drop frames whose `qc.sd` < 60 % of the day's median (condensation on the lens,
   fogger, out-of-focus).
5. **Something moved.** Hamming distance of `qc.hash` to the previous frame > 12 bits at 30 s spacing means a
   hand, a door or a moved plant. Drop that frame **and the next two**. This is the "no humans in the tent"
   rule, and it costs a 64-bit XOR.
6. **Dedup.** Identical `qc.hash` within a day → keep one.
7. If everything is culled, fall back to the frame nearest the Fotostunde and set `qc.fallback = true`; the
   Monat cell then draws a thin dashed border so the reader knows this day's picture is not vouched for.

### 8.3 Normalisation across twelve weeks

Applied at film-build time, per frame, with `sharp`:

- **Luminance:** `.linear(a, b)` so the frame's median luminance matches a **rolling 7-frame median**, not a
  global constant. Temporal smoothing means a deliberate dimming schedule reads as a slow change instead of a
  step, and one bad day cannot re-expose the whole film.
- **White balance:** grey-world correction **clamped to ±15 % per channel**. Deliberate: a magenta LED tent
  *is* magenta, and fully neutralising it produces a film that looks nothing like the room. The clamp is
  enough to stop a daylight door-open frame from strobing.
- **Stabilisation:** v1 ships *detection*, not correction. A sustained dHash discontinuity across a day
  boundary raises a `Condition`: `Kamera scheint am 12.6. verschoben worden zu sein.` with one action,
  `Ab hier neu ausrichten`, which stores a per-range crop offset applied at build time. Real optical
  stabilisation (`ffmpeg vidstab`) is v1.1 and is named as such rather than implied.

### 8.4 Der Film — what ships in October, and how it leaves

**The builder** (`/device/:id/film`, also reachable as `▶ Film aus diesem Monat erstellen` at the bottom of
the Monat grid — i.e. from the calendar, on the range you are already looking at):

```
┌────────────────────────────────────────────────┐
│ Film                                           │
│ Zeitraum   1. Juni – 29. Aug 2026   (Tag 1–90) │
│ Takt       ● 1 Bild pro Tag   ○ 1 Bild / 30 Min│
│            90 Bilder · 7 Sekunden               │
│ Daten      ☑ Datum, Tag und Werte einblenden   │
│ ─────────────────────────────────────────────  │
│              [ Film erstellen ]                │
│  Dauert etwa 40 Sekunden. Du kannst weggehen.  │
└────────────────────────────────────────────────┘
```

**Encoding — a deliberate change from what the server does today:**

```
ffmpeg -framerate 12 -f image2 -i %d.jpeg \
       -c:v libx264 -profile:v high -pix_fmt yuv420p -crf 23 \
       -movflags +faststart -f mp4 film.mp4
```

H.264, **not** the current `libx265`. x265 is smaller, and it is also the reason a file "you can hold" fails:
iOS Photos, WhatsApp and most Android galleries handle H.264/yuv420p universally and HEVC unevenly. Long edge
capped at 1920, never upscaled from the source (usually 1280×720). 12 fps, so a 90-day daily film is 7.5 s —
long enough to watch, short enough to send.

**How it leaves the product — three named routes, and I am honest about the third:**

```
GET /image/:device_id/film/:film_id?download=1&token=<imageToken>
  → Content-Type: video/mp4
  → Content-Disposition: attachment;
       filename="terpcontrol_zelt-1_2026-06-01_2026-08-29_tag1-90.mp4"
```

1. **Desktop + Android Chrome:** the `download=1` link saves straight to Downloads. Done.
2. **iOS Safari:** `<a download>` is ignored. The page therefore renders the finished film full-screen in a
   `<video controls playsinline>` with a primary button `Video sichern` calling
   `navigator.share({ files: [new File([blob], name, {type:'video/mp4'})] })`, which reaches the system share
   sheet including *Save to Photos*. If `navigator.canShare({files})` is false, one instruction line replaces
   the button: `Video antippen und halten → „Video sichern".` No pretending.
3. **A link for other people:** `ShareLink.page` gains `'film'`; `/film/:share_id` is a no-login page with the
   player, the download link, the date range and nothing else. Expiry and revoke use the existing
   `ShareLinkModule` UI unchanged. A link that needs a login is not a share, so this one does not.

**Size discipline:** a `Film` document holds its mp4 as a `Buffer` like every other `Image` and is therefore
under the 16 MB BSON cap. 90 frames at CRF 23 / 720p ≈ 3–6 MB — fine. The half-hour cadence over 90 days is
4 320 frames and is **refused**, with a real sentence: `Zu viele Bilder (4 320). Wähle einen kürzeren
Zeitraum oder den Takt „1 Bild pro Tag".` Hard cap 1 200 frames.

The three existing rolling `1d`/`1w`/`1m` timelapses **stay exactly as they are**, keeping the charts page's
current behaviour intact. Der Film is the deliberate, exportable one.

### 8.5 The camera gets an alarm

Today the camera's silence is only discoverable by looking. New server-side check in the existing hourly
compress loop: no `format:'jpeg'` frame for > 6 h **while the device itself is online** →
`deviceService.logMessage(device_id, { title: 'message-camera-silent', severity: 2,
categories: ['webcam','error'] })`, which flows into the existing notification paths, and a `Condition`-styled
row on the calendar: `⚠ Kamera stumm seit Mi 09:40`. Resolved automatically on the next frame. Cost: one
counter and two i18n keys. Cheapest headline feature in the document.

### 8.6 Image correlation — four concrete couplings

1. **Scrub the chart, move the picture.** In the Tagesblatt the still is *pinned above* the panels and
   follows the crosshair — not a 500 ms hover, which does nothing on touch. The film strip beneath it is an
   axis: thumbnails positioned by `timestamp` on the same x-scale, so uneven capture reads honestly as gaps.
   Delivered as **one sprite + JSON index per window** (100 tiles, 256×160), not N requests.
2. **Pick a picture, get its numbers.** Tapping a strip thumbnail pins the crosshair and prints the readout
   row: `12:31 · 24,9 °C · 51 % · VPD 1,34 · CO₂ 812 · Licht 100 %`.
3. **The month is the correlation.** A contact sheet whose cells carry both the picture and the day's
   deviation band is, by itself, the answer to "when did it start looking unhappy" — you scan for the amber
   cells and look at the picture next to them.
4. **Bild mit Zahlen — correlation that leaves.** Any still, and optionally every frame of a film, can carry
   a burned-in strip: `26.08.2026 · Tag 43 · Blüte 12 · 24,9 °C · 51 % · VPD 1,34 · CO₂ 812`. This is an
   SVG composited with `sharp` — **the exact code already exists** as `imageService.addOfflineOverlay`. A
   picture posted to a forum then documents itself, and that is worth more than any sync integration the
   dossier proved impossible.

## 9. Clubs

Scope per the owner: the German Anbauverein and the two-or-three-people-sharing-a-tent case. Not commercial.

### 9.1 Attribution without an auth rewrite

`Actor` is **device-scoped and account-free**: names the device owner types once
(`Grow-Kopf → Personen → + Anna`). Choosing yourself is one tap on the avatar in the Erfassen-Leiste, stored
in `localStorage['tc-actor-<device_id>']`, and shown at all times. Every `GrowEvent` and `Condition` carries
`actor_id`. `auth.middleware.ts:172` is not touched; there is exactly one writing account.

That is attribution, and it is honestly labelled as such in one line under the Personen list:
`Namen, keine Konten. Wer das Gerät bedienen darf, entscheidet weiterhin das Passwort.`
Real memberships (a `Membership` collection + rewriting two authorisation queries) are named as the v2 path
and the `actor_id` column is the migration target — an actor upgrades to a member without touching a single
stored event.

### 9.2 The double feed

The calendar's structural defence comes first: **today's cell already shows Anna's chip**, in her colour,
before Ben picks up the can. The dialog is the backstop:

```
┌────────────────────────────────────────────────┐
│ Anna hat A1–A3 vor 1 Std 30 gefüttert.         │
│ Trotzdem eintragen?                            │
│                                                │
│   09:12  Bio-Bloom 4 ml/l · 10 l · Anna        │
│                                                │
│        Abbrechen          Trotzdem             │
└────────────────────────────────────────────────┘
```

- Fires when an event of the same `type` overlaps the same plants (or both are `[]`) inside a window:
  **12 h for feed, 6 h for water**. Fixed values, not a setting.
- `Abbrechen` is the default-focused button. `Trotzdem` is one deliberate extra tap and stores
  `data.confirmedOverlap = true`, so the report can later show `2 Gaben am selben Tag (bestätigt)`.
- The guard is on at all times, including single-actor devices, where it catches the other common case: you
  already did it and forgot.

### 9.3 Conditions — the thing pinned to the tent door

`Condition` is a *span*, not an event, which is why a calendar is the right home for it: it renders as a bar
across the top of the grid for every day it was open. Created from the Erfassen `✎` sheet →
`Als Zustand merken`. Examples that shipped in the seed copy: `CO₂-Flasche fast leer`, `Steckdose 3 wackelt`,
`A3 nicht gießen — zu nass`. Anyone can close one; `closedBy` and `closedAt` are stored. A condition with
`plant_ids` shows on that plant's chip as a dot, so the person about to water A3 sees it in the same sheet.

### 9.4 Capture in a cellar

No service worker in v1 (it is a new dependency and a build change — flagged, not smuggled). What *does* ship
is the thing that makes offline safe rather than dangerous: **every capture mints a `clientKey` UUID at the
moment of the tap**, and `{device_id, clientKey}` is uniquely indexed. The in-memory retry queue can fire as
often as it likes; a duplicate is a 200 with the original event. In a shared record, a double-logged feed is
indistinguishable from a real double feed — this makes it impossible rather than unlikely. The service worker
in v1.1 then inherits a server that is already idempotent.

### 9.5 Privacy posture

- Attribution is **names typed by the owner**, not identities. No emails, no accounts, no real-name field.
- No per-member dispensing, no grams handed over, no membership numbers, no DOB. The product refuses to be
  the club's § 26 system of record, and says so once, in the Personen screen:
  `Terp Control dokumentiert den Raum, nicht die Mitglieder.`
- Harvest weights are reveal-by-data (§6.4) and default absent.
- Every export carries a `Namen: vollständig / Initialen / anonym` selector defaulting to **Initialen**.
- No location, ever. No analytics SDK. No community feed.
- Deleting a `Grow` deletes its events, its films and its stills, in one action, with a real count in the
  confirm: `Grow „Sommer 26" löschen? 412 Einträge, 90 Bilder, 2 Filme.`

## 10. Old devices (type 7) — fan, light, plug

These devices do not have a grow. They have a schedule and a state. The calendar still fits, because a
calendar of a lamp is a *photoperiod calendar*, which is exactly what a light owner wants to check.

**What lanes exist is derived from what Influx actually holds for that `device_id`**, per measure, not from
`device_type` and not from `deviceControlCapability()`.

| Device | Woche row shows | Erfassen-Leiste | Tagesblatt |
| --- | --- | --- | --- |
| `light` | photoperiod band from `out_light` + dim level as the band's tint; a **missing block is a failed schedule**, visible as a hole | `📷 ✎` only (no 💧/🧪 until a Grow exists) | dim-level panel + output lane + event list |
| `fan` | `rpm` band; night/day background from the schedule if one exists, otherwise a flat background | `📷 ✎` | rpm panel + output lane |
| `plug` | on/off state lane from `out_relais`; temperature band if the plug reports one | `📷 ✎` | temperature panel (if any) + state lane |
| `fridge` | full controller treatment — it is already the richest type | full | full |
| `dryer` | dead type per `AGENTS.md`; falls through to today's overview, unchanged | — | — |

Concretely, for a plug owner:
- `/list` gains a 14-day band on their card. That is a net improvement and costs them nothing.
- Their device home becomes the calendar; the Zeitkopf reads `Steckdose Keller` with **no** `Tag 47 · Blüte`
  segment, because no `Grow` exists and none is offered until they tap `⋮ → Grow starten`.
- `Einstellungen` still routes to `plug-settings` exactly as today — the `ngSwitchCase` block is untouched.
- The six existing outline buttons still exist, in the `⋮` menu.
- Their over/under-temperature and time alarms render as `⚠` chips in the day rows, which is more than they
  get today (today those are rows in a log they must go looking for).
- **Nothing they have breaks.** No entity is required, no migration touches them, no new field is mandatory.

The one visible regression risk: a plug with no sensor and no schedule produces a calendar of seven empty
rows, which is worse than today's small card. Mitigation: when a device produces **zero** lanes, the calendar
route renders the existing overview card above an empty grid with the line
`Dieses Gerät liefert keine Messwerte. Der Kalender füllt sich, sobald es welche gibt.` Honest, and it is the
one place I keep an old screen alive for a reason other than compatibility.

## 11. Per-user-type walkthrough

**1 · Lazy monitoring-only.** Opens the app, sees the week: seven bands, six neutral, one with an amber block
on Wednesday. That is the whole answer to "is my tent OK", and it took no reading. If curious, taps Wednesday
and gets `92 % im Band · 40 Min darüber · längste 22 Min` with the chart under it. He never creates a Grow, a
plant, an actor or a schedule, and the app never asks him to. His Erfassen-Leiste shows `📷 ✎` only.

**2 · Same, but with a camera.** Opens at Woche, taps `Monat`, and gets a contact sheet of his tent — 30
photographs, all taken at the same point in the light cycle, with the climate band under each. At the bottom,
one row: `▶ Film aus diesem Monat erstellen`. Two taps and forty seconds later he has
`terpcontrol_zelt-1_2026-08-01_2026-08-31_tag16-46.mp4` in his camera roll, seven seconds long, with the date
and the numbers burned into every frame. This is the concept's best-served user and the reason it exists.

**3 · Controls certain aspects (CO₂ or heating only).** The lanes he sees are the ones his sockets can act on
— a heater-only tent has a temperature band with a setpoint drawn on it and **no** humidity band with a
target it can never reach. The output lane shows his heater's duty cycle by day, which is the thing that
tells him his heater is undersized. He is never nagged about a dehumidifier he does not own, because the
per-role socket CSV is read directly instead of being collapsed into three fail-open buckets.

**4 · Full tent.** Gets every lane, the output state-timeline, and the setpoint drawn against every one. The
calendar shows him what he actually wants: whether the room held through the night, night after night, as a
row of bands he can compare by eye. He is also the user who most needs the honest bad news that the firmware
has five socket roles and no humidifier — the calendar does not paper over it; the lane simply is not there.

**5 · Closed-loop DIY.** Lives at Tag depth and at the URL. Every view is a query string; `DayRoll` is one
JSON endpoint (`/data/roll/:device_id?von&bis`) that returns exactly the aggregates the calendar draws, which
is the first thing in this product a script can consume without scraping. `Tag exportieren (CSV)` gives him
the raw series *including actuator state*, which no competitor exports. He will still complain there is no
write API, and he will be right; that is v2 and I am not pretending otherwise.

**6 · Club.** Three people, one tent, one login, three names. Every chip carries an initial and a colour, so
"who did what" is answered by looking rather than by asking. Ben opens the app on Friday, sees Anna's `🧪A`
already in today's cell, and does not feed again — and if he starts to anyway, the dialog stops him. The
overdue `○ Düngen überfällig seit 2 Tagen` sitting in Wednesday's cell is the duty roster. `CO₂-Flasche fast
leer · Ben, seit Di` is the note on the tent door. Dragging across the week gives the treasurer
`3 Gaben · 14 l · Bio-Bloom 40 ml · Anna 2 · Ben 1`.

**7 · Old device owner.** A light owner sees a week of photoperiod bars and, for the first time, notices that
Thursday's block is 20 minutes short. Nothing else about his product changed: same settings page, same
alarms, same device. He gains a picture of his schedule and loses nothing. A plug with no sensors keeps its
old card (§10).

## 13. Honest weaknesses

**1. A calendar is a bad shape for "right now".** The single most common question — "is my tent OK at this
moment" — is a state question, and a grid of days answers it slowly. I bolt a Jetzt-Zeile above the grid,
which is a dashboard element sitting on top of a calendar and is the one place the concept is not itself.
A critic will call it a dashboard wearing a calendar and they will be half right.

**2. An empty calendar looks broken.** A brand-new controller's first screen is seven grey outlined rows.
A tile dashboard shows a big `24,8 °C` and feels alive on day one. This concept's first impression is its
worst, and it stays weak until roughly day five. The mitigations (the Jetzt-Zeile, the "füllt sich von
selbst" line, the setup deep link) reduce the damage; they do not fix it.

**3. The primary axis is wall-clock, and growers think in day-of-run.** "Blüte Tag 12" is the unit of
horticultural thought, and this design puts it on the second line while a date owns the first. Comparing two
grows is genuinely worse here than in a day-of-run design (C10's territory): I can only offer grows as bars
at Jahr depth and a film aligned by day-of-run. If run-over-run comparison turns out to be the retention
feature, this concept is on the wrong axis and no amount of polish fixes that.

**4. Density on a phone is tight and it will overflow.** Seven rows × 48 px is 336 px of grid; a club tent on
a busy Friday has six events on one row and gets three chips plus `+3`. The overflow rule is honest but the
information *is* hidden until you open the day. On a 320 px device the hour ruler is 8 pixels per hour.

**5. DST will make the photoperiod bar jump, six weeks after launch.** `daynight.day/night` are
seconds-of-day in UTC and there is no device timezone anywhere in the stack. `Grow.tz` is a cloud-side
mitigation that makes the *rendering* right; it does not make the *controller* right, and on 25 October 2026
a 12/12 tent will show its lights-on block move by an hour. I flag it as a firmware/config gap rather than
pretending the calendar solved it. Somebody must decide before October whether `daynight` gets a timezone.

**6. `DayRoll` is a cache and caches are wrong.** A day's band colour depends on the setpoint that was active
*then*. Device configuration changes are logged but not versioned, so a `DayRoll` computed today against
yesterday's config is right and a `DayRoll` recomputed after a settings change is subtly wrong. The v1
mitigation is to stamp the setpoints used into the `DayRoll` document and never recompute a closed day. That
is correct and it means a genuine mistake in the setpoint history is uncorrectable without a manual rebuild.

**7. The release ships two chart libraries.** Keeping `/charts` on Highcharts protects every share link and
every `ChartPreset` in circulation; it also means ~130 KB gz of dead weight for one release and two visual
languages for the same data in the same product. It is the right trade and it is still a defect a critic will
photograph.

**8. Film builds are unqueued CPU.** The existing `pLimit(10)` is a concurrency clamp, not a queue, and a
150-device launch where everybody makes a film in the same week will contend with the hourly timelapse
rebuild. v1's answer is a 1 200-frame cap, one film per device at a time, and a status row
(`Film wird erstellt … etwa 40 Sekunden`). A real job queue is not in scope and I am not claiming otherwise.

**9. The no-persisted-zoom rule will annoy exactly one person: the techie.** I have argued why it is the
correct anti-mode commitment and offered URLs as the escape. If user testing shows a daily-Tag-depth user
population big enough, the honest fix is a *device-level* default (not a user-level preference) chosen by the
device's data — which is a slippery slope towards a mode, and I would rather lose the argument than start
sliding down it.

**10. It is a lot of new persistence for eight weeks.** Seven new collections, one backfill, one nightly job,
one new endpoint, a chart library migration on one surface, a video pipeline change, and both languages —
against a codebase with 38 `it()` blocks and no migration tooling. The scope in §12 is what I would commit
to; a critic is entitled to believe it is 20 % optimistic, and the cut list in §12 exists because I think so
too.
