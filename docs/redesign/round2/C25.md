# C25 — "Zettel"

**Family:** diary · **Centre of gravity:** the board of standing conditions — open, owned, closed — is the
home screen. Events scroll away; conditions persist until a human or the machine closes them.

---

## 1. Thesis

**Everything this product knows is a slip of paper with a lifecycle — open, owned, closed — and the home
screen is the board those slips are pinned to.**

What actually hangs on a tent door is not a chart and not a feed. It is four slips: *CO₂-Flasche fast leer*,
*A3 nicht gießen*, *Steckdose 3 wackelt*, *Freitag füttern*. Every one of them is a **standing fact with an
owner and no end date**, and no software in this market has a place for one. Terp Control has alarms (which
close themselves and vanish), logs (which scroll away) and a diary (which nobody writes).

C25's move is to notice these are the same object seen three ways. An **alarm is a condition the machine can
close by itself**. A **note is a condition only a human can close**. A **due feed is a condition a care event
closes**. Unify them into one entity — `Condition` — with one lifecycle, one ranking rule and one visual
form, and three things fall out for free:

1. **The home screen is a list of what is actually true right now**, ordered by cost of ignoring it, and it
   is empty when everything is fine. Nothing on it is decoration.
2. **The diary writes itself as the sediment of the board.** Closing a slip *is* the diary entry, and it
   carries something no diary in this market has: **how long the condition was open, and who ended it**.
   "Schimmelgefahr — 3 Tage offen, geschlossen von Anna" is a sentence nobody had to type.
3. **The camera's unsolvable content problems become slips.** Camera stopped, lens dirty, camera nudged on
   day 12, lights on but the frame is dark — each is a standing condition somebody can own, which is a
   better answer than pretending an algorithm fixed it.

The bet: a grower does not want to be *informed*. They want to know **what is still open**.

## 2. Information architecture

Five routes. No tab bar (the codebase has none and Ionic 6 `ion-split-pane` + `ion-menu` stays). The board is
the root; everything else is one tap from it and returns to it.

| Route | Name in the UI (de) | What it is |
| --- | --- | --- |
| `/list` | *(device name)* | **The board.** Single device → the board directly (existing behaviour). Multiple devices → a stack of per-device boards, each collapsed to its top three slips. |
| `/device/:id/verlauf` | Verlauf | The chart. ECharts, small multiples, **Zettel rail** (§5). Keeps today's query-param view model. |
| `/device/:id/tagebuch` | Tagebuch | The archive of **closed** slips + care events + photos. Replaces the `entries` report; `growreport` and `co2report` survive as filters over it. |
| `/device/:id/pflege` | Pflege | Per-plant cumulative care ledger. Only rendered when ≥1 `Plant` exists (§9.3). |
| `/device/:id/settings` | Einstellungen | Untouched `ngSwitch` on `device_type`. |

The old six outline buttons on the overview collapse into one footer row: `Verlauf › Tagebuch › Einstellungen ›`.
`Testmode` and `Maintenance` become slips (§10), not buttons — maintenance mode is literally a standing
condition and today it is a button that leaves no trace.

`/shares`, `/account`, `/demo`, `/classes`, `/diagnostics` unchanged.

**Navigation model:** the board is the only place you start. Slips expand *in place* — expansion is never
navigation. The only navigation is the footer row and a slip's own `Verlauf öffnen`, which deep-links the
chart to that slip's time window with the slip pre-selected in the rail.

## 3. The home screen

### 3.1 Layout (phone, 390 px)

```
┌────────────────────────────────────────────┐
│ ☰   Zelt 1                    ⟳ vor 40 s   │
├────────────────────────────────────────────┤
│  Am Zelt:  ( Christian )  Anna   Timo   +  │  ← only when ≥2 Actors exist
├────────────────────────────────────────────┤
│                                            │
│ ▮  A3 nicht gießen — übergossen            │  ← kind:'block'
│    Anna · seit 2 Tagen                     │
│                                            │
│ ●  Luftfeuchte 71 % — über Ziel (50 %)     │  ← machine, severity 1
│    seit 3 Std 20 · Entfeuchter läuft       │
│                                            │
│ ○  Gießen fällig — Schema Woche 4          │  ← due
│    seit 08:00 · 1,5 L · Bio-Grow 2 ml/L    │
│                                            │
│ ▮  CO₂-Flasche fast leer — 380 g Rest      │  ← human note
│    Christian · seit 6 Tagen                │
│                                            │
│ ○  Kamera: seit 2 Std 10 kein Bild         │  ← camera health
│                                            │
├────────────────────────────────────────────┤
│  Zustand                        vor 40 s   │
│  24,1 °C    58 %    1,21 kPa    Licht 80 % │
│  Ziel 25    Ziel 50      —      an bis 22:00│
├────────────────────────────────────────────┤
│  Heute erledigt                            │
│  ✓ Gegossen 1,5 L · A1–A4 · Timo · 09:12   │
│  ✓ Temperatur wieder im Ziel · 06:40       │
├────────────────────────────────────────────┤
│  Verlauf ›     Tagebuch ›   Einstellungen ›│
├────────────────────────────────────────────┤
│              [   + Zettel   ]              │
└────────────────────────────────────────────┘
```

Three zones, always in this order, never reordered: **offene Zettel → Zustand → heute erledigt**. The board
grows and shrinks; the two strips below it are fixed furniture. On a tablet/desktop (`ion-split-pane` already
gives us the width) the board occupies the left column and the Zustand strip becomes a right-hand column with
the last camera frame above it — the big screen shows the same thing, not more things.

**Slip glyphs** (one 10 px dot, no icon font):
`▮` filled square = a human said this (block or note — only a human closes it) ·
`●` filled circle = the machine says this (it will close itself) ·
`○` hollow circle = something is due (a care event or a confirmation closes it).
Severity is colour: `--tc-text-danger` / `--tc-text-warning` / `--ion-color-medium`. Colour is never the only
channel — the sentence always carries the fact.

### 3.2 Ranking — fixed, published, never adaptive

Sort key, evaluated top to bottom. It is printed in the board's overflow menu as
*"Sortierung: nach Dringlichkeit · immer gleich"*.

1. `severity === 2` machine slips (device offline, over-temperature, smoke-adjacent) — a red fact pre-empts a human's note.
2. `kind === 'block'` — a human explicitly said do not do this. Acting against one is the most expensive mistake in a shared tent.
3. `kind === 'machine'`, by severity desc, then `openedAt` asc.
4. `kind === 'due'`, by `dueAt` asc.
5. `kind === 'note'`, by `openedAt` asc.

**No behavioural adaptation. No personalisation. No "recently used floats up."** The board a stoned user sees
at 02:00 is in the same order as at 14:00, and it is in the same order as their club-mate's. The brief allows
adaptive ordering with a defence; C25 declines it, because an impaired user's only reliable skill is muscle
memory for position, and rule 1 already produces the only reordering that matters.

Rule 1 is an exception to rule 2 and I am not going to pretend it is elegant — see §13.9.

### 3.3 Real German copy — the sentence library

Machine slips are `message-*` keys resolved by the existing `LogTranslateService`. Every sentence is
**fact, number, target, duration** in that order.

```
message-cond-rh-high-text      "Luftfeuchte {{value}} % — über Ziel ({{target}} %)"
message-cond-temp-high-text    "Temperatur {{value}} °C — über Ziel ({{target}} °C)"
message-cond-temp-low-text     "Temperatur {{value}} °C — unter Ziel ({{target}} °C)"
message-cond-offline-text      "Gerät offline — zuletzt gesehen {{value}}"
message-cond-stale-text        "Keine neuen Messwerte seit {{value}}"
message-cond-socket-lost-text  "Steckdose „{{value}}“ antwortet nicht"
message-cond-cam-silent-text   "Kamera: seit {{value}} kein Bild"
message-cond-cam-dark-text     "Licht an, Bild dunkel — Lampe oder Kamera?"
message-cond-cam-moved-text    "Kamera wurde bewegt — der Zeitraffer springt hier"
message-cond-cam-dirty-text    "Kamerabild unscharf seit {{value}} — Linse beschlagen?"
message-cond-co2-low-text      "CO₂ {{value}} ppm — unter Ziel ({{target}} ppm)"
message-cond-feed-due-text     "Gießen fällig — Schema Woche {{value}}"
message-cond-maintenance-text  "Wartungsmodus aktiv — endet {{value}}"
```

**Honest cost:** `LogTranslateService.translate()` today interpolates exactly one `{{value}}` parsed from the
part after `:` in the key. Two-parameter sentences (`{{value}}` + `{{target}}`) need a ~15-line change:
accept `DeviceLog.data.params` (a `Record<string, string|number>`, already `Schema.Types.Mixed`, no migration)
and pass it into `translate.instant`. Legacy single-`:` keys keep working unchanged. One function, both
languages, no server change.

Human slips carry free text, capped at 120 characters and rendered on at most two lines with an ellipsis. The
placeholder in the compose sheet: *"Was ist gerade wahr? z. B. „CO₂-Flasche fast leer“"*.

Empty board:

```
   Nichts offen. Alles ruhig.
   Zuletzt geschlossen: Temperatur wieder im Ziel, vor 3 Std.
```

### 3.4 Stale, offline, absent

**Stale (10–30 min).** The `⟳` reads `vor 14 Min` in `--tc-text-warning` and every Zustand number gains a
superscript age: `24,1 °C ⁽¹⁴ᵐ⁾`. **No slip opens** — a 14-minute gap on tent WiFi is normal, and opening a
slip for it is exactly the nagging failure mode §13.1 describes. Past 30 min a slip does open:
`● Keine neuen Messwerte seit 34 Min`, severity 1, auto-closing on the next sample.

**Offline (>10 min past `lastseen`, the existing rule).** Severity-2 slip pinned first:
```
●  Gerät offline — zuletzt gesehen gestern 23:41
   seit 14 Std 21 · Werte unten sind von damals
```
The whole Zustand strip renders at 55 % opacity with the heading `Zustand — nicht aktuell` and each value
suffixed `(gestern 23:41)`. **The numbers are not hidden.** Hiding stale numbers is the second-worst thing
after showing them as if they were live; the age is the honesty, not the absence.

**Absent by capability.** No CO₂ upgrade → no CO₂ column, no CO₂ slip type, no "nicht verfügbar" ghost. No
paired dehumidifier → no `Entfeuchter läuft` sub-line and no actionable humidity slip; a monitor-only device
gets `message-cond-rh-high-monitor-text` instead: *"Luftfeuchte 71 % — über deinem Ziel (50 %). Dieses Gerät
misst nur."* This is the biggest correctness fix over today's `deviceControlCapability()`, which buckets three
ways and **fails open to `'full'`** on old firmware. C25 reads `hardwareInfo.sockets` per role and registers
slip types per role; a missing `sockets` key registers **no** actuator-dependent slip types (fails closed).

**Absent by data.** No `Plant` rows → no plant chips anywhere, no `/pflege` route in the footer, and care
slips read `Gießen fällig` with no scope line. No `Regime` selected → the due-feed slip type is not registered
at all; feeding is captured ad hoc.

## 4. NO-MODES MECHANISM

### 4.1 The mechanism, stated

**Der Zettel ist die Zeile und die Seite.** One condition is one line. Tapping the line unfolds it *in place*
into its full evidence — same slip, same position, same list, nothing pushed off screen except by the
expansion itself. Tapping again folds it. **Nothing is remembered.** There is no setting, no preference, no
`localStorage['expert']`, no per-user state of any kind. Every user opens the same board in the same shape
every single time.

```
│ ●  Luftfeuchte 71 % — über Ziel (50 %)      │
│    seit 3 Std 20 · Entfeuchter läuft        │
│  ┌───────────────────────────────────────┐  │
│  │ 71,4 %   Ziel 50 %   Alarmgrenze 65 % │  │
│  │ ▁▂▃▅▆▇▇▇▆   letzte 6 Std              │  │
│  │ [ Kamerabild 14:00 ]  [ jetzt ]       │  │
│  │ Entfeuchter: an seit 3 Std 05          │  │
│  │ Geöffnet 10:42 · automatisch           │  │
│  │ Schließt sich bei 30 Min unter 55 %    │  │
│  │                                        │  │
│  │ [ Übernehmen ] [ Stummschalten 8 Std ] │  │
│  │ [ Verlauf öffnen ]   [ Wert kopieren ] │  │
│  └───────────────────────────────────────┘  │
```

### 4.2 Why this is not a mode wearing a hat

A mode hides a **feature class** behind a persistent choice. This hides **nothing**, persists **nothing**, and
classifies **nobody**.

- **Everything is present on the collapsed line.** Number (`71 %`), target (`50 %`), duration (`3 Std 20`)
  and machine state (`Entfeuchter läuft`) are in the two lines you get for free.
- **Expansion adds evidence for the same one fact** — full precision, the series, the frame, the auto-close
  rule, the copy button. It never adds a *different feature*. No control, page or capability lives only
  inside an expansion. An "Advanced" accordion adds features; this adds proof.
- **Per-slip and non-sticky.** Expanding the humidity slip does not expand the CO₂ slip, does not expand it
  tomorrow, and does not tell the app anything about you.
- **Both users take the same first action** — read line 1. Paths diverge on the *second* tap, not on a
  decision made at onboarding or in settings.

### 4.3 The three other levers, and where each is used

- **Reveal by capability.** Slip types are registered per socket role (§3.4). A heater-only tent never sees a
  dehumidifier slip. This replaces the three-bucket `deviceControlCapability()` with per-role truth that
  already exists in `hardwareInfo.sockets`.
- **Reveal by data.** Plants, `/pflege`, the actor chip row, the regime prefill, the double-feed guard, the
  Zettel rail — every one of them renders only when the corresponding rows exist. A solo hobbyist with one
  tent and no plants logged sees a board, a Zustand strip and a `+ Zettel` button. That is the whole product
  for them, and it was not a choice they made.
- **Ranked density.** The board's length is set by reality, not by preference. Monitor-only, all fine: two
  lines. Club tent, week 6 of flower, three people: nine lines. Nobody configured that.

### 4.4 Progressive precision inside the sentence

The number is in the sentence. `Luftfeuchte 71 % — über Ziel (50 %)` is simultaneously a verdict ("too
humid") and a datum ("71 vs 50"). The techie's extra precision (`71,4 %`) is one tap; the raw Influx series
is two (`Verlauf öffnen`). Nobody is denied the number and nobody is forced to read a chart. `Wert kopieren`
puts `{"measure":"humidity","value":71.4,"at":"2026-08-25T14:02:11Z","target":50}` on the clipboard, which is
the techie's whole ask expressed as one button on the same line the stoner ignores.

## 5. The chart — `/device/:id/verlauf`

ECharts 6, tree-shaken, hand-rolled ~50-line directive (owner decision). Highcharts, `chart.js`, `ng2-charts`
and `chartjs-adapter-luxon` all deleted.

### 5.1 Panels — small multiples, one linked crosshair

`grid[]` + `axisPointer.link` + `echarts.connect()`. Fixed panel order, panels present only when the device
reports the measure:

```
Klima      24 °C ────────  temp (solid) + setpoint (dashed, stepped) + band
           ~~~~~~~~~~~~~~  humidity, second axis (physically coupled, allowed)
VPD        1,2 kPa ──────  actual + the stage's vpdRange as markArea
Ausgänge   ▬▬▬  ▬  ▬▬▬▬▬  state timeline: light / heater / dehum / co2
CO₂        (only with the SCD4x upgrade)
```

Max **two units per panel, and only when physically coupled** (air temp + leaf temp; temp + RH). The current
15-independent-hidden-axes stack is deleted outright.

### 5.2 Goal vs actual

- **Setpoint** = a dashed stepped line built from `device.configuration`: `day.temperature` /
  `night.temperature`, stepping at `daynight.day` / `daynight.night` (seconds-of-day, UTC — converted in an
  explicit device timezone so a 12/12 flip near DST does not drift an hour).
- **Band**, one at a time and labelled in the panel header: the user's own `Alarm.upperThreshold` /
  `lowerThreshold` if set (`Grenze`), else setpoint ± tolerance (`Ziel ±1,5 °C`), else the stage `vpdRange`
  (`Empfehlung`). Rendered as `markArea` at 12 % opacity with a 1 px edge — never a 10 %-opacity fill to the
  axis, which encodes nothing.
- **Deviation fill** between actual and setpoint, signed: warm above, cool below.
- **Envelope**: `{mean,min,max}` in one response instead of three round trips; plotted with
  `sampling:'minmax'`. A single mean line is a lie about a bang-bang controller.
- **Day/night** from measured `out_light > 0`, falling back to the `daynight` schedule and **saying which**
  in the legend (`Tag/Nacht: gemessen` vs `laut Plan`). A failed contactor then shows as a *missing* band.
- **Zeit im Ziel** header above the panels: one stacked bar, `Tag` / `Nacht` split, `im Ziel 78 % · darüber
  19 % · darunter 3 %`, longest excursion **as a duration** (`längste Abweichung 2 Std 40`), and the coverage
  figure. Below 80 % coverage the bar greys out and reads `zu wenige Messwerte (62 %)`. Computed
  **server-side on raw Influx samples** — `aggregateWindow(fn:mean)` destroys exactly the excursions the
  metric counts, and the error is invisible by eye.

### 5.3 The Zettel rail — C25's chart move

Under the x-axis, 24 px, two rows maximum. **A condition is drawn as a horizontal bar spanning `openedAt` →
`closedAt`, not as a point.** That is the whole difference from every annotation rail in the market: an
annotation is an instant, a condition has *duration*, and duration is what you want to correlate against a
sagging humidity line.

```
 Klima  ┤ ╌╌╌╌╌╌ Ziel ╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌
        │      ╭─╮        ╭──────╮
        │ ─────╯ ╰────────╯      ╰──────────────
 Ausg.  │ ▬▬▬▬▬▬▬▬▬▬▬▬       ▬▬▬▬▬▬▬▬▬▬▬▬▬▬
 Zettel │      ▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬            ← Luftfeuchte über Ziel (offen 3 Std 20)
        │  ▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬ ← A3 nicht gießen (Anna)
        └──┬────┬────┬────┬────┬────┬────┬────
          Mo   Di   Mi   Do   Fr   Sa   So
```

Row 1 = human slips (blocks and notes). Row 2 = machine and due slips. A still-open slip's bar runs to the
right edge with a soft fade — it has no end yet, and the chart says so. Care events (§7) and lifecycle
changes are the only *point* marks: care as a small drop glyph on row 2, stage changes as a full-height dashed
line. Clustering at 10 px bins with a count badge when the window is long.

Tapping a bar expands **that slip, in its full board form, above the chart** — the same component, the same
layout, the same buttons. There is no second slip renderer in the product.

`?zettel=<condition_id>` joins `measures`, `date`, `dateEnd`, `vpdMode`, … in the existing query-param view
model. Additive; old presets and share links keep working through `applyViewParams`.

### 5.4 Mobile interaction

One finger = page scroll; two fingers = pan/zoom (`dataZoom:{type:'inside'}`); tap/long-press = crosshair.
The floating tooltip is replaced by a **pinned scrubbing header** above the panels — one row per panel plus
the camera frame at the cursor (§8.5). Axis labels are never hidden: below 320 px they drop to 3 ticks and
the unit moves into the panel title. Range presets (`24 Std · 7 Tage · 30 Tage · Zyklus`) at ≥44 px.

## 6. The diary and multi-plant

### 6.1 The diary is the closed board

`/device/:id/tagebuch` is a reverse-chronological list of **closed conditions and care events**. That is the
whole diary. The user writes almost none of it.

```
┌────────────────────────────────────────────┐
│ Tagebuch — Zelt 1                          │
│ [ Alles ] [ Pflege ] [ Pflanzen ] [ Gerät ]│
├────────────────────────────────────────────┤
│  Heute                                     │
│  ✓ Gegossen 1,5 L · A1–A4                  │
│    Bio-Grow 2 ml/L · Timo · 09:12          │
│  ✓ Temperatur wieder im Ziel               │
│    war 4 Std 10 offen · von selbst · 06:40 │
├────────────────────────────────────────────┤
│  Gestern                                   │
│  ✓ Schimmelgefahr an A2                    │
│    war 3 Tage offen · Anna: „entlaubt,      │
│    Lüfter höher“ · 18:40      [Foto]       │
│  ✓ Phase: Blüte · Wedding Cake · Tag 1     │
└────────────────────────────────────────────┘
```

**`war 3 Tage offen` is the sentence that makes this diary different.** Every other grow diary records
instants. A condition's *duration* — and who ended it — is a fact only a board can produce, and it is the
single most useful thing to read three months later.

Reuses `LogEntryViewerModule` wholesale: `app-log-entry-item` (severity colours, `data` list with units, image
thumbnails → `app-image-viewer-modal`, category chips, edit/delete), `app-log-category-selector`,
`collectLogCategories` / `matchesLogCategory` / `filterLogsByCategory`.

**Two legacy bugs must die with this screen**, or the diary reads as data loss the moment it is the
centrepiece: `deleted` is a visibility flag, so "Clear logs" (`DELETE /device/logs/:device_id`) removes
nothing from the diary; and the server's own stage-transition rows carry `categories:
['diary-plant-lifecycle']` without the `'diary'` prefix, so they are invisible and uneditable while the
identical manual row is both. One-line fixes plus a boot-time backfill.

### 6.2 New collections — all cloud-side Mongo, all fields optional, no migration tooling

```ts
Condition {
  condition_id: string;  device_id: string;
  kind: 'note' | 'block' | 'machine' | 'due';
  source: 'human' | 'alarm' | 'schedule' | 'camera' | 'freshness' | 'device';
  text_key?: string;                    // 'message-cond-rh-high' for machine slips
  text?: string;                        // free text, human slips, <=120 chars
  params?: Record<string, string|number>;   // {value: 71.4, target: 50}
  plant_ids?: string[];                 // [] or absent = whole tent
  severity: 0 | 1 | 2;
  openedAt: number;      openedBy?: string;   // actor_id
  ownedBy?: string;      ownedAt?: number;
  dueAt?: number;                        // kind 'due'
  mutedUntil?: number;
  closedAt?: number;     closedBy?: string;   // actor_id, or absent = machine
  closeNote?: string;    closeLog_id?: string;
  evidence?: { imageId?: string; measure?: string; value?: number; threshold?: number; at?: number };
  autoClose?: { measure: string; comparator: 'lt'|'gt'; value: number; forSeconds: number };
  recurrence?: { everyHours: number; regimeStep?: number };
  dedupeKey?: string;                    // 'rh-high' — one open slip per key per device
  capture_uuid?: string;                 // unique index; offline-replay safe
}
Actor  { actor_id, device_id, name, colorIndex, createdAt, archivedAt? }
Plant  { plant_id, device_id, cycle_id, label, strain?, startedAt, stage,
         potLiters?, mediumLabel?, regime_id?, archivedAt? }
Cycle  { cycle_id, device_id, name?, startedAt, flipAt?, endedAt? }
```

Indexes: `{device_id, closedAt, openedAt}`, `{device_id, dedupeKey, closedAt}`,
`{capture_uuid}` unique sparse.

**Closing a slip writes a `DeviceLog`** with `categories: ['diary','diary-condition']`, `title` = the slip's
key or text, and `data: { openSeconds, closedBy, condition_id, params }`. So the diary is served by the
existing log endpoint and the existing viewer, and the new collections are only ever the *live* state.

**Server-side pagination is not optional here.** `getDeviceLogs` has no `.limit()`, no cursor and no count
today, and the entries report fetches the device's entire history on every open. A board that multiplies rows
makes that a launch bug. Budget it (§12).

### 6.3 Multi-plant, and how ignoring it costs nothing

There is **no "add your plants" step anywhere**, no onboarding question, no empty-state nag.

`Plant` rows come into existence as a side effect of scoping. Every capture and compose sheet has one line:

```
   Gilt für:   ( ganzes Zelt )   + Pflanze
```

`ganzes Zelt` is preselected and is a valid permanent answer. Tapping `+ Pflanze` asks for one thing —
a label, prefilled `A1` then `A2` — and creates the row. Strain, pot size, medium and regime are all optional
fields on a plant's own page, reached only by tapping the chip.

A user who never taps `+ Pflanze` never sees a chip row (`plants.length > 0` gates it), never sees `/pflege`
in the footer, gets tent-scoped slips and care events with `plant_ids: []`, and loses **nothing** — the
cumulative ledger still answers "how much has this tent had".

`Cycle` is created implicitly by the first stage change or the first care event, named from `lifecycleName`
if present. This replaces `convertEventsToGrowCycles()` — runtime string-comparison that forks a grow's
history when you rename a plant and fabricates a new plant on a re-veg — with an **idempotent boot-time
backfill** writing `Cycle`/`Plant` rows from existing lifecycle logs. Cycle identity stops being a start
timestamp, so editing an entry's time no longer breaks share links in circulation.

## 7. Watering & fertilising

### 7.1 The regime — medium + feed line, one selection, prefill only

Modelled the way the owner said growers say it: a `Regime` is a **substrate + feed line pair**, labelled out
loud.

```ts
Regime {
  regime_id, name;                       // "Biobizz All-Mix + Bio-Grow / Bio-Bloom"
  mediumLabel;                           // "All-Mix"
  prefertilised: 'none'|'light'|'heavy'; // All-Mix = heavy
  feedStartWeek: number;                 // All-Mix = 4, Light-Mix = 2, BioTabs = 99
  style: 'liquid' | 'slow_release';      // BioTabs => slow_release
  reTabEveryWeeks?: number;              // BioTabs = 6
  defaultIntervalHours: number;          // 72
  steps: [{ fromWeek, toWeek, phase:'veg'|'flower',
            products: [{ name, mlPerLiter?, gramsPerLiter?, note? }],
            ecBasis: 'absolute'|'delta_over_source', ecRange?: [number, number],
            phRange?: [number, number] }];
  source_url; retrieved_at; chart_version;
}
```

Numbers live in a Mongo content collection, never in the bundle, so any brand is removed in one DB update.
Brand names are plain-text labels — no logos, no brand colours, never inside a Terp Control feature name.
`retrieved_at` renders as `Werte geprüft am 14.06.2026`: a trust feature, not an apology.
`ecBasis: 'delta_over_source'` exists because CANNA publishes **EC+**, not EC — alarming against the raw
chart number is actively wrong when the tap water is EC 0.4.

Selection: one row in `Einstellungen` → `Substrat & Dünger`, a list of names, one tap. **`All-Mix` selected in
week 1 does not produce a due-feed slip until week 4** — a regime that cannot express "All-Mix, don't feed
yet" is not modelling the domain. Until then it produces `○ Nur gießen — All-Mix düngt noch selbst`.

### 7.3 The double-feed guard

At **save**, not at open. The server checks for a `CareEvent` with `kind` in `feed|water_feed` overlapping any
of the same `plant_ids` (or tent-scoped) within `regime.defaultIntervalHours / 2`, default 12 h, by a
**different `actor_id`**. If found, `Speichern` is replaced in place:

```
┌──────────────────────────────────────────┐
│  ⚠  Anna hat A1–A3 vor 1 Std 30          │
│     gefüttert. Bio-Grow 2 ml/L, 1,5 L.   │
│                                          │
│  [ Trotzdem eintragen ]   [ Abbrechen ]  │
└──────────────────────────────────────────┘
```

**One deliberate extra tap.** Soft, never hard — the second feed is sometimes correct and the product does
not know better. `Trotzdem eintragen` writes `note: 'trotz Warnung'` onto the event and opens a note slip,
`▮ Doppelte Gabe an A1–A3 — bitte prüfen · Timo · seit 4 Min`, because somebody has to look at it.
Same-actor repeats get a lighter line (`Du hast A1–A3 vor 20 Min gegossen.`) with the same two buttons — a
stoned user re-logging by accident is at least as likely as two people colliding.

### 7.4 Blocks at the point of action

A `kind:'block'` slip scoped to a plant is repeated **inside** the capture sheet the moment that plant is
selected. This is the reason blocks rank second on the board: the board is where you *see* them; the sheet is
where they *stop* you.

### 7.5 Offline capture

Minimal service worker (`@angular/service-worker` — a new dependency and a build change, flag it) caching the
app shell plus an IndexedDB **outbox** carrying exactly two operations: `CareEvent.create` and
`Condition.close`. Nothing else queues.

**`capture_uuid` is generated with `crypto.randomUUID()` when the sheet OPENS**, not when the POST fires. The
server has a unique sparse index on it and returns the existing row on collision, so a timeout retry, a
double-tap, a background-sync replay and an app relaunch are all no-ops. An offline retry queue that can
double-log is, in a shared record, indistinguishable from a double feed.

The board shows queued items inline with a clock glyph and the copy `wird gesendet, sobald du Empfang hast`.

## 8. Camera, timelapse and image correlation

### 8.1 What ships in v1

Two artefacts, both real, both leave the product:

1. **Der Lauf-Film** — one MP4 per cycle, from `Cycle.startedAt` to now (or `endedAt`), lights-on frames only,
   culled and normalised, with a burned-in bottom strip and **Zettel-Marken**.
2. **Der Tagesfilm** — today's frames, same pipeline, rebuilt hourly. This is the existing `1d` timelapse,
   fixed.

The existing `1w` / `1m` rolling durations stay, because charts and share links reference them.

**Zettel-Marken are C25's contribution to timelapse content.** The bottom strip carries, per frame,
`25.08.2026 · Tag 47 · 24,1 °C · 58 % · VPD 1,21`; when a condition opened or closed inside a frame's window
the strip's right half flashes its sentence for 1.2 s and a 4 px tick appears on a progress rail. The video
itself carries the correlation: you *watch* the humidity slip open and see the leaves at that second.

```
 ┌────────────────────────────────────────┐
 │                                        │
 │            [ tent frame ]              │
 │                                        │
 ├────────────────────────────────────────┤
 │ 25.08.2026 · Tag 47   ▮ Luftfeuchte    │
 │ 24,1 °C · 58 % · 1,21   über Ziel      │
 │ ▬▬▬▬▬▬▬▬│▬▬▬▬▬│▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬ │
 └────────────────────────────────────────┘
```

### 8.2 Culling and normalisation — the specifics

Today `compressRtspStreamRange()` takes every stored JPEG at a fixed minimum interval and hands the directory
to ffmpeg. No culling, no normalisation. Six concrete changes, in cost order:

**(a) Store three cheap statistics at capture time.** `sharp` is already a dependency. On each successful
`readRtspStreamImage`, before the Mongo write, add optional fields to `Image`:
`luma` (mean of all channels, 0–255), `rb` (mean R ÷ mean B, the colour-cast proxy), `sharp_` (variance of a
3×3 Laplacian on a 128 px greyscale thumb), and `phash` (64-bit DCT hash as a hex string). Read-time
normaliser: absent → computed lazily on first film build. ~12 ms per frame at capture, twice a minute. No
migration.

**(b) Lights-on selection — the single biggest quality win.** Query `out_light` from Influx over the film's
range at 5 min resolution and keep only frames where the lamp was on. A tent timelapse is mostly black frames
and this removes them by *knowing the schedule*, not by thresholding. Falls back to `luma > 40` when the
device has no light output. One Influx query per film.

**(c) The magenta problem is a day/night problem.** Once (b) is applied, a full-spectrum LED at 80 % is the
only illuminant in the film, and the R/B cast that survives is drift, not a mode change. Frames whose `rb`
deviates > 35 % from the 24-frame rolling median (door open, room light) are dropped.

**(d) Transient rejection — hands, doors, people.** For each frame, compute the pHash Hamming distance to its
previous and next kept neighbours. Drop the frame when `d(prev,frame) > 18` **and** `d(frame,next) > 18`
**and** `d(prev,next) < 8` — i.e. the frame disagrees with both neighbours while they agree with each other.
That is a transient: a hand, an open door, a person. It is three integer comparisons and it catches the
failure the camera critic named without any model.

**(e) Bucket-median selection instead of nearest-in-time.** For each output slot (2 min for the day film,
20 min for a 12-week run film), take the candidate frame whose `luma` is the **median** of the bucket rather
than the first. This rejects both a dark outlier and a flash outlier for free, and it is one sort per bucket.

**(f) Exposure and white-balance normalisation at write time, not in ffmpeg.** Frames are already written
individually into a temp dir (`compressRtspStreamImages`); insert one `sharp` pass per frame —
`.linear(gain, offset)` pulling `luma` onto a 48-frame rolling median, plus a per-channel multiplier pulling
`rb` onto its rolling median, gains clamped to ±25 % so a genuinely dark evening stays dark. ~15 ms/frame;
a 12-week run film at 20 min spacing is ≈1 200 frames ≈ 18 s of sharp plus the encode — acceptable **because
run films are built on demand and nightly, not hourly.**

**Explicitly NOT in v1: stabilisation.** `vidstabdetect`/`vidstabtransform` need libvidstab compiled into the
image, and the real-world failure is not jitter but a **step** — the camera got nudged on day 12 and every
frame after is 5° off. Deshaking cannot fix a step. What C25 does instead is detect it: a sustained pHash
distance jump (> 22 for more than 6 consecutive frames, then stable at the new value) opens
`● Kamera wurde bewegt — der Zeitraffer springt hier`, with the before/after pair as evidence and one button
`[ Zeitraffer ab hier neu beginnen ]` which sets `Cycle.filmRestartAt`. **The product's answer to an
unsolvable content problem is to make it a condition somebody can own.** That is the concept, applied to a
camera.

### 8.3 How a video leaves the product

**The current encoder ships HEVC and that is a launch bug.** `convertRtspStreamImagesToVideo()` uses
`-vcodec libx265 -crf 30`. Firefox does not decode HEVC in `<video>` at all, and Chrome only with platform
hardware support; a share-link visitor on desktop Firefox sees a black rectangle today. Fix, one line:

```
-c:v libx264 -profile:v high -pix_fmt yuv420p -crf 23
-r 30 -vf "scale=1280:-2,drawtext=…" -movflags +faststart
```

**The route.** New, additive, alongside the existing `GET /image/:device_id`:

```
GET /image/:device_id/film
      ?cycle=<cycle_id>            (or scope=day|week|month)
      &quality=720|1080
      &marks=1                     Zettel-Marken burned in
      &overlay=1                   the data strip burned in
      &share=<share_token>         honours ShareLink.webcam exactly as today
→ 200  Content-Type: video/mp4
       Content-Disposition: attachment;
         filename="terpcontrol-zelt-1-wedding-cake-tag-1-84.mp4"
       Content-Length: …           (real, not chunked — phones need it)
       Accept-Ranges: bytes
```

Filename shape: `terpcontrol-<device-slug>-<cycle-slug>-tag-<from>-<to>.mp4`, ASCII-folded, lowercase,
non-alphanumerics to `-`. A file called `terpcontrol-zelt-1-wedding-cake-tag-1-84.mp4` in a phone's Downloads
folder is self-describing three months later, which is the point.

**Storage: films are NOT stored in Mongo.** A 60 s 720p CRF-23 MP4 is 8–15 MB against a 16 MB BSON document
cap — the current design is one long grow from a hard failure. Films render to a disk cache on a docker
volume, keyed `sha1(device_id|cycle_id|scope|quality|marks|lastFrameTimestamp)`, LRU-evicted at a configured
ceiling (default 20 GB), rebuilt on miss; a `Film` document holds `{film_id, device_id, cycle_id, scope,
path, bytes, frames, from, to, builtAt}`. **Real infrastructure work with no precedent in the repo —
everything binary lives in Mongo today** — and the largest single server task in §12.

**The button.** In the film view and on the cycle's diary header:

```
[ ⤓ Film sichern ]      [ Link teilen ]
```

`Film sichern` fetches the URL as a `Blob` and calls `navigator.share({files:[new File([blob], name,
{type:'video/mp4'})]})` where `navigator.canShare({files})` is true (Android Chrome, iOS Safari 15+), landing
the file in the share sheet — **camera roll, WhatsApp, Telegram, wherever they want**. Fallback: `<a download>`
on the same-origin URL (Downloads on Android, the Files sheet on iOS); desktop, a plain download. Progress
line while building: `Film wird erstellt … 1 240 Bilder`. A 12-week run takes 40–90 s, then it is cached.

`Link teilen` reuses `ShareLinkModule` and produces a real, login-free URL. But the *file* is the product, and
the file is what leaves.

### 8.4 The camera alarm

Four camera slip types, registered only when `hardwareInfo.webcam_did` is set (reveal by capability):

| Slip | Rule | Severity |
| --- | --- | --- |
| `message-cond-cam-silent` | no successful capture for 2 h (4× the 30 min back-off ceiling) | 1 → 2 after 24 h |
| `message-cond-cam-dark` | `out_light > 0` and median `luma < 40` for 30 min | 1 |
| `message-cond-cam-dirty` | median `sharp_` below 60 % of its 7-day median for 6 h | 0 |
| `message-cond-cam-moved` | sustained pHash step (§8.2) | 1 |

`cam-silent` at severity 2 fires the existing e-mail/webhook alarm path. **A camera that stopped three days
into flower now tells you**, which the critic said no concept did — and it costs nothing, because the board
already has a place to say it.

### 8.5 Image correlation

Three bindings, all off the same `Image.timestamp` index:

1. **Chart → picture.** The pinned scrubbing header carries the frame nearest the cursor, delivered as a
   **sprite + JSON index per window** (`GET /image/:device_id/strip?from&to&cols=10`, 256×160 tiles, ≤100 per
   sheet), not N requests — today's 500 ms-hover-then-fetch is unusable on touch and murder on a phone.
2. **Picture → numbers.** Every frame in the product (slip evidence, diary thumbnail, strip tile) opens
   `app-image-viewer-modal` with a caption rendered from Influx at that timestamp:
   `25.08. 14:00 · Tag 47 · 24,1 °C · 58 % · VPD 1,21 · Licht 80 %`, plus `Verlauf hier öffnen` and
   `Als Beweis an Zettel hängen`.
3. **Slip → frame.** Every machine slip stores `evidence.imageId` = the frame nearest `openedAt`, and the
   expanded slip shows it next to `[ jetzt ]`. **This is the correlation with a purpose**: the humidity slip
   from Tuesday shows Tuesday's leaves. Scrubbing is a toy; a condition's before-picture is an argument.

The film strip on the chart is an **axis**, not a carousel: thumbnails positioned by timestamp on the same
x-scale, so a gap in capture reads honestly as a gap.

## 9. Clubs

### 9.1 Attribution without an auth rewrite

`Actor` is a device-scoped name the owner types once. No account, no password, no e-mail, no
`auth.middleware.ts` surgery.

```
│  Am Zelt:  ( Christian )  Anna   Timo   +  │
```

The chip row renders only when `actors.length >= 2` (reveal by data — a solo grower never sees it). The
selection is sticky in `localStorage['tc-actor-<device_id>']` and stamps `Condition.openedBy` / `.closedBy` /
`.ownedBy` and `CareEvent.actor_id` at capture. Roughly two days of work for attribution in v1.

**The copy must never over-claim, and this is a design decision, not a caveat.** Under the chip row, on
first use and in `Einstellungen`:

> *Namen am Zelt sind eine Notiz, kein Login. Jeder mit Zugang zum Gerät kann jeden Namen wählen.*

A club that reads an actor chip as § 17-Abs.-2 evidence is misreading it, and a product that lets them is
doing them harm. Real memberships (`Membership {device_id, user_id, role}` + rewriting
`auth.middleware.ts:172` and `:207` + loosening ~10 owner-scoped queries) are a later release; `actor_id`
upgrades into it cleanly — an `Actor` gains an optional `user_id` and stops being self-selectable.

### 9.2 The double feed

§7.3. Soft block at the moment of capture, one deliberate extra tap, a note slip left behind when overridden.

### 9.3 Conditions are the club feature

Everything above is table stakes; the board is the reason a club would choose this product. Three people and
one tent do not need a chat — they need to know **what is still true**. `▮ A3 nicht gießen — übergossen`,
`▮ CO₂-Flasche fast leer`, `▮ Steckdose 3 wackelt, nicht anfassen` are exactly the messages that get lost in
a Telegram group and pinned to a door instead. They persist here, they carry a name and an age, and they
appear at the moment of the action they are about (§7.4).

`Übernehmen` sets `ownedBy` — "ich kümmere mich" — and the line becomes `Anna kümmert sich · seit 20 Min`.
That is the whole coordination model. No assignment, no notification storm, no roles.

### 9.4 Privacy posture

- **No real names required.** Actor names are free strings — `A`, `Anna`, `der Neue`. Nothing validates or
  e-mails them. **`Namen löschen`** archives every `Actor` and replaces each stamp with `—`, keeping the
  opaque `actor_id` so per-person aggregates still work anonymously.
- **Export defaults to anonymised.** `/pflege`'s CSV carries `[ Namen: anonym ]` preselected; `pseudonym`
  (`Person 1/2/3`, stable) and `Klarnamen` are the other two.
- **No harvest weight, no plant count, ever prompted.** `Plant.label` is `A1`, not a count you confirm; there
  is no `Harvest.weight` field in v1, and if it lands later it is opt-in and off by default. These are
  precisely the facts separating a lawful hobby from a three-year offence.
- **No location, ever.** No GPS, no IP-geolocation persistence, no timezone-from-IP stored.
- **No compliance claim.** No `KCanG-konform` badge, no per-member dispensing record, no consumption log. The
  club's § 26 obligations belong to their club software (Cannanas, 420cloud); the honest integration is to
  feed those systems a `measurements` payload, not to replace them.
- **Retention is a visible setting**, not a silent forever: telemetry `12 / 24 / unbegrenzt Monate`, stills
  already 3 years, films LRU-evicted. Today the Influx bucket has no retention and zero downsample tasks —
  raw 5 s samples forever, which is a cost curve and, in a raid, a legible harvest calendar.

## 11. Per-user-type walkthrough

**Type 1 — lazy monitor-only.** Opens the app maybe weekly. Sees `Nichts offen. Alles ruhig.` plus the
Zustand strip with an age on every number, and closes it. That is the correct experience for someone who
wants to be left alone: the board's *emptiness is the report*. When something did go wrong while they were
not looking, it is still there — a closed slip in `Heute erledigt` or in the diary with its duration
(`war 4 Std 10 offen`), which is more than any tile dashboard ever told them. Risk: they came for values and
the values are below the fold (§13.3).

**Type 2 — monitor + camera.** The camera is not a tile here, it is four slip types and a film. Their board
tells them when the camera stopped, when the lens fogged and when somebody knocked it. Their output is
`terpcontrol-zelt-1-wedding-cake-tag-1-84.mp4` in their Downloads folder with the numbers burned into the
bottom strip and a tick on the rail everywhere something happened. Every slip they ever closed carries the
frame from the moment it opened. This is the type C25 serves best.

**Type 3 — controls certain aspects (CO₂ or heating).** Slip types are registered per socket role, so a
heater-only tent gets temperature slips and **never** a dehumidifier slip, a humidity-deviation warning or a
"Entfeuchter läuft non-stop" alarm preset. Today it gets all three because `deviceControlCapability()`
collapses per-role truth into three buckets and fails open. The board is the first surface in the product
that only mentions kit they own.

**Type 4 — full tent.** The most crowded board, and the one that benefits most from a fixed ranking rule:
with six sockets, four alarms, two people and a regime, "what is still open" is genuinely hard and this is
the only screen that answers it. Honest limit: the firmware has **five socket roles**, no humidifier, no
exhaust fan, no chiller, and `dehumidifier` doubles as the cooler. C25 does not fix that — it stops lying
about it, by never showing a slip for a role that is not paired.

**Type 5 — closed-loop DIY.** Gets the least here and should be told so. What they do get: `Wert kopieren`
emitting JSON on every slip, a real `Content-Length`-bearing film endpoint, and — the genuinely useful bit —
**`Condition` is a clean event surface**. `POST /device/:id/condition` (open) and `POST /condition/:id/close`
with `capture_uuid` idempotency means a Home Assistant automation can open a slip on this board from a soil
probe Terp Control cannot read, and it appears alongside everything else with its own name on it. That is the
first write API in the product and it is three endpoints. `VALID_SENSORS` still does not admit their EC probe,
and the Flux injection in `data.service.ts:80-89` must be fixed before any measure vocabulary widens.

**Type 6 — clubs.** §9. Actor chips, the double-feed guard, blocks that reappear at the point of action,
`Übernehmen`, the per-plant cumulative ledger with a by-person breakdown, and an anonymised CSV. The honest
line is printed under the chip row: names are a note, not a login.

**Type 7 — old devices.** §10. Three fewer buttons, a board with one to three lines, a diary that is not
empty, and a `+ Zettel` that is genuinely new. Nothing they had is removed.

**Capability lenses.** *Stoner:* one glyph, one sentence with the number already in it, one thumb-sized
button, a fixed order that never moves, and 2 taps for the feed they came to log. *Normal:* an app that looks
like a to-do list they already understand and produces a video they can send to a friend. *Techie:* every
number one tap from raw, a JSON copy button, a documented film URL, server-side time-in-range on raw samples,

## 13. Honest weaknesses

**1. A board of open conditions is a nag, and this is the concept's central risk.** If machine slips open
freely, the home screen becomes a to-do list that makes you feel bad about your hobby. Mitigations exist
(auto-close, `dedupeKey`, `Stummschalten 8 Std`, severity-0 slips that never notify) but the tuning is the
whole product and it cannot be tuned before there are users. If the first firmware batch produces flaky
sockets, every board in the field will have three red lines on it in week one and the concept will read as
broken hardware. **Test this before anything else.**

**2. The empty board is an anticlimax at exactly the wrong moment.** A brand-new €289 controller, first
launch, everything fine: `Nichts offen. Alles ruhig.` and two grey lines. AC Infinity shows gauges. The
Zustand strip is the mitigation, and a critic will correctly say the strip is tiles-with-a-to-do-list-on-top
— that C25 kept the thing it claimed to replace, in smaller type, below the fold.

**3. "Where is my chart?"** Types 1 and 2 bought a monitoring product and the board is not about values, it
is about exceptions. One tap is one tap too many for someone who opens the app to look at a number. This is a
real positioning risk, not a layout one, and no amount of copy fixes it.

**4. Nobody closes their notes.** The sticky-note graveyard is unsolved in every product that has ever had
one. A board with fourteen stale slips from March is worse than no board. C25's answer — human slips over
30 days old get `Noch aktuell?` with two taps — is the same answer Jira gives, and it does not work there
either.

**5. The chart's distinguishing feature depends on user behaviour.** A grower who opens no slips gets an
empty Zettel rail, leaving a competent ECharts rewrite with a setpoint band — good, not differentiated. The
rail's value is highest for exactly the users who need the chart least.

**6. Attribution without authorisation is deniable and someone will misread it.** An actor chip is a
self-selected string. The printed disclaimer is honest but disclaimers do not stop a club treasurer from
citing the log in a dispute. The safe version needs real memberships, which is explicitly out of v1.

**7. The capture sheet is the densest screen in the product** and it lands on the impaired user precisely
when they are least able. Two taps get them through the scheduled case, but the moment they need to change
`1,5 L` they are in a form with six numeric fields at 02:00.

**8. The ranking rule now has an exception.** Severity-2 machine slips pre-empt human blocks (§3.2 rule 1),
which is defensible — 34 °C outranks a sticky note — but it means the top of the board *can* change order.
Every exception is how a fixed list becomes an unpredictable one, and I have added the first.

**9. The camera's "make it a condition" answer is partly a dodge.** Telling the user their camera got nudged
is honest and useful, and it is also not the stabilised timelapse they wanted. A competitor who ships real
stabilisation ships a better video, and the fact that stabilisation cannot fix a step change is an argument
they will not have to make.

**10. `Condition` is a new first-class entity in a codebase with no migration tooling, 38 `it()` blocks (24
of them `should create`) and a CI pipeline that never runs `ng test`.** Every field is optional with a
read-time normaliser, which is the house style — but the only safety net under this is `./simulate-device.sh`
and careful review.

**11. The diary's best sentence depends on discipline.** `war 3 Tage offen, geschlossen von Anna` is only
true if Anna closed it when she fixed it, not three days later when she noticed the slip. Durations from a
board are self-reported and the diary presents them as fact.
