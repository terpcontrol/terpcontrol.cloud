# C19 — "Vorher / Nachher"

**Family:** camera · **Centre of gravity:** the comparison pair is the unit of the product.

---

## 1. Thesis

**Terp Control holds two moments at all times, and every screen is the difference between them.**

A grower's real question is never "what is the temperature". It is "is this going better than last
week". Today the app answers that with fifteen translucent areas on hidden axes, which is a question
only a chart-reader can ask. C19 replaces the reading task with a *seeing* task: two photographs side
by side, the numbers that belong to each one printed underneath, and the events that happened in
between listed below. That artefact — the **Paar** — is legible to somebody who cannot read a chart,
carries the full numeric delta for somebody who can, is the natural share (two photos beat any graph
in a Telegram group), and *is already a two-frame timelapse*, which makes the camera the spine of the
product instead of a tile on a dashboard. The pair also solves the diary: a diary entry is what changed
between two moments, and the app can compose almost all of that itself. The user only supplies the
things a sensor cannot see — that he watered, that he defoliated, that A3 looks sick.

The pair is not a view of the data. It is the app's state: two `Moment`s, held in the URL, pinnable
from a chart, from a photo, from a diary row, from a timelapse frame.

## 2. Information architecture

The core primitive, held in query params on every device-scoped route:

```ts
Moment = { at: number /* ms */, label?: string, plant_ids?: string[] }
Pair   = { a: Moment, b: Moment }        // a = Vorher, b = Nachher (default: now)
```

URL: `?a=<ms>&b=<ms>` (+ existing `measures`, `interval`, `share`, `vpdMode`, …).
`span = b - a`. Every window is `[moment - span, moment]`, so the two windows tile back-to-back and
nothing is double-counted. Default pair on first open: `b = now`, `a = now - 7d`.

### Routes

| Path | What it is |
| --- | --- |
| `/list` | Geräte. Unchanged shell. One device → straight through, as today. |
| `/device/:id` | **JETZT** — the pair, full size. This is home. |
| `/device/:id/verlauf` | **VERLAUF** — film strip + small-multiple chart + the two draggable pair handles. |
| `/device/:id/tagebuch` | **TAGEBUCH** — weekly cards, event list, plants, Verbrauch. |
| `/device/:id/zelt` | **ZELT** — goals, kit, people, regime, alarms, plumbing. |
| `/device/:id/moment/:ts` | **Momentkarte** (modal route) — one still + its readings + the two pin buttons. |
| `/device/:id/paar` | **Vergleich** full screen (modal route from the Paarleiste). |
| `/p/:share_id` | Public pair card. No login. |
| `/device/:id/charts` | **alias →** `/verlauf`, query string preserved. Old share links and presets keep working. |
| `/device/:id/diary` | **alias →** `/tagebuch`. |
| `/device/:id/settings` | **alias →** `/zelt`. |
| `/shares` `/account` `/login` `/demo` `/testmode` `/diagnostics` `/classes` | unchanged. |

`applyViewParams` gains a back-compat branch: an incoming `date`/`dateEnd` pair maps to
`b = dateEnd`, `a = dateEnd - (dateEnd - date)`. Nothing in circulation breaks.

### Navigation model

`ion-tabs` with four tabs at the bottom of every device-scoped route: **Jetzt · Verlauf · Tagebuch ·
Zelt**. The existing `ion-menu` stays for account-level items (Geräte, Geteilte Links, Konto,
Dark-Mode, Logout). This is new — there is no tab bar today — and it is the only structural navigation
addition C19 makes.

The **Paarleiste** (56 px, sticky, under the header) appears on Verlauf, Tagebuch and Zelt — never on
Jetzt, where the pair *is* the page:

```
┌────────────────────────────────────────────────┐
│ [thumb] 18.08. ◄─ 7 Tage ─► 25.08. [thumb]  ⌃ │
└────────────────────────────────────────────────┘
```

Tapping it opens `/paar`. Tapping either thumbnail opens that Momentkarte. It collapses to 36 px on
scroll (thumbnails 24 px, dates only).

### Stale, offline, absent — precisely

- **Sample older than 15 min, device online.** Every number carries `· vor 22 Min` in `--tc-text-warning`
  next to the Nachher column header. No number is ever rendered as if it were current.
- **Device offline** (`lastseen` older than 10 min): the Jetzt still gets a 40 % grey scrim and the
  caption becomes `Zuletzt gesehen: vor 3 Std 12 Min`. The verdict sentence switches to
  `pair.verdict.offline`. The delta list still renders — the last known values are real data — with the
  Nachher column header reading `zuletzt · 25.08. 10:48`. The `Gießen`/`Düngen` buttons stay live;
  logging does not need the device.
- **Camera silent, device online.** If the newest `format:'jpeg'` is older than 120 min: the Jetzt
  slot is replaced by an amber-bordered card:
  `Kamera meldet sich seit 14 Std nicht.` + `[ Testbild anfordern ]` (the existing
  `POST /image/test/:device_id`). The Vorher slot still shows its still. This also fires an alarm —
  see §8.6.
- **No camera paired.** Both slots become **Zustandskarten** (§10). The layout, the delta list, the
  events list and the verdict are identical. The `Zeitraffer` CTA is absent — reveal by capability.
- **Less than `span` of history.** `a` clamps to the oldest sample and the span label becomes the real
  distance (`◄─ 2 Tage ─►`) with `pair.span.short` under the verdict.
- **No data at all** (device claimed, never reported): no fake chart, no zeros.
  `Noch kein Bild und keine Messwerte. Sobald dein Zelt Daten schickt, entsteht hier dein erstes Paar.`
  plus the existing setup-wizard link.

## 4. NO-MODES MECHANISM

The mode C19 deletes: **`localStorage['app-settings-expert']` and the Einfach/Experte `ion-segment`
in fridge/controller settings go away in this release**, along with `docs/einfach-modus.md`. Nothing
replaces them. Three mechanisms do the work instead, and none of them has a state that differs between
two people. **Two users opening the same URL see byte-identical pixels.** There is no preference, no
toggle, no persisted density, no onboarding question, no "Erweitert" container.

### M1 — Der Unterschied ist die Sortierung

The delta list is **complete and always the same list**. It is ordered by normalised change:

```
rank(measure) = |Ø_b − Ø_a| / σ_typ(measure)
```

`σ_typ` is a hand-picked constant per measure, not learned, not per-user:
temperature 1.0 °C · humidity 5 % rF · VPD 0.15 kPa · CO₂ 150 ppm · Lichtstunden 0.25 h ·
Ausgangs-Minuten/Tag 30 min · lux 4000 · leaf_temperature 1.0 °C.

Rows with `rank < 0.5` collapse into one line at the bottom — `Unverändert: Licht (12,0 h),
Entfeuchter` — which is still present, still tappable, still expands in place. Measures with no sensor
render as `CO₂ — nicht gemessen (kein Sensor)` and never as `0` or `—`.

Why this is not a mode: the ordering is a pure function of the data. It is deterministic, it is
explainable in one sentence ("was sich am meisten geändert hat, steht oben"), and it is *stable* —
reopening the same pair a minute later gives the same order. It is explicitly **not** adaptive to
behaviour, because unpredictable ordering is exactly what hurts the impaired user.

The impaired user reads row one and the picture and stops, and row one is *the thing that actually
changed*, which is the only row he would have wanted anyway. The techie scrolls to row eight. Neither
was routed anywhere.

### M2 — Jede Zeile wächst, keine Zeile führt weg

Tapping any delta row expands it **in place** (Ionic accordion, `ion-item` → 260 px panel):

```
│  Wärmer       25,4  →  26,8 °C      +1,4  ▾ │
│  ┌────────────────────────────────────────┐ │
│  │  ····· Sollwert (Tag 25 / Nacht 20)    │ │
│  │  ▒▒▒▒▒ Zielband                        │ │
│  │  ──── 18.–25.08.   ── 11.–18.08.       │ │  ← both windows on a
│  │                            (min–max)   │ │     relative 0…7 d x-axis
│  └────────────────────────────────────────┘ │
│   Ø 25,4 → 26,8 · min 21,1 → 22,4           │
│   max 28,9 → 31,2 · im Zielband 91 % → 68 % │
│   Längste Abweichung 14 Min → 22 Min        │
│   [ Im Verlauf öffnen ]  [ CSV ]            │
```

Depth is vertical, never lateral. One gesture produces a bigger picture for one user and six numbers
for the other, from the same tap.

### M3 — Wort und Zahl stehen nebeneinander, nie hintereinander

Every value in the product renders on one line as **word · number · delta**:
`Trockener   58 % → 44 % rF   −14`. Never a word that hides a number behind a tap; never a bare number
with no meaning attached. The word carries the verdict at a glance; the number is right there for
whoever reads numbers. **Nobody is denied the number and nobody is forced to read it** — from the same
string, at the same moment, at the same size class.

This applies uniformly: alarms (`Zu warm · 31,2 °C · Grenze 30,0`), settings rows
(`Tag wärmer als Nacht · 25 °C / 20 °C · Δ 5`), regime steps (`Bio-Bloom · 4 ml/l · 16 ml auf 4 l`).

### The Zelt screen under the same rule

`/zelt` is one list for everybody, in one fixed hand-authored order: **Ziele** (day/night targets, VPD
band, photoperiod) → **Kit** (one row per *paired* socket, by role — a dehumidifier row exists iff a
dehumidifier socket exists) → **Personen** → **Regime** → **Alarme** → **Kamera** → **Gerät**
(firmware, maintenance, testmode for admins). Reveal by capability, not by expertise. A monitor-only
device shows Ziele as read-only reference values with the honest header
`Dieses Gerät misst nur — es steuert nichts.` and the Kit block is absent.

Dead controls are deleted rather than hidden: `daynight.floating`, `float_start`, `day_duration`,
`light_duration`, `lights.maintenanceOn`, `co2.sunsetOff`, `daynight.linearChange` are read by no
firmware and must not appear.

Apache ECharts 6, tree-shaken, hand-rolled ~50-line Angular directive. Highcharts, `highcharts-angular`,
`chart.js`, `ng2-charts` and `chartjs-adapter-luxon` are removed in the same commit.


- **Small multiples**, 4–6 stacked grids at ~100 px each, `axisPointer.link` on the x-axis, one
  crosshair. At most two units per grid and only when physically coupled (Luft-/Blatttemperatur).
  **Axis labels are never hidden** — below 320 px they shorten to 3 ticks and the unit moves into the
  panel title.
- **Goal vs actual.** A dashed **stepped** `markLine` at `day.temperature` / `night.temperature`
  stepping at `daynight.day` / `daynight.night`; a soft `markArea` band behind it. Band source, one at
  a time and labelled: **Alarmgrenzen** (hard, the user's own declaration) > **Sollwert ± Toleranz**
  (soft) > **Stage-VPD-Band** from `GROW_STAGE_PRESETS` (advisory). The deviation between actual and
  setpoint is filled with a signed tint. Never fill to the axis.
- **Day/night** from measured `out_light > 0` where present, else from the `daynight` schedule, in an
  explicit timezone (a 12/12 flip near a DST boundary otherwise drifts an hour). A failed contactor
  therefore shows as a **missing band**, which is a diagnostic.
- **Annotations** on a 16 px rail under the x-axis, two rows max (row 1 human events, row 2 device),
  pixel-clustered at 10 px with count badges, severity-ranked, category chips reusing
  `collectLogCategories`. Lifecycle changes get full-height dashed verticals. Nothing is hover-only.
- **The pair handles.** `A` and `B` are full-height draggable verticals. Dragging one re-pins that
  Moment and everything upstream — the Paarleiste thumbnails, the delta list, the verdict, the
  timelapse span — updates live on drop. This is the primary interaction of the whole app and it is
  one gesture.
- **Comparison overlay.** A `[ Beide Zeiträume übereinander ]` toggle redraws the same grids on a
  relative `0…span` x-axis with the Vorher window in `#999999` and the Nachher window in `#0072B2`.
  This is a *drawing option on one screen*, not a second screen.
- **Sampling** `'minmax'` for the plot (LTTB smooths away the very oscillation a bang-bang controller
  produces), LTTB for the navigator. Colours: Okabe-Ito.
- Mobile: one finger scrolls the page, two fingers pan/zoom (`dataZoom: {type:'inside'}`), tap
  or long-press moves the crosshair. Range presets stay ≥ 44 px.
- **Server work this needs:** a combined `{mean,min,max}` series response instead of three round trips;
  a raw-sample time-in-band endpoint (time-in-range computed on `aggregateWindow(fn:mean)` output is
  silently wrong); `measure`/`from`/`to`/`interval` allowlisted before Flux interpolation; `interval`
  constrained by `timespan`.

## 6. The diary and multi-plant

New MongoDB collections, all cloud-side and keyed by `device_id`. All new fields optional; read-time
normalisers; one idempotent boot-time backfill.

```ts
// plants
Plant { plant_id, device_id, label /* "A1" */, strain?, started_at, ended_at?,
        regime_id?, position?, archived? }

// growevents  — every NEW human event. Existing DeviceLog rows keep working, read-only.
GrowEvent {
  event_id;            // UUID generated BY THE CLIENT at capture — server upserts by it
  device_id; at; created_at;
  kind: 'water'|'feed'|'train'|'note'|'measure'|'stage'|'photo'|'harvest'|'pest';
  plant_ids: string[]; // [] = the whole tent, and this is the default
  actor_id?; images?: string[]; text?;
  water_l?; feed_items?: { product: string; ml_per_l?: number; total_ml?: number }[];
  ec?; ph?; ec_source?: 'input'|'runoff'|'reservoir'; runoff_pct?;
  stage?: DiaryLifecycleStage | 'harvest'; height_cm?; regime_step?;
  double_ack?: boolean;      // the user overrode a double-feed warning
  supersedes?: string;       // correction instead of edit; the original is never mutated
  deleted_at?: number;
}

// conditions — the standing fact that gets pinned to a tent door
Condition { condition_id, device_id, text, plant_ids: string[],
            opened_by?, opened_at, closed_by?, closed_at?, severity: 0|1 }

// actors — device-scoped names, NOT accounts
Actor { actor_id, device_id, name, colour, created_at, retired_at? }
```

### The diary is a list of pairs

`/tagebuch` is a scroll of **Wochenkarten**, newest first. Each card is a pair whose span is one week,
and almost every line of it is machine-composed:

```
┌──────────────────────────────────────────────┐
│ Woche 24 · 18.–25.08. · Blüte Woche 3        │
│ ┌───────────┐ ┌───────────┐                  │
│ │  Vorher   │ │  Nachher  │                  │
│ └───────────┘ └───────────┘                  │
│ Ø 26,8 °C (+1,4) · 44 % rF (−14)             │
│ VPD 1,48 (+0,43) · Licht 12,0 h              │
│ Im Zielband: 68 % (Woche davor 91 %)         │
│                                              │
│ Gegossen 3× · 12 l        Gedüngt 1×         │
│ Entlaubt A1, A2 (Chris)                      │
│ ⚠ 1 Alarm: Temperatur > 30 °C · 22 Min       │
│                                              │
│ „Blüte läuft, A3 hängt hinterher."   ← human │
│                                              │
│ [ Als Bild teilen ]  [ Als Text kopieren ]   │
└──────────────────────────────────────────────┘
```

**"Es macht die Tagebuchführung für dich"** is literally true here: every line above except the last is
derived from telemetry and from events the user logged with two taps. `[ Als Text kopieren ]` emits
Markdown *or* BBCode (a segmented control on the copy sheet) with hot-linked image URLs — which
collapses "post to RollItUp, THCFarmer, ICMag, Discourse" into one button and needs nobody's API.

Below the week cards: **Alle Einträge** — the existing `app-log-entry-viewer` with server-side
pagination added, now merging `growevents` and `DeviceLog`, filtered by category chips.

### Multi-plant, and how the user who ignores plants is untaxed

- `plant_ids: []` means "the whole tent". It is the default and it is always valid.
- **The plant picker does not render until `plants.length >= 2`.** With zero or one plant there is no
  chip row on a capture sheet, no per-plant column in a week card, no plant filter, no "A1" anywhere.
  Reveal by data.
- Plants are created in one place — `Zelt → Pflanzen → [ + ]` — with one required field, `label`. A
  user who never opens that screen never sees a plant in his life.
- A **plant chip row** appears on the capture sheet the moment a second plant exists, prefilled to
  **all plants** (so the untaxed default is preserved), with `[ Alle ]` as the first chip.
- The pair gains an optional third axis only when plants exist: on a week card, `Nur A3 ▾` re-filters
  the events list and the photo crops. Never forced, never default.
- `convertEventsToGrowCycles()` — today a runtime browser algorithm that forks history on a rename —
  becomes a **one-time backfill** that materialises `Plant` rows from historical
  `diary-plant-lifecycle` entries. After that, cycle identity is a stable `plant_id`, not a string
  comparison, and editing an entry's time no longer breaks a share link.
- **`deleted` is fixed.** Today `deleted:true` means "hide from the overview stream" and manual diary
  entries are created with it, so "Clear logs" deletes nothing from the diary. `GrowEvent` uses
  `deleted_at` and means it. `DeviceLog.deleted` keeps its legacy meaning for legacy rows only.
- The server's own stage-transition entry is written with `categories: ['diary-plant-lifecycle']`
  without the `'diary'` prefix and is therefore invisible and uneditable. C19 writes a `GrowEvent`
  with `kind:'stage'` instead; the legacy rows are picked up by the backfill.

## 7. Watering & fertilising

No irrigation hardware exists. This is a capture-and-recall problem, and the metric is taps.

### Capture — the numbers

**Gießen, minimal path: 2 taps.**
1. `[ 💧 Gießen ]` on the home dock (**tap 1**) → sheet.
2. Sheet is prefilled: `heute, jetzt · ganzes Zelt · 4 l` (last used volume). `[ Speichern ]` (**tap 2**).

**Düngen with a regime selected: 2 taps.**
1. `[ 🧪 Düngen ]` (**tap 1**) → sheet, prefilled from the regime's *next unfulfilled step*.
2. `[ Speichern ]` (**tap 2**).

Every prefilled value is a `value-edit-row`: tapping it expands `[−] ion-range [+]` in place
(+2 taps per value changed). Nothing is required. Without a regime, the sheet prefills from the last
feed event instead — still 2 taps.

### The double-feed soft block

On sheet open, query `growevents` for the same `kind`, intersecting the selected `plant_ids`, within a
window (`feed` 20 h, `water` 6 h). If a match exists, the warning renders and **`Speichern` is
disabled** until `[ Trotzdem eintragen ]` is pressed. That is one deliberate extra tap, and the saved
event carries `double_ack: true` so the week card and the Verbrauch report can show it
(`1× doppelt bestätigt`). A double feed is the most expensive thing that happens in a shared room and
this is the only place in the product where C19 deliberately makes a tap *harder*.

A `Condition` with `severity: 1` on the selected plants renders in the same slot:
`Nicht gießen — A3 ist übergossen (Anna, vorgestern)`.

### Schedule following

The regime advances **by feed events, not by wall clock** — growers feed Tue/Fri and slip.
`GrowEvent.regime_step` records which step a feed fulfilled. Home shows, only when a regime is
selected (reveal by data):

`Nächste Düngung: Schritt 8 von 12 · fällig seit 2 Tagen`

A regime is a **grow medium + feed regime pair**, labelled the way a grower says it out loud:

```ts
Regime { regime_id, label /* "Biobizz All-Mix + Bio-Grow / Bio-Bloom" */,
         medium /* "All-Mix" */, feed_line, prefertilised_weeks /* 4 */,
         steps: RegimeStep[], source_url, retrieved_at,
         kind: 'official_pdf'|'official_calculator'|'ownerless', owner_id? }
RegimeStep { stage: 'vegetative'|'flowering', week,
             items: { product, ml_per_l?: number|[number,number], note? }[],
             ec_target?: [number,number], ec_basis: 'absolute'|'delta_over_source',
             ph_target?: [number,number] }
```

All-Mix is heavily pre-fertilised, so its first four weeks of steps are literally
`items: [], note: 'All-Mix ist vorgedüngt — noch nicht düngen'`, and the home line reads
`Noch nicht düngen — All-Mix trägt noch (Woche 2 von 4)`. A regime that cannot express that is not
modelling the domain. BioTabs' "schedule" is `Neu tabben` every 4–6 weeks, not a liquid ladder.

`ec_basis: 'delta_over_source'` exists because CANNA and others publish **EC +**: if source water is
EC 0.4 and the chart says 1.4–1.8, the meter should read 1.8–2.2. The UI shows
`1,4–1,8 (+ Leitungswasser 0,4) = 1,8–2,2 am Messgerät`. EC is stored canonical; a bare "ppm" number is
never rendered (a Bluelab reads 1260 where a Hanna reads 900 for the same liquid).

Brand names are plain-text labels only — no logos, no brand colours, no bottle imagery, never inside a
Terp Control feature name. Numbers live in the Mongo content collection with `source_url` +
`retrieved_at`, surfaced as `Zuletzt geprüft: 12.06.2026`, so any brand can be removed in one DB update.

### Offline capture, without a service worker

The sheet writes the event to `localStorage['tc-pending-events']` **before** the network call and
renders it immediately with a `⏳ noch nicht gesendet` chip. A retry loop flushes it. The `event_id`
is a **client-generated UUID** and the server upserts by it, so a retry can never double-log — which in
a shared record is indistinguishable from a double feed. Honest limit: this survives loss of network
but **not** the tab being killed. A real service worker is `@angular/service-worker` plus a build
change and is v1.1.

### Verbrauch — the cumulative question

`Tagebuch → Verbrauch`, and the same block on a plant card:

```
A3 · dieser Durchgang (seit 15.07., Tag 41)
Wasser     46 l   in 11 Gaben     zuletzt 24.08. (Anna)
Bio-Grow   62 ml  in 8 Gaben
Bio-Bloom 148 ml  in 6 Gaben      zuletzt 22.08. (Anna)
Entlaubt   2×                     zuletzt 21.08. (Chris)
1 Gabe doppelt bestätigt
```

Pure aggregation over `growevents`. Nothing new is stored to answer it.

## 8. Camera, timelapse and image correlation

This is the headline. The existing pipeline already gives us more than any concept assumed:
`ffmpeg` and `imagemagick` are in the server image, `sharp@0.34.5` is a dependency, `pLimit(10)`
throttles encodes, stills arrive every 30 s, and `Image.timestampEnd` already marks an mp4 as spanning
a range. What is missing is content quality, a cycle-anchored span, and a way out.

### 8.1 Cycle-anchored timelapses, not epoch-aligned windows

Today's three rolling durations are anchored to `Math.ceil(now / timeStep) * timeStep` — a "week"
timelapse is a calendar-grid week, related to nothing the grower did. They stay for the live preview.
C19 adds a fourth kind:

```ts
Image.duration?: '1d' | '1w' | '1m' | 'range'    // widened, optional, back-compat
// range: timestamp = a, timestampEnd = b
```

`[ ▶ Zeitraffer dieser 7 Tage ]` on the home pair builds exactly `a → b`. Any pair is a timelapse:
"seit dem Umtopfen", "die ganze Blüte", "dieser Durchgang" (`plant.started_at → now`), "gleicher
Zeitraum, letzter Durchgang".

⚠ The unique index `{device_id, format, timestamp, duration}` collides for two range exports starting
in the same millisecond. It must become `{device_id, format, timestamp, timestampEnd, duration}` —
a real index migration on a repo with no migration tooling. Costed, not hand-waved.

### 8.2 Frame QC, computed once at capture

`sharp` at capture time, ~8 ms per frame at a 30 s cadence — negligible. Stored on the `Image` doc:

```ts
Image.qc?: {
  mean: number;      // luma mean 0..255            → sharp().stats()
  stdev: number;     // luma stdev; a black or fogged frame is near zero
  r: number; g: number; b: number;   // channel means → white balance
  dhash: string;     // 64-bit perceptual hash, from sharp().greyscale().resize(9,8).raw()
}
```

### 8.3 Culling — how the garbage is removed

A tent timelapse is mostly garbage: lights off, a hand in shot, the door open, condensation, the camera
nudged on day 12, magenta LED against daylight. In order:

1. **Nachtbilder.** `qc.mean < 25` and the timestamp falls in a night window derived from `out_light`
   → drop. A black frame is not information. Exposed as **one checkbox** on the export sheet,
   `☑ Nächte überspringen`, default on. (A checkbox on one sheet is not a mode: it changes this
   artefact, not the app.)
2. **Blind/blank.** `qc.stdev < 6` → drop. Fogged lens, blown IR, lens cap, cover on.
3. **Ausreißer (Mensch, offene Tür, Taschenlampe).** A frame whose `qc.mean` exceeds **2.5×** the
   trailing 30-frame median, *or* whose dhash hamming distance to **both** neighbours exceeds 22 while
   those neighbours are within 6 of each other → drop. A person entering a magenta tent with a phone
   torch, or the door opened to daylight, is exactly a brief large-luminance outlier.
4. **Rampenschutz.** Frames within ±10 min of `lights.sunrise` / `lights.sunset` are exempt from (3) —
   the ramp is *supposed* to change brightness.
5. **Near-duplicate thinning.** Within each keep-interval bucket, pick the frame whose dhash is closest
   to the bucket median — the most *typical* frame — not the first. This cheaply kills "the one frame
   that hour happened to have a watering can in it".
6. **Culled frames are never deleted.** They appear in the film strip as thin grey ticks labelled
   `verworfene Aufnahme`, and the export sheet offers `☐ Alle Bilder verwenden`. The frame where the
   door was open is sometimes the frame that explains the humidity spike.

### 8.4 Normalisation — what makes it watchable

Per kept frame, before encoding:

- **Exposure.** `sharp().linear(a, b)` maps `qc.mean` onto a **rolling 200-frame target mean**, not a
  global one — a grow legitimately gets brighter as the canopy fills and a global target would fight
  that.
- **White balance.** Per-channel gains map `r:g:b` onto the rolling target ratio, which is what removes
  the magenta/daylight flicker across twelve weeks.
- **Clamp both to [0.7, 1.4].** Beyond that the scene genuinely changed and we must not hallucinate it
  back.
- **Stabilisation: not in v1.** `vidstab` is not compiled into the Alpine ffmpeg and per-frame
  alignment is real work. v1 ships the cheap 80 %: a **fixed 4 % centre crop** on every frame, which
  absorbs small nudges and also removes the timestamp burn-in some cameras add. The rest is v1.1, and
  the export sheet does not pretend otherwise.

### 8.5 How a video LEAVES the product

**Format.** H.264 (`libx264`), `yuv420p`, `+faststart`, 1280×720, 25 fps, CRF 23. **Not** the existing
`libx265 -crf 30` — x265 does not play reliably in iOS Photos, in Safari, or inline in Telegram. x265
stays for the internal rolling previews (small, played in our own `<video>`); **anything the user
exports is x264.**

```
ffmpeg -y -framerate 25 -f image2 -i %d.jpeg \
  -vf "crop=iw*0.96:ih*0.96,scale=1280:-2,format=yuv420p" \
  -c:v libx264 -preset veryfast -crf 23 -movflags +faststart out.mp4
```

**Length, not frame rate.** The export sheet offers `ca. 15 s · ca. 30 s · ca. 60 s · alle Bilder`;
the builder derives the keep interval as `span / (seconds × 25)`. Nobody is asked about frame rates.

**Path.**
`GET /image/:device_id?format=mp4&duration=range&timestamp=<a>&timestampEnd=<b>&download=1&share=<id>`
→ `Content-Type: video/mp4`, `Content-Disposition: attachment; filename="…"`.

**Filename.**
`terpcontrol_zelt-1_20260818-20260825_7t.mp4`
Device-name slug, both dates, span. **No strain, no plant label, no "cannabis", nothing a phone gallery
shows to someone looking over a shoulder.** That is a deliberate privacy decision.

**Token.** Not the 30-day `imageToken`. Exports mint a **`ShareLink` scoped to this artefact** —
`{ share_id, device_id, page:'clip', query:'timestamp=…&timestampEnd=…&format=mp4' }`, default expiry
**7 days**, listed and revocable in `/shares` with its `openCount`. Reuses machinery that already
exists (`expiresAt`, `revokedAt`, `openCount`).

**The export sheet:**

```
┌──────────────────────────────────────────────┐
│  Zeitraffer · 18.–25.08. · 7 Tage        ✕   │
│  ┌──────────────────────────────────────────┐│
│  │            [ preview ▶ ]                 ││
│  └──────────────────────────────────────────┘│
│  Länge     [15 s] [ 30 s ] [60 s] [alle]     │
│  ☑ Nächte überspringen                       │
│  ☐ Alle Bilder verwenden (auch verworfene)   │
│  2 143 Bilder · 312 verworfen · ca. 6 MB     │
│                                              │
│  [ Video speichern ]   [ Link kopieren ]     │
│  Link läuft in 7 Tagen ab · widerrufbar      │
└──────────────────────────────────────────────┘
```

- `[ Video speichern ]` opens the mp4 URL in a new tab. On iOS the native player appears with a share
  sheet → *In Fotos sichern*: honestly one extra tap, and it works, which `<a download>` cross-origin
  does not.
- `[ Link kopieren ]` yields a tokenised URL that **Telegram renders inline with no login**. That is a
  real share. The community already lives on Telegram.
- Where `navigator.share({ files })` exists, `[ Video speichern ]` uses it directly — a 30 s 720p x264
  is ~4–7 MB, fine in memory.

**Storage honesty.** Videos are Mongo `Buffer`s under a 16 MB BSON cap. Exports are capped at 60 s; if
an encode exceeds 14 MB it is re-encoded at CRF 28 / 960×540; if it still exceeds, the sheet refuses
with real copy (`Zu lang für einen Download — wähle eine kürzere Länge.`). Ugly. The correct fix is
object storage and it is out of scope for October.

### 8.6 The camera alarm

Nobody gave the camera an alarm; freshness honesty only helps if you happen to look. On the existing
hourly compress tick: if `device.lastseen` is fresh but the newest `format:'jpeg'` is older than
`CAMERA_SILENT_MINUTES` (default 120), write a `DeviceLog` with `message-camera-silent`, severity 1,
and fire the existing alarm/e-mail path once with a 24 h cooldown. A camera that stopped three days
into flower tells you. Reuses everything; ~half a day.

### 8.7 Image correlation — both directions

**Chart → picture.** The Verlauf scrub header carries a 96×54 still at the crosshair. Delivered as
**sprites**, not N requests: `GET /image/:device_id/sprite?date=YYYY-MM-DD` returns one jpeg of up to
100 tiles at 160×90 (`sharp().composite()`, built on the same hourly tick), plus
`GET /image/:device_id/sprite.json?date=…` → `[{ t, x, y }]`. 100 frames in one ~250 KB request. The
film strip is the same sprite, positioned **by timestamp**, so uneven capture reads honestly as gaps
and the range covered by a `duration:'range'` mp4 renders as a bracket rather than a point.

**Picture → numbers.** Tapping any frame — film strip, paused timelapse, diary photo — opens the
**Momentkarte** (`/device/:id/moment/:ts`):

```
┌──────────────────────────────────────────────┐
│  Mo 25.08.2026 · 14:02                   ✕   │
│  ┌──────────────────────────────────────────┐│
│  │                [still]                   ││
│  └──────────────────────────────────────────┘│
│  26,8 °C  ·  44 % rF  ·  VPD 1,48 kPa        │
│  CO₂ nicht gemessen · Licht an (72 %)        │
│  Heizung an seit 6 Min · Entfeuchter aus     │
│  Tag 41 · Blüte Woche 3                      │
│                                              │
│  [ Als Vorher merken ]  [ Als Nachher merken ]│
│  [ Diesem Moment eine Notiz geben ]          │
└──────────────────────────────────────────────┘
```

Those two buttons are how the pair gets filled from a photograph. That is the whole mechanism: any
picture in the app can become half of the comparison, and the numbers travel with it.

**What v1 does NOT do:** stabilisation, ML person/hand detection, per-plant crops, audio, 4K, YouTube
upload, motion-interpolated smoothing.

## 9. Clubs

**Attribution in v1, authorisation later — and the copy never confuses them.**

- **Actors, not accounts.** The owner types names once in `Zelt → Personen`. `Actor` is device-scoped.
  Every `GrowEvent` carries `actor_id`. No login, no e-mail, **no change to `auth.middleware.ts`.**
  The picker prefills from `localStorage['tc-actor-<device_id>']` — the phone in the tent remembers who
  is usually holding it — and is one tap to change. Below two actors the chip row does not render at
  all.
- **Honesty.** The label is `Wer war's?`, never `Verifiziert`. Anyone with the device login can pick
  any name. That is sufficient for a household and for a small club where the constraint is memory, not
  fraud. **It is not an audit trail and the UI must never imply it is.** A club that mistakes it for
  compliance is a real failure mode (§13).
- **Forward path.** Real memberships (a `Membership` collection, rewriting `auth.middleware.ts:172` and
  `:207`, loosening ~10 owner-scoped queries) are v1.1+. `actor_id` is forward-compatible: a membership
  later attaches to an existing actor and every historic event keeps its attribution.
- **Double feed** — §7. The single most valuable club feature in the product.
- **Cumulative** — §7 Verbrauch. Answers "how much Bio-Bloom has A3 had this cycle, and from whom".
- **Conditions** — the standing open fact. A slim amber strip at the very top of home, above the pair,
  max three then `+2 weitere`. `CO₂-Flasche fast leer · seit 3 T · Chris` → tap → `[ Erledigt ]`
  (`closed_by`, `closed_at`). `severity: 1` conditions on specific plants surface inside the capture
  sheet for those plants. This is the note taped to the tent door, and it is the one thing in the app
  that is neither an event nor a task.
- **Corrections, not edits.** A wrong event is corrected with a new `GrowEvent` carrying
  `supersedes: <event_id>`; the original is never mutated. The week card shows the corrected value with
  a `korrigiert` chip. Append-only without cryptographic theatre.

### Privacy posture

- **Harvest weight and plant count are never prompted.** `kind:'harvest'` supports `weight_g`, but the
  field only appears after the user has typed one once, and then only on that device
  (reveal by data). Default posture is the privacy-maximal one.
- **Exports default to `PSEUDONYMIZED`** — actor names become `Person A`, `Person B`. A
  `KEINE · PSEUDONYM · ANONYM` selector sits on the export sheet.
- **The public pair link `/p/:share_id`** shows the two photos, the delta list and the events between —
  **never plant counts, never weights, never actor names**, and it carries no branded footer (§6 KCanG
  bans cannabis advertising and sponsoring with fines to €30,000; a "Powered by Terp Control" line on
  thousands of German grow posts is the single riskiest string we could ship).
- No location, no real names, no analytics SDK, EU hosting stated plainly, no compliance badge, and the
  account owner can always delete. Terp Control does not become anyone's § 26 system of record.

## 10. Old devices (type 7) — fan, light, plug

**The pair degrades by capability, not by device type.** One `<tc-pair>` component takes a
`PairSource` with three implementations: `PhotoPairSource`, `ValuePairSource`, `OutputPairSource`.
A device with no camera gets `ValuePairSource` and every other block on the page is identical.

**Plug with a slave temperature sensor:**

```
┌────────────────┐  ┌────────────────┐
│  VORHER        │  │  JETZT         │
│  Mo 18.08.     │  │  Mo 25.08.     │
│                │  │                │
│    24,1 °C     │  │    26,8 °C     │      ← Zustandskarte:
│    61 % rF     │  │    44 % rF     │        the measures this
│    An 6,2 h    │  │    An 9,1 h    │        device actually reports
└────────────────┘  └────────────────┘
       ◄──── 7 Tage ────►

Der Verbraucher lief 3 Stunden länger
als in der Woche davor.
```

**Light** (PWM `out_light`, no sensors): the cards show `Lichtzeit 12,0 h · Ø Dimmung 78 % · Sonnenauf
06:00`. Verdict: `Gleiche Lichtzeit wie in der Woche davor.` The Verlauf day/night lane makes a failed
contactor visible as a missing band: `Am 21.08. blieb das Licht 40 Min länger an als geplant.`

**Fan:** `Ø 2 140 rpm · An 18,4 h`, plus temp/rF if a sensor is present.

**What they explicitly do not get, and why it is not a demotion:** plants, regimes, watering capture,
actors, conditions, timelapse, film strip. None of those have data or hardware behind them. Reveal by
capability + reveal by data — the same two rules that hide a dehumidifier row on a heater-only
controller. Their existing `fan-settings` / `light-settings` / `plug-settings` components are
**untouched** in v1; the only change is that the device home renders the pair shell instead of the
current overview card, and `/settings` becomes an alias for `/zelt`.

`fridge` is a live product and gets the full pair, including photos when a camera is paired. `dryer` is
dead per `AGENTS.md` and is left alone.

**And the naming fix ships with it:** a `devices.controller` i18n block in both `en.json` and
`de.json`, so a controller stops calling itself `Terp Control FRIDGE GROW` and an unnamed controller
stops being *named* that. Half a day, and it is the cheapest credibility fix in the product.

## 11. Per-user-type walkthrough

**1 — Monitor only.** No sockets, no camera. His home is two Zustandskarten a week apart, a verdict
sentence, and a ranked delta list — which is the exact thing he opens the app for ("record the values
and look at them, after some time"). He gets a time-in-band number he has never had. The Zelt screen
says `Dieses Gerät misst nur — es steuert nichts.` and shows targets as reference values, and the
dehumidifier tile he can never act on is gone.

**2 — Monitor plus camera.** The concept is built for him. His pair is two photographs; his home CTA is
a timelapse of any span he can pin; his film strip is an axis; every frame carries its numbers and can
become half of a comparison. He gets a video with a filename that he can put in his camera roll and a
7-day link he can paste into the Telegram group. He is also the one user who is told when the camera
stops.

**3 — Controls some aspects (CO₂ or heating).** The Kit block on `/zelt` lists one row per *paired*
socket and nothing else, so he is never shown a humidity target he cannot act on. His delta list
promotes `Heizung 41 → 72 Min/Tag` — the output he actually controls — above ambient noise, because
that is what changed most. Alarm presets are filtered by paired role, not by a three-bucket guess that
fails open.

**4 — Full tent.** He gets the fused view: environment, machine state and human actions on one x-axis
with the setpoint drawn on it — which is the one thing no competitor offers. The honest limit stands
and is stated in the UI, not hidden: five socket roles exist, `dehumidifier` doubles as the cooler
depending on workmode, and there is no humidifier path. C19 does not pretend otherwise and does not
require firmware to ship.

**5 — Closed-loop DIY.** Least served, and I will not claim otherwise. What he gets in v1: `CSV` on
every expanded delta row, the raw two-window series, a documented stable `?a=&b=` URL contract, and the
`GrowEvent` collection behind a REST surface he can POST to (it already needs one for the webapp). What
he does not get in v1: a write API for outputs, custom measures, Home Assistant. Those are named in the
roadmap rather than implied.

**6 — Club / shared tent.** Actors, the double-feed soft block, Conditions, Verbrauch, corrections
instead of edits, pseudonymised export. The capture flow is two taps so a member logs it instead of
telling somebody later, and the week card reconstructs who did what months afterwards. Terp Control
refuses to hold per-member dispensing records.

**7 — Old device owner.** §10. Nothing breaks, his settings screens are untouched, and he gains a
before/after and a runtime comparison he did not have. He is never shown a plant, a regime or a
timelapse he cannot produce.

**Capability lenses.** *Stoner, 2am, one hand, dark tent:* two pictures, one sentence, two buttons at
thumb height, no chart to parse and nothing hidden behind a toggle he must remember he turned on.
*Normal:* a shareable artefact that beats an Instagram post, and a diary that fills itself in.
*Techie:* every number is on screen next to its word, one tap expands to min/max/time-in-band/CSV, the
URL is the view model, and no density preference stands between him and the data.

## 13. Honest weaknesses

1. **A pair is a causal claim the data cannot support.** "Wärmer und trockener" over two weeks may be
   the weather outside, not anything the grower did. The verdict sentence will be over-read and there
   is no mitigation except copy discipline — which will erode.
2. **Two 168 px stills on a 360 px phone.** Enough for "bigger, bushier". Useless for "is that a
   magnesium deficiency". Tap-to-fullscreen with a swipe wipe helps and is still cramped. The design
   genuinely wants a tablet.
3. **The Paarleiste costs 56 px on three of four screens** and duplicates state a user may never touch.
   For someone who never changes the pair it is dead chrome, and collapsing it on scroll only halves
   the cost.
4. **"Is my tent on fire right now?" is not a pair.** The single most urgent question in the product is
   instantaneous, so home must carry a current-alarm strip above the pair — which quietly undermines
   the thesis at exactly the moment that matters most. C19 designs for it and admits it.
5. **Culling can hide the frame you needed.** Rule 8.3(3) drops the open-door frame, which is often the
   frame that explains the humidity spike. Grey ticks and `Alle Bilder verwenden` mitigate; they do not
   fix the default.
6. **Video storage is genuinely bad.** x264 exports and x265 previews both live as Mongo `Buffer`s
   under a 16 MB BSON cap. The 60 s cap and the CRF-28 fallback are workarounds for an architecture
   that should be object storage, and a busy device accumulates range exports nobody prunes.
7. **`σ_typ` is hand-tuned and will be wrong for someone.** A badly chosen CO₂ normaliser puts sensor
   noise above a real temperature swing at the top of the list, which is the *only* row an impaired
   user reads. The ranking's virtue and its danger are the same property.
8. **Actor attribution is theatre against a dishonest actor**, and a club will screenshot it as if it
   were an audit trail no matter what the copy says.
9. **No service worker means the cellar case is half-solved.** Capture survives a dead network but not
   a killed tab, and "half offline" is harder to explain than either extreme.
10. **The Verlauf rewrite is the largest single risk in an eight-week window** and it is not cuttable,
    because image correlation lives on that page. If ECharts small multiples turn out slow on a
    mid-range Android with 90 days of data, the headline feature slips with it.
11. **The `Image` unique-index migration** (`{device_id, format, timestamp, timestampEnd, duration}`)
    is a real schema change on a collection with no migration tooling and no rollback story.
12. **A 7-day default span is wrong at both ends of a grow** — a week is the entire drying phase and it
    is nothing at all to a seedling. Stage-aware defaults help and add an invisible rule the user
    cannot predict, which is precisely the sin M1 was written to avoid.
13. **Deleting Einfach/Experte removes a shipped feature some users have chosen.** M1–M3 are a better
    answer; they are also unproven, and the first support ticket will say "wo ist der einfache Modus".
