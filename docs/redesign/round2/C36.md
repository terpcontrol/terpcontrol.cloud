# C36 — "Ein Objekt"

**Family:** unify · **Centre of gravity:** there is one kind of thing and one way to look at it.
Written against NEW-BRIEF.md, 00-DOSSIER.md, 00-OWNER-DECISIONS.md, 00-ORCHESTRATOR-NOTES.md and
direct reads of `/home/user/terpcontrol.cloud` (`server/src/services/image.service.ts`,
`webapp/src/app/util/socket-info.ts`, `server/src/controllers/image.controller.ts`).

---

## 1. Thesis

**Everything in Terp Control is a *Ding* — a named thing with one time, a body and named relations — and
there is exactly one way to look at a Ding, so learning the app once is learning all of it.**

A plant, a smart socket, a photograph, a feed, a pinned note on the tent door, a timelapse, a target
temperature, a person, a device alarm: today these are five pages, three collections, two report modes and
one 1205-line chart component. They are the same shape. Each has a name, a moment (or a span), some fields,
and edges to other things — "diese Gabe ging an A1 und A2, von Anna". Model them once, render them once,
browse them once.

The payoff is not elegance. It is that a person who is stoned at 2 a.m. and a person who wants to script
against the API are performing the *same operation* — tap a row, get its page — and neither of them had to
be told which kind of user they are. Depth is reached by walking, not by switching. Nobody chose a mode
because there is nothing to choose: there is one screen shape and you are always standing somewhere in it.

The obvious failure of this idea is that it becomes an abstract database browser: a type picker, a filter
panel, a grid of rows called "entities". §4 is the mechanism that prevents that, and it comes down to two
rules — *the frame is uniform, the body never is*, and *you never select a type, you follow a named
relation written as German*.

## 2. Information architecture

Three routes. That is the whole app.

| Route | Guard | What it is |
| --- | --- | --- |
| `/list` | AuthGuard | Your Zelte. Exactly one claimed → straight to it, as today. |
| `/d/:device_id/:thing_id?` | AuthGuard (+ share bypass) | **The browser.** One component. `thing_id` absent ⇒ the Zelt is the Subjekt. |
| `/d/:device_id/chart` | AuthGuard (+ share) | The chart. The only non-Ding screen. |

Untouched and still routed: `/login`, `/account`, `/shares`, `/demo`, `/link-expired`,
`/connection-error`, `/classes`, `/diagnostics`, `/device/:id/testmode`.

**Back-compat is not optional** — share links and chart presets are persisted user data:

```
/device/:id/diary          → 301 /d/:id
/device/:id/charts?<q>     → 301 /d/:id/chart?<q>     (query format unchanged, applyViewParams intact)
/device/:id/settings       → 301 /d/:id/ziele          (controller & fridge)
                           → kept as-is for fan/light/plug/dryer
```

Everything that is a page today becomes a Ding under the Zelt: settings are `ziel` Dinge, the diary is the
Zelt's `Verlauf` list, the grow report is a `phase` Ding's Tafel, maintenance is a `zustand`.

The menu loses "Diary/Charts/Settings/Maintenance/Setup" as six outline buttons and keeps: Geräte, Geteilte
Links, Konto, Dunkelmodus, App installieren, Abmelden.

### The one object

```ts
// NEW MongoDB collection `things`. The only new persistence in this concept.
interface Thing {
  thing_id: string;                 // uuid v4 — MINTED BY THE CLIENT (see §7, offline)
  device_id: string;                // scope. Matches auth.middleware.ts:172 exactly. No auth rewrite.
  art: ThingArt;                    // a concrete German noun. Closed set of 13.
  name: string;                     // "A3 · Wedding Cake", "Entfeuchter (Dose 2)"
  t: number;                        // ms epoch. EVERY Ding has one time.
  t_end?: number | null;            // spans. explicit null = still open.
  rel?: Record<string, string[]>;   // named edges: { an: [...], in: [...], betrifft: [...] }
  d?: Record<string, number|string|object>;   // kind-specific body
  bilder?: string[];                // image_ids
  akteur?: string;                  // thing_id of a `mensch`
  storniert_von?: string;           // corrections, never hard edits (club posture, §9)
}

type ThingArt =
  | 'zelt' | 'pflanze' | 'dose' | 'kamera'      //  the physical world
  | 'bild' | 'film'                              //  pictures
  | 'gabe' | 'notiz' | 'zustand' | 'phase'       //  what humans do
  | 'ziel' | 'mensch' | 'ereignis';              //  intentions, people, machine events
```

**Only six arts are stored.** `pflanze`, `gabe`, `notiz`, `zustand`, `phase`, `mensch`. The other seven are
**projected read-time** from what already exists:

| art | projected from |
| --- | --- |
| `zelt` | `Device` + last Influx point |
| `dose` | `hardwareInfo.sockets` / `socket_ips` via the existing `parseSocketRoles()` |
| `kamera` | `hardwareInfo.webcam_did` + newest `Image` |
| `bild` | `Image {format:'jpeg'\|'user/jpeg'}` |
| `film` | `Image {format:'mp4'}` — `timestampEnd` already gives `t_end` |
| `ziel` | `device.configuration` parsed (`day.temperature`, `lights.limit`, …) + `Alarm[]` |
| `ereignis` | `DeviceLog` (all of it — boot messages, alarms, recipe steps, config diffs) |

So the API surface is: `GET /things?device_id=&art=&von=&bis=&cursor=`, one union, cursor-paginated by `t`.
The webapp uses it. The public API is it. **They cannot drift, because there is only one.**

`convertEventsToGrowCycles()` (`grow-report.component.ts:691-747`) stops being a runtime algorithm and
becomes a **one-time idempotent boot backfill** that emits `pflanze` + `phase` Dinge from historic
`diary-plant-lifecycle` rows, keyed by trimmed `lifecycleName`, marked `d.aus_log: <log _id>`. Nothing is
deleted; old `DeviceLog` rows keep projecting as `ereignis`/`notiz`.

## 3. The one screen shape

Every Ding renders in exactly three sizes, and **which size you get is a function of where the Ding is
standing, never of who is looking**:

| Size | When | What |
| --- | --- | --- |
| **Zeile** | the Ding is related to the Subjekt | `[◼] Name · Wert · vor 4 Min` — one line, 48 px |
| **Tafel** | the Ding **is** the Subjekt | Kopf + Körper + Handlungen + three lists + Werte |
| — | there is no third size. A "card" is a Tafel that happens to be on screen. | |

**The Zeile has four slots, always, for every art:**

```
◼   Entfeuchter (Dose 2)                    an · 12 Min        vor 40 Sek
│   │                                        │                  │
│   └ name                                   └ Wert — ALWAYS    └ age — ALWAYS
└ 12 px status square: grün / gelb / rot / hohl(=veraltet)         PRESENT
```

The number is never removed to make room. The verdict is the colour of the square. That is progressive
precision as a *layout rule*, not a disclosure control: the person who reads only colour and the person who
reads only digits are reading the same 48 pixels.

**The Tafel has four sections, in this order, on every single Ding:**

```
Kopf        name, status, age
Körper      art-specific. THE ONLY PART THAT VARIES.
Handlungen  0–3 buttons
──────────
<Verbindungen>   present-tense relations, as Zeilen
Offen            open `zustand` Dinge touching this Ding (rendered only when non-empty)
Verlauf          time-ordered history, as Zeilen, cursor-paginated
Werte            the raw JSON + the GET URL that produced it, one copy button
```

The first header's *word* comes from the Subjekt's art. Same slot, same content, concrete German:

| Subjekt | header | | Subjekt | header |
| --- | --- | --- | --- | --- |
| `zelt` | **Im Zelt** | | `gabe` | **Ging an** |
| `pflanze` | **Steht in** | | `mensch` | **Macht mit** |
| `dose` | **Steckt in** | | `ziel` | **Gilt für** |
| `kamera` | **Sieht** | | `bild`/`film` | **Verbunden** |
| `phase` | **Betrifft** | | `notiz`/`zustand`/`ereignis` | **Betrifft** |

**Navigation grammar, complete:** tap a Zeile → it becomes the Subjekt. The previous Subjekt appears as a
Zeile in the new screen's first section. Back returns. That is one gesture and it is the only one.

## 4. NO-MODES MECHANISM

Three mechanisms, none of which is a mode with a new name.

### 4.1 Depth is subject-distance, not user identity

There is no expand control, no "mehr anzeigen", no remembered expansion state, no density preference. A
Ding is fully expanded when it is the Subjekt and one line when it is not. **You do not set depth; you
walk.** The stoner walks zero steps and sees four numbers, a picture and four buttons. The techie walks
four steps and is standing on a `ziel` Ding reading its change history. Both performed the identical
operation on the identical objects; neither was profiled, asked, or given a switch.

The critical property: **walking is reversible and stateless.** Nothing the techie does changes what the
stoner sees tomorrow, on the same account, on the same device, because expansion is not stored anywhere.
That is what a mode cannot promise. It is also what "adaptive ordering by behaviour" cannot promise, which
is why this concept does not use it — an impaired user needs the home screen to be in the same place at
2 a.m. that it was at noon.

### 4.2 `Werte` is at the bottom of every Tafel, for everybody

The last row of every Tafel — the tent, a photo, a socket, a feed — is:

```
Werte  {…}                                                              [⎘]
```

Tapped, it expands in place into the Ding's raw JSON, its resolved relations, and the literal request:

```
GET /api/things/8f3a…?device_id=sim-controller-4b2e
{"thing_id":"8f3a…","art":"gabe","t":1755892800000,
 "name":"Gabe","rel":{"an":["p_a1","p_a2"]},"akteur":"m_anna",
 "d":{"wasser_l":2,"produkte":[{"name":"Bio-Bloom","ml_pro_l":2}],"schema_id":"bb-allmix","schritt":7}}
```

This is not a developer mode. It is **the same row in the same position on every screen**, present for
every user from install, never hidden, never enabled, and it does not change any other pixel. The stoner
scrolls past it the way anyone scrolls past a page footer. The techie discovers the entire API by tapping
it once, because the URL shown is the URL that works.

Why this is the honest answer to "the techie wants density and precision": density is not a rendering
option in this product, it is a *destination*. And it is on every screen, so it is never somewhere else.

### 4.3 Capability and data decide what exists — never a preference

- **Capability, per role, not per bucket.** `Im Zelt` lists exactly the sockets `hardwareInfo.sockets`
  reports, via the existing `parseSocketRoles()`. A `ziel` Ding for humidity **is not created** unless a
  `dehumidifier` role is paired. This kills the live bug where `deviceControlCapability()`
  (`grow-presets.ts:143-173`) returns `'full'` for a heater-only tent and shows it humidity targets, a
  humidity-deviation warning and a dehumidifier alarm preset it can never act on. Missing key (old
  firmware) now fails **closed** to monitor-only, with one Zeile: `Gerät meldet keine Steckdosen — Firmware
  zu alt.`
- **Data.** No `pflanze` Dinge ⇒ the plant chooser never renders anywhere, and the word "Pflanze" appears
  in exactly one place in the whole product: the `+` on the `Im Zelt` header. No `mensch` Dinge beyond one
  ⇒ no `Wer?` row on capture sheets. No camera ⇒ no camera Körper, no `film` rows, no camera `zustand`.
- **Neither is reversible by the user through a setting**, which is precisely what makes them not modes.

| **Offline** (> 10 min) | header `● Offline · zuletzt gesehen Mi 14:02 (vor 3 Std)`; the four numbers keep their last values, greyed, each with its own age line. | **Keine Kamera gekoppelt** | no camera Körper, no camera Zeile in `Im Zelt` |

| **Neues Konto, nichts passiert** | `Verlauf` holds one Zeile, `◼ Gerät verbunden · vor 4 Min`, followed by one grey line: `Noch nichts passiert. Was du tust, steht hier.` No illustration, no onboarding card, no empty-state hero. |

## 6. The chart

The chart is the `Verlauf` list drawn on an axis instead of stacked. Same rows, same status colours, same
tap target. It is the one place where a different shape is justified, and it must earn it.

**Apache ECharts 6**, tree-shaken, hand-rolled ~50-line Angular directive (owner decision). `chart.js` /
`ng2-charts` / `chartjs-adapter-luxon` deleted from `charts.page.ts`, `charts.module.ts`, `diary.module.ts`,

- **Small multiples**, one measure per panel, 90–120 px, shared x, one linked crosshair
  (`grid[]` + `axisPointer.link` + `echarts.connect()`). Panels exist only for measures the device reports.
  At most two units per panel and only when physically coupled (Luft- + Blatttemperatur).
- **Goal vs actual, per panel, in one priority order, one at a time, labelled:**
  1. `markArea` — the user's own **alarm thresholds** (`Alarm.upperThreshold` / `lowerThreshold`, which the
     chart ignores today), hard edge;
  2. `markArea` — **Sollwert ± Toleranz** (soft, ±1,5 °C / ±7 % RH — the tolerances
     `grow-assistant-card` already uses);
  3. `markArea` — the phase's **VPD-Band** from `GROW_STAGE_PRESETS.vpdRange`, advisory, VPD panel only.
- **The setpoint is a dashed stepped `markLine`** that steps at `daynight.day` / `daynight.night` between
  `day.temperature` and `night.temperature`, with a **signed deviation fill** between actual and setpoint.
  Never `type:'area', threshold:null` — a fill to the axis encodes nothing.
- **Min/max envelope** on the primary measure (`aggregateWindow` already supports `min`/`max`; one extra
  query each). `sampling:'minmax'` for the plot — LTTB smooths away exactly the bang-bang oscillation the
  grower is looking for. LTTB for the navigator only.
- **Tag/Nacht** as `markArea` from measured `out_light > 0`, falling back to the `daynight` schedule, in an
  explicit device timezone. A missing band where the schedule says day is a **hole** — a failed contactor,
  read as a diagnostic rather than decoration.
- **Ausgänge** in a state-timeline lane. Region length = duration, null = gap. The `Entfeuchter` region
  carries a footnote on tap: `In den Betriebsarten „temp" und „breed" kühlt diese Dose, sie entfeuchtet
  nicht.` — the first time the product tells the truth about `out_dehumidifier`'s double meaning.
- **Annotation rail below the axis**, max two rows: row 1 what people did (`gabe`, `notiz`, `bild`,
  `phase`), row 2 what the machine did (`ereignis`, `ziel`-changes). Clustered into 10 px bins with count
  badges (`◼③`). Full-height dashed lines for `phase` starts. **Tapping a mark opens that Ding's Tafel** —
  the rail is literally Zeilen, positioned. No hover anywhere; there is no hover on a phone.
- **The scrubbing header replaces the tooltip.** Pinned above the panels: a 96 px camera thumbnail plus one
  compact line per panel. Dragging the crosshair moves the picture (`GET /image/:device_id?timestamp=`,
  which already exists, debounced 250 ms). **That is image correlation, on the chart, for free.**
- **Verdict strip** at the top: % time in band, longest excursion **as a duration**, day-vs-night split.
  **Computed server-side on RAW Influx samples, never on `aggregateWindow(fn:mean)`** — averaging destroys
  the excursions the metric exists to count and the error is invisible by eye. Greyed below 80 % coverage
  with `Datenabdeckung 62 % — Werte unsicher.`
- **Mobile rules:** one finger scrolls the page, two fingers pan/zoom (`dataZoom:'inside'`), tap or
  long-press sets the crosshair. Axis labels are never hidden — below 320 px drop to three ticks and move
  the unit into the panel title. Range presets stay the primary control at ≥ 44 px.
- **Before any of this:** fix the raw Flux interpolation of `measure`/`from`/`to`/`interval`
  (`data.service.ts:80-89`) and the `limit(n:50000)` that is piped after `yield()`. Constrain interval by
  timespan so `3y × 5s` is unreachable. Non-negotiable prerequisite.

## 7. Diary and multi-plant

**There is no diary feature.** The Zelt's `Verlauf` is the tent's diary; a `pflanze`'s `Verlauf` is that
plant's diary. Same Zeilen, same renderer. What the owner means by "it does the diary keeping for you" is
that `ereignis`, `bild`, `film`, `phase` and `ziel`-changes are written by the machine into the same list
the human writes into — so a user who logs nothing still opens a full diary.

New Dinge and their fields:

```
pflanze   d: { sorte, medium, topf_l, quelle:'samen'|'steckling'|'gekauft',
               keimung_t, ernte_t?, ernte_g?, entfernt_t? }
          name: "A3 · Wedding Cake"      // renaming NEVER changes thing_id — the round-one bug where
          rel: { in: [zelt] }            // renaming a lifecycleName forks the whole history is gone.

phase     d: { stufe: DiaryLifecycleStage }        t / t_end
          rel: { an: [pflanze…] }        // empty rel.an = the whole tent

gabe      d: { wasser_l, ec?, ph?, ec_ort?:'zulauf'|'ablauf'|'tank',
               produkte: [{ name, ml_pro_l }], schema_id?, schritt? }
          rel: { an: [pflanze…] }, akteur

notiz     d: { text }                     rel: { an: [...] }, bilder
zustand   d: { text }   t / t_end(null=offen), akteur, d.geschlossen_von
mensch    d: {}                           name only, device-scoped, no account
```

`DiaryLifecycleStage` is unchanged (`germination…curing`); **`ernte` is added as a seventh stage** — harvest
is not a stage today and "how did this grow do" is therefore unanswerable. That is a shared-types change,
optional field, read-time normaliser, no migration tool needed.

**How a plant-ignorer is untaxed.** `rel.an` is optional everywhere. Zero `pflanze` Dinge means: no plant
chooser in any sheet, no per-plant sections, no plant column in any list, and the string "Pflanze" appears
once — behind the `+` on `Im Zelt`. This is reveal-by-data, and it is not reversible by a setting, so it is
not a mode. A monitor-only user can run three years and never learn the product has plants.

| Repeat feed, one grower, schema selected | **2** — `Gabe`, `Eintragen` |
| Water only, no schema, no plants | **2** — volume prefilled from the last Gabe |
| Change volume by 1 L | 4 (`[+]` steps 0,5 L) |
| Feed a subset | 3 — `Alle 3` → tap the chip to drop → `Eintragen` |
| Club member, actor remembered in this browser | **2** |
| Club member, first time on this phone | 3 |
| Double-feed warning present | **+1, deliberate** |
| With EC and pH | +4 (two number pads) |

**Prefill order:** the selected Schema at its current step → the last `gabe` on this device → empty. Every
prefilled value is editable; the grower who deviates is the normal case.

**The double-feed soft block (the club critic's gap #1).** At the moment the sheet opens, query `gabe`
Dinge in the last 6 h whose `rel.an` intersects the current selection. If non-empty:
`⚠ Anna hat A1–A3 vor 1 Std 30 gefüttert.` and the primary button **relabels** to `Trotzdem eintragen`. It
never blocks; it costs one deliberate tap and it moves the button's text so muscle memory cannot fire it.
A double feed is the most expensive thing that happens in a shared room and this is ~40 lines.

**Offline capture in a cellar (gap #5).** The client mints `thing_id` (uuid v4) *before* the request. The
Zeile renders immediately with `⟳ nicht gesendet`. The server **upserts on `thing_id`**, so replaying the
queue is idempotent by construction — a retry can never double-log, which in a shared record is
indistinguishable from a real double feed. Requires `@angular/service-worker`: one new dependency, one
build change, ~1 day. If it slips, the same client-minted id retries in-memory for the session, which is
80 % of the value.

**Schema = Medium + Feed regime**, the way growers say it out loud. A Mongo content collection, never in
the bundle:

```
Schema { schema_id, label: "Biobizz All-Mix",
         medium: "All-Mix — stark vorgedüngt",
         start_ab_tag: 21,                       // ← "so don't feed yet"
         schritte: [{ ab_tag, phase, produkte:[{name, ml_pro_l}],
                      ec_ziel?, ph_ziel?, ec_basis:'absolut'|'plus_leitungswasser' }],
         quelle_url, geprueft_am }
```

Selected once, on the `Ziele` Tafel. The current step advances **by feed events (Schritt 7 von 14) with a
soft calendar mapping**, not by wall clock — growers feed Tuesday and Friday and slip. Before
`start_ab_tag` the sheet prefills **no products** and shows one line:

> `All-Mix ist vorgedüngt — bis Woche 3 nur gießen.`

That is the "it thinks for me" payoff and it is the only place in the design where the product refuses to
fill something in. Seed set: Biobizz Light-Mix, Biobizz All-Mix, Floragard Light, Green House Feeding
(Powder Feeding), BioTabs. Brand names as plain text labels only, no logos, no colours, never inside a
Terp Control feature name; each entry carries `quelle_url` + `geprueft_am`, surfaced as
`zuletzt geprüft 14.07.2026` — legal posture and a genuine trust feature in the same string. EC is stored
canonical; `ec_basis:'plus_leitungswasser'` renders as `EC-Ziel 1,4 + dein Leitungswasser` and never as a
bare ppm number.

**The cumulative question (gap #3)**, answered on the `pflanze` Tafel's Körper, where it is asked:

```
Bisher in dieser Blüte
  Wasser        18,5 L      über 11 Gaben
  Bio-Bloom     31 ml       zuletzt vor 2 Std
  Bio-Heaven    14 ml
  von           Anna 7 · Ben 3 · ich 1
```

Aggregation over `gabe` Dinge with this plant in `rel.an`; volume split evenly across the Gabe's plants.

## 9. Camera, timelapse and image correlation

Three things ship in v1. The correlation is free; the film is the work.

### 9.1 A photo is a Ding, so correlation is the default

```
┌ Bild · Di 12.08. 14:22 ────────────────────┐
│  [ full-bleed photo, swipe ← → in time ]   │
│                                            │
│  24,8 °C · 58 % · VPD 1,29 kPa · 412 ppm   │
│  Licht 100 % · Heizung aus · Blüte Tag 12  │
│                                            │
│  [ Im Chart zeigen ]        [ Teilen ]     │
├────────────────────────────────────────────┤
│ Verbunden                                  │
│ ◼ A1 · Gorilla Glue         Blüte Tag 12   │
│ ◼ Gabe · 2,0 L              vor 8 Min      │
├────────────────────────────────────────────┤
│ Werte  {…}                            [⎘]  │
└────────────────────────────────────────────┘
```

Numbers are resolved read-time from Influx at the frame's timestamp (nearest sample within ±60 s). No new
storage. Swiping left/right walks the camera roll and the numbers update under the thumb — that is
scrubbing, on a phone, without a chart. Because a `bild` is a Ding like any other, "picking a picture shows
its numbers" and "scrubbing the chart moves the picture" (§6) are the same mechanism seen from two ends.

### 9.2 Der Film — a video someone can actually hold

The pipeline extends the existing hourly `compressRtspStreams` job. **Everything below is buildable with
`sharp` and `ffmpeg`, both already dependencies of the server container** (`image.service.ts:28,502,567`).

1. **Goldenes Fenster.** Three candidate windows per day at lights-on +1 h / +4 h / +7 h, derived from the
   device's own `daynight` config or the measured `out_light` rise, each ±20 min wide. This single rule
   removes every lights-off frame, all magenta-LED-versus-daylight mixing and nearly all exposure flicker,
   because every keeper is taken at the same phase of the same photoperiod. **When the grower flips
   18/6 → 12/12 the windows move with the light** — and no competitor can do this, because none of them
   owns the light schedule.
2. **Mensch/Tür-Ausschluss.** Each candidate is compared to the previous keeper on a 32×18 downscale
   (`sharp().resize(32,18).raw()`), mean absolute block difference. `> 22 %` = a hand, an open door, a moved
   plant → reject, take the next candidate in the window. Additionally reject any frame within ±5 min of a
   human-authored `gabe`/`notiz`/`bild`, because somebody was demonstrably in the tent.
3. **Eingefrorene Kamera.** `< 0,4 %` difference → do not add the frame **and open a `zustand`**:
   `Kamera liefert seit Di 04:00 dasselbe Bild.` Also fires on no frames at all for 6 h:
   `Kamera meldet sich seit 6 Std nicht.` Both close automatically when frames resume; both push through
   the existing alarm notification path (`actionType:'info'` + the existing webhook machinery). **That is
   the camera alarm all ten round-one concepts omitted, and it is a standing condition rather than a new
   alarm type, so it also appears in `Offen` on the home screen above the fold.**
4. **Kamera bewegt.** Phase correlation on the same 32×18 downscale; a shift > 2 tiles opens
   `Kamera hat sich am 12.08. bewegt — der Film springt hier.` **v1 does not stabilise.** It tells you, and
   the `film` Tafel offers `[ Film ab hier neu bauen ]`. Announcing a defect is honest; it is not the same
   as fixing it.
5. **Normalisierung.** Per keeper, `sharp().stats()` → per-channel means → a grey-world gain triple, then
   overall luminance scaled toward the rolling median of the previous 7 keepers, **clamped to ±8 % change
   per keeper** so real change (a canopy filling the frame, a lamp dimmed) ramps instead of snapping.
   Applied with `.linear(a,b)`. Two `sharp` calls per keeper, ~200 keepers per run.
6. **Eingebrannte Bildunterschrift.** The existing `addOfflineOverlay` SVG-composite technique
   (`image.service.ts:127-158`, already unit-tested), repositioned to a bottom-left strip:
   `Blüte · Tag 12 · 12.08. 14:20 · 24,8 °C · 58 %`. Composited before encoding. This is what makes the
   file self-explanatory once it has left the product, and it reuses code that already exists.
7. **Encode.**
   ```
   ffmpeg -framerate 12 -f image2 -i %d.jpeg \
          -c:v libx264 -profile:v baseline -level 3.1 -pix_fmt yuv420p \
          -crf 23 -vf scale=1280:-2 -movflags +faststart out.mp4
   ```
   **Correction to today's pipeline, and it is the highest-value two lines in this document:**
   `convertRtspStreamImagesToVideo()` currently encodes **`libx265`** (`image.service.ts:581`). HEVC in mp4
   **does not play in Chrome or Firefox**. Today's timelapse is invisible to most customers who have one.
   v1 switches both the in-app and the exported encode to H.264 baseline + yuv420p.
8. **Budget.** 3 keepers/day × 70-day run = 210 frames = 17,5 s at 12 fps. A 12-week run ≈ 21 s. At
   1280×720 crf 23 that is roughly **4–7 MB** — under Discord's 10 MB free-tier limit and Telegram's 50 MB
   document limit, and sendable over mobile data.

### 9.3 How a video LEAVES the product

The `film` Tafel's primary button is `Video speichern`, a plain `<a download>` to:

```
GET /device/:device_id/film/:thing_id.mp4?token=<imageToken>
→ 200 video/mp4
  Content-Disposition: attachment;
    filename="terpcontrol-zelt-keller-bluete-2026-08-01_2026-10-12.mp4"
  Content-Length: 5210448
```

Filename shape: `terpcontrol-<slug(zeltname)>-<slug(phase|zeitraum)>-<von>_<bis>.mp4`, ASCII-slugged,
≤ 96 chars. `imageToken` is the existing 30-day URL-embeddable token, so a pasted link works in Telegram
and inside a share link.

**Honest platform caveat, stated in the UI rather than hidden:** iOS Safari ignores `download` on a
cross-origin URL. The button falls back to opening the video in a new tab with one line beneath it:
`Lange auf das Video tippen → „Video sichern".` Second path: `navigator.share({files:[File]})` where
supported (Android Chrome, iOS 15+), which lands the mp4 directly in WhatsApp, Telegram or the camera roll.
Feature-detected, falls back to the download.

**Which films exist:** one per `phase` Ding, one per calendar week, plus the existing rolling `1d`/`1w`/`1m`.
A `film` Ding appears as a Zeile in `Verlauf` the moment it finishes building — the timelapse **arrives in
the diary** instead of hiding behind the current interaction, which requires deselecting every measure and
turning auto-update off on the charts page.

**Later, not v1:** a sprite+index endpoint (`GET /device/:id/sprite?from&to&n=50`, 50 tiles at 256×144,
built with `sharp`) turning the chart's thumbnail into a full film strip that *is* an axis, with
`timestampEnd`-bearing mp4s drawn as brackets rather than points.

## 10. Clubs

**Attribution is a label; authorisation is a gate. v1 ships the label, honestly, and does not pretend it is
the gate.**

- A `mensch` Ding is device-scoped, has a name the owner types once, and **has no account**. Every capture
  writes `akteur`. This is ~2 days of work and it needs no change to `auth.middleware.ts`.
- The `Wer?` chip row appears **only when the device has ≥ 2 `mensch` Dinge** — a solo grower never sees it.
  Names are free text with the hint `Vorname oder Spitzname reicht`; we never ask for identity.
- The **double-feed soft block** (§8) is the safety feature that matters most in a shared room.
- **Standing conditions (gap #4).** `zustand` is the note pinned to the tent door: opened by anyone from the
  `Zettel` button, owned by whoever opened it, closed by anyone with `[ Erledigt ]` which stamps
  `d.geschlossen_von` + `t_end`. It is the second block on the home screen because an open fact outranks
  history.
- **Corrections, not edits.** Editing a `gabe` writes a new `gabe` with `storniert_von` pointing at the old
  one; the old Zeile renders struck through. The club gets a reconstructable history without cryptographic
  immutability, which would victimise the unregulated grower.
- **Not in v1: real memberships.** A second login writing to the same device is a membership collection +
  a rewrite of `auth.middleware.ts:172` and `:207` + loosening ~10 owner-scoped queries + an
  account-lookup-by-email endpoint that does not exist. Until then a club shares one login and the `mensch`
  picker is what makes that survivable. **The upgrade path is designed in:** `Thing.akteur` already points
  at a `mensch`; a later real account sets `mensch.d.user_id` and every historic row keeps resolving.

**Privacy posture — privacy-maximal by default, no jurisdiction question asked at install:**

- `pflanze.d.ernte_g` and plant counts are **never prompted**. The harvest sheet's weight field starts
  empty, labelled `optional`. No screen anywhere counts plants or sums grams unless the user typed them.
- No location, ever. No real-name enforcement. No analytics or ad SDK.
- **`Alles löschen`** on the Zelt Tafel deletes `things` + `DeviceLog` + `Image` for that device, for real,
  behind one confirm. This also fixes the live data-loss-shaped bug where `DELETE /device/logs/:device_id`
  removes nothing from the diary because `deleted` is a visibility flag, not a deletion
  (`device.service.ts:739`, `diary.page.ts:112`).
- A public diary URL is a share link, unlisted, with actor names replaced by `Mitglied 1..n` unless the
  owner opts in. **No community feed.** Not v1 in any case.
- Never a `KCanG-konform` badge. Terp Control does not become anyone's system of record for § 26, and
  stores no per-member dispensing data.

## 12. Per-user-type walkthrough

**1 · Lazy monitoring-only.** Opens the app, lands on the Zelt Tafel, reads four numbers with four ages and
stops. `Im Zelt` holds no Dosen (none paired), so no target the device cannot act on is anywhere in the
product — no humidity row, no dehumidifier alarm preset, no "Entfeuchter läuft dauerhaft" warning. Weeks
later he taps `Chart`, picks `30 Tage`, and gets the verdict strip: 88 % im Band, longest excursion
41 minutes. That is the first time this product has told him anything.

**2 · Same, but with a camera.** Identical screen plus a photo under the numbers with its own timestamp and
its own conditions. Every Monday a Zeile appears in `Verlauf`: `◼ Film · Blüte Woche 2 · 21 Sek`. He taps
it, taps `Video speichern`, and a captioned 5 MB H.264 file with a readable filename is in his downloads. If
the camera dies on day 3 of flower, `▲ Kamera meldet sich seit 6 Std nicht` is in `Offen` on the home
screen — not discovered three weeks later.

**3 · Controls certain aspects (CO₂ or heating).** `Im Zelt` lists exactly the sockets he owns.
`Ziel CO₂ 400 ppm` and `Ziel Tag Temperatur 25,0 °C` are Zeilen; `Ziel Feuchte` **does not exist** because
no `dehumidifier` role is paired. The chart draws bands only for the two measures he steers. He is never
nagged about the third.

**4 · Full tent.** The densest screen: seven or eight `Im Zelt` Zeilen, an output lane with three regions,
the Ausgänge footnote telling him that `Entfeuchter` cools in `temp`/`breed` mode. He edits targets by
tapping `Ziele` and walking to each one, where the change history is visible per target. **The honest
limit:** five socket roles exist in firmware and there is still no humidifier, no exhaust-fan role and no
"cool AND dehumidify". This concept surfaces that truth rather than papering over it, but it does not fix
it — that is firmware work.

**5 · Closed-loop DIY.** `Werte` is on every Tafel, showing the exact `GET` that produced the screen.
`GET /api/things?device_id=&art=gabe&von=&bis=&cursor=` is the documented public read API and it is
byte-for-byte what the webapp consumes, so it cannot rot. His own EC probe still cannot become an Influx
measure (`VALID_SENSORS` is hard-coded; no firmware change), but it enters as `gabe.d.ec` and appears on the
annotation rail. Outbound automation is the existing per-alarm webhook in v1; a `thing.created` webhook is
the obvious v1.1.

**6 · Grow club.** Two names typed once. Every Gabe carries `von Anna`. Feeding A1–A3 ninety minutes after
Anna did produces `⚠ Anna hat A1–A3 vor 1 Std 30 gefüttert` and a relabelled button. `A3 nicht gießen —
überwässert` sits in `Offen` on the home screen until someone taps `Erledigt`. Three months later the
`pflanze` Tafel answers "how much Bio-Bloom did A3 get, and from whom" in four lines. What they do not get
in v1 is separate logins — stated plainly, not implied.

**7 · Old device owner.** §11. Everything he has still works, reached one tap differently, plus notes,
photos, honest data ages and a chart with axis labels.

**Capability lenses.** *Stoner:* one screen, four buttons in fixed positions that never move, one gesture,
nothing collapsed to hunt for, and the number always next to the colour. *Normal:* a camera card, a weekly
film that arrives on its own, and a chart that says whether the tent was OK rather than showing fifteen
translucent areas. *Techie:* the last row of every screen, and one API that the product itself is built on.

## 14. Honest weaknesses

1. **The abstraction risk never goes away.** Every future feature request will arrive as "add a new art",
   and adding arts is exactly how this becomes the database browser the brief warns about. The guard is a
   rule — a new art needs a concrete German noun a grower says out loud *and* a bespoke Körper — and rules
   erode under deadline. Five years from now this is either the cleanest product in the market or it has
   twenty-eight arts and a filter panel.
2. **Uniformity flattens importance.** `◼ Heizung aus` and `▲ Feuchte 40 Min über 65 %` are the same 48
   pixels in the same list. All the ranking is carried by one status square and the `Offen` section, and
   that is thin. C33's ranked density is straightforwardly better at this, and I am worse at it *by
   construction*, not by oversight.
3. **Deep walks are slower than forms.** Changing the night temperature is Zelt → `Ziele` → the Zeile →
   edit: three taps where today's settings form is two. My mitigation — the `Ziele` Tafel renders all
   targets as inline `value-edit-row`s so a batch edit is one screen — is a partial climb-down toward a
   settings page, and a critic will correctly call it that.
4. **`Werte` is a wart for most users.** It is one row saying `{…}` at the bottom of every screen and it
   will be tapped by confused people. I accept it because the alternative — hiding it behind a preference —
   is precisely the banned pattern, and because a techie payoff that lives somewhere else is a techie payoff
   nobody finds.
5. **The read-time adapters are a performance liability, and the blast radius is total.** One `GET /things`
   over a 12-week run touches `things`, `DeviceLog`, `Image` metadata and Influx. There is only one screen,
   so if that request is slow the entire product is slow. It needs cursor pagination and a per-request
   Influx budget from day one, and there is no second screen to fall back on.
6. **Renaming is safe; merging is not.** `thing_id` survives renames — a real improvement over today, where
   renaming a `lifecycleName` forks the history. But two club members logging `A3` and `A 3`, or `Anna` and
   `anna`, create two Dinge and there is no merge tool in v1.
7. **The camera pipeline assumes a fixed camera and a stable photoperiod.** An autoflower under 20/4, a
   clamp camera knocked weekly, or a moved tent produces a film with jumps that I detect and announce but do
   not fix. Announcing a defect honestly is not the same as a good film, and the owner is selling the film.
8. **Three keepers a day is a taste decision I cannot defend with data.** Twenty-one seconds may be too
   short to feel like a product and too long to watch twice. Tuning it needs one real ten-week run and there
   is not time for one before October.
9. **No firmware change means the tent is still not expressible.** Humidity can only go down;
   `out_dehumidifier` still doubles as the cooler; there is no humidifier, exhaust-fan or pump role. My
   design *names* that ambiguity on screen for the first time, which is progress in honesty and zero
   progress in capability. Type 4 remains the type the marketing promise is written for and the firmware
   cannot serve.
10. **One route means one component, and one component means a monolith.** The browser Tafel will be the
    new `charts.page.ts` — the thing everybody edits and nobody refactors — unless the art-specific Körper
    are separate declared components from the first commit. That discipline is a plan, not a guarantee.
