# C32 — "Was du hast"

**Family:** unify · **Centre of gravity:** capability is the only filter

---

## 1. Thesis

**The whole app is generated from the device's own capability report: every card, target, alarm,
chart panel and menu item exists only because the hardware said it exists — so a heater-only tent
has no humidity target anywhere in the product, and nobody ever chose a mode to get there.**

Terp Control today ships one interface and then argues with itself about which parts of it apply.
`deviceControlCapability()` collapses per-role truth into three buckets, and when the truth is
missing it **fails open to `'full'`** (`webapp/src/app/util/grow-presets.ts:158-173`) — so a tent
with one heater socket is shown a humidity target it cannot reach, a `humidity_low` alarm preset for
humidity it can only ever lower, and a "Entfeuchter läuft ununterbrochen" alarm on a socket that
does not exist (`webapp/src/app/util/alarm-presets.ts:64-105`).

C32 inverts that. The device already publishes a complete, verifiable capability manifest over MQTT —
`sockets`, `socket_ips`, `co2`, `leaf_temp`, `ppfd`, `webcam_did`, `firmware_version`
(`firmware/src/wifi.cpp:1751`, `firmware/src_hwtype/controller/controller.cpp:784-800`,
`firmware/src/fridgecloud.cpp:164-165`). Nine keys, all already flowing into `Device.hardwareInfo`
(`server/src/services/device.service.ts:592-606`). C32 makes that manifest the **only** input to
what the UI renders. Nothing is hidden, because nothing that does not apply is ever built.

This solves the audience problem sideways. The monitoring-only user and the twelve-socket techie do
not open the same app — not because either picked a persona, but because their rooms are different
and the product finally admits it.

**Das Gesetz** — four rules, applied everywhere, no exceptions:

1. **Kein Regler ohne Gerät.** No control without hardware that can act.
2. **Kein Ziel ohne Regler.** No target for a quantity nothing can move.
3. **Kein Alarm ohne Messwert.** No alarm on a sensor that is not fitted.
4. **Kein Messwert ohne Alter.** No number without the age of the number.

## 2. Information architecture

Seven routes. Four of them are generated; three are unchanged from today.

| Route | Name | What it is |
| --- | --- | --- |
| `/device/:id` | **Zuhause** | The generated home. One card per capability. |
| `/device/:id/ding/:cap_id` | **Ein Ding** | One capability, all the way down. |
| `/device/:id/verlauf` | **Verlauf** | The chart. Panels generated from the manifest. Replaces `/charts`, keeps the query-param contract. |
| `/device/:id/buch` | **Buch** | The diary. Replaces `/diary`, keeps the report switcher. |
| `/device/:id/buch/pflanze/:plant_id` | **Eine Pflanze** | Only reachable when ≥ 1 `Plant` exists. |
| `/device/:id/film` | **Film** | Camera, stills, timelapse, export. **Only routed when a camera capability exists.** |
| `/device/:id/anlage` | **Deine Anlage** | The manifest itself, human-readable and correctable. |
| `/device/:id/testmode`, `/list`, `/shares`, `/account` | | unchanged |

**Navigation model.** The `ion-split-pane` + `ion-menu` shell stays for account-level things
(Geräte, Geteilte Links, Konto, Abmelden). Inside a device, an `ion-tab-bar` at the bottom whose
**items are generated from the manifest**:

```
 ┌────────┬────────┬────────┬────────┐
 │ Zuhause│ Verlauf│  Buch  │  Film  │   ← "Film" present only if hardwareInfo.webcam_did ∉ {absent,'none'}
 └────────┴────────┴────────┴────────┘
```

A monitoring-only user without a camera gets a **three-item** bar. Nobody configured that. The
tab bar is the first place the thesis is visible, and it is visible before you read a word.

`Deine Anlage` is reached from the home header (the device name is a button), not from the bar. It
is a place you go twice a year.

**What is deleted:** the six outline buttons on the device overview, the Simple/Expert
`ion-segment`, `localStorage['app-settings-expert']`, and the workmode dropdown (see §4).

### 3.2 Card generation and order

One card per manifest entry, in a **fixed** order: senses `[temperature, humidity, vpd, co2,
leaf_temperature, ppfd, dli]`, then acts `[light, heater, dehumidifier, co2, secondary_light]`, then
camera, then Buch. Only one thing overrides it: a card that is **rufend** (alarm triggered, output
stuck on > 30 min, camera silent > 6 h, sensor expected but absent) floats to position 1 with a red
left border. Nothing else ever moves.

**Adaptive-by-behaviour ordering is deliberately rejected.** The brief allows it and warns it hurts
the impaired user. It does. At 2 a.m. the value of this screen is that the third card is always the
third card; muscle memory is the accessibility feature. Ranked density in C32 comes from *what you
own*, which changes twice a year — not *what you tapped*, which changes hourly.

### 3.3 Capability-honest copy — the signature detail

Terp Control can lower humidity and can never raise it: five socket roles exist and none of them is a
humidifier (`firmware/src/wifi.cpp:1694-1704`). A humidity **target** is therefore a lie on every
device this company sells. C32 writes what the hardware can do:

| Manifest state | Line 2, Luftfeuchte |
| --- | --- |
| dehumidifier socket, workmode small/dry | `Obergrenze 60 % · 2 % Luft nach oben` |
| the same socket bound to a cooler (workmode temp/breed) | `Wird nicht geregelt — der Sockel kühlt gerade.` |
| no dehumidifier socket | `Wird nur gemessen. Du hast nichts, was Feuchte senkt.` |

| Manifest state | Line 2, Temperatur |
| --- | --- |
| heater only | `Mindestens 25,0 °C. Nach oben regelt nichts.` |
| cooler only | `Höchstens 25,0 °C. Nach unten regelt nichts.` |
| neither | `Wird nur gemessen.` |

Not a warning banner bolted on — it is the only sentence that card has ever had.

### 3.4 Stale, offline, absent

Rule 4 of Das Gesetz, rendered literally, on every value in the product:

| State | Definition | Rendering |
| --- | --- | --- |
| **frisch** | age < 5 min | Value full weight, `vor 40 Sek` in `--tc-text-info`. |
| **alt** | 5–10 min | Value in `step-500` grey, no strike-through, `Letzter Wert vor 7 Min` in `--tc-text-warning`. Line 2 stays — the goal is still true. |
| **offline** | age ≥ `ONLINE_TIMEOUT` (10 min) | Header: `Offline seit 14:20 · seit 3 Std 40`. All cards grey. Values stay readable — hiding the last number is the most-complained-about behaviour in the competitor reviews. Actuators read `Zustand unbekannt, seit 3 Std 40`, never `AUS`. |
| **nie** | capability present, no sample ever | `—` and `Noch kein Wert. Das Gerät hat sich mit diesem Sensor noch nie gemeldet.` |

Derived values (VPD, DLI, Taupunkt) carry `berechnet` and inherit the **worst** freshness of their
inputs: a VPD from a 9-minute-old humidity reading says `aus Werten von vor 9 Min`.

Offline copy, verbatim: *"**Zelt 1 ist offline.** Seit 14:20 (vor 3 Std 40). Die letzten Werte stehen
unten, sie sind von 14:20. Was der Controller seitdem gemacht hat, weiß die Cloud nicht."*

## 4. NO-MODES MECHANISM

Two mechanisms, stacked. They do different jobs and I will not pretend one does both.

### 4.1 Mechanism A — Generation by capability (separates the seven types)

The manifest is computed server-side, cached on `Device`, recomputed on every `hardware-info` MQTT
line, and served alongside the device payload:

```ts
// GET /device/:device_id/capabilities
interface CapabilityManifest {
  device_id: string;
  source: 'device' | 'device+override' | 'static' | 'unknown';
  reported_at: number;              // when hardwareInfo.sockets last changed
  firmware_version?: string;
  senses: Array<{ id: SenseId; origin: 'builtin'|'hw'|'derived'; from?: SenseId[] }>;
  acts:  Array<{ id: ActId; origin: 'builtin'|'socket'|'override'; ip?: string;
                 appliance?: 'dehumidifier'|'cooler' }>;
  sees:  Array<{ id: 'camera'; did: string }>;
  unknown: ActId[];                 // non-empty only when hardwareInfo.sockets is absent
}
```

Everything downstream is a projection of it: home cards, tab-bar items, chart panels, alarm presets
(`availableAlarmPresets` takes the manifest instead of `{hasCo2}`), settings rows, the notification
catalogue, export columns.

**The workmode dropdown is deleted.** This is the sharpest consequence and the riskiest. Today the
user picks `small | temp | dry | breed | off`, and that choice silently decides whether the
`dehumidifier` socket *is* a dehumidifier or an air conditioner
(`firmware/src_hwtype/controller/controller.cpp:815-865`: `MODE_SMALL` calls `controlDehumidifier()`,
`MODE_TEMP` calls `controlCooling()` on the same output). A mode that changes what your hardware *is*
is the worst mode in the product.

C32 replaces it with **one hardware question, asked once, at socket pairing**:

> **Was hängt an diesem Sockel?**
> ( ) Luftentfeuchter — zieht Feuchte raus
> ( ) Kühlung / Klimagerät — macht kälter

Stored as `SocketBinding { device_id, role, appliance, set_by, set_at }`. Workmode is then derived:
`stage = drying → 'dry'`; else `appliance='cooler' → 'temp'`; else `appliance='dehumidifier' →
'small'`; no light and no dehumidifier → `'breed'`; tent paused → `'off'`. Existing devices are
migrated by reading their current `workmode` once and seeding `appliance` from it (`temp`/`breed` →
cooler, `small`/`dry` → dehumidifier). Nobody is asked anything.

This is not a mode under a new name because **there is no chooser and no persona** — there is a fact
about a physical object in a room, and one place to correct it.

### 4.2 Mechanism B — Depth inside one card (separates stoner from techie)

Mechanism A cannot separate the stoned user from the techie, because they own the same tent. This
does, and it is the harder half.

**Every value in C32 is rendered as three tiers, all on screen at once, in reading order.**

```
Temperatur                          24,6 °C     ← Tier 1  32 px / 600  URTEIL + ZAHL
Passt. Ziel 25,0 · seit 4 Std im Rahmen         ← Tier 2  15 px / 400  ZIEL + LAGE
▁▂▃▄▅▄▃▂▁▂▃▄▅▆▅▄▃▂▁▂▃                vor 40 Sek ← Tier 3  12 px / 400  VERLAUF + ALTER
```

The typographic ratio does the filtering, not a toggle. The impaired user's eye lands on 32 px and
leaves. The techie reads down. **Nothing is collapsed, nothing has a chevron, no "Mehr anzeigen"
exists anywhere in the product.**

Tapping the card opens `/ding/temperature`, which begins with **the same three lines, pinned**, and
then continues downward:

```

                                      vor 40 Sek
```

**"Expert" is a scroll position.** That is the whole answer. A drilldown is *more of the same thing*,
never a different rendering of it. The stoner and the techie use identical controls
(`value-edit-row`: tap the number to reveal `[−] slider [+]`, already ARIA-annotated, already
scroll-protected by `rangeGuard`). One taps `+` four times. The other taps the number and types.

**Applied to writing, too** (§7): the capture sheet is one sheet. The stoner taps twice and never
scrolls. The club scrolls to EC, pH, runoff and per-plant volumes. Same sheet, same route, same
saved object.

### 4.3 What C32 refuses

No `Einfach / Experte` segment (`localStorage['app-settings-expert']` is read once at migration, then
deleted). No "Erweitert" accordion — no `<ion-accordion>` in any new surface. No onboarding question
about the *user*; the wizard asks about the *room*. No `Fokus`, `Ruhe`, `Pro`, `Lite`, `Kompakt`.
Density is not a preference — it is `manifest.senses.length + manifest.acts.length`.

## 5. The chart — "Verlauf"

Apache ECharts 6, tree-shaken, hand-rolled ~50-line Angular directive (owner decision). Chart.js and
`ng2-charts` deleted.

**The panel set is generated from the manifest.** Nobody picks measures on first open. One panel per
sense you have, ~110 px each, shared x-axis, one linked crosshair via `axisPointer.link`. Two panels
for a monitoring device; six for a full tent. The measure picker still exists — it is *addition*,
not *configuration*, and the URL query-param contract (`measures`, `date`, `dateEnd`, `interval`,
`timespan`, `logs`, `share`) is preserved verbatim so existing `ChartPreset` rows and `ShareLink`
queries keep working.

**Goal vs actual — and the capability twist.** The setpoint is a **dashed stepped `markLine`** that
steps at `daynight.day` / `daynight.night` between `day.temperature` and `night.temperature`. The
band behind it is a `markArea`. But the *shape of the band is a capability question*:

- heater only → the band has a **floor and no ceiling**. It is drawn open at the top and labelled
  `Untergrenze 25,0`. There is no "too warm" region, because "too warm" is not a failure of a machine
  that cannot cool — it is weather.
- cooler only → floor open, ceiling drawn, labelled `Obergrenze`.
- dehumidifier → the humidity panel is always one-sided (open downward). Forever, on all hardware.
- monitor-only → **no band at all**, and the panel title reads `Temperatur (nur gemessen)`. The
  advisory stage VPD range is still drawn on the VPD panel, in grey, labelled `Empfehlung`, because
  advice is not a claim of control.

No other concept in this bake-off will draw a one-sided target band, and it falls straight out of
the thesis.

**Band source priority**, one at a time, always labelled: alarm thresholds (hard, the user's own
declared line) > setpoint ± tolerance (soft) > stage VPD window (advisory grey).

**Day/night** from measured `out_light > 0` where a light capability exists, otherwise from the
`daynight` schedule, with a legend saying which (`Tag/Nacht aus dem Licht gemessen` vs `aus dem
Plan`), rendered in the device's timezone so a 12/12 flip near a DST boundary does not drift. A
failed contactor then shows as a **missing band** — a diagnosis, not decoration.

**Outputs** are a state-timeline lane per actuator you own: region length = duration, `null` = gap.
Not 0/1 lines fighting the value axis. **Annotations** are a 20 px rail under the x-axis, max two
rows (human notes / device events), clustered at 10 px bins with count badges, reusing
`collectLogCategories` for the filter chips, with full-height dashed lines for stage changes. Tap,
not hover.

**Verdict card** above the chart, computed **server-side on raw Influx samples**, never on
`aggregateWindow(mean)` output:

```
Letzte 24 Std · Temperatur
Im Rahmen 22 Std 40 (94 %) · Zu warm 1 Std 05 · Zu kalt 15 Min
Längste Ausreißer-Strecke 38 Min, gestern 15:10
Datenabdeckung 99 %
```

Below 80 % coverage the card greys out and says `Zu wenig Daten für ein Urteil.`

**Fix required first:** `from`, `to`, `interval` and `measure` are interpolated raw into Flux
(`server/src/services/data.service.ts:80-89`) and the `limit(n:50000)` guard is piped after `yield()`.
Because C32 generates the measure list from a manifest rather than a fixed component array, this must
be allowlisted from the manifest before anything ships. It is in v1 scope.

**Mobile:** one finger scrolls the page, two fingers pan/zoom (`dataZoom: inside`), tap/long-press
moves the crosshair, axis labels are never hidden — reduced to three ticks with the unit in the panel
title. `sampling:'minmax'` on the plot (LTTB smooths away exactly the bang-bang oscillation a grower
is looking for), LTTB on the navigator.

## 6. The diary and multi-plant — "Buch"

Two new Mongo collections. `DeviceLog` stays exactly as it is for **device-authored** events (boot,
MQTT errors, alarm transitions, recipe steps). User-authored entries move to `Note`. The read path
is a union for one release; a one-shot idempotent backfill converts `categories[0] === 'diary'` rows.

```ts
interface Plant {
  plant_id: string;  device_id: string;
  label: string;                 // "A1" — what is written on the pot
  name?: string;                 // "Gorilla Glue #4"
  source?: 'seed' | 'clone' | 'unknown';
  started_at: number;
  stage?: DiaryLifecycleStage;   // per plant, not per device
  scheme_id?: string;            // -> GrowScheme (§7)
  position?: string;             // "hinten links"
  archived_at?: number;
  created_by?: string;           // actor_id
}

interface Note {
  note_id: string;               // CLIENT-generated UUIDv4 at the moment of capture — idempotency key
  device_id: string;
  kind: 'giessen' | 'duengen' | 'messung' | 'notiz' | 'schnitt' | 'stufe' | 'ernte' | 'zustand';
  at: number;  created_at: number;
  actor_id?: string;             // §9
  plant_ids: string[];           // [] = the whole tent
  water_ml?: number;
  scheme_id?: string;  step_index?: number;
  products?: Array<{ name: string; ml_per_l?: number; ml_total?: number }>;
  ec?: number;  ph?: number;  ec_runoff?: number;  ph_runoff?: number;
  temp_c?: number;  ppfd?: number;  distance_cm?: number;   // the old diary-measurement fields
  wet_g?: number;  dry_g?: number;   // kind 'ernte' only, NEVER prompted (§9 privacy)
  text?: string;
  image_ids: string[];
  frame_at?: number;             // reference to the camera still at capture time (§8f)
  supersedes_note_id?: string;   // corrections are new rows, not edits
  deleted_at?: number;           // and this one actually means deleted
}

interface Condition {            // the standing fact nobody had a place for
  condition_id: string; device_id: string;
  text: string; plant_ids: string[];
  opened_by?: string; opened_at: number;
  closed_by?: string; closed_at?: number;
}
```

### How a user who ignores plants is untaxed

Reveal by data, exactly:

| `Plant` count | What appears |
| --- | --- |
| **0** | Nothing. No plant picker, no plant column, no `/pflanze` route, no "Pflanze anlegen" nag. Every `Note` is device-scoped with `plant_ids: []`. The Buch is a flat time list — which is what it is today, only with watering and feeding in it. |
| **1** | Still no picker. Notes auto-attach `plant_ids: [that one]`. The plant's name appears as a subtitle on the Buch header and nowhere else. |
| **≥ 2** | The picker appears in the capture sheet, pre-selected to **all**, as chips: `[A1] [A2] [A3] [A4]` — tap to deselect. The Buch gains a plant filter row. `/pflanze/:id` becomes reachable. |

Plants are created from exactly one place: `Buch → Pflanzen → + Pflanze`. Nothing ever creates one
implicitly. A user who never taps it never learns the feature exists, and loses nothing.

**"It does the diary keeping for you"** — the diary is not empty even if you never write in it. Every
day the cloud writes exactly one **Tageszeile** per device: `Tag 61 · 26,4/20,1 °C · 58 % · 12 Std
Licht · 3 Ausreißer`. That row is generated, not typed, it is what makes the Buch worth opening on
day one, and it is generated from the manifest — a monitoring device's Tageszeile has three fields,
a full tent's has seven.

## 7. Watering & fertilising — capture with tap counts

No irrigation or dosing hardware exists. This is capture-and-recall, and the only metric that matters
is taps-to-recorded, in a dark tent, one-handed.

### 7.1 The flow and the tap counts

`✚ Notieren` (sticky, 56 px, thumb-reachable) opens a sheet whose **buttons are generated** from the
manifest and the data: `💧 Gegossen` · `🧪 Gedüngt` · `📷 Foto` · `✎ Notiz` · `✂ Geschnitten` ·
`⚠ Zustand`, plus `🌡 CO2 gefüllt` only when the manifest carries the `co2` sense.

| Action | Taps | What happens |
| --- | --- | --- |
| Gegossen, same as last time | **2** | `Notieren` → `Gegossen`. Saved, prefilled from the last `giessen` note (volume, plants). |
| Gedüngt, following the scheme | **2** | `Notieren` → `Gedüngt`. Saved with the scheme's current step prefilled. |
| Gegossen, different volume | **4** | …→ undo bar's `Ändern` → `[−][+]` → fertig. |
| Gegossen, only A3 | **3** | `Notieren` → deselect chips → `Gegossen`. |
| Gedüngt with EC/pH (club) | **2 + scroll + 2 fields** | Same sheet, scrolled. |
| Standing condition | **3** | `Notieren` → `Zustand` → tippen → `Offen lassen`. |

The 2-tap saves are **immediate writes** with an 8-second undo bar, never a confirm dialog:

```
┌──────────────────────────────────────────────────┐
│ Gegossen · 1,5 L · alle 4 Pflanzen               │
│                        Rückgängig    Ändern      │
└──────────────────────────────────────────────────┘
```

`Ändern` reopens the full sheet with the saved note loaded. Mechanism B on the write side: the casual
flow terminates at tap 2, the detailed user continues into the same object.

```
┌─────────────────────────────────────────────┐
│ Gedüngt                          21:14  ▾   │
│ Pflanzen  [A1]✓ [A2]✓ [A3]✓ [A4]✓           │
│ ─────────────────────────────────────────── │
│ Nach Plan: BioBizz All-Mix · Woche 5        │
│   Bio-Grow    2 ml/L      [ − ] 3,0 ml [ + ]│
│   Bio-Heaven  2 ml/L      [ − ] 3,0 ml [ + ]│
│   Menge                   [ − ] 1,5 L  [ + ]│
│ ─────────────────────────────────────────── │
│ Optional                                    │
│   EC [      ]  pH [      ]                  │
│   EC Ablauf [   ]  pH Ablauf [   ]  Foto [+]│
│ ─────────────────────────────────────────── │
│              [   Speichern   ]              │
└─────────────────────────────────────────────┘
```

Every prefilled number stays editable. Deviating is the normal case, not the error case.

### 7.2 The scheme — medium + feed regime

```ts
interface GrowScheme {
  scheme_id: string;
  label: string;                       // "BioBizz All-Mix" — how the grower says it out loud
  medium: { label: string; prefertilised: 'none' | 'light' | 'heavy' };
  regime: 'liquid' | 'tabs' | 'none';
  steps: Array<{ from_week: number; to_week: number; stage?: DiaryLifecycleStage;
                 products: Array<{ name: string; ml_per_l: [number, number] }>;
                 hint_key?: string }>;   // i18n key — never brand prose
  ec_basis: 'absolute' | 'delta_over_source';
  source_url: string; retrieved_at: number; chart_version: string;
  kind: 'official_pdf' | 'official_calculator' | 'ownerless';
}
```

A MongoDB content collection, never in the webapp bundle, so any brand goes away in one DB update.
Brand names are plain text labels — no logos, no colours, no bottle imagery, never inside a feature
name. Each scheme card shows `Zuletzt geprüft: 12.06.2026`: legal posture and trust feature at once.

**All-Mix must be expressible or the model is wrong.** `prefertilised:'heavy'` means the early steps
carry no products and a hint: *"All-Mix ist vorgedüngt. Diese Woche nichts geben. Erst ab Woche 4
füttern — zu früh düngen verbrennt."* The `Gedüngt` button is **not** removed (that would be a mode);
it carries the hint at the top of the sheet and prefills nothing. **BioTabs** is `regime:'tabs'`: the
schedule is a re-tab reminder every 4-6 weeks and no `ml/L` appears anywhere in it.

**Which step you are on is computed, and capability decides how.** With a light capability, the
18/6 → 12/12 flip is detected from `out_light` history (photoperiod dropping > 3 h and holding three
days) and bloom weeks count from the flip: `Blüte Woche 5 (Umstellung erkannt am 04.08.)`. Without
one (monitor-only, plug, fan), weeks count from `Plant.started_at` and the UI says so:
`Blüte Woche 5 (nach Kalender — dein Gerät sieht das Licht nicht)`. No bottle brand's calculator can
do the first, and it is the one thing a controller uniquely owns here.

**The reminder** is one notification per device per day, never per plant: *"Zelt 1 — Düngen fällig.
Nach Plan (BioBizz All-Mix, Woche 5) seit 2 Tagen. Zuletzt am 08.09. von Timo."* Snooze 1 Tag / 3
Tage / Plan pausieren.

### 7.3 Double feed, and capture in a cellar

Before writing a `duengen` note the client checks for a note of the same kind touching any of the
same `plant_ids` inside a window (`duengen` 6 h, `giessen` 4 h). If one exists **from a different
`actor_id`**:

```
┌──────────────────────────────────────────────────┐
│ ⚠ Anna hat A1–A3 vor 1 Std 30 gedüngt.           │
│   Bio-Grow 2 ml/L, 1,5 L.                        │
│   [ Doch eintragen ]        [ Abbrechen ]        │
└──────────────────────────────────────────────────┘
```

One deliberate extra tap, and `Doch eintragen` is the narrower button. A repeat from the **same**
actor inside 20 min is a correction instead: `Letzten Eintrag ändern statt neu anlegen?`

**Offline.** `@angular/service-worker` is added (a real new dependency, costed in §12); the outbox is
IndexedDB. **The double-log problem is solved by construction:** `note_id` is a UUIDv4 generated on
the phone at the moment of the tap and the server route upserts on it, so replaying the queue three
times writes one row. The double-feed check also runs locally against the outbox, so a cellar double
feed is caught before it is ever sent.

### 7.4 The cumulative question

On `/buch/pflanze/A3`, one generated block above the timeline — a single aggregation over `Note`
filtered by `plant_ids ∋ A3` and `at ≥ Plant.started_at`:

```
A3 · Gorilla Glue #4 · Tag 61 · Blüte Woche 5
──────────────────────────────────────────────
Diesen Lauf:  14× gegossen (21,4 L) · 6× gedüngt
              Bio-Grow gesamt 42 ml · Bio-Heaven 42 ml
```

## 8. Camera, timelapse and image correlation

The camera is the second screen in the tab bar for anyone who owns one, and it produces a file a
person can hold. This is the section where round one failed and where C32 spends the most of its
budget after the chart.

### 8.1 What is broken today (verified, not assumed)

| Fact | Source |
| --- | --- |
| Timelapses are encoded **`libx265`, crf 30** | `server/src/services/image.service.ts:578-582` |
| → H.265 in MP4 **does not play in Chrome, Firefox, or most Android browsers.** A large share of users cannot watch the videos the product already builds. | — |
| Only three durations exist: `1d`, `1w`, `1m`, each on **epoch-aligned rolling windows** unrelated to a grow | `image.service.ts:296-298` |
| Every timelapse is 720 frames at 25 fps ≈ **29 s**, whatever the span | `TIMELAPSE_DAY_FRAMEINTERVAL_MS`, `TIMELAPSE_FRAME_RATE` |
| **No frame culling, no exposure or white-balance normalisation, no deduplication, no stabilisation** — every dark frame, every open door, every hand in shot goes in | `compressRtspStreamRange` |
| **No download path.** No `Content-Disposition` anywhere in the codebase | `image.controller.ts` |
| **No camera alarm** of any kind | `alarm-presets.ts` |
| `sharp` is already a dependency, `ffmpeg` already shells out, `?width=` resize already works | `image.service.ts:28,151`, `image.controller.ts:176-190` |

The last row is why this is affordable: the pipeline exists, it is just not making a watchable film.

### 8.2 v1 — "Der Film"

**a) Codec fix.** `-vcodec libx264 -profile:v high -pix_fmt yuv420p -movflags +faststart -crf 26`,
`-vf scale='min(1280,iw)':-2`. One argument list in `convertRtspStreamImagesToVideo()`. Existing
`1d`/`1w`/`1m` timelapses keep working and become playable everywhere. This is a half-day and it is
the single highest-value camera change in the document.

**b) Frame culling — four filters, in order, at build time.** All operate on a 32×32 grayscale
thumbnail via `sharp().resize(32,32).greyscale().raw()`, ~1 ms per frame:

1. **Dunkelfilter.** Mean luma < 12 → drop. The film shows the day. A 12/12 tent's night is 12 hours
   of black and nobody wants it. Stated in the UI: `Der Film zeigt nur die Lichtstunden.`
2. **Türfilter.** Mean luma more than 45 % away from the median of the 5 neighbouring kept frames →
   drop (door open, room light on, IR flip). **And**: L1 distance of the thumbnail to the previous
   kept frame > 35 % of full scale → drop. A plant does not change 35 % of its pixels in two minutes;
   a person walking through does.
3. **Dublettenfilter.** L1 distance to the previous kept frame < 1.5 % → drop. Kills stalled cameras
   and lights-off runs.
4. **Schärfefilter.** Variance-of-Laplacian on a 128×128 luma crop, below the camera's rolling
   20th percentile → drop. Condensation, refocus hunting, a fogged lens after watering.

**Floor rule:** if culling would leave fewer than 200 frames, thresholds relax by 50 % and the film is
labelled `Weniger Bilder als sonst — die Kamera hatte einen schlechten Zeitraum.` The product never
returns a 4-second film silently.

**c) Normalisation across 12 weeks.** Two `sharp` operations per kept frame, no new dependency.
*Weißabgleich:* grey-world gains per channel, **clamped to the rolling 24-frame median gain ±15 %** —
the clamp is what stops magenta-LED-versus-daylight flicker; unclamped per-frame grey-world is worse
than doing nothing. *Belichtung:* linear stretch to a target mean luma of 110, gain capped at ±25 %.

**d) No stabilisation in v1 — but a nudge detector.** If the thumbnail's distance to the 24 h median
exceeds a threshold **and stays there for 6 h**, the cloud opens a `Condition` automatically:
*"**Kamera hat sich bewegt.** Am 12.09. gegen 14:00. Der Film springt an der Stelle. Richte sie
wieder aus, dann passt der Rest. `[Erledigt]`"* Cheap, honest, and it turns an invisibly ruined
timelapse into a 30-second fix. `vidstab` two-pass is v1.1.

**e) The Film itself** — a fourth `Image.duration` value: **`'run'`**. Built nightly per device with
at least one non-archived `Plant`, spanning `min(Plant.started_at)` → now (with zero plants, the last
90 days). Frame budget **1500 frames at 25 fps = 60 s**, sampled evenly across the span *after*
culling — a 12-week grow holds roughly 2000 frames once the existing thinning tiers have run, so this
is a real even sample and not a truncation. Stored exactly like today's timelapses:
`Image { format:'mp4', duration:'run', timestamp, timestampEnd }`. `timestampEnd` already means
"spans a range". **No schema change.** Target size ≤ 9 MB at 720p / crf 26 — deliberately under
Discord's free 10 MB limit and far under Telegram's.

**f) How the video LEAVES the product.** Three exits, all real.

1. **Download.** `GET /image/:device_id?format=mp4&duration=run&download=1&token=<imageToken>`, with
   `Content-Disposition: attachment; filename="terpcontrol-zelt-1-gorilla-glue-4-20260610-20260902.mp4"`
   (device-name slug + plant label + span). The `/film` button is **`Film speichern`**, a plain
   `<a download>` on a same-origin URL. **Stated limits, in the UI:** Android Chrome puts it in
   Downloads with the system share sheet one tap away; iOS Safari puts it in **Dateien, not the
   camera roll** — the camera roll needs the Capacitor shell, which is not in the October build. The
   iOS sublabel reads `Landet in „Dateien". Von dort kannst du ihn teilen.`
2. **A link that needs no login.** `ShareLink` gains `page: 'film'`. The recipient gets a page that
   plays the video and offers the same download, no account, honouring `expiresAt` / `revokedAt`.
   This is what gets pasted into Telegram, and Telegram renders it.
3. **The file itself.** At ≤ 9 MB H.264 the user attaches it in any messenger from their own device.
   C32 ships **no auto-posting**: § 6 KCanG makes a branded auto-footer on thousands of German
   cannabis posts the riskiest string in the product.

**g) Image correlation — three bindings.**

1. **Scrub the chart, the picture moves.** The camera panel in `/verlauf` is a **film strip on the
   same x-scale**, so uneven capture reads honestly as gaps. One request per window, not N:
   `GET /image/:device_id/streifen?from&to&cols=10` returns a single JPEG **sprite** (up to 100 tiles
   at 160×90, built with the `sharp` resize that already exists) plus a JSON index of tile timestamps.
2. **Pick a picture, see its numbers.** Tapping a tile opens the still full-bleed with a footer that
   is the manifest again: `12.09. 14:32 · 26,4 °C · 58 % · VPD 1,21 kPa · CO2 980 ppm · Licht 100 % ·
   Tag 61`. A monitoring device's footer has three fields. A value stale at that moment renders `—`,
   never an interpolation.
3. **A note carries its frame.** Saving any `Note` without a photo sets `frame_at = note.at`, so the
   Buch row shows the tent as it looked when you wrote it, as a 64 px thumbnail — a reference, not a
   copy, so it costs nothing. The most literal reading available of "it does the diary keeping for
   you": you write two words and the record has a picture.

**h) The camera alarm nobody built.** A cloud-computed `camera_age` sensor added to `ALARM_PRESETS`
and **defaulted ON the moment a `webcam_did` appears in the manifest**: no new frame for **6 h while
the device is online** → info-level log and the home card turns rufend; **24 h** → e-mail/webhook,
`Kamera meldet sich seit 24 Std nicht.` Plus a culling anomaly: > 90 % of a day's frames dropped by
the Dunkelfilter while `out_light` reports day → `Die Kamera sieht nichts, obwohl das Licht an ist.`

### 8.3 v1.1 and later

`vidstab` stabilisation · per-plant crops from a drawn rectangle · a "wächst" measurement (green-pixel
area over time, plotted as a real series next to temperature) · sprite pre-generation and CDN caching ·
YouTube upload behind the audit.

## 9. Clubs

The club need is attribution and safety between people, not authorisation. C32 ships the first
without touching `auth.middleware.ts`, and is explicit that it is not the second.

```ts
interface Actor { actor_id: string; device_id: string;
                  name: string;      // "Anna" — a first name is enough, no real names required
                  colour: string;    // one of 8 tokens; the dot in the Buch
                  created_by: string; archived_at?: number; }
```

The owner types the names once on `/anlage`. No invitations, no e-mails, no accounts, no enumeration
surface. Every capture stamps `Note.actor_id`. A chip on the home header reads `Du bist: Anna ▾`,
persisted in `localStorage['tc-actor-<device_id>']` and re-asked after 12 h of silence — and it
appears **only when `Actor` count ≥ 2**, so a solo grower never sees it. Shown once, on the day the
second actor is created:

> **Namen sind Notizen, keine Zugänge.** Wer den Link hat, kann jeden Namen wählen. Das Buch sagt,
> wer was gemacht hat — es hält niemanden auf.

That sentence is the privacy posture and the honest limit in one. The **double-feed guard** (§7.3) is
what earns the actor list; without actors it degrades to a same-device check. **Conditions** (§6) are
pinned at the top of Zuhause and closed by anyone in one tap — the tent-door note, and the one part
of C32 that is deliberately **not** capability-gated, because a standing fact is free text and exists
on every device. **Cumulative recall** is §7.4.

**Privacy posture — what C32 refuses.** Default is privacy-maximal: `wet_g` / `dry_g` exist on `Note`
and are **never prompted** — you add a harvest weight from the note's `…` menu, deliberately, and
there is no yield dashboard. **No per-member dispensing, no gram inventory, no § 26 KCanG filings, no
member identity, DOB or address. No location, no GPS, no persisted IP geolocation.** Export defaults
to anonymised (`Person 1 / Person 2`) with a `Namen / Anonym` switch that starts on `Anonym`. Notes
stay deletable by the owner always: corrections are `supersedes_note_id` rows, but deletion is real —
tamper-evidence protects a regulated club and victimises an unregulated grower.

**What C32 does not deliver:** real memberships. Two people still share one login, or one holds a
read-only `ShareLink`. The membership collection plus rewriting `auth.middleware.ts:172` and `:207`
plus loosening ~10 owner-scoped queries is v1.1. Actors buy attribution for about two days of work
and buy nothing else — and the product says so, not just this document.

## 10. Old devices (type 7) — fan, light, plug

`dryer` is dead per `AGENTS.md`. `fan`, `light`, `plug` and `fridge`/`fridge2` never report
`hardwareInfo.sockets` and never will. Under Das Gesetz they need a manifest, so they get one:
`source: 'static'`, a table in `capability-manifest.ts`, not a probe.

| device_type | senses | acts | camera | Tab bar |
| --- | --- | --- | --- | --- |
| `plug` | temperature (+ humidity when reported) | `relais` | no | Zuhause · Verlauf · Buch |
| `fan` | temperature, humidity, vpd, rpm | fan speed (PWM) | no | Zuhause · Verlauf · Buch |
| `light` | (temperature when reported) | light PWM + photoperiod | no | Zuhause · Verlauf · Buch |
| `fridge`/`fridge2` | temperature, humidity, vpd, co2 | compressor (`out_dehumidifier`), heater, light | if paired | 4 items |

**What a plug owner actually sees.** Home: a `Temperatur` card (three tiers, freshness, verdict) and a
`Steckdose` card reading `AN · Seit 4 Std 10 · Schaltet aus über 28 °C`. Then the Buch card. Three
cards. No VPD panel if humidity is not reported, no CO2 anywhere, no light schedule, no camera tab,
no Düngen scheme step-detection by light flip (§7.4 falls back to the calendar and says so).

**Their settings are not rewritten.** `fan-settings`, `light-settings` and `plug-settings` stay
exactly as they are, `ngSwitch` and all. The new `/ding/:cap_id` page for an old device's actuator
renders the same three pinned lines, the same run-history block and the same alarm list, and then
ends with one row:

```
Einstellungen für diese Steckdose                    →
```

which deep-links into the existing settings page. That is the whole integration. A type-7 owner gains
freshness honesty, the diary, the generated chart with its output lane, and the verdict card. They
lose nothing, and no existing settings form is touched in the October release.

**Fridges are the one place `'full'` was already correct** — their actuators are built in, so
`deviceControlCapability` returning `'full'` for `device_type !== 'controller'` is not a bug for them.
The static manifest reproduces exactly that behaviour, so fridge owners see no change to what is
offered, only to how it is laid out.

### Old controller firmware that reports nothing

`hardwareInfo.sockets` absent means "firmware too old to report" — the firmware distinguishes it from
`'none'` deliberately (`firmware/src/wifi.cpp:1720-1725`). Today that case **fails open to `'full'`**.
C32 makes it a third state, `source: 'unknown'`, and it is neither full nor empty:

```
┌─────────────────────────────────────────────────┐
│ Zelt 1  ▾                                       │
│ Terp Control weiß nicht, was du angeschlossen   │
│ hast. Deine Firmware ist zu alt, um es zu sagen.│
│                        [ Firmware aktualisieren ]│
├─────────────────────────────────────────────────┤
│ Temperatur                          24,6 °C     │  ← senses always render: sensors are builtin
│ Wird gemessen. Ziel unbekannt.                  │
├─────────────────────────────────────────────────┤
│ Was hängt an deinem Controller?                 │
│   Heizung          [ Habe ich ] [ Habe ich nicht ]│
│   Entfeuchter/Kühlung [ Habe ich ] [ Habe ich nicht ]│
│   Licht            [ Habe ich ] [ Habe ich nicht ]│
│   CO2-Ventil       [ Habe ich ] [ Habe ich nicht ]│
│ Sobald der Controller sich meldet, gilt seine   │
│ Antwort — deine hier wird dann überschrieben.   │
└─────────────────────────────────────────────────┘
```

Answers are stored cloud-side as `CapabilityOverride { device_id, act_id, present, set_by, set_at }`
and produce `source: 'device+override'`. **Device truth always wins:** the first `hardware-info:sockets`
line the device ever sends discards the overrides for the roles it mentions.

A critic will call this an onboarding mode-picker, and the difference is load-bearing: it asks about
**the room**, not the person; it is stored **per device**, not per account; it has **no persona
outcome**; and it is **destroyed by the device's own answer**. A user who ignores it entirely gets a
monitoring app — the truthful floor rather than the flattering ceiling. That is the fails-open bug
fixed, not relocated. And the primary CTA is the firmware update, because the real fix is that the
device should be telling us.

## 11. Per-user-type walkthrough

**1 — Lazy monitoring-only** (`sockets='none'`). Four cards: Temperatur, Luftfeuchte, VPD, Buch.
Three tab items. No targets anywhere, no dehumidifier tile, no humidity alarm preset she can never
act on, no dead `daynight.floating` controls. Two chart panels with no bands and titles reading
`(nur gemessen)`. She opens the app monthly, reads `Alles im Rahmen · vor 40 Sek`, closes it. The
daily Tageszeile means her Buch is full of history she never typed.

**2 — Same, with a camera.** Identical plus a fourth tab. The camera card is full-bleed on home with
`14:32 · 26,4 °C · 58 % · Tag 61` beneath it. Every night the cloud rebuilds `duration:'run'`; when
she opens `/film` there is a 60-second H.264 file with the black nights and door-openings already
cut, and one button that puts it in Downloads under a filename that says what it is. Scrubbing the
Verlauf moves the picture. This is the user C32 serves best.

**3 — Controls certain aspects (CO2 or heating).** Heater socket, no dehumidifier. Today he is shown
a humidity target, a `humidity_low` preset and a "Entfeuchter läuft ununterbrochen" alarm for a
socket he does not own. In C32 none of those exist. Temperatur reads `Mindestens 25,0 °C. Nach oben
regelt nichts.` and his chart's band is open at the top; Luftfeuchte reads `Wird nur gemessen. Du
hast nichts, was Feuchte senkt.` Nothing nags him about kit he chose not to buy. This is the user
the concept was designed around.

**4 — Full tent.** Eight cards, six panels, three output lanes. No workmode dropdown: he told the app
once that the socket holds a dehumidifier and `small` follows. He is the one who scrolls into
`/ding/temperature`, reads the time-in-range block, types alarm thresholds instead of sliding them,
and finds the Flux measure name at the bottom. Same screens as user 1, denser because his room is.
**Honest gap:** he still cannot raise humidity and still cannot cool and dehumidify at once, and C32
prints both facts where today they are silent. Correct, and he will not enjoy it.

**5 — Closed-loop DIY.** The manifest is a documented JSON object at `GET /device/:id/capabilities` —
the first machine-readable contract this product has had. Every `/ding` page ends with its Flux
measure name and API path, so the UI is the discovery doc. His EC probe still enters as a
`Note{kind:'messung'}` and plots as an annotation, not a series. **Honest gap:** no write API and no
custom sensor ingestion in October. He gets a read surface and an honest contract, not the API he wants.

**6 — Club.** Four actor names typed once; `Du bist: Timo ▾` on the header. Two taps to record a feed
with All-Mix week 5 prefilled. The double-feed bar catches him 90 minutes after Anna did the same
plants. `CO2-Flasche fast leer · Anna, vor 2 Tagen` is pinned where the tent-door note would be. A3's
page reconstructs the run months later. Export defaults to `Person 1 / Person 2`. No member identity,
no grams, no filing.

**7 — Old device owner (fan/light/plug).** Static manifest, three cards, three tabs, the old settings
form still reachable from the actuator's thing page. He gains a diary with watering in it, a chart
with an output lane, and values that finally say how old they are. Nothing removed, no existing form
rewritten before October.

## 13. Honest weaknesses

1. **Capability is the wrong axis for this round's hard problem.** It separates the seven user types
   cleanly and separates the stoner from the techie not at all — they own the same tent. Mechanism B
   does that work, and it is softer than the headline: typography and information order rather than
   architecture. A critic is right that the title solves the easy half. My answer is that the easy
   half was still broken and that Mechanism B is a mechanism, not a switch — but the asymmetry is real.

2. **The manifest is only as honest as the firmware.** `sockets=heater` means a heater *role* is
   paired to an IP. It does not mean a heater is plugged in, or that it works. C32 will confidently
   render a heater card, a temperature floor and a run history for an empty socket. "You see what you
   have" is really "you see what you configured", and the gap between those is where the tickets live.

3. **The stock-take screen for old firmware is the most attackable thing here.** Four yes/no
   questions on one screen looks exactly like the banned onboarding mode-picker. My defence — about
   the room not the person, per-device not per-account, destroyed by the device's own answer — is
   genuine, and it is still a defence.

4. **Deriving workmode from appliance type deletes a control users have.** Someone who deliberately
   flips `temp` in summer and `small` in autumn must now change the socket's appliance to do it,
   which reads as lying about their hardware. The migration seeds the binding correctly; the
   affordance is still worse for that user. This is the riskiest single decision in the concept.

5. **A monitoring-only home screen is four cards and may read as cheap.** €289 buys a screen with two
   numbers on it. The passive `Was du noch anschließen kannst` block softens it without upselling,
   but the concept's most honest state is also its least impressive screenshot.

6. **Frame culling can eat the film.** A badly-lit tent, an IR camera under 12/12, or a fogged lens
   can push a whole week under the thresholds. The 200-frame floor stops a silent 4-second film, but
   the four thresholds are unvalidated guesses until they meet real tents. Most likely part of C32 to
   need a second pass after launch.

7. **The ECharts migration is nine of sixty days and it carries the concept's proof.** If it slips,
   the one-sided band slips with it. And Highstock's implicit `dataGrouping` — never configured,
   currently load-bearing — disappears in the swap; `sampling:'minmax'` replaces a safety net nobody
   wrote down.

8. **Actor names are social, not secure.** Anyone with the login picks any name. Fine among four
   friends, theatre as an audit trail. C32 says so in the UI rather than selling it, but a club that
   reads "wer was gemacht hat" as accountability will be disappointed the first time it matters.

9. **Two stores for one timeline, with no migration tooling in the repo.** `Note` supersedes user
   `DeviceLog` rows via a one-shot idempotent backfill plus a union read. A half-run backfill splits
   the diary across two collections and the union hides it. Fine in testing, ugly at 3 a.m. on launch
   weekend.

10. **Capability honesty is a worse marketing surface than silence.** Today the app quietly shows a
    humidity target and nobody asks whether it works. C32 prints `Du hast nichts, was Feuchte senkt.`
    on the home screen of every customer without a dehumidifier. That is the correct sentence and it
    will generate more "why can't it do this" mail than the current lie does. The concept accepts the
    trade; the company has to decide whether it wants it.
